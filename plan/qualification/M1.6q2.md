# M1.6q2 owner qualification: Search keystroke benchmark

Time Search from the last keystroke to the first rows in the app on
your Mac, over the same seeded synthetic archive M1.6q times in the
core (100,000 messages, no mail of yours), and record the dated result
here against spec/08's budget.

## Seed the archive

On a release build, with the Mac otherwise idle (pick a directory that
doesn't exist yet; the import takes a while):

```sh
SB_SEARCH_TIMINGS_ROOT=~/sweetbriar-search-archive \
SB_SEARCH_TIMINGS_SEED_ONLY=1 \
SB_SEARCH_TIMINGS_OUT=~/sweetbriar-search-archive/seed.json \
  cargo test -p sb-engine --release --lib search_timings -- --ignored --nocapture
```

## Run the benchmark

Launch the Release app over that archive and leave it in front until
it quits (each query is typed ten times):

```sh
open -W -n -a /path/to/Sweetbriar.app --args \
  -runSearchBenchmark ~/search-benchmark.json \
  -dataRoot ~/sweetbriar-search-archive/store \
  -cacheRoot ~/sweetbriar-search-archive/cache
```

Launched with only `-dataRoot` and `-cacheRoot`, Debug → Run Search
Benchmark runs the same queries and shows the report in a window.

The run types each query into the search field, all but its last
character first, then times the last character to the first display
frame showing the new rows. The 30 ms debounce is included. Queries:
an exact reference word, an exact sender address, a phrase, a sender
domain and date scoped to Projects, and a word without a body word.

| Budget (spec/08) | Report field | Result |
|---|---|---|
| Search results after the last keystroke: p95 under 100 ms | `search.budget` (`p95Milliseconds`, `met`) | missed: 145.8 ms (run 1), 150.0 ms (run 2) |

`met` is empty when the run failed a check or a sample never rendered;
see `failures`. Also note `search.perQuery`, `search.stages` (when
the field showed the query, the core's opening page returned, the
first rows landed in the list and its open returned), the environment
block (Mac model, macOS, refresh rate) and `storeMessages`. A missed budget
is a finding to resolve, not a threshold to relax.

Result, run 1: 2026-10-28, b1be23d, Apple M3 Pro (Mac15,6), macOS
27.2, 60 Hz, 100,000 messages. Missed: p95 145.8 ms, p50 116.8 ms,
50 of 50 samples rendered. Per-query p95: exact reference 120 ms,
exact address 122, negative body 128, scoped filter 144, phrase 152.
Notes: the field shows the query at about 34 ms (the debounce). After
that, the app adds 35 to 80 ms (p50) over the core's warm first page
from M1.6q: the exact address query takes 4 ms in the core and renders
at 103 ms. On the exact queries and phrase's three slowest samples,
rows render 17 to 64 ms after the open returns, which points to frame
delivery; on the rest they render before it, since the open also
waits for the id index. M1.6r stays open.

Result, run 2: 2026-10-29, the same app and core code as run 1 (no
change under `apps` or `crates` since b1be23d), same Mac, external
60 Hz display, 100,000 messages. Missed: p95 150.0 ms, p50 119.0 ms,
50 of 50 samples rendered. Per-query p95: exact address 132 ms,
scoped filter 141, exact reference 148, phrase 152, negative body 211
(one outlier; the next slowest sample overall is 152). Notes: the
same shape as run 1. The exact queries' open returns at ~70 ms p50
and every one of their rows renders 21 to 81 ms after it; phrase,
scoped filter and negative body render at 119 to 129 ms p50, before
their open returns. M1.6r4 takes both on.
