# M0 — Foundations

**Outcome:** a workspace with green Linux and macOS CI; a durable store
skeleton with the publication protocol under fault injection; the core
API reachable from a minimal macOS app; the list and composer prototypes
decided.

### M0.1 Repository bootstrap — S, linux + macos-ci

- **Goal:** the Cargo workspace and agent tooling exist, and Linux CI is
  green on an empty core.
- **Spec:** 01 (layout, licence policy), 11 (CI `ci.yml`, `macos.yml`).
- **Deliverables:**
  - `Cargo.toml` (workspace, resolver 3, edition 2024);
    `rust-toolchain.toml` (1.99.0); `.cargo/config.toml`;
  - empty crates per 01 with `lib.rs` doc comments stating each crate's
    layer and role;
  - `xtask` with `ci` (fmt, clippy `-D warnings`, test, `cargo deny
    check`);
  - `deny.toml` (allow-list and UniFFI exceptions per 01);
  - `THIRD_PARTY_NOTICES.md` generated by `cargo-about` 0.9.2, with an
    `about.toml`/template, plus the drift check in `xtask ci` and
    `ci.yml`;
  - `CONTRIBUTING.md` ("This project doesn't accept contributions. You're
    free to fork it under the Unlicense or 0BSD.");
  - `AGENTS.md` (commands, the Linux vs macOS-CI split, the rules from
    plan/README);
  - `.gitignore`;
  - `.github/workflows/ci.yml`: `ubuntu-24.04`,
    `permissions: contents: read`, concurrency with cancel-in-progress
    for PRs, timeouts, actions pinned to SHAs, sccache, and a final
    aggregate `ci` job (the merge gate, 11);
  - `.github/workflows/macos.yml` in its **Rust-only** first shape (on
    `macos-26`: `cargo test --target aarch64-apple-darwin`, plus the
    always-reporting `macos` job). M0.8 adds the FFI checks and M0.9 the
    app build.
  - `license = "Unlicense OR 0BSD"` under `[workspace.package]`, with
    `license.workspace = true` in every crate (the licence files already
    exist).
- **Acceptance:**
  - `cargo xtask ci` passes locally;
  - `ci.yml` and the Rust-only `macos.yml` pass on the PR;
  - `cargo deny check` passes with the allow-list;
  - the notices drift check passes, and fails when a dependency is added
    without regenerating.

### M0.3 Store open path — L, linux + macos-ci

- **Goal:** `sb-store` opens or creates the database exactly as spec/03
  requires, and refuses anything else.
- **Spec:** 03 (On-disk layout, SQLite configuration), 07 (CoreError
  mapping for `Locked`, `Unavailable`, `Corrupt`, `Internal`).
- **Depends on:** M0.1.
- **Deliverables:**
  - in `sb-types`: the `Fs` seam trait, complete (`create`, `write`,
    `open`/`read`, `metadata` (existence, length), `read_dir`,
    `create_dir`, `sync_all`, `sync_dir`, `rename`, `remove`,
    `canonicalize`, `lock_exclusive`, `location` (local, synced or
    network));
  - in `sb-platform`: its real implementation (`fcntl(F_FULLFSYNC)` on
    macOS, `fsync` on Linux; synced folders by path prefix, network
    mounts by filesystem type). M0.5 adds the fault-injecting one;
  - in `sb-test-support`: the real `Fs` for `sb-store`'s tests (01
    rule 5);
  - `sb-store::open(paths, fs)`: the location check, then the lease via
    `Fs::lock_exclusive` (01 rule 5), then the store directories (03
    On-disk layout), the connection constructor with pragma
    set-and-read-back, and the version and source-id checks;
  - `LIBSQLITE3_FLAGS` in `.cargo/config.toml`.
- **Acceptance** (tests):
  - linked SQLite version ≥ 3.51.3 and ≠ 3.52.0, and equal to the
    pinned version and source id; FTS5 available (create, insert,
    match); `PRAGMA compile_options` shows the 03 flags;
  - after open: `journal_mode=wal`, `synchronous=2`, `foreign_keys=1`;
    DQS rejected (`SELECT "x"` errors);
  - a second open in another process returns `Locked` and creates
    nothing;
  - a pragma mismatch (simulated) refuses to open;
  - a synced or network location is refused with `Unavailable`; the
    path classification is tested for the macOS and Linux prefixes on
    every host;
  - a `state.sqlite` that isn't a database yields `Corrupt` and is left
    untouched.

### M0.4 Schema v1 and migrations — L, linux

- **Goal:** schema v1 from spec/02 is created through the migration
  runner.
- **Spec:** 02 (all DDL, Migrations), 06 (search tables), 01 (Layers
  rule 5: the `Clock` and `Random` seams).
- **Depends on:** M0.3.
- **Deliverables:**
  - the migration runner, owned, in `sb-store` (decided here; recorded
    in 01's crate table);
  - migration 1 containing the 02 and 06 DDL;
  - `store_meta` initialisation (store UUID, incarnation, `created_at`,
    both version keys);
  - in `sb-types`: the `Clock` and `Random` seam traits, `Timestamp`
    (02 rule 4) and `Uuid` (02 rule 3; version 4 from random bytes). In
    `sb-platform`: the system clock and OS randomness (`getentropy`). In
    `sb-test-support`: those, plus a fixed clock and deterministic
    randomness;
  - `sb-store::open` takes the clock and randomness alongside the `Fs`,
    and runs the migrations after the version check (02 Migrations).
- **Acceptance:**
  - a fresh store reaches version 1; reopening runs no migration;
  - `foreign_key_check` and `integrity_check` are empty or `ok`;
  - the migrated schema equals one built from spec/02's and spec/06's
    SQL blocks;
  - `store_meta` holds two distinct lowercase hyphenated v4 UUIDs, the
    clock's `created_at`, and the workspace version in both version
    keys;
  - a migration whose checks find a problem rolls back and yields
    `Corrupt`, leaving `user_version` unchanged (a test-only migration);
  - a foreign database yields `Corrupt` with the file unchanged:
    `user_version` 0 with a table, in WAL or another journal mode, and
    a supported `user_version` without the identity keys, also when a
    crash left WAL frames;
  - a test asserts every application-owned ordinary table is `STRICT`
    (via `pragma_table_list` with `type='table'` and
    `name NOT GLOB 'sqlite_*'`, which excludes virtual, shadow and
    internal tables);
  - the schema version is read from `PRAGMA user_version`, and a store
    with a higher version yields `NewerStore` naming
    `store_meta.last_migrated_by`, with `state.sqlite` unchanged.

### M0.5 Object store and publication protocol — L, linux + macos-ci

- **Goal:** the `ObjectStore` trait and its file implementation follow the
  publication protocol, with fault tests.
- **Spec:** 03 (Object store, Publication protocol, Reads and
  verification), 11 (Fault injection), 07 (`NotFound`, `Corrupt`,
  `Unavailable`).
- **Depends on:** M0.3.
- **Deliverables:**
  - the `Fs` seam and its real implementation from M0.3, plus, in
    `sb-test-support`, a fault-injecting wrapper (short write, `ENOSPC`,
    `EIO` on sync, rename and directory-sync failures, chosen by
    operation) and an in-memory `Fs` that keeps flushed and unflushed
    file data and directory entries apart and drops the unflushed ones
    on a simulated power cut. Callers inject the real one: tests here,
    `sb-resources` from M0.7;
  - in `sb-store`: `ObjectStore` and the file implementation. Reservation
    pins (03) arrive with GC in M1.8; until then nothing removes objects;
  - in `sb-test-support`: the crash-cut harness (spawn a child, kill at
    numbered cut points, reopen, check invariants). A cut point is an
    `Fs` operation: the child kills itself before the Nth one.
- **Acceptance:**
  - publish → open returns identical bytes; a wrong length or hash is
    `Corrupt` with the file moved to `recovery/`; an absent object is
    `NotFound`;
  - a new store's directories and data-root entry are flushed (03);
  - publishing the same bytes twice keeps one file;
  - every injected failure (short write, `ENOSPC`, `EIO` on sync, rename
    failure, directory-sync failure) returns an error and creates no
    reference. Before the rename, no object exists. After it, a complete,
    hash-valid orphan may remain. Retrying the publication succeeds;
  - crash cuts at every protocol step leave either no object or a
    complete verified one;
  - a failed directory flush, then a retry in the same process, then a
    simulated power cut that drops unflushed directory entries, loses no
    acknowledged object; so do two concurrent publications into a new
    directory;
  - on macOS, `sb-platform`'s `Fs::sync_all` calls `fcntl(F_FULLFSYNC)`
    explicitly rather than relying on `std`'s choice, and a macOS CI test
    checks that the call succeeds on APFS;
  - `check-layers` passes: `sb-store` references only `sb-types` for the
    seam.

### M0.6 Writer, readers and receipts — M, linux

- **Goal:** the store's write path (one writer thread, priority queue)
  and read pool exist, plus idempotent command receipts.
- **Spec:** 03 (Connections, Write discipline), 02 (`command_receipts`),
  07 (Commands: idempotency).
- **Depends on:** M0.4.
- **Spec also:** 01 (Process model: store threads).
- **Deliverables:**
  - `sb-store::Writer`: one OS thread owning the writer connection; a
    closure is submitted with a priority (user, then sync, then index,
    01) and runs in one `BEGIN IMMEDIATE` transaction; submitting
    returns a future of its result. The future needs no runtime, so
    `sb-store` takes no async dependency. When the queue drains, the
    writer checkpoints (03);
  - the reader pool (default 4): read-only connections from the one
    constructor, each read one short transaction;
  - receipt helpers: run a command under an idempotency key in one
    write; a repeated key returns the stored receipt without running,
    a key reused for another command is `Conflict` (07);
  - the read-only open (02 Migrations): an existing store, newer or
    current, under the lease, with readers only. It creates no store
    and no lock for an absent one, and writes nothing to `state.sqlite`
    or its WAL; like any WAL reader, SQLite may create its
    shared-memory index (`-shm`) and an empty WAL.
- **Acceptance:**
  - writes from many tasks are serialized;
  - a user-priority write overtakes queued sync writes (test with
    controlled scheduling);
  - repeating an idempotency key returns the stored receipt without
    re-running;
  - readers use `query_only` and `wal_autocheckpoint=0`
    (pragma readback), and a write through one fails;
  - a key reused for a different command is `Conflict`;
  - a store with a newer `user_version` opens read-only, and its
    `state.sqlite` is unchanged afterwards.

### M0.7 Core skeleton and CLI — M, linux

- **Goal:** `sb-service`, `sb-engine` and `sb-resources` carry one command
  and one query end to end; `sb-cli` uses them.
- **Spec:** 01 (Layers, Process model), 07 (Lifecycle, Errors, one
  command: `set_setting`, one query: `settings()`).
- **Depends on:** M0.2, M0.6.
- **Deliverables:**
  - the command and query through `sb-service`, `sb-engine` and
    `sb-resources`: `set_setting` under an idempotency key (a receipt,
    02 Settings registry) and `settings()`. Each layer maps the errors
    of the one below; types climb by item re-exports only (01 rule 3);
  - `open_core` and `shutdown`, with the runtime (`tokio` 1.53.2,
    01) owned by the engine; `CoreConfig` carries the data and cache
    roots;
  - the clean-shutdown marker: `shutdown` records it, and the next
    open runs `PRAGMA quick_check` when it's missing (03 Integrity);
  - `sb-cli settings get [key]` and `settings set <key> <value>`, with
    `--data-root` (default: the platform's data root, 03);
- **Acceptance:**
  - `sb-cli settings set appearance.compose_cue standard` then `get`
    round-trips across process restarts;
  - `check-layers` passes;
  - opening a store locked by another process yields `CoreError::Locked`
    and creates nothing;
  - an unknown key or value is `InvalidInput`; a repeated idempotency
    key returns the first receipt;
  - after a shutdown the marker is present; after a killed process it
    isn't, and the next open runs `quick_check` (observable in a
    test).

### M0.8 FFI exports and bindings — M, linux (+ macos-ci for the XCFramework)

- **Goal:** `sb-ffi` exports the M0.7 API through UniFFI. Swift bindings
  are generated and committed; macOS CI builds the XCFramework. This step
  extends `macos.yml` with `xtask ffi` and `check-ffi`.
- **Spec:** 07 (Threading, cancellation and FFI rules), 01 (sb-ffi,
  sb-bindgen).
- **Depends on:** M0.7.
- **Deliverables:**
  - `sb-ffi` (proc-macro exports; `lib` + `staticlib` + `cdylib`): its own
    UniFFI records, error and object mirroring the service's (`sb-service`
    stays UniFFI-free): `open_core`, `Core.set_setting`,
    `Core.settings`, `Core.shutdown` (07: a shared object), all async;
  - `sb-bindgen` pinned to `uniffi` 0.32.2;
  - `cargo xtask ffi [--bindings-only]` (bindings on Linux from the host
    `cdylib`; XCFramework on macOS);
  - `cargo xtask check-ffi` (regenerate and diff);
  - generated Swift in `apps/macos/SweetbriarCore/Sources/SweetbriarCore/`,
    the generated C header and modulemap in
    `apps/macos/SweetbriarCore/Headers/` (both committed); the
    XCFramework at `apps/macos/SweetbriarCore/SweetbriarCoreFFI.xcframework`
    (built, ignored by git).
- **Acceptance:**
  - `check-ffi` reports no drift;
  - on macOS CI, the XCFramework builds for `aarch64-apple-darwin`;
  - no async foreign callback traits in the exported surface (a
    `check-ffi` lint, shown to fail on one in a test);
  - the exported calls work from Rust: open, set, read back, shut down;
    a call after `shutdown` is `Unavailable`, and `shutdown` waits for a
    call in flight.
