# M0 — Foundations

**Outcome:** a workspace with green Linux and macOS CI; a durable store
skeleton with the publication protocol under fault injection; the core
API reachable from a minimal macOS app; the list and composer prototypes
decided.

### M0.1 Repository bootstrap — S, linux

- **Goal:** the Cargo workspace and agent tooling exist, and Linux CI is
  green on an empty core.
- **Spec:** 01 (layout, licence policy), 11 (CI `ci.yml`).
- **Deliverables:**
  - `Cargo.toml` (workspace, resolver 3, edition 2024);
    `rust-toolchain.toml` (1.99.0); `.cargo/config.toml`;
  - empty crates per 01 with `lib.rs` doc comments stating each crate's
    layer and role;
  - `xtask` with `ci` (fmt, clippy `-D warnings`, test, `cargo deny
    check`);
  - `deny.toml` (allow-list and UniFFI exceptions per 01);
  - `THIRD_PARTY_NOTICES.md` generated by `cargo-about` 0.9.2, with an
    `about.toml`/template, plus the drift check in `xtask ci` and
    `ci.yml`;
  - `CONTRIBUTING.md` ("This project doesn't accept contributions. You're
    free to fork it under the Unlicense.");
  - `AGENTS.md` (commands, the Linux vs macOS-CI split, the rules from
    plan/README);
  - `.gitignore`;
  - `.github/workflows/ci.yml`: `ubuntu-24.04`,
    `permissions: contents: read`, concurrency with cancel-in-progress
    for PRs, timeouts, actions pinned to SHAs, sccache.
  - If owner task O2 says yes, `LICENSE-0BSD` plus a note in `README.md`.
- **Acceptance:**
  - `cargo xtask ci` passes locally;
  - `ci.yml` passes on the PR;
  - `cargo deny check` passes with the allow-list;
  - the notices drift check passes, and fails when a dependency is added
    without regenerating.

### M0.2 Layering check — M, linux

- **Goal:** `cargo xtask check-layers` enforces the owner's
  adjacent-layer rule.
- **Spec:** 01 (Layers, The layering check).
- **Depends on:** M0.1.
- **Deliverables:**
  - `layers.toml` covering every module in the skeleton;
  - the `syn`-based checker in `xtask`;
  - fixtures in `xtask/tests/layers/`:
    - negative: a direct skip-layer import, an alias, a re-export
      shortcut, a glob, an `include!`, an exported macro with a `$crate`
      path;
    - positive: a legal adjacent re-export;
  - wired into `xtask ci` and `ci.yml`.
- **Acceptance:**
  - every negative fixture fails with a message naming the file, line
    and forbidden edge;
  - the positive fixture passes;
  - an unclassified file fails;
  - the real workspace passes.

### M0.3 Store open path — M, linux

- **Goal:** `sb-store` opens or creates the database exactly as spec/03
  requires, and refuses anything else.
- **Spec:** 03 (On-disk layout, SQLite configuration), 07 (CoreError
  mapping for `Locked`, `Corrupt`, `NewerStore`).
- **Depends on:** M0.1.
- **Deliverables:**
  - `sb-store::open(paths)`: lease file (`flock`), the connection
    constructor with pragma set-and-read-back, version and source-id
    checks, refusal of synced and network locations (detected by path
    prefix and filesystem type);
  - `LIBSQLITE3_FLAGS` in `.cargo/config.toml`.
- **Acceptance** (tests):
  - linked SQLite version ≥ 3.51.3 and ≠ 3.52.0; FTS5 available
    (create, insert, match);
  - after open: `journal_mode=wal`, `synchronous=2`, `foreign_keys=1`;
    DQS rejected (`SELECT "x"` errors);
  - a second open in another process returns `Locked`;
  - a pragma mismatch (simulated) refuses to open.

### M0.4 Schema v1 and migrations — M, linux

- **Goal:** schema v1 from spec/02 is created through the migration
  runner.
- **Spec:** 02 (all DDL, Migrations), 06 (search tables).
- **Depends on:** M0.3.
- **Deliverables:**
  - the migration runner (`rusqlite_migration` 2.6.0, or an owned
    runner; decide and record in the PR);
  - migration 1 containing the 02 and 06 DDL;
  - `store_meta` initialisation (store UUID, incarnation).
- **Acceptance:**
  - a fresh store reaches version 1;
  - `foreign_key_check` and `integrity_check` are empty or `ok`;
  - a test asserts every ordinary table is `STRICT` (via
    `pragma_table_list`, excluding virtual tables and FTS5 shadow
    tables);
  - the schema version is read from `PRAGMA user_version`, and a store
    with a higher version yields `NewerStore` naming
    `store_meta.last_migrated_by`.

### M0.5 Object store and publication protocol — L, linux

- **Goal:** the `ObjectStore` trait and its file implementation follow the
  publication protocol, with fault tests.
- **Spec:** 03 (Object store, Publication protocol, Reads and
  verification), 11 (Fault injection).
- **Depends on:** M0.3.
- **Deliverables:**
  - in `sb-platform`: the `Fs` seam trait (`create`, `write`,
    `sync_all`, `sync_dir`, `rename`, `remove`) with a real
    implementation and a fault-injecting test implementation;
  - in `sb-store`: `ObjectStore` and the file implementation;
  - in `sb-test-support`: the crash-cut harness (spawn a child, kill at
    numbered cut points, reopen, check invariants).
- **Acceptance:**
  - publish → open returns identical bytes;
  - publishing the same bytes twice keeps one file;
  - injected short write, `ENOSPC`, `EIO` on sync, rename failure and
    directory-sync failure each return an error and leave no published
    object;
  - crash cuts at every protocol step leave either no object or a
    complete verified one;
  - on macOS, the file implementation calls `fcntl(F_FULLFSYNC)`
    explicitly rather than relying on `std`'s choice, and a macOS CI test
    checks that the call succeeds on APFS.

### M0.6 Writer, readers and receipts — M, linux

- **Goal:** the store's write path (one writer thread, priority queue)
  and read pool exist, plus idempotent command receipts.
- **Spec:** 03 (Connections, Write discipline), 02 (`command_receipts`),
  07 (Commands: idempotency).
- **Depends on:** M0.4.
- **Deliverables:** `sb-store::Writer` (submit a closure with a priority,
  returning a future) and the reader pool; receipt helpers.
- **Acceptance:**
  - writes from many tasks are serialized;
  - a user-priority write overtakes queued sync writes (test with
    controlled scheduling);
  - repeating an idempotency key returns the stored receipt without
    re-running;
  - readers use `query_only` and `wal_autocheckpoint=0`
    (pragma readback).

### M0.7 Core skeleton and CLI — M, linux

- **Goal:** `sb-core` has its three layers, with one command and one query
  end to end; `sb-cli` uses them.
- **Spec:** 01 (Layers, Process model), 07 (Lifecycle, Errors, one
  command: `set_setting`, one query: `settings()`).
- **Depends on:** M0.2, M0.6.
- **Deliverables:**
  - `sb-core::{service, engine, resources}` modules;
  - `open_core` and `shutdown`, with the runtime owned by the engine;
  - `sb-cli settings get|set`.
- **Acceptance:**
  - `sb-cli settings set appearance.compose_cue standard` then `get`
    round-trips across process restarts;
  - `check-layers` passes;
  - opening a store locked by another process yields `CoreError::Locked`
    and creates nothing.

### M0.8 FFI exports and bindings — M, linux (+ macos-ci for the XCFramework)

- **Goal:** `sb-ffi` exports the M0.7 API through UniFFI. Swift bindings
  are generated and committed; macOS CI builds the XCFramework.
- **Spec:** 07 (Threading, cancellation and FFI rules), 01 (sb-ffi,
  sb-bindgen).
- **Depends on:** M0.7.
- **Deliverables:**
  - `sb-ffi` (proc-macro exports; `staticlib` + `cdylib`);
  - `sb-bindgen` pinned to `uniffi` 0.32.2;
  - `cargo xtask ffi [--bindings-only]` (bindings on Linux from the host
    `cdylib`; XCFramework on macOS);
  - `cargo xtask check-ffi` (regenerate and diff);
  - generated Swift in `apps/macos/SweetbriarCore/`.
- **Acceptance:**
  - `check-ffi` reports no drift;
  - on macOS CI, the XCFramework builds for `aarch64-apple-darwin`;
  - no async foreign callback traits in the exported surface (a
    `check-ffi` lint).

### M0.9 macOS app shell — M, macos-ci + owner

- **Goal:** a minimal AppKit app calls the core through the Swift
  adapter, and macOS CI builds and tests it.
- **Spec:** 08 (Platform, Windows: main window only), 07 (cancellation,
  main-actor delivery), 11 (`macos.yml`).
- **Depends on:** M0.8.
- **Deliverables:**
  - `apps/macos/project.yml` (XcodeGen): AppKit app target, Swift 6,
    strict concurrency, macOS 26 deployment, arm64;
  - `SweetbriarBridge`: an async wrapper with
    `withTaskCancellationHandler` and `@MainActor` batching;
  - a main window showing a setting read from the core;
  - a Swift Testing unit test for the adapter;
  - `.github/workflows/macos.yml` per 11, with path filters.
- **Acceptance:**
  - `macos.yml` is green: Rust aarch64 tests, `xtask ffi`, `check-ffi`,
    `xcodegen`, then `xcodebuild build test` with strict concurrency and
    warnings as errors;
  - an unsigned `.app` zip is uploaded as an artifact;
  - **owner (O3):** it launches on the owner's Mac.

### M0.10 Message list prototype — M, macos-ci + owner

- **Goal:** decide between AppKit `NSTableView` and SwiftUI `List` for the

- **Spec:** 08 (Message list), research D8 (fair prototype).
- **Depends on:** M0.9.
- **Deliverables:**
  - a debug-only core command that fills a synthetic in-memory window
    source with 500,000 rows (same `ListRow` shape as spec/07);
  - two list implementations behind a debug toggle;
  - a scroll and selection benchmark (XCTest `measure` plus signposts).
- **Acceptance:**
  - benchmark numbers for both are recorded in the PR;
  - **owner checklist (O4)**, completed for both:
    - smooth scrolling;
    - keyboard selection;
    - shift and ⌘ multi-select of 10k rows;
    - a context menu;
    - VoiceOver row reading;
    - Dark Mode;
  - the decision is written into spec/08 (AppKit stays unless SwiftUI
    matches it on every checklist item and benchmark).
