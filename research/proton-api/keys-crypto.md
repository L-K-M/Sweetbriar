# R2 — Keys and cryptography in Rust

Sources: repositories under `/Volumes/PaseoData/sbt/proton-research/src/` (cited as `repo/path:lines`) and public URLs. `proton-bridge` (GPL-3.0) was read for protocol facts only. **Inference:** marks deductions; **Unverified:** marks claims I could not confirm.

## 1. Key model

**User keys vs address keys.** `User.Keys` and `Address.Keys` are lists of the same `Key` type (`go-proton-api/user_types.go:3-18`, `go-proton-api/address_types.go:3-12`). A `Key` has `ID`, `PrivateKey` (armored), `Token`, `Signature`, `Primary`, `Active`, `Flags` (`go-proton-api/keyring.go:59-68`). The Rust model is `LockedKey` (`proton-crypto-rs/proton-crypto-account/src/keys/api_keys.rs:141-176`); `UserKeys = Vec<LockedKey>` (`…/keys/user_keys.rs:182`), `AddressKeys = Vec<LockedKey>` (`…/keys/address_keys.rs:294`). Unlocked types are `DecryptedUserKey` (`…/keys/user_keys.rs:378-386`) and `DecryptedAddressKey { id, flags, primary, is_v6, private_key, public_key }` (`…/keys/address_keys.rs:537-545`).

**Salts and passphrase derivation.** Salts come from `GET /core/v4/keys/salts` (`go-proton-api/salt.go:9-20`) as `{ID, KeySalt}` base64 (`go-proton-api/salt_types.go:11-13`). `SaltForKey` decodes the 16-byte salt, calls `srp.MailboxPassword`, and keeps the last 31 bytes (`go-proton-api/salt_types.go:17-35`). `MailboxPassword` is bcrypt `$2y$10` over the password with a bcrypt-base64 salt (`go-srp/hash.go:33-52`, `76-80`). Rust: `KeySalt::SALT_LEN = 16` (`proton-crypto-rs/proton-crypto-account/src/salts.rs:71-72`); `salted_key_passphrase` calls `SRPProvider::mailbox_password` and takes `password_hash()` (`salts.rs:104-116`); `mailbox_password_hash` is bcrypt cost 10 / version `$2y$` (`proton-crypto-rs/proton-srp/src/pmhash.rs:131-146`, `178-186`); `MailboxHashedPassword` splits a 29-byte prefix (`$2y$10` + 22-char salt) from the 31-byte hash (`pmhash.rs:27, 49-59`). That 31-byte hash is the `KeySecret` used to unlock user keys (`salts.rs:43-50`; `…/keys/user_keys.rs:199-250`).

**Token-encrypted address keys.** A new address key is locked with a random 32-byte hex token; the token is encrypted to the parent user key and signed with a detached plaintext signature (`proton-crypto-rs/proton-crypto-account/src/crypto/key_export.rs:57-95`; `TOKEN_SIZE=32`, `EXPECTED_ENCRYPTED_TOKEN_SIZE=380` in `…/src/crypto/mod.rs:7-8`). The API stores `Token`/`Signature` on the address key (`go-proton-api/keyring.go:59-68`; `…/keys/api_keys.rs:149-152`). Unlock decrypts the token with the user key, verifies the detached signature, then imports the private key with the token as passphrase (`…/crypto/key_import.rs:20-48, 51-85`). Legacy address keys have no token/signature and are unlocked directly with the `KeySecret` (`…/keys/address_keys.rs:611-613, 678-700`; `…/crypto/key_import.rs:122-160`).

**Primary vs inactive/obsolete.** `LockedKey.primary`/`active` are 0/1 integers (`…/keys/api_keys.rs:155-166`). Address-key flags: 1 = not compromised, 2 = not obsolete, 4 = no email encryption, 8 = no email signing (`proton-crypto-rs/proton-crypto-account/src/constants.rs:1-4`; accessors `…/keys/api_keys.rs:25-110`). Public-key flags from `/core/v4/keys` are a different bitmap: `KeyStateTrusted=1`, `KeyStateActive=2` (`go-proton-api/keys_types.go:70-74`). Selection: user primary = first key (`…/keys/user_keys.rs:106-109`); address `primary_default` = first non-v6 key (`…/keys/address_keys.rs:130-143`); `primary_for_mail` prefers a v6 primary for encryption and signs with v4+v6 (`…/keys/address_keys.rs:146-190, 204-260`).

## 2. Decryption

**Message bodies.** `Message.Body` is an armored PGP message; `Message.MIMEType` is the body MIME type (`go-proton-api/message_types.go:61-69`). `Message.Decrypt` unarmors and decrypts with the address key ring at the current time (`message_types.go:146-158`); `DecryptInto` streams (`160-175`). Rust equivalent: `Decryptor::decrypt(data, DataEncoding::Armor)` (`proton-crypto-rs/proton-crypto/src/crypto/decrypt.rs:158-180`), delegated to `proton-rpgp` by the pure-Rust backend (`proton-crypto-rs/proton-crypto/src/rust/pgp/decrypt.rs:160-176`). Signature failures are reported via `VerifiedData::verification_result()`, not as a hard error (`proton-crypto-rs/proton-crypto/src/crypto/verify.rs:38-84`). MIME types are `text/plain`, `text/html`, `multipart/mixed` ([WebClient constants.ts:651-658](https://raw.githubusercontent.com/ProtonMail/WebClient/main/packages/shared/lib/constants.ts)); `multipart/mixed` selects PGP/MIME handling (`go-proton-api/message_build.go:22`).

**Attachments.** `Attachment` has `KeyPackets` and `Signature` (`go-proton-api/attachment_types.go:8-20`). Upload signs the raw attachment body with a detached signature, encrypts with `EncryptAttachment`, and posts multipart fields `KeyPackets`, `DataPacket`, `Signature` to `POST /mail/v4/attachments` (`go-proton-api/attachment.go:25-75`). `EncryptAttachment` sets the literal-data filename and binary/text mode ([gopenpgp v2 attachment.go:121-142](https://raw.githubusercontent.com/ProtonMail/gopenpgp/v2.11.1-proton/crypto/attachment.go)). Download decrypts `NewPGPSplitMessage(KeyPackets, DataPacket)` (`go-proton-api/message_build.go:94-125`). Rust split encryption returns key packets + data packet and can produce a detached signature (`proton-crypto-rs/proton-crypto/src/crypto/encrypt.rs:280-300`; `proton-crypto-rs/proton-crypto/src/rust/pgp/encrypt.rs:473-496`); a bare data packet can be decrypted with a session key (`proton-crypto-rs/proton-rpgp/tests/encrypt.rs:734-766`). **Gap:** neither Rust backend exposes literal-data filename/metadata; `proton-rpgp`'s encryptor has no filename setter (no `filename` matches in `proton-rpgp/src`), and `pgp` 0.21's high-level builder always creates an empty filename (`pgp` 0.21.0 `src/packet/literal_data.rs:68-75`; `LiteralData::from_bytes(file_name, data)` exists at `literal_data.rs:154-160` but is unused by `proton-rpgp`). Inference: Proton's own `Attachment.Name` metadata is probably sufficient for Proton clients, but non-Proton OpenPGP clients may not see the filename.

**Signature verification.** `ExtractSignatures` parses the encrypted message and collects `msg.UnverifiedSignatures` (`go-proton-api/keyring.go:22-60`); `buildPGPRFC822` rebuilds `multipart/signed` when signatures exist, else `multipart/encrypted` (`go-proton-api/message_build.go:142-160`). Rust: `Verifier::verify_detached`/`verify_inline`/`verify_cleartext` (`proton-crypto-rs/proton-crypto/src/crypto/verify.rs:86-160`). Proton signatures carry a notation `context@proton.ch` (`proton-crypto-rs/proton-rpgp/src/signature/context.rs:7`; `gopenpgp/constants/context.go:3`); the SKL context value is `key-transparency.key-list` (`proton-crypto-rs/proton-crypto-account/src/keys/signed_key_list.rs:15`). Inference: Sweetbriar must choose which context values to require for bodies/attachments; only the SKL value is documented in the cloned sources.

## 3. Encrypting for storage

**Drafts.** `CreateDraft`/`UpdateDraft` encrypt `Message.Body` with the sender's address key ring and armor it, then `POST/PUT /mail/v4/messages` (`go-proton-api/message_send.go:11-73`). `CreateDraftReq` also carries `AttachmentKeyPackets` (`go-proton-api/message_draft_types.go:28-44`). The WebClient reuses the draft's encrypted body/session key when sending to enable backend deduplication ([WebClient sendEncrypt.ts:200-208](https://raw.githubusercontent.com/ProtonMail/WebClient/main/packages/mail-composer/src/helpers/send/sendEncrypt.ts)).

**Attachments.** As above: detached signature + split encryption, uploaded as `KeyPackets`/`DataPacket`/`Signature` (`go-proton-api/attachment.go:25-75`).

## 4. Sending: the send-package model

`SendDraftReq{Packages}` is posted to `POST /mail/v4/messages/{draftID}` (`go-proton-api/message_send_types.go:98-100`; `go-proton-api/message_send.go:75-84`). `MessagePackage` has `Addresses map[email]MessageRecipient`, `MIMEType`, `Type` (OR of schemes), `Body` (base64 data packet), `BodyKey` (cleartext session key), `AttachmentKeys` (`message_send_types.go:38-46`). `MessageRecipient` has `Type`, `Signature` (0 none, 1 detached, 2 attached), `BodyKeyPacket`, `AttachmentKeyPackets` (`message_send_types.go:22-36`). `SessionKey{Key, Algorithm}` (`message_send_types.go:58-66`); the WebClient uses `Algorithm='aes256'` ([WebClient constants.ts:1106](https://raw.githubusercontent.com/ProtonMail/WebClient/main/packages/shared/lib/constants.ts)).

Schemes (`message_send_types.go:11-19`; identical to [WebClient mailSettings.ts:97-104](https://raw.githubusercontent.com/ProtonMail/WebClient/main/packages/shared/lib/mail/mailSettings.ts)):

- `InternalScheme=1`: body/attachment session keys are encrypted to the recipient's public key (`PKESK`) and sent as `BodyKeyPacket`/`AttachmentKeyPackets` (`message_send_types.go:245-281`).
- `EncryptedOutsideScheme=2` (password / encrypt-to-outside): the session key is encrypted with a user password (`SKESK`) and placed in `BodyKeyPacket`/`AttachmentKeyPackets`; the password is shared out-of-band ([WebClient sendEncrypt.ts:26-70, 195-237](https://raw.githubusercontent.com/ProtonMail/WebClient/main/packages/mail-composer/src/helpers/send/sendEncrypt.ts)). `go-proton-api`'s `newTextPackage` does not implement scheme 2 (falls through to an error, `message_send_types.go:236-253`); the Rust `Encryptor` supports `with_passphrase` and `encrypt_session_key` (`proton-crypto-rs/proton-crypto/src/crypto/encrypt.rs:145, 211`; test `proton-crypto-rs/proton-rpgp/tests/encrypt.rs:584-605`).
- `ClearScheme=4`: cleartext (signed or not); the session key is sent in clear in `BodyKey`/`AttachmentKeys` (`message_send_types.go:238-243`).
- `PGPInlineScheme=8`: `text/plain` only; key packet still sent separately as `BodyKeyPacket` (`message_send_types.go:220-233, 245-281`).
- `PGPMIMEScheme=16`: `multipart/mixed`; detached signature required; key packet per recipient (`message_send_types.go:140-194`).
- `ClearMIMEScheme=32`: cleartext MIME with the session key in `BodyKey` (`message_send_types.go:179-184`).

`encSplit` generates a session key, encrypts the body, splits key/data packets, and re-decrypts the session key to return it (`message_send_types.go:291-307`). The bridge maps internal → `InternalScheme`; external sign+encrypt → `PGPInline` or `PGPMIME`; sign without encrypt → `Clear`/`ClearMIME`; otherwise `Clear` (`proton-bridge/internal/services/smtp/smtp_prefs.go:239-268`). The Rust account crate exposes the same decision data (`encrypt`, `sign`, `pgp_scheme`, `mime_type`, `selected_key`) via `EncryptionPreferences::from_key_model_and_settings` (`proton-crypto-rs/proton-crypto-account/src/keys/recipient.rs:478-580`).

## 5. Public key lookup

`GET /core/v4/keys?Email={address}` returns `Keys []PublicKey` and `RecipientType` (`go-proton-api/keys.go:9-21`); `PublicKey{Flags KeyState, PublicKey armored}` (`go-proton-api/keys_types.go:9-14`); `RecipientTypeInternal=1`, `RecipientTypeExternal=2` (`go-proton-api/contact_types.go:14-19`). The richer model is `GET core/v4/keys/all?Email=` with `InternalOnly` ([WebClient api/keys.ts:6-15](https://raw.githubusercontent.com/ProtonMail/WebClient/main/packages/shared/lib/api/keys.ts)); its Rust type `APIPublicAddressKeys` has `Address` (keys + `SignedKeyList`), `CatchAll`, `Unverified`, `Warnings`, `ProtonMX`, `IsProton` (`proton-crypto-rs/proton-crypto-account/src/keys/api_keys.rs:223-244`). `APIPublicKey` has `Source` (Proton=0, WKD=1, KOO=2), `Flags`, `PublicKey`, `Primary` (`api_keys.rs:14-18, 186-197`). `into_inbox_keys` filters by `supports_mail()` and classifies internal/external/catch-all (`…/keys/mail_public_keys.rs:46-140`). **Key transparency:** the cloned Rust code has only placeholders: `KT_UNVERIFIED`/`KT_VERIFIED` and an empty `KTFailure` enum, with a TODO to move to a key-transparency crate (`proton-crypto-rs/proton-crypto/src/keytransparency.rs:1-9`); SKL signature verification exists (`…/keys/signed_key_list.rs:168-215`) but no Merkle-tree/epoch verification. Unverified: whether full key transparency is required to match Proton's warnings.

## 6. Rust implementation options

**proton-crypto-rs crates** (workspace `proton-crypto-rs/Cargo.toml:3-11`; MIT `LICENSE`, workspace package license `Cargo.toml:13-17`):

- `proton-crypto` 0.15.0 (Proton registry) / 0.14.1 (crates.io) (`proton-crypto/Cargo.toml:2-6`). Default feature `gopgp`; `rustpgp` enables `proton-rpgp`; `multi_be` enables both (`proton-crypto/Cargo.toml:31-35`). Provides the `PGPProvider` API: encrypt/decrypt/sign/verify, session keys, key import/export, SRP (`proton-crypto/src/crypto/*.rs`).
- `proton-crypto-account` 0.20.2 / 0.20.1 (`proton-crypto-account/Cargo.toml:2-6`, features `28-36`): user/address key model, salts, token import/export, recipient key model, SKL (`proton-crypto-account/src/keys/*.rs`).
- `proton-rpgp` 0.10.0 / 0.9.0 (`proton-rpgp/Cargo.toml:2-6`): pure-Rust OpenPGP on `pgp` 0.21.0 with features `pqc`, `malformed-artifact-compat`, `draft-wussler-openpgp-forwarding`, `large-rsa` (`proton-rpgp/Cargo.toml:10`); pins `kem =0.3.0-pre.0` (`:18`); `x25519-dalek` for forwarding (`:22`); feature `hazmat-key-gen` (`:27-30`).
- `proton-srp` 0.9.0 / 0.8.4 (`proton-srp/Cargo.toml:2-6`): pure-Rust SRP + bcrypt mailbox hash (`proton-srp/src/pmhash.rs`).
- `gopenpgp-sys` 0.3.10 / 0.3.9 (`gopenpgp-sys/Cargo.toml:2-6`): requires Go 1.23 (`gopenpgp-sys/go/go.mod:3`), `CGO_ENABLED=1` and `bindgen` 0.72 (`gopenpgp-sys/Cargo.toml:15`); builds a static library from `gopenpgp/v3 v3.5.2-proton` (`gopenpgp-sys/go/go.mod:5`; `gopenpgp-sys/build.rs:132-199`).
- `proton-crypto-subtle` 0.2.1 (AEAD/HKDF) and `proton-device-verification` 0.1.1 (device keys) are separate MIT crates; not needed for mail crypto.

**Build without Go/cgo.** Verified by me: in a copy of the workspace, `cargo check -p proton-crypto --no-default-features --features rustpgp` and `-p proton-crypto-account --no-default-features --features rustpgp` succeed, and `cargo tree … | grep gopenpgp` is empty (no `gopenpgp-sys`). The default `gopgp` build does invoke Go. Inference: for a native macOS app, use `rustpgp` and avoid `gopenpgp-sys` entirely.

**Registry and versions.** The newest versions are on Proton's sparse registry (`proton-crypto-rs/.cargo/config.toml:1-2`; `https://rust-registry.proton.me/index/config.json`), not crates.io. crates.io has older versions: `proton-crypto` 0.14.1, `proton-crypto-account` 0.20.1, `proton-rpgp` 0.9.0, `proton-srp` 0.8.4, `gopenpgp-sys` 0.3.9 (`https://crates.io/api/v1/crates/<crate>/versions`). The crates.io packages declare only `license-file = "LICENSE"` (crates.io reports "non-standard"); the Proton-registry packages declare `license = "MIT"` plus the file (verified by downloading `https://rust-registry.proton.me/downloads/proton-crypto@0.15.0.crate`; its `Cargo.toml:27-30` has `license = "MIT"` and `license-file = "LICENSE"`). All are MIT.

**Transitive licences.** Verified by me: `cargo deny check licenses` on the `rustpgp` feature reports "licenses ok" with an allowlist of MIT, Apache-2.0, BSD-2/3-Clause, ISC, Unicode-3.0, Zlib. `cargo metadata` shows the tree is dominated by MIT OR Apache-2.0, MIT and BSD-3-Clause; `r-efi` is "MIT OR Apache-2.0 OR LGPL-2.1-or-later" (target-specific) and `unicode-ident` is "(MIT OR Apache-2.0) AND Unicode-3.0". No GPL/AGPL dependencies were found in the `rustpgp` tree.

**Maturity.** The workspace README says the crates are "Not intended or vetted for general usage outside Proton" (`proton-crypto-rs/README.md:3`). The `rustpgp` backend was added in `proton-crypto` 0.9.0 (2026-02-10) (`proton-crypto/CHANGELOG.md:116-120`), so it is ~9 months old at the snapshot. `proton-rpgp` tracks unresolved advisories: RUSTSEC-2023-0071 (RSA timing), RUSTSEC-2025-0144 and GHSA-5x2r-hc65-25f9 (ML-DSA) (`proton-rpgp/README.md`, security table). The default Rust profile is SEIPDv1/AES256/SHA512/uncompressed (`proton-rpgp/src/profile/settings.rs:165-205`), matching Proton's v4 compatibility.

**Plain `pgp` crate.** Latest is 0.21.1, licence MIT OR Apache-2.0 (`https://crates.io/api/v1/crates/pgp/0.21.1`); `proton-rpgp` 0.10.0 uses 0.21.0. It is a general OpenPGP library without Proton's key model, token format, send packages or SRP.

## 7. Recommendation

Use `proton-crypto-account` + `proton-crypto` with `--no-default-features --features rustpgp` (plus `proton-srp` for auth), and depend on the Proton-registry versions (or vendor the crates) rather than crates.io's older ones. This gives the exact Proton key/token/salt model, send preferences and SKL types, with a pure-Rust backend and no Go/cgo. Treat `gopenpgp-sys` as a fallback only if some behaviour is found to depend on GopenPGP. Budget for: (a) implementing the send-package builder and the EO/password scheme (go-proton-api does not implement scheme 2); (b) the missing attachment literal-filename API; (c) key transparency, which is placeholder-only; (d) the tracked RSA/ML-DSA advisories. If (b) proves required, the workaround is to build the literal-data packet with `pgp::packet::LiteralData::from_bytes(filename, data)` and encrypt it with `pgp`'s packet API, since `proton-rpgp`'s high-level encryptor cannot set the filename. A plain-`pgp` implementation is possible but would re-implement the Proton key model and is not recommended as the primary path.
