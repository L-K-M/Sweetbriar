# Sweetbriar architecture research: Rust core + native UIs (macOS/Swift, Linux)

*Research compiled 2026-10-11. Facts verified against live sources on that date; versions and statuses age quickly.*

## 1. TL;DR

- **The architecture is proven — including for email.** Proton Mail mobile was rewritten on a shared Rust core (Sept 2025, ~80% shared code, crash rate 0.12%→0.05%); Delta Chat runs a Rust mail engine behind CFFI *and* JSON-RPC across five frontend types; Element X rebuilt both clients on matrix-rust-sdk. Mozilla's Thunderbird is the notable counterexample (desktop C++/Rust, Android Kotlin, iOS pure-Swift), driven by legacy constraints rather than a verdict on the pattern.
- The dominant proven pattern for "Rust core + native UIs" is **a single Rust library with a deliberately small, coarse-grained façade** (matrix-sdk-ffi for Element X, application-services for Firefox, bitwarden-uniffi, Wire core-crypto, proton-pass-common) exposed via **UniFFI**. UniFFI 0.32.x is the de-facto standard: async/await on both sides, callback interfaces for push updates, active releases every ~6-10 weeks, but still pre-1.0 with breaking changes and only partial Swift 6 strict-concurrency support.
- The credible alternative is a **message-based boundary**: serialize small typed messages (bincode/protobuf) across the FFI and keep the surface to 2-3 functions. This is what Crux does (it *left* UniFFI for BoltFFI + facet typegen in June 2026), what AppFlowy does (Dart FFI + protobuf events), and what Delta Chat's JSON-RPC core does out-of-process. It costs you serialization overhead on every call and buys near-total freedom in API evolution and language coverage.
- Nobody exposes Rust `Stream`s across UniFFI today — there is no first-class stream type ([issue #1485](https://github.com/mozilla/uniffi-rs/issues/1485), [#2755](https://github.com/mozilla/uniffi-rs/issues/2755)). The standard pattern is a **callback "sink" trait** on the foreign side that Rust pushes into; wrap it in `AsyncStream`/`AsyncSequence` on the Swift side. That is how Element X's timelines and room lists work (VectorDiff events over a `Task`/`Listener` pair).
- On macOS the big fork is **in-process library vs background daemon**. An XPC service or embedded framework gives crash isolation but dies with the app; an `SMAppService`-registered **LaunchAgent keeps syncing while the UI is closed**, which an email client wants (push-style new-mail notifications, instant launch). Tailscale and Mullvad both ship daemon+GUI; Delta Chat ships the same core in-process on mobile and as an RPC server on desktop — Sweetbriar can do both with one codebase.
- Multi-process SQLite works (WAL + `SQLITE_FCNTL_PERSIST_WAL` in an App Group container), but **only the daemon should write**; other processes read or, better, go through the daemon's IPC so change notification stays coherent (GRDB-style observation does not see other processes' commits).
- macOS 26 Tahoe is the **last macOS for Intel**; macOS 27 (Sept 2026) is Apple-Silicon-only. For an app starting now, `arm64`-only is defensible, `x86_64` a cheap optional extra while Rust's `x86_64-apple-darwin` target remains tier-1.
- On Linux the same core is consumed **directly as Rust crates** (no FFI) from a gtk4-rs/libadwaita app; gtk4 0.11.x and relm4 are actively maintained. Put the façade API in a `sweetbriar-ui-api` crate that both the UniFFI bindings and the Rust-native shells use.
- Email ecosystem is ready: `imap-codec` 1.0 (transport-agnostic IMAP types), `async-imap` 0.12, `lettre`, stalwart's `mail-parser`/`mail-builder`/`jmap-client`/`calcard`, `tantivy` for search. Caveat: Microsoft began disabling **EWS in Exchange Online in October 2026** — new Exchange work should target Microsoft Graph, not EWS (Thunderbird's `ews` crate is for on-prem accounts only going forward).
- **BoltFFI** (Dec 2025) is the interesting newcomer — zero-copy codegen, async streams, ~5-600× faster calls than UniFFI in its own benchmarks — and Crux already migrated to it, but it is ~10 months old. Track it; don't bet the app on it yet.
- Recommendation: **single workspace, layered crates, daemon-owns-the-store**, UniFFI façade for macOS UI today, direct crate use on Linux, JSON-RPC/UDS boundary for out-of-process clients (extensions, CLI, web frontend later).

## 2. Findings

### 2.1 Case studies

How shipping products actually split "Rust core + native UI", what crosses the boundary, and what they regret.

#### Element X / matrix-rust-sdk

The canonical modern case: Element X is a full rewrite of the Element iOS/Android clients on **matrix-rust-sdk**, bridged by the `matrix-sdk-ffi` crate over UniFFI. As of Oct 2026 the workspace uses matrix-sdk **0.19.1** and uniffi **0.32.1** ([Cargo.toml](https://github.com/matrix-org/matrix-rust-sdk/blob/main/bindings/matrix-sdk-ffi/Cargo.toml)).

- **Split**: Rust owns sync (Sliding Sync), E2EE (vodozemac), room state/event cache, timelines, room lists, SQLite persistence — three layers: `matrix-sdk` → `matrix-sdk-ui` (UI-oriented primitives incl. the room-list service) → `matrix-sdk-ffi` (UniFFI façade over "important concepts"). The apps keep screens, navigation and product opinions; element-x-ios's own AGENTS.md makes it a rule: *services* hold product logic, and views never import `MatrixRustSDK` directly — FFI types are mapped to app-owned Swift types via `init(rustValue:)` adapters ([AGENTS.md](https://github.com/element-hq/element-x-ios/blob/develop/AGENTS.md)). That adapter discipline is worth copying.
- **FFI mechanics**: proc-macro exports are preferred over the legacy `api.udl`; Apple packaging is `cargo xtask swift build-framework` → static libs → lipo → `uniffi-bindgen-swift` → `MatrixSDKFFI.xcframework`, distributed as an SPM binary target from `matrix-rust-components-swift` — though Element X iOS actually consumes its own *cutdown* fork (iOS+simulator only) for size and versioning reasons ([bindings/apple](https://github.com/matrix-org/matrix-rust-sdk/blob/main/bindings/apple/README.md)). Android gets an AAR via `matrix-rust-components-kotlin` on Maven.
- **Live updates**: **listener callbacks, not async streams.** `TimelineListener.onUpdate(diff: [VectorDiff])`, `RoomListEntriesListener.onUpdate([RoomListEntriesUpdate])` — the update enums are exactly the list ops I recommend for mail (`append/clear/push/pop/insert/set/remove/truncate/reset`). Subscription registration returns a `TaskHandle` for cancellation; internally the FFI crate spawns a tokio task per subscription that forwards stream items to the foreign callback ([sync_service.rs](https://matrix-org.github.io/matrix-rust-sdk/src/matrix_sdk_ffi/sync_service.rs.html)). The room list exposes `entries_with_dynamic_adapters(page_size)` → `(Stream<VectorDiff>, Controller)` where the controller does `set_filter` / `add_one_page` / `reset_to_one_page` ([RoomList docs](https://matrix-org.github.io/matrix-rust-sdk/matrix_sdk_ui/room_list_service/struct.RoomList.html)) — a paginated, filtered, diff-streamed windowed list, which is *the* model for a 100k-message mailbox.
- **What went well**: one engine — "bug fixes on one platform immediately benefit the other"; instant launch/sync; E2EE correctness ([Element blog](https://element.io/blog/element-x-experience-the-future-of-element)). **Pain**: Element had to *contribute* cancellable async support upstream to UniFFI itself ([Matrix 2.0 blog](https://matrix.org/blog/2023/09/matrix-2-0)); Sliding Sync's first design was too complicated and was simplified; the Swift API is explicitly unstable; binary-size tuning is a real cost (iOS `opt-level="s"` ≈ −33%, Android LTO+strip ≈ −50%).

#### Mozilla application-services / Thunderbird

**application-services** ([mozilla/application-services](https://github.com/mozilla/application-services)) is where UniFFI itself was born: Mozilla needed to share Rust components (sync, logins/FxA, autofill, places, push, Nimbus, Glean, suggest) between Firefox Android (Kotlin) and Firefox iOS (Swift), built UniFFI for it, then spun it out. Their distribution pattern is the **megazord**: a `megazords/ios-rust` crate re-exports every component and builds to one static lib → `MozillaRustComponents.xcframework` → SPM binary target consumed by a Swift package with the generated bindings ([a-s SPM guide](https://mozilla.github.io/application-services/book/design/swift-package-manager.html)). The separate `rust-components-swift` repo is now deprecated in favor of a *local* SPM package inside firefox-ios whose binaryTarget points at nightly xcframework artifacts ([deprecation note](https://github.com/mozilla/rust-components-swift)). Lesson: one fat artefact beats many small frameworks; keep the generated-bindings package *inside the app repo* rather than a second repo to release.

**Thunderbird** is the deepest email-domain precedent on the desktop side. Desktop Thunderbird is a C++/JS codebase (comm-central), but their new Exchange support — the first new mail protocol in 20+ years — is **written in Rust**: the reusable [`ews` crate](https://github.com/thunderbird/ews-rs) ("generic enough for use in other projects") vendored at `third_party/rust/ews`, exposed to C++ via a thin `ews_xpcom` XPCOM layer. EWS email shipped in **Thunderbird 141 (beta) and 145 (Nov 2025 release)** — account setup, folders, messages, attachments, search ([blog](https://blog.thunderbird.net/2025/11/thunderbird-adds-native-microsoft-exchange-email-support/), [wiki](https://wiki.mozilla.org/Thunderbird:Exchange)). Calendar/contacts and a **Microsoft Graph backend are on the roadmap** — explicitly because Microsoft is retiring EWS in Exchange Online (Oct 2026–Apr 2027). Takeaways: (a) new protocol work in an old codebase gets written in Rust — vindicates the core-in-Rust bet; (b) the `ews` crate is directly reusable by Sweetbriar *for on-prem Exchange only*; (c) Graph is the future-proof Exchange backend.

**Thunderbird for iOS** ([thunderbird/thunderbird-ios](https://github.com/thunderbird/thunderbird-ios)) is — significantly — **not** built on a shared Rust core. It's a ground-up, still-early pure-Swift app: a `Core` Swift package with hand-written `Autoconfiguration`, `EmailAddress`, `IMAP`/`SMTP` (over **SwiftNIO**+NIOIMAP), `JMAP` and `MIME` libraries, plus `Bolt` (SwiftUI design system). Thunderbird for Android is likewise a Kotlin rewrite (K-9 Mail heritage). So Mozilla itself runs **three independent native mail stacks** (C++/Rust desktop, Kotlin Android, Swift iOS) — the strongest counter-precedent to Sweetbriar's plan *from the email domain itself*, though it arguably reflects legacy constraints (comm-central isn't embeddable; the iOS effort started fresh with a small team) more than a considered rejection.

#### Bitwarden, 1Password, Signal (libsignal), Wire (core-crypto)

**Bitwarden** is mid-migration to "everything except presentational logic belongs in the SDK" ([contributing docs](https://contributing.bitwarden.com/architecture/sdk)). Their private `sdk-internal` Rust workspace (`bitwarden-core`, `bitwarden-crypto`, `bitwarden-vault`, generated API bindings) is consumed by the web/desktop clients monorepo via **wasm-bindgen** (npm `@bitwarden/sdk-internal`), by iOS/Android via **UniFFI** (`bitwarden-uniffi`), and by desktop via **napi-rs** for OS features. Cipher decryption and Argon2 KDF migrated into the SDK behind feature flags in 2025 ([PR #14206](https://github.com/bitwarden/clients/pull/14206), [PR #15401](https://github.com/bitwarden/clients/pull/15401)); async `InternalClient` accessors landed across both UniFFI and WASM in 2026 ([PR #906](https://github.com/bitwarden/sdk-internal/pull/906)). Their hardest operational problem is *breaking-change coordination*: automated detection CI plus rolling auto-PRs to each consuming client, with a "breaking change window" blocking other teams' SDK bumps. Lesson: the boundary's velocity, not its technology, is what hurts.

**1Password 8** is the most complete "thick Rust core" story publicly told ([1Password blog](https://1password.com/blog/1password-8-the-story-so-far), [corrode podcast](https://corrode.dev/podcast/s04e06-1password)). Their core owns not just sync/crypto/data model but **view models** — state lives in the core, the SwiftUI/web shells render it ("just short of the user interface"); a sidebar re-grouping shipped with zero frontend changes. FFI is **hand-written** on native platforms with a Tokio runtime watching a request channel; they built and open-sourced **Typeshare** (proc-macro → Swift/Kotlin/TS type definitions, [blog](https://1password.com/blog/typeshare-for-rust)) to keep DTOs in sync. Browser/desktop additionally use WASM+Neon. Regrets they have stated publicly: WASM "did not take us as far as we hoped" — a full runtime in WASM was very hard; and they built *two* macOS apps (SwiftUI + Electron) then killed the SwiftUI one. Lesson for Sweetbriar: putting view-state in the core buys real consistency, and one UI per platform is enough — decide the macOS UI stack once.

**Signal / libsignal** ([signalapp/libsignal](https://github.com/signalapp/libsignal)) is the main counter-example to "just use UniFFI": Signal wrote its own proc-macro bridge — one `#[bridge_fn]` annotation emits the C-FFI entry (Swift, headers via cbindgen), the JNI entry (`Java_org_signal_client_internal_Native_*`), and the Node/Neon entry ([bridge README](https://github.com/signalapp/libsignal/blob/main/rust/bridge/README.md)). Async is asymmetric: only the Node bridge runs futures; FFI/JNI are synchronous by design. iOS ships `LibSignalClient` as a **CocoaPod**, not SPM binary target ([swift/README](https://github.com/signalapp/libsignal/tree/main/swift)). Their principle: generate *safe* interfaces, build idiomatic wrappers on top per language. For a crypto library that's defensible; for an app façade it's a lot of owned machinery — but it proves the extreme-control end of the spectrum is viable.

**Wire / core-crypto** ([wireapp/core-crypto](https://github.com/wireapp/core-crypto)): MLS+Proteus in Rust shared by iOS/Android/web. **UniFFI** for Kotlin/Swift (shipped as Maven + `WireCoreCrypto` XCFramework with real async/await APIs), **wasm-bindgen** + uniffi-bindgen-react-native for JS. Their notable pattern: all mutations go through an explicit **transaction context** (`newTransaction`/`transaction`) that buffers changes and commits atomically — a clean answer to "FFI can't enforce Rust ownership semantics." Their pains were API-drift during migration (per-platform newtype timing, method renames when dropping a hand-written Kotlin wrapper) — the same breaking-change-coordination story as Bitwarden.

#### Delta Chat, Mullvad, Proton

**Delta Chat** ([chatmail/core](https://github.com/chatmail/core), formerly deltachat-core-rust) is the closest living analog to Sweetbriar: a Rust *email engine* (IMAP/SMTP/MIME/rPGP/Iroh, per-account SQLite stores) consumed by Android (JNI), iOS (Swift via CFFI), Electron desktop, and Python/Go/Node bots. Their 2025 blog post explains the boundary evolution in detail ([delta.chat/en/2025-02-11-why-jsonrpc-bindings-exist](https://delta.chat/en/2025-02-11-why-jsonrpc-bindings-exist)): the legacy C FFI (blocking calls, pointers) worked in-process on mobile but made Electron desktop unresponsive under API traffic, and pointers can't cross Electron's process boundary anyway. So they defined a **JSON-RPC 2.0 API on the core** and serve it over *any* transport: `deltachat-rpc-server` is a binary the desktop spawns and talks to over **stdio**; mobile keeps calling the *same* JSON-RPC API transported through in-process CFFI calls; WebSocket and Electron-IPC transports also exist ([deltachat-rpc-server](https://github.com/chatmail/core/tree/main/deltachat-rpc-server), [UPDATE_CORE.md](https://github.com/deltachat/deltachat-desktop/blob/main/docs/UPDATE_CORE.md)). Typed clients are generated (TypeScript `jsonrpc-client` on npm; Python `deltachat-rpc-client`; a Go client). Events flow back over the same channel. **This is precisely the transport-pluggable façade I recommend for Sweetbriar** — one message API, FFI in-process or stdio/socket out-of-process — proven by an email-shaped product for years. The core is *not* an embeddable library you import, though: it's an application core you run, which is exactly the daemon/librarian shape contemplated below.

**Mullvad VPN** ([mullvadvpn-app](https://github.com/mullvad/mullvadvpn-app)) is the archetypal **daemon + thin frontends** product. `mullvad-daemon` (Rust, actor system) is a privileged system service owning all security guarantees — tunnel, firewall/killswitch, API. Every frontend is "a program that connects to the daemon's management interface": Electron+React GUI, Rust CLI, Kotlin Android app. The management interface is **gRPC over protobuf** (`mullvad-management-interface`), transported over a unix socket (`/var/run/mullvad-vpn`), Windows named pipe, or JNI inside the Android process ([docs/architecture.md](https://github.com/mullvad/mullvadvpn-app/blob/main/docs/architecture.md)). Settings/tunnel state are owned by the daemon and **broadcast as events to all connected clients** — which is why CLI+GUI+Android can drive it concurrently. iOS is the exception that proves the constraint: app-extension/Store rules forced a *standalone* Swift implementation (`ios/`, WireGuardKit) with no daemon at all. Lessons for Sweetbriar: the daemon-authoritative model works at scale and gives multi-client for free; gRPC/protobuf is a solid wire choice over raw JSON; but watch for platforms whose process model forbids your daemon.

**Proton** is — surprisingly — the single most relevant case study of 2025-2026. **Proton Mail mobile was completely rewritten on a shared Rust core** (internal "Engineering Transformation"; new apps launched Sept 2025, detailed in [Proton's Feb 2026 blog](https://proton.me/blog/next-generation-proton-mail-mobile-apps)): the Rust core holds all business logic, ~80% of the codebase is shared, SwiftUI on iOS + Compose on Android, and published crash rates *fell* (iOS 0.12% → 0.05%). An actual shipping email client proving this architecture at scale — with the caveat that it's mobile-only so far. Adjacent: **Proton Pass** runs on `proton-pass-common` (pure-Rust core; UniFFI mobile bindings as `PassRustCore`, wasm for web — [repo](https://github.com/protonpass/proton-pass-common)); **Proton Authenticator** same architecture ([blog](https://proton.me/blog/authenticator-rust)); **ProTUN** is a Rust VPN client engine with UniFFI bindings rolling out 2026 ([blog](https://protonvpn.com/blog/protun-technical)). Not Rust: Proton Mail Bridge (Go — local IMAP/SMTP for desktop clients, [proton-bridge](https://github.com/ProtonMail/proton-bridge)); Proton Mail desktop (unverified). Takeaway: Proton is *converging* on "one Rust core per product, thin native shells" — and for Proton accounts, Sweetbriar integrates via Bridge's localhost IMAP, not a private API.

#### Crux, AppFlowy, Spacedrive, Anytype, Ghostty, others

**Crux** ([redbadger/crux](https://github.com/redbadger/crux)) is the purest expression of the "thick core, thin shell" idea: the entire app — every screen's state and behaviour — lives in an Elm-architecture Rust core (`Event → update → Model/ViewModel`), and the Swift/Kotlin/React shell only renders the `ViewModel` and *performs* effects the core requests (HTTP, KV store, time). The whole FFI surface is three functions on a `Bridge`: `update`, `resolve`, `view`, all passing `bincode`-serialized bytes. Notably, in **crux_core 0.19.0 (June 2026) they migrated the byte-oriented FFI bindings from UniFFI to BoltFFI**, and generate the *typed* message layer separately via facet-based typegen (you `#[derive(Facet)]` on boundary types; a codegen binary emits Swift/Kotlin/TS/C# types plus matching serialization). 0.20.0 shipped Aug 2026; still pre-1.0. Trade-off vs UniFFI: a much smaller, more stable binding surface and enforced architectural discipline, at the price of per-call serialization and manual shell plumbing ([crux book](https://redbadger.github.io/crux/), [releases](https://github.com/redbadger/crux/releases)).

**AppFlowy** (Notion-like; Flutter UI + Rust workspace): the Rust core owns SQLite, CRDT (yrs), search and all logic. The boundary is **Dart FFI with an event-dispatch protocol**: Dart calls `async_event(port, protobuf_bytes)`; Rust handles and replies via `allo_isolate` ports. Events and payloads are declared in Rust (`#[event(input=.., output=..)]`, `ProtoBuf` derives) and codegen emits matching Dart/TS classes. They deliberately chose events over a function-shaped bridge so the same backend can serve a Tauri/TypeScript front-end too; the admitted cost is protobuf serialization on every call, which hurt for large payloads like images ([AppFlowy architecture docs](https://appflowy.com/blog/tech-design-flutter-rust), [docs.appflowy.io](https://docs.appflowy.io/docs/documentation/software-contributions/architecture/backend/event)).

**Spacedrive** (file manager): pure-Rust `sd-core` (filesystem, SeaORM/SQLite, jobs, P2P) behind **rspc** — end-to-end typesafe RPC where a Rust function in a router is callable from TypeScript with types generated by Specta. rspc is transport-agnostic: Tauri IPC for the embedded app, **JSON-RPC 2.0 over unix-domain sockets for the daemon** that CLI/web/desktop all share; the iOS build embeds the core in-process via FFI plus Specta-generated Swift types. Events broadcast on an internal `EventBus` (`ResourceChanged`) that clients fold into a normalized client-side cache ([spacedrive repo](https://github.com/spacedriveapp/spacedrive), [rspc.dev](https://rspc.dev/)). The instructive shape: *one query/mutation API, several transports*.

**Anytype** (Go, not Rust, but same shape): `anytype-heart` is a Go core used by desktop via **gRPC + protobuf with a persistent event stream**, and by mobile as a C-ABI library via gomobile with generated protobuf types. Same lesson: typed message boundary, transport varies per host ([anytype-heart](https://github.com/anyproto/anytype-heart)).

**Ghostty** (Zig, not Rust) is the closest structural analog to what Sweetbriar wants on the *UI* side: `libghostty` is a cross-platform C-ABI library; the macOS app is Swift/SwiftUI/AppKit and the Linux app is GTK4 — two fully native UIs embedding the same core with embedder callbacks for wakeup/clipboard/actions. The authors explicitly describe it as core-as-library + native embedder ([ghostty docs](https://ghostty.org/docs/about), [embedding API](https://mintlify.wiki/ghostty-org/ghostty/api/embedding)).

**Email-specific landscape:** no shipping GUI email client is built on a shared Rust core yet (as of Oct 2026, unverified but no counterexample found). The pieces exist: **himalaya**'s `io-email` is a sans-IO, no-std-capable protocol stack (IMAP, JMAP, SMTP, Gmail API, Graph, Maildir) used by its CLI/TUI — the closest existing "Rust mail core"; **meli** is a monolithic Rust TUI; **Stalwart** proves JMAP/MIME at scale server-side. Sweetbriar would be the first GUI client to take the shared-core route seriously.

**Mailspring** deserves its own paragraph because it is a shipping *email client* built exactly like the proposed design — in C++/Electron rather than Rust/Swift. Each account runs its own **`mailsync` C++ process** (MailCore2 for IMAP/SMTP, own sqlite store); the Electron UI sends **tasks over stdin** and receives **newline-delimited JSON entity deltas on stdout** ([Mailspring-Sync](https://github.com/Foundry376/Mailspring-Sync), [CLAUDE.md](https://github.com/Foundry376/Mailspring/blob/master/CLAUDE.md)). The UI is *read-only on the database* — all writes go through the sync engine; tasks decompose into an immediate "local" half and a retryable "remote" half (an outbox). Per-account processes mean auth/connection failures just kill one process; SQLite WAL allows concurrent readers. It is a decade of validation for: **per-account sync workers + single-writer store + delta-streamed UI updates** — the same shape as Delta Chat's RPC core and the daemon model in §4.

#### Counter-examples and historical precedents

**Outlook Mobile / Acompli** is the classic *email-client* precedent: Acompli built the client that became Outlook for iOS/Android around a shared portable C++ core (sync engine, caching, crypto) with native UIs on each platform — the same shape Sweetbriar proposes, in C++ rather than Rust. Microsoft kept and evolved that architecture after the 2014 acquisition ([Petri/MS Learn](https://petri.com/outlook-mobile-gets-new-architecture/), [learn.microsoft.com](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/outlook-for-ios-and-android/outlook-for-ios-and-android)). Interesting twist: the *sync* in modern Outlook Mobile happens partly in Microsoft's cloud rather than on-device — an architectural option a privacy-focused client explicitly should not take.

**Dropbox** is the canonical failure mode to study: they shared a C++ core between iOS and Android from 2013 and abandoned it in 2019, publishing a candid post-mortem — custom tooling they had to build (Djinni, json11, nn), debugging across the boundary taking weeks not days, hiring friction, and platform defaults always winning ([dropbox.tech](https://dropbox.tech/mobile/the-not-so-hidden-cost-of-sharing-code-between-ios-and-android)). Context: mobile-only, 2013-era C++, no crates.io, hand-rolled glue. Both conditions (Rust + mature FFI tooling; a domain-heavy rather than UI-adjacent core) differ for Sweetbriar — but it's the strongest honest argument against the whole approach and worth one section in §4.

#### UniFFI production users

No formal users list is maintained; the README only cites Mozilla's own usage. Verified production users from ecosystem evidence: Mozilla (Firefox Android/iOS via application-services), Element X (matrix-sdk-ffi), Wire core-crypto, Bitwarden (`bitwarden-uniffi`), uniffi-bindgen-react-native consumers, juspay/hyperswitch, Synonym's VSS client. Counter-evidence: Signal and 1Password use hand-rolled bridges; Crux migrated off UniFFI to BoltFFI ([uniffi-rs](https://github.com/mozilla/uniffi-rs)).

Important mechanics of UniFFI worth internalizing:

- Every argument/return that isn't a primitive travels **by value through a `RustBuffer`** — data is serialized (UniFFI's own compact encoding) and copied across the boundary. Fine for view-model structs and commands; bad for megabyte-scale payloads. `[ByRef] bytes` (UDL) / `&[u8]` args map to pointer+length `ForeignBytes` as of 0.32 ([0.32.0 changelog](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md)).
- The foreign runtime *drives* Rust futures: Swift's `Task` polls `rust_future_poll`; there is no hidden Rust thread unless you opt into `async_runtime="tokio"` ([async overview](https://mozilla.github.io/uniffi-rs/latest/internals/async-overview.html)). Cancellation = the foreign side stops polling and drops the future handle → Rust future is dropped (cooperative; design APIs accordingly).
- 0.32 added `uniffi_parse_rs` — parse Rust sources for binding metadata without compiling the crate first — and an experimental `uniffi-bindgen-kotlin-jni` with "large performance improvements" ([changelog](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md)).
- Swift code quality: generated `struct`/`enum`/protocol types are real Swift value types; objects are `@unchecked Sendable` classes wrapping an opaque handle with a lock-protected handle map. Generated code is readable but not something you'd write by hand ([Swift overview](https://mozilla.github.io/uniffi-rs/latest/swift/overview.html)).

**Serialization overhead in numbers.** UniFFI calls cost ~625ns for a primitive and ~2µs for a small string in BoltFFI's (biased but plausible) [benchmarks](https://boltffi.dev/docs/overview); passing 1,000 structs ≈ 1.2ms. For a mail client that means: **never ship whole message lists or bodies through the façade** — ship IDs and windowed fetches (see §2.4).

### 2.3 Async across the boundary

The proven recipe, matching Element X and app-services:

- **One tokio runtime owned by the Rust core.** Create it inside the façade crate (`tokio::runtime::Runtime`, multi-threaded, sized modestly). UniFFI's `async_runtime="tokio"` handles the common case; for finer control you can also `handle.spawn()` internally and expose only handles.
- **Rust→Swift pull**: exported `async fn` becomes `async throws` in Swift; Swift's executor polls the Rust future. Works with `async_trait` for exported traits ([futures guide](https://mozilla.github.io/uniffi-rs/latest/futures.html)).
- **Rust→Swift push**: `#[uniffi::export(with_foreign)]` callback interface implemented in Swift — e.g. a `MailListener`/`MessageListSink`. Rust calls it on its own threads; the Swift impl hops to the right executor (usually feeding an `AsyncStream`/`AsyncSequence` continuation or posting `Notification`s). This is exactly the "sink" pattern UniFFI docs and community libs use in lieu of streams.
- **Cancellation**: dropping the Swift `Task` drops the Rust future — cooperative only. For long sync operations expose an explicit `cancel()`/`SyncHandle` API and checkpoint in Rust, because a dropped future stops at the next `.await`, possibly mid-transaction; put data-safety invariants in the storage layer, not in cancellation semantics.
- **Backpressure**: don't stream raw `Vec<Row>` per event. Push *deltas* (`insert at index`, `update`, `remove`, `clear` — the matrix-sdk `VectorDiff` model) at UI-visible batch sizes, and let the UI pull windowed contents on demand. If the sink can be called faster than Swift drains it, the Rust side should coalesce (debounce) or use a bounded channel and drop/merge older deltas.
- **Main thread**: never call Swift UI code on a Rust thread except through the sink, and document/implement every callback as "arrives on an arbitrary thread; the sink hops to `@MainActor` itself" — Element X's listeners follow exactly this.

### 2.4 API granularity

The single most important boundary decision. Evidence:

- **matrix-sdk-ffi deliberately re-wraps** matrix-rust-sdk in a coarse façade (a `Client`/`Room`/`Timeline` object graph with listener registration) rather than exporting the SDK's rich internal API — specifically to keep the FFI surface small, stable and mockable; Element X's room list is `RoomListService` with *dynamic filters* and paginated subscriptions that emit `VectorDiff`/`RoomListEntriesUpdate` streams ([RoomList API](https://matrix-org.github.io/matrix-rust-sdk/matrix_sdk_ui/room_list_service/struct.RoomList.html)).
- **Crux is the extreme**: 3 functions total, all bytes. **AppFlowy/Anytype/Spacedrive** settle in the middle: a typed message/RPC protocol with ~dozens of verbs.
- The rule that falls out: **coarse objects + typed messages + pull-windowed lists + push deltas**. For a 100k-message mailbox the façade should expose:
  - `list_descriptors()` (mailboxes), `message_list(mailbox, filter)` → returns a **list handle + snapshot window** (e.g. 200 `MessageSummary` around the viewport) not the whole list;
  - **diff streams** on that handle (`inserted/updated/removed/moved` with stable `rowid`-like keys) for live updates;
  - `message(id) -> full metadata`, `message_body(id) -> file path / mmap'd blob reference`, **not** `Vec<u8>` bodies through the façade — bodies and attachments should be delivered as paths/FD references to on-disk blobs so Swift can hand them to `WKWebView`/`NSData` without copying through RustBuffer. UniFFI can pass `bytes` efficiently as pointer+length for *calls* but large copies still happen on decode.
- Push vs pull: **push small invalidations/deltas, pull payload data** on demand. Never push a 100k list diff the UI can't consume.

### 2.5 Process model on macOS

Apple's own framing ([Designing Daemons and Services](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/DesigningDaemons.html)):

| Option | Lifetime | UI? | Managed by launchd | Fit for mail sync |
|---|---|---|---|---|
| In-process Rust lib | = app | n/a | no | Simplest; sync dies with UI |
| XPC service (.xpc) | on-demand, **killed when app exits/idle** | no | yes (per-app) | Crash isolation only; useless for background sync |
| `SMAppService` **LaunchAgent** (macOS 13+) | user session, outlives app | no | yes | **Right answer**: embed `sweetbriard` in `Contents/Library/LaunchAgents/`, register via `SMAppService.agent(plistName:)`, user-toggleable ([SMAppService docs](https://developer.apple.com/documentation/servicemanagement/smappservice)) |
| `SMAppService` daemon | system-wide | no | yes | Overkill + notarization pain |
| App extension (notification/share/Spotlight/QuickLook) | on-demand | limited | yes | Needs read access to the store, not the network |

- **Recommended topology**: `sweetbriard` LaunchAgent owns accounts/network/SQLite-writes; the UI app talks to it over **XPC** (`NSXPCConnection` to a Mach service — sandbox-friendly; alternatively a unix socket in the App Group if you want one transport shared with Linux). GUI apps doing exactly this: Tailscale (daemon + GUI over LocalAPI on a unix socket/XPC, [tailscale docs](https://tailscale.com/docs/concepts/macos-variants)) and Mullvad (Rust `mullvad-daemon` + GUI over IPC).
- **App extensions** (share, Spotlight index, Quick Look, notification) are sandboxed and short-lived: give them **read-only** access to the store in an **App Group container**, or better, have them IPC to the daemon.
- **SQLite multi-process** is workable but sharp-edged: WAL mode permits concurrent readers across processes on one host; use `SQLITE_FCNTL_PERSIST_WAL` so read-only connections don't need the `-shm`/`-wal` to exist; protect DB setup/migration with `NSFileCoordinator` ([GRDB sharing guide](https://groue-grdb-swift.mintlify.app/guides/sharing-a-database)). The big caveat: change *notification* doesn't cross processes — SQLite gives you no "another process committed" hook, so readers poll or get poked via IPC/Darwin notifications. On iOS the famous `0xDEAD10CC` crash (holding a DB lock across suspension) leads veterans to advise **not** sharing a SQLite file in an app group at all ([Marco Arment via mjtsai.com](https://mjtsai.com/blog/2025/05/15/sqlite-databases-in-app-group-containers-dont/)); that specific failure mode is iOS-only, but the lesson — *one writer process, everyone else goes through it* — is the right default on macOS too.
- Crash isolation win: a panic/abort in the sync engine leaves the UI alive and vice-versa; launchd restarts the agent. Cost: two debuggable processes, an IPC protocol to design (versioned!), and lifecycle coordination (agent must checkpoint gracefully when the UI asks it to stop/start).

### 2.6 Build and tooling

- **Packaging**: standard pipeline is per-arch `cargo build --target` → `lipo`/`xcodebuild -create-xcframework` → SPM **binary target** (local `path:` for dev, remote zip + `swift package compute-checksum` for distribution) with generated UniFFI `.swift` bindings compiled as a normal SPM target. Well-documented by Ferrostar/Stadia Maps ([blog](https://stadiamaps.com/blog/ferrostar-building-a-cross-platform-navigation-sdk-in-rust-part-2/)) and Mozilla's "megazord" approach: one xcframework containing *all* Rust components so consumers link a single blob. Note Mozilla's evolution: the standalone `rust-components-swift` package repo is **deprecated** — firefox-ios now ships a *local* `MozillaRustComponents` SPM package in-repo whose binaryTarget points at the published xcframework zip (nightly artifacts) or a local path for dev ([a-s SPM guide](https://mozilla.github.io/application-services/book/design/swift-package-manager.html), [deprecation note](https://github.com/mozilla/rust-components-swift)). In-repo local package + artifact URL is the simpler pattern — copy it.
- **`cargo-swift`** ([antoniusnaumann/cargo-swift](https://github.com/antoniusnaumann/cargo-swift/)) automates exactly this (`cargo swift package` → ready SPM package incl. bindings + xcframework). Caveat: version-locked to UniFFI (0.11.x ↔ uniffi 0.31.x as of Oct 2026; check for a 0.32-compatible release before adopting, or replicate its ~3 commands in a `just`/`make` recipe).
- **Architectures**: macOS 26 Tahoe is the last Intel-capable macOS — only the 2019 Mac Pro/16" MBP, 2020 4-port 13" MBP and 2020 iMac are supported, and macOS 27 (Sept 2026) is Apple-Silicon-only; full Rosetta 2 ends after macOS 27, with a legacy-games subset surviving into macOS 28 ([Apple via MacRumors](https://www.macrumors.com/2026/02/16/macos-tahoe-26-4-rosetta-2-warnings/), [Ars Technica](https://arstechnica.com/gadgets/2025/06/apple-details-the-end-of-intel-mac-support-and-a-phaseout-for-rosetta-2/), [Wikipedia](https://en.wikipedia.org/wiki/MacOS_Tahoe)). → **Ship `arm64` first; adding `x86_64-apple-darwin` to the xcframework is cheap if you want it, but no new app should *need* Intel.**
- **Debugging**: lldb via Xcode works on Rust code (the rust-lldb wrapper adds formatters); `cargo` runs `dsymutil` automatically so release builds emit `.dSYM`s usable for `.ips` crash-report symbolication; crashes inside Rust appear as normal crash reports ([rust#79361](https://github.com/rust-lang/rust/issues/79361), [symbolicate](https://github.com/conradirwin/symbolicate)). Rust panics across FFI are UB if they unwind over `extern "C"` — UniFFI installs its own panic handling; with hand-rolled FFI use `panic = "abort"` in the FFI staticlib or `catch_unwind`.
- **Binary size**: a real UniFFI core lands in the ~8-25MB range per arch for a dependency-rich core (async-imap+lettre+tantivy+reqwest will be at the upper end). Static linking into the app means no separate framework to sign; keep `panic="abort"`, LTO, and `strip = "symbols"` (with dSYMs kept) in the release profile.
- **CI**: GitHub `macos-*` runners build the Rust matrix (`aarch64-apple-darwin` ± `x86_64`) + `cargo test` + `swift build/test`; produce the xcframework zip as a release artifact. For dev flow, keep the SPM package + generated bindings in the *app repo* with a `path:` binary target (the post-deprecation Mozilla pattern); a published URL+checksum is only needed for external consumers.

### 2.7 Reuse on Linux

Two consumption models, both cheap because the core is pure Rust:

1. **Direct crate use** (recommended): a GTK4/libadwaita app — `gtk4` 0.11.5 (2026-09-20), `libadwaita` 0.9.2 (2026-07-07), `relm4` 0.11 (2026-04-08) all actively maintained — `use`s `sweetbriar-ui-api` directly, with the same façade types the UniFFI bindings wrap. Zero FFI, full Rust type fidelity (real `Stream`s, borrowing), shared Tokio runtime with the glib main loop (`tokio` + `glib` integration is well-trodden; relm4 is tokio-native).
2. **Same daemon + IPC as macOS**: on Linux the `sweetbriard` process is a systemd user service; UIs and a CLI talk over a unix socket. If the macOS UI already speaks to a daemon via XPC, write the Linux UI against the *same* socket protocol and the code paths converge.

The boundary that keeps both front ends thin is the **façade crate**: all UI-facing types are owned by `sweetbriar-ui-api`; on Linux it's a normal crate dependency, on macOS it's the UniFFI export surface, on the wire it's serialized via the daemon's protocol. Ghostty demonstrates the end-state: `libghostty` C-ABI core, SwiftUI on macOS, GTK4 on Linux ([docs](https://ghostty.org/docs/about)).

### 2.8 Proposed architecture

Strict layering — each layer only talks to the one directly below it. The façade crate is the *only* thing UIs ever see; protocol backends never see each other; the store never sees the network.

Key insight for the boundary: `sweetbriar-ui-api` is an **abstract interface with two transports** — in-process FFI (UniFFI→Swift, direct use→GTK) and out-of-process IPC (XPC/unix socket → `sweetbriard`). In daemon mode the Swift UI links a thin `ui-api` *client stub* speaking the wire protocol; UniFFI is then only needed for optional embedded mode. Mullvad, Tailscale and Delta Chat desktop all make that choice — one protocol, both transports.

## 4. Recommendations for Sweetbriar

1. **Layered workspace as drawn above.** Put *all* boundary types in `sweetbriar-ui-api` and nothing transport-specific below it. This single discipline is what makes Linux reuse free and a later daemon split possible.
2. **Façade style: coarse objects + typed diffs.** Objects (`Client`, `Account`, `Mailbox`, `MessageList`, `Composer`) with ~tens of methods; `MessageList` = handle + windowed snapshot + `MessageListDiff` stream (`Reset/Insert/Set/Remove/Move/PushBack/Truncate` — the eyeball-im `VectorDiff` model) + a controller with `set_filter`/`add_one_page`/`reset`. That is exactly the mechanism Element X settled on for room lists; for a 100k-message folder it is the only pattern that keeps FFI traffic O(viewport). Bodies/attachments: opaque `BlobRef { path | fd }`, rendered by Swift without round-tripping megabytes.
3. **FFI: UniFFI 0.32 with proc-macros** for the whole `ui-api` surface; Swift 5.10+ language mode (or 6 with the known async-foreign-trait gap patched — check [#2929](https://github.com/mozilla/uniffi-rs/issues/2929) status). Keep `sweetbriar-ffi` as the *only* UniFFI-dependent crate so version churn is contained. Re-evaluate **BoltFFI** ~mid-2027 — if your façade is message-shaped, migrating to BoltFFI (or Crux-style facet typegen) is cheap later precisely because the boundary is small.
4. **Async**: one tokio runtime inside `sweetbriar-core`; every long op returns a handle with `cancel()`; push events through `#[uniffi::export(with_foreign)]` sink traits adapted to `AsyncStream` in Swift and `glib` channels/relm4 on Linux; batch/coalesce diffs in Rust so the UI is never flooded.
5. **Process model: phase it.** Phase 1 ship in-process (simplest, fastest to iterate — this is also what Delta Chat does on iOS). Design `ui-api` to be *transport-pluggable* (in-proc FFI today, IPC tomorrow — the Spacedrive pattern of one API over two transports). Phase 2 add `sweetbriard` as an `SMAppService` LaunchAgent owning all writes + sync, giving background sync, new-mail notifications while the app is closed, and crash isolation; the UI and extensions then reach it via XPC/unix-socket with read-only App-Group SQLite access only as a fallback. **The daemon should be the single writer.**
6. **Linux**: GTK4 + libadwaita app consuming `ui-api` directly (and later the same daemon socket as macOS). No FFI, same façade types — this is the Ghostty end-state.
7. **Data safety**: single-writer store, WAL, `SQLITE_FCNTL_PERSIST_WAL`, atomic draft writes (drafts are store rows, autosave debounced), outbox as an append-only queue, `NSFileCoordinator`-guarded migrations, crash-consistency tests (kill -9 mid-sync) from day one.
8. **Exchange**: for Microsoft 365 use **Graph API**, not EWS — Microsoft began disabling EWS in Exchange Online in Oct 2026 (full disable Apr 2027); keep an optional `backend-ews` for on-prem only ([Microsoft timeline](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-exchange-web-services-in-exchange-online)).

**Strongest counter-arguments, honestly stated.**

- *Against the shared core entirely (the Dropbox argument):* Dropbox abandoned their shared C++ mobile core in 2019 — custom tooling (they had to build Djinni), debugging pain across the boundary, hiring friction, platform defaults always winning. Their conclusion: writing it twice was cheaper ([dropbox.tech](https://dropbox.tech/mobile/the-not-so-hidden-cost-of-sharing-code-between-ios-and-android)). Context matters: 2013-era C++, *mobile-only* platforms, hand-rolled glue, no crates.io ecosystem. Rust+UniFFI in 2026 removes most of the tooling pain, and an email *core* (sync/index/MIME) is far more domain-heavy and far less platform-shaped than Dropbox's UI-adjacent code — the same reason Element, Signal and Bitwarden all moved *toward* shared cores after Dropbox moved away. Still: the organizational lesson stands — the core becomes a bottleneck if the boundary is too chatty or too product-shaped; the façade discipline is the mitigation.
- *Against the daemon:* Mullvad/Tailscale justify daemons because they hold *system* state (tunnels, elevated privileges). A mail sync engine holds only user data; Delta Chat iOS runs in-process and survives. A second process doubles your testing matrix, adds an IPC protocol to version forever, and makes "quit the app" semantics murky (users hate hidden background processes). Counter to the counter: for a *desktop* email client, background sync is what users expect — Outlook, Apple Mail and Proton Bridge all keep working when the window closes — and `SMAppService` makes the agent user-visible and toggleable. So: in-process first, daemon when the façade is stable.
- *Against UniFFI:* pre-1.0 churn, per-call serialization, Swift 6 strict-concurrency gaps, no streams. If those bite, the escape hatch is real: keep `ui-api` message-shaped internally so swapping UniFFI→BoltFFI/hand-C is a contained change in one crate.

## 5. Risks and open questions

- **UniFFI Swift 6 strict concurrency**: async foreign-trait codegen fails under `.v6` strict mode as of 0.31.2 ([#2929](https://github.com/mozilla/uniffi-rs/issues/2929)); check whether 0.32.2 closes it, else budget a template patch or Swift 5 mode.
- **cargo-swift version lag**: it pins to specific UniFFI versions (0.11.x ↔ uniffi 0.31.x); may need hand-rolled packaging for 0.32 ([repo](https://github.com/antoniusnaumann/cargo-swift/)).
- **BoltFFI is ~10 months old** (Dec 2025): bus factor, API churn, missing languages. Track, don't adopt yet.
- **Multi-process notification**: SQLite has no cross-process commit hook — extensions reading the store can show stale data unless the daemon pokes them (Darwin notification / XPC / polling). Design for it.
- **macOS notification UX**: a LaunchAgent must be registered by user action; macOS 26 keeps tightening login-item visibility — budget UX work for "enable background sync" onboarding.
- **Proton Mail** has no official third-party API: real clients go through Proton Mail Bridge (Go app exposing local IMAP/SMTP, [proton-bridge](https://github.com/ProtonMail/proton-bridge)). Sweetbriar's "Proton backend" = excellent IMAP + Bridge detection; a native Proton API backend is a research project, not a feature.
- **Multi-device coherence**: flag/draft state synced to multiple clients (UIDPLUS/CONDSTORE/QRESYNC semantics) — the sync engine needs careful conflict rules; Delta Chat's core is the best reference implementation to study.
- **tantivy index + multi-process**: index is single-writer too — keep it inside the daemon-owned directory, never in a shared container written by two processes.
- **UniFFI breaking-change cadence**: 0.28→0.32 in 18 months; pin versions, isolate in `sweetbriar-ffi`, subscribe to the changelog.
- **Open**: whether UI state (view-model) should live in Rust Crux-style. Probably not for Sweetbriar v1 — SwiftUI `@Observable` view models are more idiomatic on Apple platforms and the diff-stream façade gives you most of the benefit without Crux's rigidity.
