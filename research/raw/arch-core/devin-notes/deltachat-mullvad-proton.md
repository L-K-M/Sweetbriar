# Sharing a Rust Core Between Native UIs: Delta Chat, Mullvad VPN, Proton

Research notes for a report on the "one Rust core, many native frontends" pattern. All three products ship real consumer apps on 3+ platforms with Rust at the center, but they made very different interface and process-model choices.

## 1. Delta Chat — the chatmail core (closest analog to an email client)

**What lives in Rust.** The core (repo `chatmail/core`, formerly `deltachat-core-rust`; crate `deltachat`) owns everything non-visual: IMAP/SMTP transports with TLS, DNS caching and shadowsocks/proxy support, MIME parse/build, rPGP-based end-to-end encryption, Autocrypt and SecureJoin, per-profile SQLite storage, webxdc, Iroh P2P multi-device sync, and the scheduler that drives background I/O. Frontends (Android Java/Kotlin, iOS Swift, desktop TypeScript/Electron, Python/Node bots) contain only UI, platform glue, and translations.

**Two parallel interface styles.**

- **C FFI (`deltachat-ffi`)**: a raw C ABI (`dc_*` functions over opaque handles) used in-process by mobile. Events are delivered via an event channel: `start_io`/`stop_io` drive the async runtime, and a callback (`event_emitter` + user-data pointer) streams `Event` values to the UI thread. Android reaches it through JNI; iOS imports a `DcCore` Swift wrapper module around the same FFI, also in-process.
- **JSON-RPC (`deltachat-jsonrpc`)**: a high-level typed API built on `yerpc`, consumed over stdio by the `deltachat-rpc-server` subprocess (desktop, since v1.45.0, 2024-05-24) and by Python/Node bots. Events surface as a stream via `get_next_event`; TypeScript bindings are autogenerated from the RPC module.

**Why both exist.** Per the team's retrospective (delta.chat blog, 2025-02-11): the original C FFI worked fine in-process on mobile, but Electron's multi-process model forbids passing C-struct pointers across the process boundary, and the FFI's blocking `block_on` calls froze the single-threaded desktop main process. Their intermediate fix — a JSON API over Node NAPI on top of the C FFI (`deltachat-node`) — required touching six code places to add one method. JSON-RPC (merged into core in v1.33.0, 2022-10) cut that to two; the NAPI layer was then deleted in favor of the stdio `rpc-server` binary. CFFI bindings are now explicitly maintenance-only; new APIs appear only in JSON-RPC.

**Process model.** In-process on Android and iOS (core is a linked library; calls can be made from the UI thread). Out-of-process on desktop (Electron main spawns `deltachat-rpc-server`, talks over pipes). An experimental Tauri-based desktop (`deltachat-tauri`) also exists. Lessons: FFI suits same-process mobile embedding; typed RPC with generated bindings suits everything else; keep the old ABI for existing consumers but stop extending it.

## 2. Mullvad VPN — daemon + native frontends

**Daemon/UI split.** The `mullvadvpn-app` monorepo ships a privileged system service, `mullvad-daemon` (Rust, actor system), which upholds all security guarantees: tunnel management, firewall, DNS, kill switch, API communication. Frontends are explicitly defined as "any program that connects to the daemon's management interface": the desktop GUI (Electron + React), the CLI (Rust binary `mullvad`), and the Android app (Kotlin UI). `talpid-core` is the Mullvad-agnostic, privacy-preserving VPN client library; `mullvad-*` crates add the service-specific logic on top.

**IPC: gRPC, not JSON-RPC.** The management interface is defined as Protocol Buffers (`mullvad-management-interface`) and transported over a Unix domain socket on Linux/macOS (`/var/run/mullvad-vpn`), a Windows named pipe (`//./pipe/Mullvad VPN`), and via JNI (`mullvad-jni`) on Android, where the daemon runs inside the app process and listens on `/data/data/net.mullvad.mullvadvpn/rpc-socket`. The socket path can be restricted by group (`MULLVAD_MANAGEMENT_SOCKET_GROUP`). A notable 2024 fix: stop gRPC from routing daemon IPC through an `http_proxy` environment variable.

**State sharing.** Settings and tunnel state are owned by the daemon and broadcast as events to every connected frontend; the GUI keeps only per-user display preferences (`gui_settings.json`). This is why CLI, GUI, and Android app can all drive the same daemon concurrently.

**Platform matrix.** Desktop GUI is Electron+React; CLI and daemon are Rust. Android pairs Kotlin UI with the Rust daemon over JNI. iOS is "a completely standalone implementation" in `ios/` (Swift, WireGuardKit, NWPathMonitor for offline detection) — there is no daemon on iOS, and the App Store build is not even GPL. The workspace also contains a `mullvad-ios` Rust crate alongside the Swift app (exact role: unverified — plausibly a static library linked into the iOS app, analogous to `mullvad-jni`). Other org repos show the Rust depth: `gotatun` (userspace WireGuard), `wfp-rs`/`nftnl-rs` (firewall), `windows-service-rs`. Recent retrospectives: OpenVPN support is being removed (2025.14), and a 2026 iOS change (`includeAllNetworks`) trades update-loop risk for guaranteed tunnel coverage. Lesson: a daemon-centric gRPC design gives one authoritative security core across desktop/mobile/CLI, but iOS's extension model may force a separate native implementation anyway.

## 3. Proton — verified Rust cores, uneven rollout

**Proton Pass: verified.** `protonpass/proton-pass-common` is a pure-Rust core shared by all clients. `proton-pass-mobile` is a thin UniFFI binding layer for Android and iOS (iOS consumes it as the Swift package `PassRustCore`); `proton-pass-web` uses wasm-pack for the web. The shared markdown renderer lives in Rust so link classification is platform-neutral.

**Proton Authenticator: verified.** Same architecture, documented in Proton's August 2025 blog "How Rust powers Proton Authenticator": `proton-authenticator` (pure Rust core — cryptography, validation, serialization, TOTP generation, sync engine) + UniFFI mobile bindings + wasm-bindgen/tsify web bindings. The TOTP base is shared with Pass.

**Proton Mail mobile: verified.** The September 2025 iOS/Android relaunch (internal name "Engineering Transformation", detailed in the February 2026 blog "Next-generation Proton Mail mobile apps") is a complete rewrite on a Rust core that holds all business logic; roughly 80% of the codebase is shared, with SwiftUI on iOS and Jetpack Compose on Android on top. Reported crash rates fell (iOS 0.12% → 0.05%). This is the strongest published evidence for the pattern's payoff, and the post is candid about the risk (few precedents, limited in-house Rust experience).

**Proton VPN: verified, in progress.** The August 2026 "Proton protocols" post documents ProTUN: a Rust client engine with `libpvpnclient` (WireGuard crypto forked from Cloudflare's BoringTUN) as a platform-independent core, plus a Rust-rewritten LocalAgent control channel and `muon` for pre-tunnel connections. The public `ProtonVPN/protun` repo contains UniFFI bindings and `vpn-core-android`, confirming Kotlin/Swift integration intent. Early-access builds ship on Windows, Android, iOS, iPadOS, and Linux; this replaces `wireguard-go`.

**Crypto libraries: mixed.** The `ProtonMail/proton-crypto-rs` org repo (created Feb 2025) offers `proton-crypto` and `proton-crypto-account` with two backends: GopenPGP (Go, still the default, via `gopenpgp-sys` bindings) or pure Rust (`proton-rpgp` feature), plus `proton-srp` and `proton-device-verification`. So gopenpgp is not yet fully replaced by Rust.

**Not Rust (verified).** Proton Mail Bridge desktop remains Go (`ProtonMail/proton-bridge` v3.27, Sept 2026). Proton VPN's Windows app is C#, Android Kotlin, Linux GTK Python, iOS/mac Swift (verified via org repos). **Unverified:** whether Proton Drive has a Rust core; whether the Proton Mail desktop app uses any Rust; the exact contents/role of `mullvad-ios`.

**Cross-product synthesis.** All three converge on the same rule: put security-sensitive, protocol-heavy, stateful logic in one Rust core; expose it via generated, typed bindings (UniFFI for iOS/Android, gRPC or JSON-RPC for desktop/daemon boundaries, WASM for web); keep native UI layers thin. Delta Chat shows a full FFI→RPC migration arc; Mullvad shows a daemon-authoritative design; Proton shows the newest, most aggressive adoption, with published before/after reliability numbers.
