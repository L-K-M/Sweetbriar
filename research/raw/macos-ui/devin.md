# Sweetbriar — Building a modern, fast, native macOS email UI in Swift (macOS 26/27 era)

*Research report, 2026-10-11. Platform context: macOS 27 "Golden Gate" shipped 2026-09-14 (Apple silicon only; 27.0.1 is current), macOS 26 "Tahoe" shipped 2025-09-15 and is the last macOS for Intel Macs.*

## 1. TL;DR

- **Hybrid, AppKit-anchored.** The pragmatic architecture for a serious Mac mail app in late 2026 is an AppKit shell (windows, menu bar, three-pane split view, NSTableView message list, NSTextView composer) with SwiftUI used where it is strong (Settings, inspectors, onboarding, menu-bar extra, some toolbar content). This is the same mix Apple itself uses — even AppKit's NSSlider/NSSwitch/NSSegmentedControl are now SwiftUI-rendered under the hood in the Liquid Glass design — and the same mix Mimestream ships ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/272/), [HN](https://news.ycombinator.com/item?id=24422434)).
- **SwiftUI is much better than its reputation, but still wrong for the two hottest spots.** Lists of 100k+ items load ~6x faster and update up to ~16x faster since macOS 26 ([WWDC25](https://developer.apple.com/videos/play/wwdc2025/256/)), the Observation framework now drives AppKit invalidation automatically, and macOS 27 adds a real Document API. Yet the message list (variable heights, outline disclosure, type-select, context-menu-without-selection, drag-out file promises) and the composer are precisely the places where NSTableView and NSTextView remain decisively better.
- **Message list: NSTableView/NSOutlineView.** Proven at mail scale (Apple Mail, MailMate), correct Mac semantics for free. Wrap it in `NSViewControllerRepresentable` if the surrounding shell is SwiftUI.
- **Viewer: one reused, prewarmed WKWebView** — `WKWebpagePreferences.allowsContentJavaScript = false`, a `WKContentRuleList` that blocks all remote loads (the exact technique MailMate documents in its release notes), a `WKURLSchemeHandler` for `cid:`/attachment loads, `color-scheme` CSS for dark mode, public `find(_:configuration:)` and `printOperation(with:)`. Plain-text mail gets a native NSTextView/TextKit 2 fast path.
- **Composer: NSTextView + TextKit 2.** Plain text and Markdown-first authoring (the MailMate model — generate `multipart/alternative` HTML from Markdown), `format=flowed` (RFC 3676) honored on display and offered on send with interop warnings. Writing Tools, spelling/grammar, dictation, data detectors come free.
- **The system-integration layer is now excellent for a mail app specifically.** App Intents ships a dedicated `.mail` schema domain (12 intents, 5 entities — "Archive emails from Nancy", "Reply to an email") wired into Siri AI, Shortcuts, and Spotlight ([docs](https://developer.apple.com/documentation/appintents/making-email-actions-available-to-siri-and-apple-intelligence?changes=_7%2C_7)). Add Core Spotlight indexing + a Quick Look preview extension, UNNotificationActions incl. inline reply, `SetFocusFilterIntent`, and a `.sdef` AppleScript dictionary for the Mailsmith crowd.
- **Distribute direct: Developer ID + notarization + Sparkle.** Mimestream deliberately sells direct (sandboxed and notarized anyway); MailMate never went near the MAS; Airmail and Spark Desktop (an Electron app — the anti-goal) are the MAS examples. Keep the app sandbox-compatible so a reduced MAS build stays possible.
- **Design for Liquid Glass as it exists in macOS 27** — refined for readability after Tahoe's rough launch — and ship an Icon Composer icon. Target macOS 26.0 minimum.
- **Rust core → Swift UI over UniFFI** (or swift-bridge), push model via foreign-callback events into `@Observable` view models — the Ghostty libghostty pattern, but with Rust.

## 2. Findings

### 2.1 AppKit vs SwiftUI in 2026

**OS baseline.** macOS 27 Golden Gate released 2026-09-14 and runs only on Apple silicon ([MacRumors](https://www.macrumors.com/2026/09/14/apple-releases-macos-golden-gate/), [Apple Support](https://support.apple.com/en-us/127257)). macOS 26 Tahoe (2025-09-15) was the last release supporting Intel at all, and only a handful of T2 machines ([Ars Technica](https://arstechnica.com/gadgets/2025/09/macos-26-tahoe-the-ars-technica-review/)). The full Rosetta translation layer is removed in macOS 28 except for legacy games ([macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)). Practically: build `arm64`-only if you target 27, universal only if you want Tahoe-on-Intel users. Note that Sparkle 2.10 now requires a macOS 12 deployment floor, because Xcode 27 dropped deployment targets older than that ([Sparkle releases](https://github.com/sparkle-project/Sparkle/releases)).

**Liquid Glass.** Tahoe introduced the design language; reception on the Mac was rough — Jeff Johnson documented inconsistent corner radii across window configurations, Gruber called the look "goofy", Howard Oakley described Light Mode as a "whiteout", and Steve Troughton-Smith argued the language "wasn't designed Mac-first" (collected by [Cloudship](https://cloudship.co.uk/blog/macos-tahoe-liquid-glass/); also [The Verge](https://www.theverge.com/tech/711358/apple-macos-tahoe-26-public-beta-impressions-macbook-liquid-glass), [Decoding](https://decoding.io/2025/08/first-impressions-of-liquid-glass-in-macos-tahoe/)). macOS 27 is the correction release: Apple advertises "enhanced Liquid Glass, ensuring exceptional readability and greater consistency" ([apple.com/os/macos](https://www.apple.com/os/macos/)); the SDK adds concentricity (`NSViewCornerConfiguration`/`.containerConcentric`), an interactive glass effect on click, refined sidebars/scroll-edge effects/toolbar items, and — tellingly — menu item symbol images are hidden by default again after Tahoe's icon-everything experiment ([macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes); [WWDC26 "Modernize your AppKit app"](https://developer.apple.com/videos/play/wwdc2026/289/)). App icons should now be built with **Icon Composer** (the layered `.icon` format; Icon Composer itself requires macOS 26.4+) — Xcode generates legacy variants automatically ([Apple](https://developer.apple.com/icon-composer/), [docs](https://developer.apple.com/documentation/xcode/creating-your-app-icon-using-icon-composer.md), [jimeh.io](https://jimeh.io/how-to-add-apples-new-liquid-glass-icons-to-applications-67e0ff054de9)).

**SwiftUI's actual maturity.** Two consecutive years of real work:

- *macOS 26 (WWDC25):* lists of 100,000+ items load ~6x faster and update up to ~16x faster on macOS; improved update scheduling reduces dropped frames; nested lazy stacks inside scroll views get lazy behavior; a dedicated **SwiftUI Instrument** in Instruments 26 profiles long view-body and representable updates ([WWDC25 What's new in SwiftUI](https://developer.apple.com/videos/play/wwdc2025/256/), [Optimize SwiftUI performance with Instruments](https://developer.apple.com/videos/play/wwdc2025/306/)). `TextEditor` gained an `AttributedString` binding — first-party rich text editing, though still rough (no font panel hookup; erratic as-you-type spellcheck per [troz.net](https://troz.net/post/2025/swiftui-mac-2025/)). WebKit gained a first-party **SwiftUI `WebView`/`WebPage`** API with a Swift `URLSchemeHandler` protocol and navigation `AsyncSequence`s ([WWDC25 Meet WebKit for SwiftUI](https://developer.apple.com/videos/play/wwdc2025/231/), [troz.net](https://troz.net/post/2025/swiftui-webview/)).
- *macOS 27 (WWDC26):* new **Document API** — `ReadableDocument`, `WritableDocument`, `Document` with async incremental I/O and progress; `FileDocument`/`ReferenceFileDocument` are deprecated. Reorderable containers beyond `List`, `swipeActions` on any scroll view, toolbar APIs (`visibilityPriority`, `toolbarOverflowMenu`, `topBarPinnedTrailing`, `toolbarMinimizeBehavior`), `AsyncImage` HTTP caching, a `@State` macro that stops re-evaluating initial expressions, and `NSGestureRecognizerRepresentable`/`NSHostingMenu`/`NSHostingSceneRepresentation` for deeper AppKit interop ([WWDC26 SwiftUI guide](https://developer.apple.com/wwdc26/guides/swiftui/), [What's new in SwiftUI](https://developer.apple.com/videos/play/wwdc2026/269/), [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)).
- *Observation framework:* since macOS 26, AppKit automatically tracks `@Observable` property reads inside `draw(_:)`, `layout()`, `updateConstraints()`, `viewWillLayout()` etc. and re-invalidates views — no manual `needsDisplay`; it back-deploys to macOS 15 via the `NSObservationTrackingEnabled` Info.plist key ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/272/), [philz.blog](https://philz.blog/built-in-support-for-swift-observable-in-appkit-and-uikit-on-macos-26-and-ios-26-3/), [Apple docs](https://apple-docs.everest.mt/docs/appkit/updating-views-automatically-with-observation-tracking-in-appkit/)). This is a big deal for Sweetbriar: plain AppKit views can now bind to the same `@Observable` view models SwiftUI uses.

**Known pain points that remain.** SwiftUI `Table`'s identifiable-data diffing has historically shown O(n²)-ish behavior on bulk updates (a `.id(UUID())` "nuke identity" workaround exists) ([Stack Overflow](https://stackoverflow.com/questions/74412194/can-you-disable-content-diffing-to-improve-swiftui-table-performance)); a FetchRequest-backed `Table` could hang for seconds on sort changes ([FB13639482](https://openradar.appspot.com/FB13639482)); editable `TextField` cells degrade badly at 10k rows ([Apple Forums](https://developer.apple.com/forums/thread/705109)); `List` was not lazy on macOS for years and still wants fixed row heights for good performance ([Stack Overflow](https://stackoverflow.com/questions/72070486/bad-performance-of-large-swiftui-lists-on-macos)); `.contextMenu` on a row doesn't select the row or expose the "clicked but unselected" semantic Mac users expect ([mjtsai.com](https://mjtsai.com/blog/2024/04/15/nstableview-with-swiftui/), original: [byla.lt](https://byla.lt/posts/in-search-of-smooth-scroll/)); `NSHostingView` inside table cells has sizing bugs and a crashable layout loop with `usesAutomaticRowHeights` ([feedback project](https://github.com/Nemesisprime/Apple-Feedback-Projects/blob/a813d21530fbea80311049ace664b9fbcde6abcf/NSHostingViewSizeInTableView/readme.md), [mactrix PR#85](https://github.com/viktorstrate/mactrix/pull/85)) — and when embedding, you must create the hosting view once and update `rootView`, never per-cell ([interop guidance](https://charleswiltgen.github.io/Axiom/skills/macos/appkit-interop)). Practitioners' verdicts are consistent: "You can't make a good native Mac app in pure SwiftUI" ([Tagavari](https://tagavari.me/blog/swiftui-vs-appkit/)), "SwiftUI is a convenience extension to Cocoa, not a replacement" (Helge Heß via [mjtsai](https://mjtsai.com/blog/2024/04/15/nstableview-with-swiftui/)), and even SwiftUI advocates still flag text editing and huge lists as the AppKit cases ([JuniperPhoton](https://juniperphoton.substack.com/p/swiftui-2025-whats-fixed-whats-not), [troz.net](https://troz.net/post/2025/swiftui-mac-2025/)).

**How Apple mixes them.** Apple's own strategy is explicit: "SwiftUI was designed from the beginning to work great alongside AppKit" — Logic Pro uses SwiftUI for plugins, Xcode's coding assistant is SwiftUI and expanding from sidebar to editor in Xcode 27, and in the Liquid Glass design AppKit controls like `NSSlider`, `NSSwitch` and `NSSegmentedControl` are rendered by SwiftUI under the hood ([WWDC26 "Use SwiftUI with AppKit and UIKit"](https://developer.apple.com/videos/play/wwdc2026/272/)). On macOS 27, `SwiftUI.Slider` and bordered `Menu`/`Picker` no longer use `NSSlider`/`NSPopUpButton` in their implementation — the dependency direction is now bidirectional ([release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)). The last binary-level survey (Sonoma) counted 349 binaries using SwiftUI while AppKit remained the foundation of large productivity apps ([timac.org](https://timac.org/2023/1128-state-of-appkit-catalyst-swift-swiftui-mac/)).

**Verdict for Sweetbriar:** AppKit-owned structure, SwiftUI islands — see §4 for the recommended split. Pure-SwiftUI would be defensible for a simpler app; a mail client's list and editor argue against it. (Ghostty shows pure-SwiftUI *can* anchor a serious Mac app — but its hot view is a custom Metal surface, not a 100k-row list; [ghostty.org](https://ghostty.org/docs/about).)

### 2.2 Message list

Requirements: 100k+ rows, variable heights (1–3 lines + snippets), thread disclosure, multiple selection, drag & drop in/out, type-select, full keyboard navigation.

**NSTableView/NSOutlineView.** The right default:

- Data-source driven with view recycling; rows materialize only when visible. `NSOutlineView` (an `NSTableView` subclass) adds the disclosure hierarchy Apple Mail uses for threads ([class docs](https://leopard-adc.pepas.com/documentation/Cocoa/Reference/ApplicationKit/Classes/NSOutlineView_Class/Reference/Reference.html)).
- Variable heights: `tableView(_:heightOfRow:)` + `noteHeightOfRowsWithIndexesChanged(_:)`; Apple explicitly warns the method must be cheap for large tables — precompute heights in the model, don't measure text per row ([SDK header](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX10.7.sdk/System/Library/Frameworks/AppKit.framework/Versions/C/Headers/NSOutlineView.h)).
- Type-select: built in; customize per-column via `typeSelectStringForTableColumn:item:` and `nextTypeSelectMatchFromItem:toItem:forString:` ([same header](https://github.com/phracker/MacOSX-SDKs/blob/master/MacOSX10.7.sdk/System/Library/Frameworks/AppKit.framework/Versions/C/Headers/NSOutlineView.h)).
- Multi-select, column sorting/reordering, context menus (with correct clicked-row semantics), `pasteboardWriter(forRow:)`/`NSFilePromiseProvider` for dragging messages/attachments out to Finder, and deep keyboard hooks (`keyDown`, custom key bindings — MailMate supports user-remappable keys).
- Discipline that matters: NetNewsWire's coding guidelines forbid Auto Layout and stack views inside table/outline cells because "performance is critical" there ([CodingGuidelines.md](https://github.com/Ranchero-Software/NetNewsWire/blob/main/Technotes/CodingGuidelines.md)). Drawn (non-layer-backed) or simply-constructed cell views keep scrolling at 120fps.
- New in macOS 27: `NSRefreshController` adds pull-to-refresh to `NSScrollView` — a natural fit for "check for new mail" ([release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)).

**SwiftUI `Table`/`List`.** `Table` is lazy and supports `selection` (single or `Set`), `sortOrder`, `TableColumnCustomization` (user column rearrange/hide), and hierarchical rows via `init(_:children:...)` + `OutlineGroup` — disclosure is supported in principle ([Table docs](https://developer.apple.com/documentation/SwiftUI/Table)). But: diffing cost on large identifiable collections (above), coarse row-height control, no public type-select customization, context-menu semantics that don't match Mac convention, disclosure-state persistence you must manage yourself, and — per reports — sort/update hangs at scale. Apple's own guidance for long custom scrolling content is now LazyVStack internals ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/321/)), which buys laziness but not mail-list semantics. Even after the 26/27 wins, `Table` is the riskiest single component for this use case.

**Recommendation:** `NSOutlineView` (threads on) / `NSTableView` (flat mode) inside the shell; keep the row model precomputed (subject, snippet, flags, height class) fed by the Rust core. If the rest of the app is SwiftUI, embed via `NSViewControllerRepresentable` — this is the documented, supported seam ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/272/)).

### 2.3 Message viewer

**WKWebView for HTML mail — the proven recipe.** MailMate's release notes describe exactly the architecture to copy: configure `WKWebView` with a `WKContentRuleList` that blocks **all** external resources (macOS 10.13+ API), rewrite allowed `img src` references to a custom URL scheme served by the app's own `WKURLSchemeHandler`, and gate remote loading behind a per-message/per-sender allow decision ([MailMate r6272 notes](https://updates.mailmate-app.com/release_notes_archive/MailMate_r6272.html); the underlying APIs were introduced in [WWDC17 "Customized Loading in WKWebView"](https://devstreaming-cdn.apple.com/videos/wwdc/2017/220ugyk0ejmva/220/220_customized_loading_in_wkwebview.pdf)). Mimestream ships the same pattern — ~78 tracker URL patterns enforced through WebKit's content blocker, and it passes emailprivacytester.com's suite ([gblock.app analysis](https://www.gblock.app/articles/is-mimestream-tracking-your-email-block-2026), [Mimestream help](https://mimestream.com/help/user-guide/viewing-settings), [release notes](https://mimestream.com/releases)).

Concrete configuration:

- **JavaScript:** `WKPreferences.javaScriptEnabled` is deprecated since macOS 11; use `WKWebpagePreferences.allowsContentJavaScript = false`, applied per-navigation via `WKNavigationDelegate`. Crucially, this blocks *page* JS while your own `evaluateJavaScript`/`callAsyncJavaScript`/user scripts still work — you keep the ability to measure, style, and annotate the DOM ([WWDC20](https://developer.apple.com/videos/play/wwdc2020/10188/), [header](https://github.com/WebKit/webkit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebpagePreferences.h)).
- **Remote content:** compiled `WKContentRuleList` (JSON rules, compiled to bytecode by `WKContentRuleListStore`) blocking `image`/`style-sheet`/`font`/`media`/`fetch` resource types; a second "load remote images" rule list or per-domain whitelist when the user clicks Load. Keep a curated tracker list too. Use `WKWebsiteDataStore.nonPersistent()` so messages can't accumulate cookies/cache across views.
- **cid:/attachments:** register a `WKURLSchemeHandler` (e.g. `sweetbriar-part://`) for MIME parts; the message HTML itself is best loaded from the same custom scheme rather than `loadHTMLString` so that relative/`cid:` resolution is uniform (mixed-content gotchas documented on [Stack Overflow](https://stackoverflow.com/questions/49826107/wkwebview-custom-url-scheme-doesnt-work-with-https-mixed-content-blocked)).
- **Process behavior:** `WKProcessPool` is deprecated and does nothing since macOS 12 — WebKit manages pooling automatically ([header](https://github.com/WebKit/webkit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKProcessPool.h)). What still matters is **prewarming**: the first `WKWebView` spins up a WebContent process (~seconds on a cold launch); create a hidden view and `loadHTMLString("")` at app start, and **reuse one web view per message pane** across messages (replace content, don't recreate) ([SO](https://stackoverflow.com/questions/74301868/wkwebview-ios-slow-on-first-launch), measured ~10x improvement by [WebViewWarmupper](https://github.com/simorgh3196/WebViewWarmupper)).
- **Dark mode:** WebKit does not auto-darken. Ship a stylesheet with `:root { color-scheme: light dark; }` plus `@media (prefers-color-scheme: dark)` overrides; for hostile HTML, an invert/hue-rotate filter (excluding `img`) is the pragmatic fallback; set `isOpaque`/background color to prevent white flash ([useyourloaf](https://useyourloaf.com/blog/supporting-dark-mode-in-wkwebview/), [SO](https://stackoverflow.com/questions/57203909/how-to-use-ios-13-darkmode-for-wkwebview)).
- **Find in page:** public since macOS 11 — `find(_:configuration:completionHandler:)` with `WKFindConfiguration` (case, direction, wrap) ([header](https://github.com/WebKit/WebKit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKWebView.h)). There is no built-in find *bar* on macOS; wire `NSTextFinder` yourself (WebKit's own SwiftUI WebView does exactly this internally — [WebKit PR #38458](https://github.com/WebKit/WebKit/pull/38458)).
- **Printing:** `printOperation(with:)` (macOS 11+) returns an `NSPrintOperation`; known quirks — run it modally against a window, set `operation.view?.frame` (≥100×100) first, and off-screen content can clip ([SO 1](https://stackoverflow.com/questions/69839911/using-nsprintoperation-from-wkwebview), [SO 2](https://stackoverflow.com/questions/33319295/how-does-one-print-all-wkwebview-on-and-offscreen-content-osx-and-ios)). A custom print template (headers + body) laid out as HTML for print is the robust route.
- **Links:** intercept `decidePolicyFor navigationAction` — `targetFrame == nil` (i.e. `target=_blank`) means "open externally"; route all links to the default browser, optionally with a hover-status readout.
- **Modern alternative:** macOS 26 adds SwiftUI `WebView` + `WebPage` (`@Observable`, `URLSchemeHandler` protocol in Swift, navigation `AsyncSequence`s, `callJavaScript`) — a nicer façade over the same engine; usable from AppKit via `webView`/backing access ([WWDC25](https://developer.apple.com/videos/play/wwdc2025/231/), [troz.net](https://troz.net/post/2025/swiftui-webview/)).

**Plain-text fast path.** For `text/plain` messages a native `NSTextView` (TextKit 2) is faster, selectable, searchable via `NSTextFinder`, and prints natively — and gives you quote-level coloring, flowed reflow, and `format=flowed` fidelity for free. Note the counterexample: MailMate renders *everything* through its HTML pipeline, generating HTML for plain text to unify features ([r6272 notes](https://updates.mailmate-app.com/release_notes_archive/MailMate_r6272.html)) — a valid simplification if you'd rather maintain one renderer.

### 2.4 Composer

**Editor substrate.** `NSTextView` on TextKit 2 is the answer: it's been the default stack for all AppKit text controls since Ventura ([WWDC22](https://developer.apple.com/videos/play/wwdc2022/10090/)), is now roughly TextKit-1-fast in benchmarks ([ChimeHQ/TextViewBenchmark](https://github.com/ChimeHQ/TextViewBenchmark)), and gives you continuous spelling/grammar, smart quotes/dashes, substitutions, dictation, data detectors (dates→Calendar links), `NSTextAttachment` inline images, undo, and — since macOS 15 — **Writing Tools** for free, customizable via `writingToolsBehavior`, `isWritingToolsActive`, delegate hooks (`textViewWritingToolsWillBegin/DidEnd`, `writingToolsIgnoredRangesInEnclosingRange:`) and `NSWritingToolsCoordinator` (macOS 15.2+) for custom views ([Apple docs](https://developer.apple.com/documentation/appkit/writing-tools?language=objc), [sosumi](https://sosumi.ai/documentation/appkit/nswritingtoolscoordinator/delegate-swift.protocol)). Early TextKit 2 breakage is documented ([Indie Stack](https://indiestack.com/2022/11/opting-out-of-textkit2-in-nstextview/), and mind the `ensureLayout` cost for jumping to the end of huge documents — [Apple forums](https://developer.apple.com/forums/thread/761364)); if NSTextView disappoints, the open-source [STTextView](https://github.com/krzyzanowskim/STTextView) is a maintained TK2 text component. The new SwiftUI `TextEditor`+`AttributedString` (macOS 26) is not yet composer-grade ([troz.net](https://troz.net/post/2025/swiftui-mac-2025/)).

**Rich text vs plain text vs Markdown.** Three defensible models:

- *MailMate model:* plain-text editing only — "a feature" — with Markdown that generates a real `multipart/alternative` HTML part (themes, code highlighting, math); incoming HTML quoted replies are handled by editing a plain-text rendering and regenerating HTML ([manual](https://manual.mailmate-app.com/)). Power users love it; it also sidesteps every WYSIWYG-HTML edge case.
- *Rich NSTextView:* WYSIWYG attributed editing serialized to an HTML alternative part + plain-text fallback. Matches mainstream expectations; you own HTML generation/quoting.
- *Web editor (ProseMirror/TipTap inside WKWebView):* best HTML fidelity (what Gmail's web compose is), worst native integration — spelling, key equivalents, paste semantics, undo, and attachment DnD all have to be re-bridged. Wrong trade for a "feels native" product.

Recommendation: one NSTextView with two authoring modes — Plain text, and Markdown (live-styled editing, generated HTML alternative). It covers Eudora/Mailsmith purists and produces professional HTML; add WYSIWYG later if demanded.

**format=flowed.** RFC 3676 (obsoleting RFC 2646): soft line breaks marked by a trailing space let receivers reflow; honor it on display, always. On send, support it but know the interop reality: MailMate itself disabled it by default in 2021 because Outlook and Gmail ignore `format=flowed` and recipients then see hard-wrapped text; Thunderbird's quoting support is half-broken ([MailMate list](https://lists.freron.com/mailmate/attachments/20210519/7fb73957/attachment.htm), [cpbotha](https://cpbotha.net/2016/09/27/thunderbird-support-of-rfc-3676-formatflowed-is-half-broken/)). Sane default: emit `format=flowed; delsp=yes` for plain-text-only messages, hard-wrap when generating HTML alternatives, and put it behind a preference — RFC author Pete Resnick's own take on the interop failure is in the same thread ([mail-archive](https://www.mail-archive.com/mailmate%40lists.freron.com/msg18623.html)).

**Compose plumbing.** Attachments: an attachment well plus inline `NSTextAttachment`s; drag out via `NSFilePromiseProvider`; paste/drag images → `multipart/related` + `cid:`. Signatures: per-account, per-identity, plain + HTML variants, inserted above a proper `-- ` signature delimiter (RFC 3676 §4.3). Quoting: `>`-levels with distinct colors in plain text, `blockquote` in HTML; "reply citing selection" should quote just the selection. Drafts are a data-safety feature: autosave continuously to the Rust store (atomic writes), restore on relaunch — this is core behavior, not polish.

### 2.5 macOS integration surface

- **App Intents / Shortcuts / Siri:** the standout find. Apple ships a **`.mail` schema domain** — 12 required-as-a-set intents (`createDraft`, `updateDraft`, `saveDraft`, `openDraft`, `deleteDraft`, `sendDraft` incl. scheduling, `openMessage`, `replyMail`, `forwardMail`, `updateMail`, `archiveMail`, `deleteMail`) and 5 entities (`account`, `draft`, `mailbox`, `message`, `thread`) ([docs](https://developer.apple.com/documentation/appintents/making-email-actions-available-to-siri-and-apple-intelligence?changes=_7%2C_7)). Adopting it makes Sweetbriar's core actions work with Siri AI ("Reply to an email", "Archive emails from Nancy"), Shortcuts, and Spotlight action execution — Spotlight on Mac has run app actions since Tahoe ([Apple newsroom](https://www.apple.com/newsroom/2025/06/macos-tahoe-26-makes-the-mac-more-capable-productive-and-intelligent-than-ever/), [WWDC25](https://developer.apple.com/videos/play/wwdc2025/260/)). macOS 27 adds `RelevantEntities` for context-aware suggestions ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/345/)).
- **AppleScript:** implement Cocoa Scripting via a `.sdef` with **scripting access groups** so sandboxed callers can target you with `com.apple.security.scripting-targets` rather than doomed temporary exceptions ([QA1802](https://developer.apple.com/library/archive/qa/qa1802/_index.html), [entitlements ref](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html)). Mailsmith is the heritage benchmark — fully scriptable *and recordable*, with attachable scripts bound to menu items; its factored architecture routed UI→core through scriptable objects ([MacTech 1998](https://www.mactech.com/1998/05/04/md1-bare-bones-mailsmith/), [TidBITS](https://tidbits.com/2003/07/28/true-confessions-of-a-mailsmith-switcher/), [Macworld](https://www.macworld.com/article/168357/mailsmith2.html)). Also ship the Script menu pattern and a `mailto` scripting command (MailMate has one, incl. sign/encrypt args — [r6272-era notes](https://updates.mailmate-app.com/release_notes_archive/MailMate_r6272.html)).
- **Spotlight:** index messages via `CSSearchableIndex` with stable unique identifiers, expose a Quick Look preview through `preparePreviewOfSearchableItem(identifier:queryString:)` ([QLPreviewingController](https://developer.apple.com/documentation/quicklook/qlpreviewingcontroller)); donate `NSUserActivity` (`isEligibleForSearch`) for recently-viewed mail ([docs](https://developer.apple.com/documentation/Foundation/NSUserActivity?changes=_5_3&language=objc)); App Intents donation feeds semantic search and Siri retrieval ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/345/)).
- **Quick Look:** ship a data-based Quick Look preview extension (`QLPreviewProvider`→`QLPreviewReply`, extension point `com.apple.quicklook.preview`) for `.eml` files; the old `.qlgenerator` plugin API is deprecated ([docs](https://developer.apple.com/documentation/QuickLookUI/QLPreviewProvider), [QLJupyter example](https://github.com/Yike-Ye/QLJupyter)).
- **Share extension:** a `com.apple.share-services` extension ("Send via Sweetbriar") plus `NSSharingService` outbound (NetNewsWire's toolbar uses `NSMenuToolbarItem` for the share menu — [code](https://github.com/Ranchero-Software/NetNewsWire/blob/main/Mac/MainWindow/MainWindowController.swift)).
- **Notifications:** `UNUserNotificationCenter` + `UNNotificationCategory` with `UNNotificationAction`s (Archive/Trash/Mark Read/Flag) and `UNTextInputNotificationAction` for inline reply ([docs](https://apple-docs.everest.mt/docs/usernotifications/untextinputnotificationaction/)). Mimestream ships exactly this plus **Focus filters** — `SetFocusFilterIntent` (`@Parameter`s such as which account/profile may notify) so a Work Focus can silence personal mail ([SetFocusFilterIntent](https://developer.apple.com/documentation/appintents/setfocusfilterintent), [WWDC22](https://developer.apple.com/videos/play/wwdc2022/10121/), [Mimestream releases](https://mimestream.com/releases)).
- **Handoff:** `NSUserActivity` for reading/composing, forward-compatible with an iOS companion ([docs](https://developer.apple.com/documentation/Foundation/continuing-user-activities-with-handoff)).
- **Default mail app:** declare `mailto` (and `.eml`/`message/rfc822`) in `CFBundleURLTypes`; request default status via `NSWorkspace.setDefaultApplication(at:toOpenURLsWithScheme:)` (macOS 12+, shows a user-consent prompt) ([docs](https://apple-docs.everest.mt/docs/appkit/nsworkspace/setdefaultapplication(at:toopenurlswithscheme:completion:)/)).
- **Menu bar extra:** `MenuBarExtra` scene (macOS 13+) for unread counts/quick compose, or `NSStatusItem` if you need a custom view ([docs](https://apple-docs.everest.mt/docs/swiftui/menubarextra/)).
- **Keyboard shortcuts:** menu `keyEquivalent`s for commands, MailMate-style remappable keys for mail actions, and [sindresorhus/KeyboardShortcuts](https://github.com/sindresorhus/KeyboardShortcuts) for global hotkeys — sandbox/MAS-safe, production-proven.
- **Accessibility:** implement `NSAccessibility` on custom cells (label/role/subrole), verify full keyboard navigation (incl. System Settings' Full Keyboard Access), honor Reduce Transparency/Motion, support text sizing — VoiceOver got richer image descriptions in macOS 27 ([apple.com](https://www.apple.com/os/macos/)).
- **Localization:** String Catalogs (`.xcstrings`), locale-aware date/grouping formats, RTL support.
- **Foundation Models:** `SystemLanguageModel` (~3B on-device LLM; requires an Apple-Intelligence-capable Mac — check `availability`) with `LanguageModelSession`, `@Generable`/`@Guide` structured output, tool calling, and — new in the 2026 releases — extensibility to server models (Claude, Gemini, etc.) via the `LanguageModel` protocol, plus `Dynamic Profiles` and a `SpotlightSearchTool` ([framework](https://developer.apple.com/foundation-models-framework/), [docs](https://developer.apple.com/documentation/foundationmodels.md), [WWDC25](https://developer.apple.com/videos/play/wwdc2025/301/)). Mail use cases: thread summaries, suggested replies, NL→search translation, smart-folder classification. Caveat: the on-device context window is small (the 27.0 notes show even a default Spotlight tool schema exceeds it — [release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)); plan fallbacks. Writing Tools already covers basic rewrite in the composer for free.
- **Services menu:** still alive — advertise via `NSServices` in Info.plist and register send/return types so "New email with selection" works from any app ([archive docs](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/SysServices/Articles/properties.html)).

### 2.6 Distribution

**Mac App Store** means mandatory sandbox: mail storage itself is fine inside the container, and importing other clients' archives works via user-picked files + security-scoped bookmarks. The friction: sending Apple events to other apps needs `com.apple.security.scripting-targets`/temporary exceptions (which Apple is phasing out — [QA1888](https://developer.apple.com/library/archive/qa/qa1888/_index.html); real-world failures documented on [SO](https://stackoverflow.com/questions/71543618/macos-app-no-longer-can-compose-e-mail-via-applescript-if-sandboxed)); third-party plug-in loading, helper tools, and background agents are constrained (login items via `SMAppService`; daemons effectively out); every bug fix waits on review; and Apple takes 15–30%.

**Developer ID + notarization** is the indie standard: hardened runtime, `notarytool` staple, and [Sparkle](https://sparkle-project.github.io/documentation/) for signed EdDSA delta updates — Sparkle 2.10 ("Golden Gate Bump", Sept 2026) requires macOS 12+ and works in sandboxed apps via its XPC services ([releases](https://github.com/sparkle-project/Sparkle/releases), [sandboxing guide](https://sparkle-project.org/documentation/sandboxing/)). Billing via Paddle/FastSpring or your own subscription server.

**What mail apps actually do:** **Mimestream** — direct only, explicitly: "we have decided to initially focus on direct sales only" (better pricing control, team licenses), while staying sandboxed, notarized, Developer-ID-signed; $49.99/yr subscription ([pricing](https://mimestream.com/pricing/), [TidBITS](https://tidbits.com/watchlist/mimestream-1-10/)). **MailMate** — direct only (FastSpring), hardened+notarized since early, unusual patronage-style $10/quarter subscription with Paid/Free modes ([pricing](https://freron.com/pricing/), [model](https://freron.com/2024/new-license-key-system/)). **Airmail** — MAS exclusive, subscription ([FAQ](https://help.airmailapp.com/en-us/article/faq-1j9ztiz/)). **Spark Desktop** — MAS + Homebrew + Setapp; it's Electron (v36.9.5, ~732 MB) — chosen to ship Mac+Windows cheaply, and the canonical example of what Sweetbriar is *not* ([desktopinsights](https://desktopinsights.com/apps/spark-desktop), [Spark blog](https://sparkmailapp.com/blog/all-new-spark-desktop-vs-spark-2)). **NetNewsWire** — direct + Sparkle on Mac ([netnewswire.com](https://netnewswire.com/), [releases](https://github.com/Ranchero-Software/NetNewsWire/releases)).

**Recommendation:** Developer ID + notarization + Sparkle, sandbox-enabled anyway, own billing. Keep MAS viability as a compile-time option for a later reduced SKU (Mimestream's stated plan), not as a launch channel.

### 2.7 Exemplary native Mac apps (and what to steal)

- **MailMate** — one developer; plain-text/Markdown composer; the documented WKWebView+content-rules+scheme-handler viewer; user-remappable key bindings; bundle system for integrations; direct, notarized, sustainable pricing ([manual](https://manual.mailmate-app.com/), [freron.com](https://freron.com/motivation/)). Lesson: depth + honesty beats breadth; ship the WKWebView recipe wholesale.
- **Mimestream** — ex-Apple-Mail lead Neil Jhaveri; Swift, AppKit+SwiftUI; Gmail API; tracker prevention via WebKit content rules; private push; Focus filters; fast Tahoe/26 adoption ([HN](https://news.ycombinator.com/item?id=24422434), [site](https://mimestream.com/)). Lesson: closest existing model of "feels like Mail.app, but better, and paid for."
- **NetNewsWire** — open source and readable: AppKit on Mac, UIKit on iOS, shared non-UI frameworks (`Articles`, `Account`, `RSCore`); no Auto Layout/stack views in table cells; template+CSS HTML rendering in WKWebView ([repo](https://github.com/Ranchero-Software/NetNewsWire), [Brent Simmons on layering](https://inessential.com/2020/04/29/netnewswire_code_layout.html), [coding guidelines](https://github.com/Ranchero-Software/NetNewsWire/blob/main/Technotes/CodingGuidelines.md)). Lesson: your reference codebase for three-pane Mac apps.
- **Tower** — proves Sweetbriar's exact thesis: shared logic, *native UI per platform* (Obj-C/Swift AppKit on Mac, C#/WPF on Windows), deliberately rejecting cross-platform UI toolkits ([Tower blog](https://www.git-tower.com/blog/developing-for-the-desktop-tower/)).
- **Ghostty** — the architectural precedent for Rust core + native shells: `libghostty` C-ABI core; Swift + AppKit/SwiftUI on macOS; GTK4 on Linux ([about](https://ghostty.org/docs/about), [repo](https://github.com/ghostty-org/ghostty)). Sweetbriar = the same shape with Rust.
- **Nova** — AppKit, premium native pricing that works ($99 + $49/yr update plan) ([bundl.run](https://bundl.run/apps/nova), [nova.app](https://nova.app)); **Things** — fit-and-finish benchmark, unified Mac/iOS list rendering, App Intents Shortcuts, keyboard-layout-aware shortcuts ([Apple profile](https://developer.apple.com/articles/things/), [3.15 notes](https://culturedcode.com/things/blog/2021/10/all-things-speed/), [release notes](https://culturedcode.com/things/support/articles/1100684/)).
- **Ivory (Tapbots)** — well-made *Catalyst* app, and yet: Services menu items don't work, some views don't take standard scroll keys, smart punctuation lags ([Daring Fireball](https://daringfireball.net/linked/2023/05/26/ivory-for-mac), [mjtsai](https://mjtsai.com/blog/2023/05/24/ivory-for-mac/)). Lesson: the last 10% of "feels native" is exactly what Catalyst doesn't give you — and mail users will notice.
- **Mailsmith/BBEdit lineage** — deep scriptability, recordability, attachability as a design principle ([TidBITS](https://tidbits.com/2003/07/28/true-confessions-of-a-mailsmith-switcher/)); **Spark** — Electron: the counterexample (above).

### 2.8 Recommended stack & structure

**Technology stack:** Swift 6, Xcode 27, deployment target **macOS 26.0** (you inherit the SwiftUI perf wins, `WebPage`, AppKit Observation tracking, and the mature Liquid Glass refinements; 27-only APIs adopted opportunistically via `@available`). Universal binary only if Tahoe-on-Intel matters — it barely does; `arm64`-first is fine.

**Module layout (mirroring NetNewsWire's layering):**

- `SweetbriarCore` (Rust staticlib; sync, storage, MIME, search, accounts) → exposed via **UniFFI**-generated Swift bindings (production-grade, [docs](https://mozilla.github.io/uniffi-rs/0.28/swift/overview.html); `cargo-swift` for packaging) — swift-bridge or cxx-style shims are the alternatives.
- `SweetbriarKit` (Swift): `@Observable` view models, FFI boundary, event streams from Rust via UniFFI foreign callbacks pushed into Observation (the state-replication pattern described by [Tantalus](https://www.tantaluspath.com/tech/rust_to_swift_state_syncing/)). Both AppKit and SwiftUI views read the same models — enabled by macOS 26's automatic tracking (§2.1).
- `SweetbriarMac` (AppKit + SwiftUI): the app itself.

**The AppKit/SwiftUI split (recommended):**

| Surface | Choice | Why |
|---|---|---|
| App/windows/menus/toolbar, 3-pane `NSSplitViewController` | AppKit | Precise control, unified-titlebar/sidebar idioms, `NSToolbar` customization |
| Message list | `NSOutlineView`/`NSTableView` | §2.2 |
| HTML viewer | `WKWebView` (reused, prewarmed) | §2.3 |
| Plain-text viewer + composer | `NSTextView`/TextKit 2 | §2.3–2.4 |
| Settings window | SwiftUI `Settings` scene (reachable from AppKit via `NSHostingSceneRepresentation`, new in 27) | Forms are SwiftUI's sweet spot |
| Inspector / account setup / onboarding / about | SwiftUI | Fast to build, low-risk |
| Menu-bar extra | `MenuBarExtra` | One line of integration |
| Row content inside table cells | AppKit views (drawn or simple), no auto layout | NNW's perf rule; optionally isolated SwiftUI via reused `NSHostingView` where richness wins (badges, avatars) — mind the sizing gotchas (§2.1) |

This is also exactly how you'd absorb SwiftUI improvements over time: each surface can migrate when the framework earns it.

## 4. Recommendations for Sweetbriar

1. **Ship AppKit-anchored hybrid** (structure per §2.8). SwiftUI for Settings, inspector, onboarding, menu-bar extra, and progressively more as it earns its place. *Counter-argument (steal-manned):* going pure SwiftUI now aligns you with Apple's investment — WWDC25/26 are the two biggest SwiftUI years ever, controls are SwiftUI-rendered under the hood anyway, and every AppKit surface you build is future rework. *Why it loses:* the two components that define a mail client's feel — the 100k-row list and the composer — are precisely where SwiftUI's remaining defects (diffing cost, context menus, editable cells, rich text maturity) concentrate, and the interop architecture makes incremental adoption cheap later.
2. **NSTableView/NSOutlineView for the list**, precomputed row model, no auto layout in cells, `NSFilePromiseProvider` for drag-out, custom type-select strings, `NSRefreshController` for pull-to-refresh.
3. **One prewarmed, reused WKWebView** for HTML mail: JS off via `allowsContentJavaScript`, `WKContentRuleList` blocking all remote loads, tracker list, `WKURLSchemeHandler` for `cid:`/parts, ephemeral data store, `color-scheme` CSS, public find API, modal `printOperation`. Plain text → `NSTextView`/TK2.
4. **NSTextView composer, MailMate-style**: plain text + Markdown→`multipart/alternative` generation; `format=flowed` honored on read, optional on send; Writing Tools/spelling/detectors free; continuous draft autosave into the Rust store.
5. **Integration breadth is a differentiator — invest**: `.mail` App Schema intents (Siri AI/Shortcuts/Spotlight actions), `.sdef` + access groups (Mailsmith-grade scripting, incl. a Script menu), Core Spotlight + Quick Look preview extension for `.eml`, share extension, notification actions incl. inline `UNTextInputNotificationAction` reply, `SetFocusFilterIntent`, `NSUserActivity` Handoff, `mailto` default via `NSWorkspace`, `MenuBarExtra`, remappable keys, String Catalogs, `NSAccessibility` pass, Foundation Models features (summarize/suggest/classify) gated on `SystemLanguageModel.availability`.
6. **Distribute direct**: Developer ID + hardened runtime + notarization, Sparkle 2.10 with EdDSA appcasts, sandbox enabled (keeps MAS optionality and is good hygiene), subscription or pay-once via your own billing. Icon via Icon Composer.
7. **Rust core ↔ Swift via UniFFI**, push-model events into `@Observable`s; keep FFI calls batched (per-mailbox/mutation grain, never per-pixel).

**Strongest counter-argument overall:** the hybrid's real cost is perpetual two-framework expertise and occasional impedance-mismatch bugs (responder chain, focus, menu validation across the boundary). The all-AppKit alternative sacrifices Apple's clearest direction-of-travel and makes adopting each year's SwiftUI improvements harder. The hybrid is still right — but staff the team accordingly.

## 5. Risks and open questions

- **SwiftUI goalposts move yearly.** List/Table may become unambiguously right within 1–2 OS releases; re-evaluate the split each fall. The Document API arriving in 27 hints SwiftUI wants document/productivity apps too.
- **WKWebView ceilings:** no public find-bar UI, printing quirks, no Mail.app-private conveniences; acceptable, but measure real HTML-mail corpuses for render fidelity (Outlook-style VML, dark-mode emails that pin white backgrounds).
- **FFI chat-then-jank:** per-row synchronous Rust calls will hitch scrolling; design push/streaming APIs and prefetch batches (open question: exact event-schema granularity).
- **App Schema all-or-none:** the `.mail` domain requires implementing the full intent set at build time — meaningful surface area; plan it as a feature, not a checkbox.
- **Sandbox-first discipline** (or MAS dies on the vine later): scripting-target access groups in the `.sdef`, security-scoped bookmarks for import, no private APIs (e.g., no `_registerURLSchemeAsSecure` tricks).
- **Foundation Models limits:** small on-device context window; availability varies by device/region/settings — every AI feature needs a non-AI fallback. Server-model extensibility in 27 is promising for heavier summarization.
- **Data safety** (project goal): autosaved drafts, atomic writes, never-destructive sync — UI must checkpoint composer state continuously; belongs in the Rust core contract, not the view layer.
- **TCC tightening:** macOS 27 blocks direct reads of the TCC database — don't build anything that inspects other apps' permissions ([release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)).
- **Open questions:** (a) compose WYSIWYG later or never? (b) index full bodies into Spotlight or headers+snippets only (volume vs. duplicating your own search)? (c) ship a MailKit extension for Apple-Mail interop/migration? (d) `NSSplitViewController` vs `NavigationSplitView` for the 3-pane frame — prototype both; (e) does SwiftUI `Table` on 27 survive a real 100k-message mailbox in Instruments? cheap to spike, worth doing once before locking the list decision.
