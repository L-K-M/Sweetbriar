# Embedded database engines for Sweetbriar

Saved as this file, with benchmark scripts, raw results and consulted sources alongside it.

**Research and measurement date: 2026-10-11.** Current-status statements below refer to that date unless a release or deprecation date is given explicitly. Recommendations and proposed acceptance thresholds are judgments; benchmark numbers are observations. The macOS target is macOS 27 Golden Gate, released 2026-09-14, with Apple silicon support, as the assignment states and Apple's current compatibility page confirms. The measurements here were made on Linux, not on that target. [Apple compatibility information](https://support.apple.com/en-ca/127255).

## 1. TL;DR

- **Choose bundled SQLite for authoritative state.** Its ordered covering B-tree access and live cross-process readers fit the specified workload. In the 500,000-message run, a deep 50-row page took 0.026 ms median in SQLite versus 7.69 ms in DuckDB. This recommendation follows requirements and measurements, not an assumption that SQLite should win. [Raw SQLite results](codex-artifacts/artifacts/run1/sqlite.json), [raw DuckDB results](codex-artifacts/artifacts/run1/duckdb.json).
- **DuckDB wins useful parts of this comparison.** At 500,000 rows, initial import was 2.50 seconds versus SQLite's 5.00 seconds, before secondary-index construction; an aggregate took 6.04 ms versus 137.80 ms. Its compression and analytical execution are valuable. [Raw results](codex-artifacts/artifacts/run1/duckdb.json), [SQLite comparison](codex-artifacts/artifacts/run1/sqlite.json).
- **DuckDB is an ACID database, not merely a disposable analytics cache.** It syncs committed WAL records. Version 1.5.6 source contains conditional macOS `F_FULLFSYNC` support, followed by ordinary sync fallback; the exact macOS shipping build still needs verification. [WAL implementation](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/storage/write_ahead_log.cpp), [filesystem implementation](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/common/local_file_system.cpp).
- **DuckDB's decisive mismatches are access paths and process sharing.** Its composite ART index does not provide SQLite's ordered covering scan, and a separate read-only process cannot open its live file while a writer owns it. Our process probe reproduced the lock failure. [Indexing documentation](https://duckdb.org/docs/stable/guides/performance/indexing), [concurrency documentation](https://duckdb.org/docs/stable/connect/concurrency), [probe results](codex-artifacts/artifacts/process_probe.json).
- **Use FTS5 initially, with a replaceable search interface.** DuckDB FTS offers BM25 but requires index recreation after underlying data changes. It failed the freshness probe, as documented; FTS5 passed with an explicit incremental insert. [DuckDB FTS](https://duckdb.org/docs/stable/core_extensions/full_text_search), [FTS5](https://www.sqlite.org/fts5.html), [measurements](codex-artifacts/artifacts/run1/duckdb.json).
- **SQLite's quirks are substantially controllable.** Use STRICT tables, domain checks, foreign keys, disabled double-quoted string literals, explicit WAL and FULL synchronization, and verified bundled build options. Do not mistake STRICT for exact-type or semantic validation. [STRICT tables](https://www.sqlite.org/stricttables.html), [connection configuration](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html).
- **Other contenders deserve different levels of attention.** LMDB is a credible transactional KV alternative; redb is a credible Rust-native alternative. Turso Database is promising but still beta, with experimental process coordination. KV engines transfer index, constraint, query and migration responsibilities to Sweetbriar. [LMDB API](https://www.lmdb.tech/doc/group__mdb.html), [redb](https://docs.rs/redb/4.3.0/redb/struct.ReadOnlyDatabase.html), [Turso source](https://raw.githubusercontent.com/tursodatabase/turso/main/README.md).
- **Every tested engine retained every witnessed commit through the recovery trials.** Five engines passed 30 kills each; SQLite and DuckDB additionally passed 30 each on copies of the large stores. In total: **210 relevant kills, 12,600 acknowledged new rows, no partial transactions**. Existing large-store data fingerprints also remained unchanged. This is process-death evidence, not power-loss proof. [Crash harness](codex-artifacts/crash_test.py), [large-store trials](codex-artifacts/large_crash_test.py), [SQLite results](codex-artifacts/artifacts/crash-large/sqlite.json), [DuckDB results](codex-artifacts/artifacts/crash-large/duckdb.json), [RocksDB native-write trials](codex-artifacts/artifacts/crash-native/rocksdb.json).
- **Do not add a DuckDB hybrid yet.** Keep the option for an analytics feature that demonstrably needs it, preferably consuming a consistent snapshot or Parquet export. Preserve one authoritative transaction boundary. [SQLite attachment extension](https://duckdb.org/docs/stable/core_extensions/sqlite).

## 2. Findings

### 2.1 DuckDB in depth

#### Current release, architecture and OLTP fit

DuckDB **1.5.6**, released **2026-09-28**, is the current release shown by its installation page; 1.4.5 is separately listed as LTS and 2.0 is preview. The installed Python wheel reports 1.5.6. Claims from preview documentation below are distinguished from release behavior. [Release announcement](https://www.duckdb.org/2026/09/28/announcing-duckdb-156), [installation page](https://duckdb.org/docs/installation?version=stable).

DuckDB stores columns in compressed row groups and executes operations on vectors; the standard vector size is 2,048 values. Its MVCC and optimistic concurrency control let readers retain a transaction snapshot while other threads modify data. Its update representation is designed to handle changes across many rows and a few columns efficiently. Those are real advantages for import, statistics and bulk transformations. They do not imply low latency for hundreds of separate tiny transactions. [Storage internals](https://duckdb.org/docs/stable/internals/storage), [vectors](https://duckdb.org/docs/stable/internals/vector), [transaction design](https://duckdb.org/2024/10/30/analytics-optimized-concurrent-transactions).

For this workload, distinguish three operations:

| Operation | DuckDB mechanism and implication |
|---|---|
| Lookup by message id | A primary-key ART index can accelerate selective equality probes. This is supported functionality, not an inevitable full scan. |
| Mailbox page ordered by date and id | Current ART scan eligibility is limited to single columns without expressions; ART does not accelerate sorting. Creating a composite index does not supply an ordered covering B-tree scan. |
| Update flags | Unindexed-column bulk updates suit column-oriented MVCC. Updates to indexed columns can become delete-plus-insert operations, increasing maintenance work and exposing documented index/constraint limitations. |

The first two facts come from the current [index performance guide](https://duckdb.org/docs/stable/guides/performance/indexing); the update behavior is documented in [SQL indexes](https://duckdb.org/docs/stable/sql/indexes). The measured mailbox plan contained sequential scans, a Top-N operator and a semi-join. SQLite's plan named its covering index. Both plans are saved with the results. [DuckDB plan](codex-artifacts/artifacts/run1/duckdb.json), [SQLite plan](codex-artifacts/artifacts/run1/sqlite.json).

**Interpretation:** an ART is not intrinsically unsuitable for OLTP. DuckDB's current optimizer and storage implementation are the relevant limitation. Ordering the physical data can improve zonemap pruning, but an email client continually receives backfilled dates and mailbox membership changes. Depending on periodically reorganized physical order is a different design from maintaining the required ordered index. [Zonemap guidance](https://duckdb.org/docs/stable/guides/performance/indexing).

The Python-driver caveat is substantial. The baseline inserted 250 rows into each affected table using bound multi-row `VALUES`. DuckDB took 351/415 ms median/p95 per transaction. A separate run using registered Arrow tables and `INSERT SELECT`, with Arrow conversion prepared outside the timer, reduced this to **33.1/55.2 ms**. Its Rust API also exposes an Appender. Consequently, the baseline is evidence about that tested path, not DuckDB's best possible Rust ingestion throughput. [Arrow experiment](codex-artifacts/artifacts/duckdb_arrow_batches.json), [Rust Appender API](https://docs.rs/duckdb/1.10506.0/duckdb/struct.Appender.html).

#### WAL, checkpointing and durability

DuckDB writes transaction changes to a WAL and replays committed records when reopening. Checkpointing incorporates changes into the main database and retires WAL state. Automatic checkpoints normally occur at a **16 MiB** WAL threshold and on orderly shutdown; explicit `CHECKPOINT` is available. Modern checkpoint behavior must be checked in current documentation: older descriptions of `FORCE CHECKPOINT` aborting transactions predate its changed behavior. [Transaction design](https://duckdb.org/2024/10/30/analytics-optimized-concurrent-transactions), [current checkpoint statement](https://duckdb.org/docs/stable/sql/statements/checkpoint), [configuration](https://duckdb.org/docs/stable/configuration/overview).

The strongest current durability evidence is pinned source. In 1.5.6, `WriteAheadLog::Flush()` writes a flush record and calls `writer->Sync()`. The Unix filesystem implementation attempts `fcntl(fd,F_FULLFSYNC)` under `HAVE_FULLFSYNC`, otherwise or after failure uses `fdatasync` under `HAVE_FDATASYNC`, or `fsync`. An `EIO` during syncing becomes a fatal error. **The conditional support is verified; whether the particular macOS binary Sweetbriar would ship enables that branch is unverified.** This Linux experiment cannot resolve it. [WAL source](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/storage/write_ahead_log.cpp), [filesystem source](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/src/common/local_file_system.cpp).

The installed 1.5.6 settings do **not** expose `fsync_mode`. Preview documentation describes `STANDARD`, `FULL` and `NONE`, including macOS full syncing. Treating that as a configurable 1.5.6 feature would be wrong. [Recorded environment](codex-artifacts/artifacts/environment.json), [preview I/O documentation](https://www.duckdb.org/docs/preview/data/io).

On Apple platforms, flushing to a device cache, enforcing write ordering and flushing to permanent media are distinct promises. Apple describes `F_BARRIERFSYNC` as an ordering barrier and `F_FULLFSYNC` as a device-cache flush. On Linux, syncing a file does not necessarily sync the directory entry naming it. These distinctions also apply to Sweetbriar's external message files. [Apple storage presentation](https://developer.apple.com/videos/play/wwdc2019/419/), [Linux fsync documentation](https://man7.org/linux/man-pages/man2/fsync.2.html).

Crash-recovery maturity is meaningful, but not absolute. The 1.5.6 release includes failed-checkpoint-marker recovery and WAL recovery handle fixes. Public reports include silent secondary ART wrong results with independently opened engines in one process, filed **2026-07-13**, and interleaved schema/index WAL replay crashes, filed **2026-09-19**. Both issue records were open when consulted. An open issue does not establish that the newest release still reproduces it; some fixes are described as present on development/release branches. We did not reproduce these specific cases. [1.5.6 fixes](https://www.duckdb.org/2026/09/28/announcing-duckdb-156), [ART report #23788](https://github.com/duckdb/duckdb/issues/23788), [WAL replay report #25928](https://github.com/duckdb/duckdb/issues/25928).

**Judgment:** DuckDB has credible transactional engineering. For irreplaceable drafts and settings, it still needs a release-specific qualification campaign covering migrations, indexes and interrupted checkpoints. The same demand applies to SQLite and every alternative; SQLite itself recently fixed a long-lived corruption bug.

#### Storage format and migration

DuckDB's backwards-compatibility effort began with **0.10**, not 1.0. Its documentation promises newer versions can read older formats from that compatibility era, while forwards compatibility is best effort. Versions **1.0–1.5 default to storage version 64**, corresponding to the 1.0-compatible format. Since 1.2, `STORAGE_VERSION` can explicitly select newer formats; selecting `latest` can prevent older engines opening the file. [Storage version policy](https://duckdb.org/docs/stable/internals/storage).

For Sweetbriar, pin the engine and storage version separately. Preserve the previous file before migration, test opening with supported old/new application builds, and retain an export path. DuckDB documents `EXPORT DATABASE` with the old engine and `IMPORT DATABASE` with the new engine as a migration escape route. That is useful, although export/import costs extra storage and does not remove the need to migrate Sweetbriar's own schema and invariants. [Storage migration instructions](https://duckdb.org/docs/stable/internals/storage).

#### Concurrency and desktop defaults

The direct-file concurrency contract is one read/write process, or multiple read-only processes with no writer. Threads within the owning process can use independent connections and MVCC; concurrent writers can conflict on changed rows. Current documentation also describes Quack remote access as a separate, beta client-server route. A protocol server changes the architecture; it does not make independent extensions direct-file readers. [Concurrency](https://duckdb.org/docs/stable/connect/concurrency).

For Rust, `Connection` is `Send` but not `Sync`; the documented pattern is one connection per thread, using `try_clone()` to connect to the same existing database instance. That also avoids casually opening unrelated engine instances on the same file. [Rust connection guidance](https://duckdb.org/docs/current/clients/rust/connecting).

Relevant defaults, verified on 2026-10-11:

| Default | Consequence and proposed mitigation |
|---|---|
| `memory_limit`: 80% of RAM | Too broad a desktop policy. Set a deliberate budget; the setting is not a universal process-RSS cap, and ART buffers are not currently freely evictable. |
| Threads: detected CPU cores | This host defaulted to 16. Limit background analytical work so the UI and sync retain resources. |
| Known-extension autoinstall/autoload: enabled | Queries can initiate extension installation and loading. Disable both; ship only explicitly selected extensions. |
| External access: enabled | SQL can interact with files and external resources. Restrict it and lock configuration after initialization if exposing any query surface. |
| Temporary/extension paths | Configure writable application-container paths instead of assuming unrestricted home-directory or temporary-directory access. |

Defaults are documented in [configuration](https://duckdb.org/docs/stable/configuration/overview); security controls and extension privileges in [securing DuckDB](https://duckdb.org/docs/stable/operations_manual/securing_duckdb/overview); resource caveats in [indexing](https://duckdb.org/docs/stable/guides/performance/indexing) and [memory limits](https://duckdb.org/docs/stable/guides/troubleshooting/oom_errors).

Extensions execute with the application's privileges. Distribution normally uses signed extensions; signatures reduce download tampering risk but do not make extension code harmless or satisfy macOS signing/sandbox requirements automatically. Our HTTPS extension download failed with HTTP 403; plain HTTP succeeded and the normal DuckDB loader accepted the signed FTS extension. Its bytes were saved locally. The job never enabled unsigned loading. [Extension distribution](https://duckdb.org/docs/stable/extensions/extension_distribution), saved extension (binary, not committed).

#### FTS, Rust bindings, size, licence and a hybrid

DuckDB FTS creates auxiliary tables and a `match_bm25` macro. It supports stemming, stopwords, field selection and conjunctive matching. **It does not incrementally track inserts, updates or deletes.** Recreating the index is the documented refresh mechanism. This is a serious mismatch for continuously arriving mail and changing drafts/notes, independent of query speed. [FTS extension](https://duckdb.org/docs/stable/core_extensions/full_text_search).

The Rust `duckdb` crate is **1.10506.0**, published **2026-09-30**, encoding DuckDB 1.5.6 in the second semver component. Current DuckDB documentation lists Rust as a core-team primary client; older claims that it is merely a third-party binding are stale. `bundled` builds vendored C++ through `libduckdb-sys` and the `cc` crate; it is a Rust API over C/C++, not a Rust-native engine. Pinning with a tilde requirement avoids silently moving to another embedded DuckDB version. Both engine and bindings use MIT licensing. [Crate metadata](https://crates.io/api/v1/crates/duckdb), [client support tiers](https://duckdb.org/docs/stable/clients/overview), [bundled build documentation](https://docs.rs/crate/libduckdb-sys/1.10506.0), [engine licence](https://raw.githubusercontent.com/duckdb/duckdb/v1.5.6/LICENSE).

As a packaging observation, the installed Linux Python `_duckdb` library is **57.58 MiB**, versus **3.04 MiB** for APSW's main native library. Neither number predicts a stripped Apple-silicon Rust application: selected extensions, linking and Python binding code differ. The exact macOS binary size is **unverified**, because no native build was available. [Measured library sizes](codex-artifacts/artifacts/environment.json).

A hybrid is technically real: DuckDB's SQLite extension attaches SQLite files, reads their tables directly, and also supports writes. Thus it could provide statistics or ad-hoc SQL over an authoritative SQLite store, while DuckDB handles Parquet-based exports efficiently. **Recommendation:** if adopted, make its access explicitly read-only and use a consistent snapshot for expensive work. Live scanning adds another SQLite reader that can retain WAL history, consumes resources and introduces another bundled SQLite/extension version to qualify. Cross-engine writes would complicate the atomic intent-journal guarantee without helping this single-writer design. [SQLite extension](https://duckdb.org/docs/stable/core_extensions/sqlite), [SQLite WAL reader/checkpoint behavior](https://sqlite.org/wal.html).

### 2.2 SQLite's odd defaults and their limits

SQLite's compatibility choices are real. They should be explicit inputs to configuration, rather than dismissed as harmless or accepted accidentally.

| Quirk | Mitigation | Residual risk |
|---|---|---|
| Flexible typing/type affinity | Use STRICT for authoritative tables and bind Rust types consistently. Add checks for flag ranges, lengths and domain values. [STRICT](https://www.sqlite.org/stricttables.html). | Lossless coercion still occurs; `ANY` deliberately accepts heterogeneous values. A valid INTEGER can still be an invalid sync cursor or timestamp. |
| Foreign keys off in ordinary upstream builds | Enable and verify `PRAGMA foreign_keys=ON` on **every** connection, before transactions; optionally compile the default on. [Foreign keys](https://www.sqlite.org/foreignkeys.html). | The setting is connection-specific; changing it inside a transaction is ineffective. All account/backend paths must obey it. |
| Double-quoted string literals accepted | Compile `SQLITE_DQS=0`; also disable `SQLITE_DBCONFIG_DQS_DDL` and `_DML` in connection initialization. [Connection configuration](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html). | Legacy migrations may depend on the misfeature. Test them with the strict settings. |
| DELETE rollback journaling by default | Establish and verify `journal_mode=WAL` for the file. [Journal modes](https://www.sqlite.org/pragma.html#pragma_journal_mode). | Long reader snapshots retain WAL pages; checkpoints and space reclamation require scheduling. WAL is unsuitable for ordinary network filesystems. |
| Synchronization depends on mode/build | Set and read back `synchronous=FULL` on each writer; do not infer it from WAL. Upstream defaults are normally FULL, although wrappers/builds can change them. [Synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous). | WAL NORMAL preserves consistency but can lose recent commits after power/OS failure. FULL costs real flush latency. |
| NULLs historically accepted in many primary keys | STRICT or WITHOUT ROWID, with explicit required keys. [STRICT primary keys](https://www.sqlite.org/stricttables.html). | `INTEGER PRIMARY KEY` still turns inserted NULL into an allocated rowid, even in STRICT. Enforce explicit-id policy in the Rust API. |
| LIKE is case-insensitive for ASCII, not general Unicode | Use explicit normalized fields/collations for address/name matching and a chosen tokenizer for full text. [LIKE semantics](https://www.sqlite.org/lang_expr.html#like). | Normalization, accents, locales and email address semantics need product decisions. Avoid deprecated `case_sensitive_like` as a Unicode solution. |
| Limited ALTER TABLE | Use transactional create/copy/validate/swap migrations for unsupported changes. Rename/add/drop are supported; **3.53.0, released 2026-04-09, also added setting/dropping NOT NULL**. [ALTER TABLE](https://www.sqlite.org/lang_altertable.html). | Large rebuilds need time and free space; an application supporting 3.51.3 cannot use later syntax unconditionally. |
| Apple system-library sync behavior | Bundle audited upstream SQLite and test its actual VFS calls on macOS. Upstream `fullfsync` requests `F_FULLFSYNC`. [fullfsync](https://www.sqlite.org/pragma.html#pragma_fullfsync). | Apple's historical substitution with `F_BARRIERFSYNC` is discussed in the SQLite forum; the exact macOS 27 system binary mapping is **unverified here**. A pragma name/value alone does not establish the flush primitive. [System-library discussion](https://sqlite.org/forum/info/a712b73d9e71952223cb7a2447932a3615d2bc50e52f159f2b6f887b2522c47b). |

For the last row, Apple's own explanation confirms why the distinction matters: a barrier orders I/O; a full sync flushes the device cache to permanent media. Historical reports should not be promoted into a verified claim about the currently shipped macOS 27 library. Bundling provides control of the source and version, but the actual compiled VFS and unsupported-filesystem fallback still need checking on the target. [Apple storage presentation](https://developer.apple.com/videos/play/wwdc2019/419/).

The minimum **3.51.3** is justified. Released **2026-03-13**, it fixes the WAL-reset corruption race affecting older WAL versions. The documented trigger involves multiple connections trying to write/checkpoint at the same time. Having only one designated application writer does not automatically exclude another checkpointing connection. Our benchmark used **3.53.4**, released **2026-07-24**. [WAL-reset documentation](https://sqlite.org/wal.html), [3.51.3 release](https://www.sqlite.org/releaselog/3_51_3.html), [3.53.4 release](https://www.sqlite.org/releaselog/3_53_4.html).

#### Bundling through rusqlite

The inspected release build script for **rusqlite 0.40.2** already defines `SQLITE_DEFAULT_FOREIGN_KEYS=1` and enables FTS5. It accepts additional defines/undefines through the **`LIBSQLITE3_FLAGS` environment variable**; these are build inputs, not arbitrary Cargo features. [Pinned build script](https://raw.githubusercontent.com/rusqlite/rusqlite/v0.40.2/libsqlite3-sys/build.rs).

| Build option | Purpose and recommendation | Bundled-build control |
|---|---|---|
| `SQLITE_DQS=0` | Disable double-quoted string literals. Use it. | Pass through `LIBSQLITE3_FLAGS`; retain runtime disablement. |
| `SQLITE_DEFAULT_FOREIGN_KEYS=1` | Make enforcement the default. Use it. | Already set by the inspected build; still verify each connection. |
| `SQLITE_DEFAULT_WAL_SYNCHRONOUS=2` | Default WAL writes to FULL. Use it. | Additional define; runtime FULL remains the operational contract. |
| `SQLITE_STRICT_SUBTYPE=1` | Detect incorrectly registered application-function subtypes. Useful; unrelated to STRICT-table typing. | Additional define. |
| `SQLITE_DEFAULT_MEMSTATUS=0` | Reduce global memory-accounting overhead if those statistics are unnecessary. Optional. | Additional define. |
| `SQLITE_OMIT_DEPRECATED` | Remove deprecated APIs if bindings and extensions do not need them. Optional after build validation. | Additional define. |

The meanings are specified by [SQLite compile options](https://www.sqlite.org/compile.html); the available injection mechanism is in the [bundled build script](https://raw.githubusercontent.com/rusqlite/rusqlite/v0.40.2/libsqlite3-sys/build.rs). Do **not** copy SQLite's size-optimized `THREADSAFE=0` suggestion into an application with multiple reader threads. Preserve progress/cancellation support needed to interrupt expensive searches.

There is a version trap: the consulted **libsqlite3-sys 0.38.1 release archive bundles SQLite 3.53.2** for its normal SQLite build. Installing a current-looking rusqlite crate therefore does not prove that Sweetbriar ships the **3.53.4** binary tested here. Pin the exact dependency/source, verify `sqlite_version()`, `sqlite_source_id()` and effective settings in CI, and qualify the actual packaged artifact. [Release source archive](https://crates.io/api/v1/crates/libsqlite3-sys/0.38.1/download), [bundled SQLite header](https://docs.rs/crate/libsqlite3-sys/0.38.1/source/sqlite3/sqlite3.h).

**Judgment:** the remaining issues are manageable, but not free. SQLite's strongest advantages for a decades-long store are its documented application-file format and backward-compatibility policy, its inspectable tooling, and transactional relational constraints. Its public-domain engine has no commercial licence dependency. [Application file format](https://www.sqlite.org/appfileformat.html), [file format specification](https://www.sqlite.org/fileformat2.html), [licensing](https://www.sqlite.org/copyright.html).

### 2.3 Other alternatives

The following current-version labels are registry observations **as of 2026-10-11**. A non-prerelease crate version is not a claim of production maturity. The fit assessments are recommendations, not vendor statements.

#### libSQL and the separate Turso Database

These are different engines. **libSQL** is the SQLite fork, retaining its fundamental single-writer architecture and adding remote access/replicas. Its maintainers now direct new projects toward **Turso Database**, a separate Rust rewrite described as beta. The libSQL Rust registry lists **0.9.30** as the latest non-prerelease version and **0.10.0-pre.4** as a prerelease. Its MIT licence and SQLite-format compatibility are attractive, but cloud replication does not replace Sweetbriar's IMAP/JMAP/Gmail/Exchange synchronization logic. [libSQL project and compatibility policy](https://raw.githubusercontent.com/tursodatabase/libsql/main/README.md), [registry](https://crates.io/api/v1/crates/libsql), [licence](https://raw.githubusercontent.com/tursodatabase/libsql/main/LICENSE.md).

The tested `libsql-experimental` Python wheel is **0.0.55** and reports **SQLite 3.45.1**. That is below the requested upstream fixed-version floor. This does **not** prove the fork contains the WAL-reset bug: backports are possible. The wheel's inclusion of the fix is **unverified**; do not qualify it for authoritative storage from its Python package version or successful kill tests alone. Its benchmark represents that binary, not current Turso Database. [Driver probe](codex-artifacts/artifacts/driver_probes.json), [benchmark](codex-artifacts/artifacts/run1/libsql.json), [SQLite affected versions](https://sqlite.org/wal.html).

Turso Database released **0.8 on 2026-09-29**, improving MVCC group commit and concurrent writers; the registry currently lists **0.8.2** as a non-prerelease release and **0.8.3-pre.1** as a prerelease. Version **0.5, released 2026-03-04**, moved concurrent writes to beta for limited production use. Current documentation is not fully consistent: the README reports production users and still calls some features experimental, while portions of the manual retain stronger limitations and a warning against critical-data MVCC use. Treat this inconsistency as a qualification question, not proof of either universal instability or complete compatibility. [0.8 announcement](https://turso.tech/blog/turso-0.8.0), [0.5 announcement](https://turso.tech/blog/turso-0.5.0), [registry](https://crates.io/api/v1/crates/turso), [README](https://raw.githubusercontent.com/tursodatabase/turso/main/README.md), [manual](https://raw.githubusercontent.com/tursodatabase/turso/main/docs/manual.md).

Turso exposes `BEGIN CONCURRENT` on separate connections when MVCC is enabled, with row-level optimistic conflict detection; callers must handle commit conflicts. Its grouped-commit performance claims concern concurrent writers, a workload deliberately absent here. The MVCC implementation adds a log/version layer over SQLite-compatible B-trees and eventually checkpoints it into the SQLite-format file. Current manual limitations include checkpoint blocking and changes being invisible when opening without MVCC before checkpointing. Cross-process WAL coordination through `.tshm` remains explicitly experimental. FTS uses Tantivy and is also experimental. The engine is MIT-licensed and has a native Rust API. **Recommendation:** maintain a watchlist prototype, but its main advantage—multiple writers—solves a problem Sweetbriar deliberately avoids. [Concurrent-write design](https://turso.tech/blog/concurrent-writes-in-practice), [current manual](https://raw.githubusercontent.com/tursodatabase/turso/main/docs/manual.md), [experimental features and licence](https://raw.githubusercontent.com/tursodatabase/turso/main/README.md).

#### Rust-native and conventional KV engines

| Engine; current releases observed | Durability, maturity and process considerations | Rust support, licence and Sweetbriar fit |
|---|---|---|
| **redb 4.3.0** | Copy-on-write B+trees, MVCC, checksums and durable commit/recovery by default; non-durable commits are optional. The format is described as stable with upgrade support. 4.3.0 fixes a recovery case that could roll back a commit after prior integrity repair. Process sharing is available behind `experimental-multiprocess`, not an established default. A macOS nuance applies to the Rust-native engines: the consulted Rust standard-library implementation maps both file sync methods to `F_FULLFSYNC` on Apple targets. It is wrong to infer that a Rust `File::sync_data()` necessarily means ordinary Darwin `fsync`. Nevertheless, qualify the exact compiler/engine combination and error handling; this source inspection is not a hardware test. [Rust filesystem implementation](https://raw.githubusercontent.com/rust-lang/rust/master/library/std/src/sys/fs/unix.rs).

Our KV benchmark actually implemented three namespaces: primary messages, ordered covering list entries and remote-locator keys, plus intent records. Atomic batches preserve them together. It did **not** implement general foreign-key enforcement, duplicate-locator rejection, mailbox joins, arbitrary rules, Unicode search or schema migration. Faster KV operations would therefore demonstrate a narrower service, not a free replacement for SQLite. Conversely, carefully typed Rust access can make that narrower service safer and simpler for a sufficiently fixed schema. [KV implementation](codex-artifacts/bench.py).

### 2.4 Reproducible benchmark and recovery tests

#### Environment and methodology

The job used **CPython 3.11.2**, Linux **7.0.0-38-generic**, glibc 2.36, an **Intel Xeon W-2145** with eight cores/16 logical CPUs, approximately **125.5 GiB RAM**, and **ext4 on `/dev/md2`**. There was no CPU or memory cgroup quota. It was a shared machine: a recorded load average was about 6, and other jobs were active. Disk hardware/cache guarantees were not established. No Rust or C compilation was used; packages were installed only into the job's virtual environment. [Environment record](codex-artifacts/artifacts/environment.json).

|---|---|

| `redb` | 0.5.0; installed module exposes no usable database API |

These are local observations, not guesses about Rust crates or current upstream engine releases. The redb wheel could be imported, but its native module exported no database interface; **redb was not benchmarked**. That says nothing about Rust redb's performance. [Pinned requirements](codex-artifacts/requirements.txt), [driver probes](codex-artifacts/artifacts/driver_probes.json).

The SQL workload used separate `messages`, `memberships` and `intents` tables. Memberships included per-folder flags, mailbox/date/id, sender/subject summaries and a unique `(mailbox,uidvalidity,uid)` locator. Foreign keys and primary keys were active during import; a secondary index beginning `(mailbox,date DESC,id DESC)` and containing all displayed columns was built afterward. SQLite/libSQL used STRICT. DuckDB used BIGINT for corresponding integer fields. KV implementations atomically maintained primary, covering-list, locator and intent keys. [Schema and implementation](codex-artifacts/bench.py).

The deterministic corpus places all initial **500,000**, or **1,000,000**, messages in one mailbox. Dates are deliberately non-monotonic and tied; keyset cursors cover deep positions rather than only the newest messages. Bodies are synthetic derived search text, not MIME originals, with about 61 normalized terms. Content hashes stand in for external immutable-message references. Consequently, file sizes exclude real message files, attachments, accounts, draft revisions and the full production schema.

Each run measured:

1. One atomic bulk import from the same CSV; CSV generation excluded, CSV parsing included.
2. Secondary-index construction, separately from import.
3. **100 transactions × 250 new messages**, each with membership and per-message intent records.
4. **500 flag-change-plus-intent commits**, **1,000 random id lookups**, and **200 keyset pages of 50 rows**.
5. One **10,000-row mark-read transaction**, including 10,000 journal records.
6. One writer and two reader threads, plus a separate sustained-reader experiment.
7. FTS build and 20 warmed runs per query, a freshness probe, settled file sizes and five warm opens.

SQLite/libSQL used WAL, FULL synchronization, foreign keys and a 64 MiB cache budget. `fullfsync` and `checkpoint_fullfsync` were enabled, although they add no macOS-specific behavior on this Linux host. DuckDB used its durable native WAL, four threads and a 1 GB configured memory budget. LMDB had sync/metasync enabled and writable maps disabled. RocksDB used WAL and synchronous WriteBatch commits. No result below uses intentionally disabled durability. [Benchmark settings](codex-artifacts/bench.py), [environment](codex-artifacts/artifacts/environment.json).

#### Crash tests: what passed and what remains unproved

For each engine, a child committed three 20-row transactions per cycle. Only after commit returned did it send an acknowledgement; the parent appended that acknowledgement to a separately fsynced witness file. It then killed the child with **SIGKILL**, reopened the store, compared exact committed-id sets, and checked message/membership/intent consistency. SQL and LMDB kills paused at varied pre-commit boundaries, including after a message effect but before its membership/journal. [Harness](codex-artifacts/crash_test.py).

RocksDB required a different test because WriteBatch preparation is client-side. Its relevant run killed around actual native WriteBatch submission, using varied 0–30 ms offsets. A batch not witnessed by the parent was allowed to recover entirely or not at all. Across the 30 runs, **13,000 such unwitnessed rows** recovered in whole 500-row batches, with no partial batches. Earlier buffered-before-write trials were weaker and are retained separately, not substituted for these native-write results. [Native RocksDB results](codex-artifacts/artifacts/crash-native/rocksdb.json).

## 3. Options compared

This table summarizes the decision for the **specified** store. “Fit” is an assessment based on the cited findings above, not a benchmark-independent guarantee.

| Option | Ordered mailbox pages | Live readers in other processes | Atomic effect + journal | Continuously updated search | Overall fit |
|---|---|---|---|---|---|
| Bundled SQLite + FTS5 | Native covering B-tree | Supported, with WAL/SHM permissions and snapshot discipline | Native SQL transaction | Incremental FTS maintenance | Best initial balance |
| DuckDB alone | Scan/Top-N rather than required covering-index path | Direct-file reader blocked by writer | Native transaction | FTS recreation required | Strong analytics, weak authoritative-store match |
| SQLite + DuckDB analytics | SQLite provides pages | SQLite retains normal process model | Keep all authoritative writes in SQLite | FTS5 or separate search engine | Worth adding only for a proved analytical need |
| libSQL fork | SQLite-style indexes | Inherits SQLite-style model | Native transaction | FTS5 | Little local-only benefit; qualify exact fork/version |
| Turso Rust engine | SQLite-compatible indexing goal | Coordination currently experimental | Native transaction/MVCC log | Tantivy integration experimental | Reevaluate after feature qualification |
| LMDB/heed | Efficient manually encoded ordered keys | Supported | One atomic write transaction | Separate index engine/application | Credible if query/model needs stay narrow |
| redb/native_db | Ordered B+tree/index APIs | redb sharing experimental | Native Rust transactions | Separate search integration | Credible Rust path, more qualification/work |
| fjall/RocksDB | Ordered LSM keys | fjall excludes sharing; RocksDB secondary mode differs | Atomic batches/transactions | Separate search integration | Better case at substantially higher write volume |
| SurrealDB | Query engine over indexed storage | Target sharing behavior needs verification | Embedded transactions with selected durable backend | Integrated search facilities | Broader engine/licence/format commitment |
| Object/mobile/Apple stores | Product-specific indexing | Product-specific | Usually transactional, settings matter | Product-specific | Less direct fit for this reusable Rust core |

SQLite read-only WAL access has specific requirements: shared-memory/WAL files must exist or be creatable under documented conditions. An extension needs the right App Group/container access. Do not use `immutable=1` to bypass coordination on a changing live database. [Read-only WAL rules](https://sqlite.org/wal.html).

## 4. Recommendations for Sweetbriar

### Authoritative state

Use **an explicitly versioned bundled SQLite build**, at least 3.51.3 and qualified against the fixes required by the chosen maintenance branch. Preserve the proposed WAL/FULL/fullfsync/STRICT/single-writer design. Initialize every connection through one Rust constructor that verifies settings; route mutations through a writer queue, outside the UI thread. Use explicit transactions for local effects, intent records and sync cursors. Return “saved” only after the durable commit succeeds.

The recommendation should not turn into “whatever the OS happens to ship” or “whatever `bundled` happens to include.” The tested APSW build and shipping rusqlite build are different artifacts. Record their actual source id and compile options. SQLite's WAL bug and rusqlite's vendored version demonstrate why this distinction matters. [SQLite WAL fix](https://sqlite.org/wal.html), [rusqlite build](https://raw.githubusercontent.com/rusqlite/rusqlite/v0.40.2/libsqlite3-sys/build.rs), [vendored header](https://docs.rs/crate/libsqlite3-sys/0.38.1/source/sqlite3/sqlite3.h).

For original messages, **the database cannot atomically commit an external file with its SQL transaction**. Proposed ordering: write a temporary content-addressed object; sync its contents using the target platform's durable operation; publish its final name and durably persist required directory metadata; then commit database references and intent. A crash before the database commit may leave an orphan, which is safer than an authoritative reference to an absent object. Garbage collection must respect active reads, retained backups and migration snapshots. This is an application protocol, not a property obtained by choosing SQLite. [File/directory sync distinction](https://man7.org/linux/man-pages/man2/fsync.2.html), [Apple sync primitives](https://developer.apple.com/videos/play/wwdc2019/419/).

Use a consistent SQLite backup API or equivalent database snapshot, together with a manifest of referenced immutable objects. Validate restored databases and object hashes. Preserve pre-migration snapshots and implement migrations as transactional, restartable transformations with invariant checks. Keep a documented logical export independent of database engine and Rust serialization versions. SQLite's backup API supplies a consistent database image, not an automatic complete backup of the external message tree. [Backup API](https://www.sqlite.org/backup.html), [schema-change procedure](https://www.sqlite.org/lang_altertable.html).

### Search

Start with **SQLite FTS5**, populated incrementally from decoded message text and the fields Sweetbriar actually wants to search. Its BM25, prefix/phrase queries, snippets/highlighting and tokenizer interfaces provide a concrete baseline. The measured rare-query and two-term paths were fast; common ranked queries were materially slower and deserve optimization. [FTS5 capabilities](https://www.sqlite.org/fts5.html), [search measurements](codex-artifacts/artifacts/run2/sqlite.json).

For the first implementation, keep FTS updates transactional with text changes if using the same database. Flags/moves should not rewrite body postings. If search is later moved to a separate derived store, append an indexing event in the authoritative transaction, track an index-generation watermark, and make rebuilding/replaying idempotent. A lagging search index must never be the only record of a draft, note or sent message.

Benchmark **Tantivy** before claiming best-in-class search: it is a native Rust engine with BM25, fielded queries, phrase/range/fuzzy facilities and commit/reload APIs. It is not automatically superior for this corpus, and was not measured in this job. A separate Tantivy index creates a second consistency/rebuild protocol, but that cost is tolerable for derived data when product requirements justify it. [Tantivy project](https://raw.githubusercontent.com/quickwit-oss/tantivy/main/README.md), [writer commit API](https://docs.rs/tantivy/latest/tantivy/indexer/struct.IndexWriter.html), [reader API](https://docs.rs/tantivy/latest/tantivy/struct.IndexReader.html).

Do not choose DuckDB FTS as the continuously maintained primary mail-search index. Its rebuild requirement is a functional mismatch even if a future benchmark produces faster queries. [DuckDB FTS maintenance](https://duckdb.org/docs/stable/core_extensions/full_text_search).

### Hybrid and the strongest counter-argument

Skip DuckDB in the initial application. SQLite can answer simple statistics, and an optional analytics engine would add binary size, resource budgeting, extension packaging and another failure surface before a demonstrated need.

**The strongest argument against this choice:** DuckDB combines strict SQL typing, compression, fast bulk import and excellent analytical execution in one embedded engine. The baseline overstates its incremental-write cost because Arrow improved it tenfold. If all store access went through a single Rust process, extensions used IPC, ordered views were maintained differently, and search used another engine, DuckDB could be an attractive foundation. Its measured aggregate advantage and compact storage are substantial. [Arrow result](codex-artifacts/artifacts/duckdb_arrow_batches.json), [aggregate/size results](codex-artifacts/artifacts/run2/duckdb.json).

**My response:** those changes replace two explicit requirements—direct live file readers and ordered indexed mailbox access—with additional application mechanisms. Sweetbriar's saved mutable state is the least useful place to trade established access/backup tools for analytical throughput. A hybrid leaves DuckDB's strengths available without making mail safety depend on its suitability for that workload.

The strongest KV counterproposal is **LMDB/heed**, or **redb with mature process sharing**, plus a carefully designed typed query layer. That could remove unwanted SQL semantics and reduce FFI or query-planning overhead. The cost to assess is the entire replacement service: indexes, uniqueness, relationship integrity, migrations, troubleshooting and search—not just KV `get` throughput.

### Measurable conditions that would change the choice

These are **proposed Sweetbriar gates**, not measured product requirements:

- Reconsider DuckDB authority if the required reader/process contract becomes supported or IPC is explicitly adopted, deep 50-row pages stay below **5 ms p95** at one million messages under sustained writes, and native Rust 250-row durable transactions meet a **50 ms p95** budget on the actual Mac. The exact build must also pass power-fault, interrupted-migration and checkpoint/index qualification.
- Reconsider a KV authority if a prototype includes the complete index/constraint/migration service, provides the required process readers, and gives at least a **2× meaningful latency or memory advantage** on the real workload without increasing recovery risk. Current raw KV timings do not establish that.
- Add DuckDB analytics if a real user-facing operation exceeds **250 ms p95** in tuned SQLite and DuckDB reduces it by at least **3×**, including snapshot/export overhead and its resource budget.
- Move search to Tantivy if a real multilingual corpus fails agreed relevance tests, or warm interactive queries exceed **100 ms p95 for selective searches / 200 ms for broad ranked searches**, and Tantivy improves those outcomes while preserving reliable indexing watermarks and rebuild behavior.

## 5. Risks and open questions

1. **Target-device durability remains unverified.** Test the exact Apple-silicon/macOS 27 packaged build, its sync calls, APFS behavior, external-object publication and storage failures. Process-kill success does not prove “saved survives power loss.” Distinguish ordering barriers from permanent-media flushing. [Apple storage guidance](https://developer.apple.com/videos/play/wwdc2019/419/).
2. **Engine versions are not binding/package versions.** The libSQL wheel's old reported base, rusqlite's actual vendored SQLite, DuckDB's guarded macOS branch and preview-only settings each need artifact-level qualification. [Driver probes](codex-artifacts/artifacts/driver_probes.json), [vendored header](https://docs.rs/crate/libsqlite3-sys/0.38.1/source/sqlite3/sqlite3.h).
3. **Benchmarks are synthetic and Python-heavy.** Repeated tiny vocabulary compresses unusually well; JSON serialization penalizes KV paths; parameter binding affects DuckDB; caches were warm; shared-machine flush latency varied. Test the Rust core with real MIME-derived, multilingual text and realistic summary widths before establishing capacity budgets.
4. **Recovery coverage is incomplete.** Extend recovery trials to one-million-row stores and add interrupted-checkpoint/DDL, concurrent backup, disk-full, I/O-error, external-file orphan and repeated upgrade/downgrade trials. Particularly retain regressions for documented engine bugs. No engine earns an absolute corruption-free claim from 30 kills.
5. **Schema complexity matters.** Multiple memberships, remote UIDVALIDITY resets, intent deduplication, draft revisions, outbox retries and thread-graph rebuilding were not fully modeled. Compare alternatives after implementing those invariants, not only the hot message table.
6. **Search quality remains open.** Choose normalization/tokenization for non-Latin scripts, diacritics, quoted phrases, addresses, attachment names and local notes; evaluate snippets, ranking and filter combinations. Neither BM25 availability nor these timing results proves best-in-class search.
7. **Lifetime migration and restore are application obligations.** Define an export specification, object manifest, backup retention and interrupted-migration strategy. Test decades of schema evolution through representative historical fixtures; do not serialize authoritative records solely through unstable Rust layouts.
8. **Alternative maturity can change.** Track Turso's documentation/compatibility and `.tshm` stabilization, redb's experimental process sharing, native_db API stability and SurrealKV changes. Object/mobile engines require specific target distribution and maintenance commitments, not only attractive feature lists. [Turso manual](https://raw.githubusercontent.com/tursodatabase/turso/main/docs/manual.md), [redb changelog](https://docs.rs/crate/redb/4.3.0/source/CHANGELOG.md), [native_db status](https://raw.githubusercontent.com/vincent-herlemont/native_db/main/README.md), [SurrealKV warning](https://surrealdb.com/docs/running/file-backed).
