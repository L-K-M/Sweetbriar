# Sweetbriar research: email standards and plumbing a modern client must get right

*Compiled 2026-10-11. Facts marked with dates were verified against the linked sources on that date; "(unverified)" marks claims I could not confirm.*

## 1. TL;DR

- **Account setup is five mechanisms, not one.** Ship Thunderbird's chain (local file → `autoconfig.<domain>` → ISPDB → MX→ISPDB → hostname guessing) *plus* Microsoft Autodiscover (POX XML; the JSON "V2" endpoint exists but is undocumented) *plus* RFC 6186 SRV lookups. The autoconfig spec is finally on a standards track as `draft-ietf-mailmaint-autoconfig` (-06, June 2026, post-WGLC revision pending).
- **Passwords are nearly dead for the big providers.** Google killed password auth for all accounts by mid-2025; Microsoft finished IMAP/POP in 2022 and is phasing SMTP AUTH basic auth through 2027. OAuth 2.0 (XOAUTH2/OAUTHBEARER) + app passwords are the reality; budget time for Google's restricted-scope app verification and Yahoo's manual API access approval.
- **On macOS, do OAuth in ASWebAuthenticationSession with a loopback or claimed-HTTPS redirect.** Google's loopback flow remains supported for *desktop* client types (it was deprecated only for iOS/Android/Chrome, Oct 2022). Store refresh tokens in the Keychain, not files.
- **The MIME edge cases are the product.** 2047/2231 decoding with broken-input tolerance, WHATWG charset handling (`encoding_rs` + `chardetng`), format=flowed, TNEF (`winmail.dat`), `message/rfc822` attachments, and crypto MIME structures decide whether users see "correct" mail. The `mail-parser` crate (Stalwart, v0.11.9) is the strongest Rust starting point.
- **Threading = JWZ + provider IDs.** Implement JWZ/RFC 5256 client-side, use `X-GM-THRID` on Gmail, and parse `Thread-Index`/`ConversationId` for Exchange. The IMAP `THREAD=REFS` extension never became an RFC (draft expired) — don't depend on it.
- **Sending has real subtlety**: port 465 implicit TLS vs 587 STARTTLS per RFC 8314; Gmail *and* M365 save SMTP-submitted mail to Sent themselves (don't double-append); DSN, BURL (rare), FUTURERELEASE (rare) round out the "real client" feature set.
- **Trust display is worth doing**: parse `Authentication-Results` (RFC 8601) written by *your own provider* only; show BIMI logos — Apple Mail only displays provider-asserted BIMI, so client-side validation is a differentiator.
- **RFC 9979 (2026) quietly standardized a lot of folklore**: Apple's `$MailFlagBit0-2` color-flag keywords, `$hasattachment`, `$muted`, `\Snoozed`/`\Scheduled` mailboxes. Implement Apple flag colors at launch — it makes Sweetbriar the only third-party client that round-trips them.
- **Sieve/ManageSieve (RFC 5228/5804) is how "server-side rules" works** on Dovecot/Cyrus/Fastmail-class providers; Gmail and Exchange have no Sieve. MDN (RFC 8098) exists but should default to never auto-respond.
- **Nothing in macOS 27 "Golden Gate" changes this picture** — Mail got "better search" and a Smart Mailbox fix; no deprecations affecting third-party mail apps were found in the release notes.

## 2. Findings

### 2.1 Account setup and autodiscovery (Q1)

**Thunderbird autoconfig / ISPDB.** Thunderbird's autoconfiguration is documented in an [MDN overview](https://developer.mozilla.org/en-US/docs/Mozilla/Thunderbird/Autoconfiguration) and a normative [file-format spec](https://developer.mozilla.org/en-US/docs/Thunderbird/Autoconfiguration/FileFormat/Definition): an XML `<clientConfig version="1.1">` describing incoming/outgoing servers, socket types (`SSL`, `STARTTLS`, `plain`), authentication methods (`password-cleartext`, `password-encrypted`, `NTLM`, `GSSAPI`, `OAuth2`, `client-IP-address`, `TLS-client-cert`), and username patterns (`%EMAILADDRESS%`, `%EMAILLOCALPART%`). For `fred@example.com`, Thunderbird looks up, in order ([MDN](https://developer.mozilla.org/en-US/docs/Mozilla/Thunderbird/Autoconfiguration)):

1. `<tb-install-dir>/isp/example.com.xml` (local file),
2. `https://autoconfig.example.com/mail/config-v1.1.xml?emailaddress=fred@example.com` (preferred) and `https://example.com/.well-known/autoconfig/mail/config-v1.1.xml`,
3. the ISPDB at `https://autoconfig.thunderbird.net/v1.1/example.com`,
4. an MX lookup of `example.com`, then the *hoster's* parent domain in the ISPDB,
5. hostname guessing (`imap.`, `smtp.`, `mail.`…) with live probing of SSL/STARTTLS/CRAM-MD5.

The ISPDB is MPL-2.0-licensed data in [github.com/thunderbird/autoconfig](https://github.com/thunderbird/autoconfig) (moved from `thundernest`), "free to use for any client," covering most ISPs with >0.1% share — Mozilla claims it autoconfigures ~50% of accounts. HTTPS for autoconfig was added to the spec in June 2019; plain HTTP is deprecated but still supported for legacy hosters ([MDN](https://developer.mozilla.org/en-US/docs/Mozilla/Thunderbird/Autoconfiguration)).

**Standards-track status.** The long-stalled `draft-bucksch-autoconfig` / `draft-ietf-mailautoconfig` work has been adopted by the IETF **mailmaint** WG as [`draft-ietf-mailmaint-autoconfig-06`](https://datatracker.ietf.org/doc/draft-ietf-mailmaint-autoconfig/), last revised 2026-06-28, intended Informational, currently "Revised I-D Needed" after issues raised in WG Last Call; expires 2026-12-30; WG milestone "Nov 2026: Submit legacy Mail Autoconfig draft" ([datatracker history](https://datatracker.ietf.org/doc/draft-ietf-mailmaint-autoconfig/history/)). Not an RFC yet, but the de-facto format is stable — implement it.

**Microsoft Autodiscover.** V1 is the documented, stable path: POX (plain-old-XML) POST to `https://autodiscover.<domain>/autodiscover/autodiscover.xml` or `https://<domain>/autodiscover/autodiscover.xml`, plus SCP lookup in AD, HTTP→HTTPS redirect following, and `_autodiscover._tcp` SRV ([Microsoft Learn](https://learn.microsoft.com/en-us/exchange/client-developer/exchange-web-services/autodiscover-for-exchange)). "Autodiscover V2" is a JSON GET endpoint — `https://autodiscover-s.outlook.com/autodiscover/autodiscover.json?Email=…` — working for Exchange Online and Exchange Server 2016+ on-prem, but Microsoft has published no formal client documentation for it and V1 "remains stable and fully supported" ([Microsoft Q&A](https://learn.microsoft.com/en-my/answers/questions/4374341/does-autodiscover-v2-supports-only-exchange-online), [c7solutions](https://c7solutions.com/2022/11/troubleshooting-autodetect)). Outlook mobile additionally uses the hosted **AutoDetect** service `prod-autodetect.outlookmobile.com/detect` — useful intelligence about what works, but an undocumented third-party path.

**RFC 6186 SRV records.** [RFC 6186](https://www.rfc-editor.org/rfc/rfc6186.html) defines `_submission._tcp`, `_imap._tcp`/`_imaps._tcp`, `_pop3._tcp`/`_pop3s._tcp` SRV lookups. Deployment remains sparse — Thunderbird itself notes "we currently do not" use SRV ([MDN](https://developer.mozilla.org/en-US/docs/Mozilla/Thunderbird/Autoconfiguration)). Querying them costs little and helps organized self-hosters; keep it in the chain after MX heuristics.

**Apple Mail.** Apple documents a provider list (iCloud, Google, Exchange, Yahoo, AOL, Outlook.com…) with automatic identification "based on the email address" ([Apple Support](https://support.apple.com/en-us/102088)); for "Other" accounts Mail "will try to find the email settings" — an undocumented heuristic probe of common hostnames — and can "automatically manage connection settings" (ports and auth methods) thereafter ([Apple Support](https://support.apple.com/guide/mail/change-server-settings-cpmlprefacctadv/mac)). Managed deployment uses `.mobileconfig` MailAccount payloads. Apple's exact probe list is not published (unverified specifics); empirically it tries `mail.`/`imap.`/`pop.`/`smtp.` prefixes plus hardcoded big-provider profiles.

**MX-based heuristics.** Mapping `MX → provider` (Google's `aspmx.l.google.com`, Microsoft's `*.mail.protection.outlook.com`, `mx*.fastmail.com`…) is the highest-value heuristic for hosted domains because it selects the right *authentication path* (OAuth endpoints, app-password flow), not just hostnames. It fails for on-prem Exchange, multi-provider setups, and providers hosting others' MX.

### 2.2 Authentication (Q2)

**SASL mechanisms.** `XOAUTH2` is Google's de-facto-standard mechanism (`user=<addr> auth=Bearer <token>`), also used by Microsoft. `OAUTHBEARER` is the IETF-standardized equivalent ([RFC 7628](https://www.rfc-editor.org/rfc/rfc7628.html)), used by Yahoo/AOL and supported by Microsoft; it can carry `host=`/`port=` GS2 parameters ([Yahoo docs](https://senders.yahooinc.com/developer/documentation/)). `SASL-IR` ([RFC 4959](https://www.rfc-editor.org/rfc/rfc4959.html)) saves a round trip for all of these. `SCRAM-SHA-1` ([RFC 5802](https://www.rfc-editor.org/rfc/rfc5802.html)) and `SCRAM-SHA-256`/`SCRAM-SHA-256-PLUS` ([RFC 7677](https://www.rfc-editor.org/rfc/rfc7677.html), channel binding per [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266.html)) are the right *password* mechanism where offered — the server never sees the password — but deployment is thin (Dovecot supports it; the big hosted providers do not). `GSSAPI`/Kerberos matters in enterprise. TLS client certificates are a niche enterprise option (Apple Mail exposes them via "TLS Certificate" in account settings).

**OAuth flow mechanics.** Follow [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html) (BCP 212, OAuth for native apps): use the system browser — on macOS that means `ASWebAuthenticationSession`, which shares Safari state and is Apple's sanctioned approach — with PKCE ([RFC 7636](https://www.rfc-editor.org/rfc/rfc7636.html)). For the redirect: **loopback IP** (`http://127.0.0.1:port`, ephemeral port) remains supported by Google *for desktop client types* — Google deprecated it only for iOS/Android/Chrome, completing Oct 21, 2022 ([Google migration guide](https://developers.google.com/identity/protocols/oauth2/resources/loopback-migration)); **custom URI schemes** must be reverse-domain (`com.sweetbriar.app:`) per RFC 8252 §7.1 and are still accepted for desktop. On macOS, `ASWebAuthenticationSession` + custom scheme is the most robust combination (the callback is delivered to *your* app, immune to loopback-port races), with loopback as fallback.

**Provider matrix (verified 2026-10-11):**

**Deprecation timeline (verified):** Google turned off password auth ("less secure apps") for *all* accounts — Workspace final step May 1, 2025 ([Google Workspace](https://support.google.com/a/answer/14114704), [domainindia summary](https://domainindia.com/support/kb/how-to-use-app-passwords-and-oauth-2.0-in-google-workspace-a-complete-setup-guid)). Microsoft disabled basic auth for IMAP/POP/Exchange protocols in 2022; for SMTP AUTH client submission the timeline was revised Jan 27, 2026: disable-by-default for existing tenants **end of December 2026** (admins may re-enable), unavailable for tenants created after Dec 2026, final removal date to be announced in H2 2027 ([Microsoft Tech Community](https://techcommunity.microsoft.com/blog/exchange/exchange-online-to-retire-basic-auth-for-client-submission-smtp-auth/4114750), [MC786329](https://mc.merill.net/message/MC786329)).

**Token lifecycle.** Client IDs for desktop apps are public constants — ship them in code/config; the *secret* is the refresh token. Store it in the macOS Keychain (and Secret Service/libsecret on Linux), refresh access tokens proactively, and treat `invalid_grant` as "re-authenticate" not "delete account." Thunderbird and Mailspring each ship their own registered client IDs — the precedent is that each client registers its own.

### 2.3 Message-format edge cases (Q3)

- **Baselines:** [RFC 5322](https://www.rfc-editor.org/rfc/rfc5322.html) and MIME [RFC 2045–2049](https://www.rfc-editor.org/rfc/rfc2045.html). Real mail violates all of it: plan for missing boundaries, unencoded 8-bit headers, folded `References`, NULs, and duplicate header names.
- **Encoded words & parameters:** [RFC 2047](https://www.rfc-editor.org/rfc/rfc2047.html) encoded words arrive broken constantly (unterminated `=?`, words inside quoted strings/addresses, charset lies). Filename parameters come in three interoperable-in-theory-but-messy forms: RFC 2231 continuations+charset (`filename*0*=utf-8''`), RFC 2047 inside `filename=`, and raw UTF-8/8-bit. Decode all three; emit RFC 2231.
- **Charsets:** WHATWG requires `iso-8859-1` → `windows-1252` mapping — implement that, plus detection for undeclared 8-bit. Rust: `encoding_rs` (0.8.42, WHATWG encoding set) + `chardetng` (1.0.0, Firefox's detector). GB2312→GBK, `x-user-defined`, and `unknown-8bit` labels need remapping tables.
- **Transfer encodings:** 8BITMIME ([RFC 6152](https://www.rfc-editor.org/rfc/rfc6152.html)) and `BINARY`/`BDAT` ([RFC 3030](https://www.rfc-editor.org/rfc/rfc3030.html)) on submission; tolerate malformed quoted-printable (`= ` mid-word, trailing junk, soft breaks without `=`).
- **EAI / SMTPUTF8:** [RFC 6530–6533](https://www.rfc-editor.org/rfc/rfc6531.html) + `UTF8=ACCEPT` on IMAP ([RFC 6855](https://www.rfc-editor.org/rfc/rfc6855.html)). Inbound support is broad in 2026 — Gmail (since 2014), Outlook.com/M365, iCloud, Yahoo, Proton per [smtpedia](https://smtpedia.com/rfc-6531/) and [mailtester](https://mailtester.com/blog/smtputf8-support-mailbox-providers-esps/); Postfix ≥3.0 ships it enabled by default. A client must *parse* UTF-8 local-parts and headers (no RFC 2047) and *send* with the `SMTPUTF8` MAIL FROM parameter only when the server advertises it.
- **format=flowed:** [RFC 3676](https://www.rfc-editor.org/rfc/rfc3676.html) (`format=flowed; delsp=yes`) — required for correct quote-reflow and for composing plain-text that reads well in Gmail/Thunderbird; also *emit* it.
- **TNEF:** `application/ms-tnef`/`winmail.dat` still leaks out of Outlook/Exchange on-prem. The format is fully specified in [`[MS-OXTNEF]`](https://learn.microsoft.com/en-us/openspecs/exchange_server_protocols/ms-oxtnef/1f0544d7-30b7-4194-b58f-adc82f3763bb) (rev 15.0, May 2025) — TLV-encoded MAPI properties incl. the real body, recipients, attachments, and meeting requests. No mature Rust crate exists (unverified — candidates are thin); budget for a decoder.
- **Multipart semantics:** `multipart/alternative` (pick the most faithful part for display; keep `text/plain` authoritative for plain-text purists and quoting), `multipart/related` ([RFC 2387](https://www.rfc-editor.org/rfc/rfc2387.html)) with `cid:`/`Content-Location` resolution, `message/rfc822` attachments (render as attached messages with their own headers), `text/calendar` parts ([RFC 5545](https://www.rfc-editor.org/rfc/rfc5545.html)) especially `method=REQUEST/REPLY/CANCEL` even when mislabeled, and `multipart/appledouble` for old-Mac interop.
- **Crypto structures:** S/MIME per [RFC 8551](https://www.rfc-editor.org/rfc/rfc8551.html) (`multipart/signed` + `application/pkcs7-mime`/`pkcs7-signature`, opaque-signed vs clear-signed), PGP per OpenPGP [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html) (July 2024, obsoletes 4880/5581/6637) with `PGP/MIME` [RFC 3156](https://www.rfc-editor.org/rfc/rfc3156.html) *and* legacy inline PGP. These parts are structure, not attachments — a signed `multipart/signed` must not render its signature as a downloadable `.p7s` "attachment" by default.
- **Rust tooling:** `mail-parser` (Stalwart) **0.11.9** — a battle-tested parser that already handles the edge cases above and drives the Stalwart server; `mailparse` 0.18.0 (simpler, less tolerant); `mail-builder` 1.0.0 for generation (crates.io, checked 2026-10-11).

### 2.4 Threading and conversations (Q4)

- **JWZ** is the canonical client-side algorithm ([jwz.org/doc/threading.html](https://www.jwz.org/doc/threading.html), 1997–2002): build containers by `Message-ID`, link via `References`+`In-Reply-To` (appending IRT's first msg-id to References), prune empty containers, group root-set orphans by normalized subject. It survives missing ancestors and circular refs.
- **IMAP THREAD** ([RFC 5256](https://www.rfc-editor.org/rfc/rfc5256.html)): `THREAD=REFERENCES` is literally formalized JWZ + subject fallback; `THREAD=ORDEREDSUBJECT` is "poor man's threading." Dovecot/Cyrus support it — server-side threading saves shipping every header to the client, but don't require it.
- **`THREAD=REFS` / `SEARCH=INTHREAD`:** [`draft-ietf-morg-inthread-01`](https://datatracker.ietf.org/doc/draft-ietf-morg-inthread/) is **expired and dead** — never became an RFC — though Dovecot implements `THREAD=REFS` (subject-blind threading). Treat as optional.
- **Gmail:** `X-GM-THRID` FETCH attribute returns the 64-bit thread ID matching the web/API `threadId`; also `X-GM-MSGID`, `X-GM-LABELS` ([Google IMAP extensions](https://developers.google.com/gmail/imap/imap-extensions)). Use it when present — it matches Gmail's own grouping including subject-changed merges.
- **Exchange:** conversations are `ConversationId` + `ConversationTopic` + `ConversationIndex` in EWS/Graph ([Microsoft Learn](https://learn.microsoft.com/en-us/exchange/client-developer/exchange-web-services/how-to-work-with-conversations-by-using-ews-in-exchange)); over IMAP the same data rides the `Thread-Topic`/`Thread-Index` headers — parse `Thread-Index` (base64 blob encoding parent chains with timestamps) to recover threading when `References` is stripped.
- **Fallbacks:** normalized subject ("Re:/Fwd:" prefixes in many languages — Aw:, Sv:, VS:, WG:, Odp:, απ:, etc.), sender/date clustering windows, and merging drafts with their thread. Keep provider thread IDs as hints, not ground truth — users move messages between folders and accounts.

### 2.5 Sending (Q5)

- **Submission:** message submission on 587 with STARTTLS per [RFC 6409](https://www.rfc-editor.org/rfc/rfc6409.html)/[RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html); **implicit TLS on 465 ("submissions") is preferred where offered** per [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html), which also recommends implicit TLS for IMAP (993) and POP3 (995). Never send credentials before TLS is up.
- **DSN:** request delivery status with `NOTIFY=` and `ENVID`/`RET` per [RFC 3461](https://www.rfc-editor.org/rfc/rfc3461.html); parse `message/delivery-status` per [RFC 3464](https://www.rfc-editor.org/rfc/rfc3464.html). Sparse server support — nice-to-have.
- **Sent-folder semantics (get this wrong and users get duplicates):** Gmail automatically copies SMTP-submitted mail to `[Gmail]/Sent Mail` — Google's own IMAP guidance says "don't save sent messages on the server" ([Gmail Help](https://support.google.com/mail/answer/78892)). Microsoft 365 SMTP AUTH client submission likewise saves to Sent Items ([Microsoft Learn](https://learn.microsoft.com/en-us/Exchange/mail-flow-best-practices/how-to-set-up-a-multifunction-device-or-application-to-send-email-using-microsoft-365-or-office-365) — "Saves to Sent Items folder: Yes" for client SMTP submission), a duplicate-generator Thunderbird has an open bug about ([Bugzilla 1431562](https://bugzilla.mozilla.org/show_bug.cgi?id=1431562)). Rule: maintain a per-provider "server saves sent" flag (from autoconfig heuristics/hostname), else `APPEND` to the `\Sent` SPECIAL-USE folder ([RFC 6154](https://www.rfc-editor.org/rfc/rfc6154.html)) yourself.
- **BURL:** [RFC 4468](https://www.rfc-editor.org/rfc/rfc4468.html) + Lemonade profile [RFC 4550](https://www.rfc-editor.org/rfc/rfc4550.html) (with `CATENATE` [RFC 4469](https://www.rfc-editor.org/rfc/rfc4469.html)/`URLAUTH` [RFC 4467](https://www.rfc-editor.org/rfc/rfc4467.html)) enables forward-as-attachment without download — elegant, rarely deployed; opportunistic only.
- **Send later:** `FUTURERELEASE` ([RFC 4865](https://www.rfc-editor.org/rfc/rfc4865.html)) exists but is barely deployed; the practical design is a client-side outbox queue (data-safety-critical: survive restarts) and/or stashing drafts in a `\Scheduled` mailbox — a name attribute newly registered by [RFC 9979](https://www.rfc-editor.org/rfc/rfc9979.html) (see §2.7). "Undo send" has no wire standard: implement a client-side send delay (Apple Mail ~10s, Gmail web up to 30s).

### 2.6 Security and trust (Q6)

- **Transport:** TLS 1.2+ (prefer 1.3) everywhere; implicit TLS per RFC 8314 where offered; hard-fail (don't silently downgrade) when account policy says TLS required; pin nothing but do surface certificate errors to the user with real detail. Rust: `rustls` 0.23 + `webpki`, or `native-tls` for platform stores. MTA-STS ([RFC 8461](https://www.rfc-editor.org/rfc/rfc8461.html)) and DANE ([RFC 7672](https://www.rfc-editor.org/rfc/rfc7672.html)) protect *MTA↔MTA* hops — irrelevant to a client that talks to a known MSA/IMAP host; document that and move on.
- **Trust display:** parse `Authentication-Results` ([RFC 8601](https://www.rfc-editor.org/rfc/rfc8601.html)) — but only the topmost instance(s) written by the account's own provider (`authserv-id` match); everything deeper is attacker-controlled decoration. Show SPF/DKIM ([RFC 6376](https://www.rfc-editor.org/rfc/rfc6376.html), with [RFC 8301](https://www.rfc-editor.org/rfc/rfc8301.html) sha1-deprecation and Ed25519 [RFC 8463](https://www.rfc-editor.org/rfc/rfc8463.html))/DMARC ([RFC 7489](https://www.rfc-editor.org/rfc/rfc7489.html)) verdicts and ARC ([RFC 8617](https://www.rfc-editor.org/rfc/rfc8617.html)) chains for forwarded mail.
- **BIMI:** Gmail displays logo+checkmark for VMC and logo-only for CMC (announced Sep 24, 2024 — [Google Workspace Updates](https://workspaceupdates.googleblog.com/2024/09/gmail-additional-bimi-protections.html)) and requires DMARC enforcement. **Apple Mail shows BIMI logos only when the mail *provider* is on Apple's verified list and injects `BIMI-Indicator`/evidence headers** — iCloud gets them; Gmail-sourced mail in Apple Mail does not ([Apple Developer](https://developer.apple.com/support/bimi/), [letsbimi](https://letsbimi.com/docs/apple-mail)). A third-party client that does its own BIMI record lookup + DMARC-enforcement check + VMC/CMC chain validation + SVG Tiny-PS profile check would therefore show logos Apple Mail can't — but that's real work; phase 1 = honor provider-asserted BIMI headers.
- **E2EE:** OpenPGP is now [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html); Autocrypt Level 1.1 (Jan 2019, [spec](https://docs.autocrypt.org/level1.html)) automates key distribution via headers — implemented in Delta Chat (full), K-9, Mutt/Neomutt; Thunderbird is partial (sends/receives headers, requires user approval to accept keys — [status table](https://docs.autocrypt.org/dev-status.html)). Rust libraries: `pgp` (rPGP) 0.21.0 — Apache-2.0/MIT, used by Delta Chat, actively maintained (updated Oct 3, 2026) — vs `sequoia-openpgp` 2.4.1 — LGPL-2.0-or-later, the reference-quality implementation with RFC 9580/crypto-refresh coverage. S/MIME: RFC 8551 + CMS [RFC 5652](https://www.rfc-editor.org/rfc/rfc5652.html); verification against platform trust stores is the sane default on macOS.
- **Proton:** Proton Mail Bridge is open source ([github.com/ProtonMail/proton-bridge](https://github.com/ProtonMail/proton-bridge), paid plans only) — a localhost IMAP/SMTP server backed by their Gluon IMAP library and `go-proton-api`. Sweetbriar interop path 1 = treat Bridge as a normal account; path 2 (later) = implement the Proton API directly with `pgp`/rPGP for crypto (Proton's own clients use OpenPGP.js/gopenpgp).

### 2.7 Productivity standards (Q7)

- **Unsubscribe:** `List-Unsubscribe` ([RFC 2369](https://www.rfc-editor.org/rfc/rfc2369.html)) + one-click `List-Unsubscribe-Post: List-Unsubscribe=One-Click` ([RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html)). Since Feb 1, 2024 Gmail requires bulk senders (>5,000/day) to have SPF+DKIM+DMARC and one-click unsubscribe for marketing/subscribed mail, spam rate <0.3%, unsubscribe honored in 48h ([Gmail sender guidelines](https://support.google.com/mail/answer/81126)). UI rule: offer the button, prefer the HTTPS POST, fall back to `mailto:`; never auto-fire.
- **Calendar interop:** iMIP — `text/calendar; method=…` MIME parts ([RFC 6047](https://www.rfc-editor.org/rfc/rfc6047.html)) carrying iTIP ([RFC 5546](https://www.rfc-editor.org/rfc/rfc5546.html)) REQUEST/REPLY/CANCEL/COUNTER; render a banner with RSVP buttons, track `SEQUENCE` bumps, and write back REPLYs. CalDAV ([RFC 4791](https://www.rfc-editor.org/rfc/rfc4791.html)) + scheduling ([RFC 6638](https://www.rfc-editor.org/rfc/rfc6638.html)) and CardDAV ([RFC 6352](https://www.rfc-editor.org/rfc/rfc6352.html)) are the open-protocol companions — iCloud and Fastmail support both; Yahoo's hub offers CalDAV/CardDAV under the same OAuth access program.
- **Sieve:** base [RFC 5228](https://www.rfc-editor.org/rfc/rfc5228.html) (+ `fileinto`, `reject`/`ereject`, `envelope`); the extensions that matter in the wild: `vacation` [RFC 5230](https://www.rfc-editor.org/rfc/rfc5230.html), `imap4flags` [RFC 5232](https://www.rfc-editor.org/rfc/rfc5232.html), `subaddress` [RFC 5233](https://www.rfc-editor.org/rfc/rfc5233.html), `variables` [RFC 5229](https://www.rfc-editor.org/rfc/rfc5229.html), `body` [RFC 5173](https://www.rfc-editor.org/rfc/rfc5173.html), `editheader` [RFC 5293](https://www.rfc-editor.org/rfc/rfc5293.html), `regex` (expired draft, Dovecot-deployed), `include` [RFC 6609](https://www.rfc-editor.org/rfc/rfc6609.html), `duplicate` [RFC 7352](https://www.rfc-editor.org/rfc/rfc7352.html), `imapsieve` [RFC 6785](https://www.rfc-editor.org/rfc/rfc6785.html), `spamtest`/`virustest` [RFC 3685](https://www.rfc-editor.org/rfc/rfc3685.html), `vacation-seconds` [RFC 6131](https://www.rfc-editor.org/rfc/rfc6131.html). Management is **ManageSieve** ([RFC 5804](https://www.rfc-editor.org/rfc/rfc5804.html)), port 4190, implemented by Dovecot Pigeonhole and Cyrus ([Dovecot docs](https://doc.dovecot.org/main/core/config/sieve/managesieve.html)) and exposed by providers such as mailbox.org (Fastmail runs Cyrus with a Sieve editor in its web UI; external ManageSieve access there is unverified) — but **not** by Gmail (API filters) or Exchange (Inbox rules via EWS/Graph). A Sieve editor + ManageSieve client in Sweetbriar instantly gives power users cross-provider server-side rules.
- **IMAP METADATA/annotations:** `METADATA`/`METADATA-SERVER` ([RFC 5464](https://www.rfc-editor.org/rfc/rfc5464.html)) for mailbox/server annotations (Cyrus, some Dovecot), and the older `ANNOTATE-EXPERIMENT-1` ([RFC 5257](https://www.rfc-editor.org/rfc/rfc5257.html)) for per-message annotations. Useful for syncing Sweetbriar's own per-mailbox settings where offered; expect most providers to lack it.
- **Keywords & flags:** the [IANA IMAP/JMAP keywords registry](https://www.iana.org/assignments/imap-jmap-keywords) lists `$MDNSent` (RFC 3503), `$Forwarded`/`$Submitted`/`$SubmitPending` (RFC 5550), `$Junk`/`$NotJunk` (registered by A. Melnikov — mutually exclusive; clients must clear both if both set, per the [registry notes](https://www.iana.org/assignments/imap-jmap-keywords/junk/junk-template)), `$Phishing` (show a warning when combined with `$Junk`), `$Important` (RFC 8457). **RFC 9979** ("Registration of Further IMAP/JMAP Keywords…", Informational, 2026 — Jenkins & Eggert) formalizes 17 more: `$MailFlagBit0/1/2` (Apple colors), `$hasattachment`/`$hasnoattachment`, `$muted`, `$notify`, `$autosent`, `$canunsubscribe`, `$unsubscribed`, `$memo`, `$hasmemo`, `$maskedemail`, `$imported`, `$istrusted`, `$followed`, `$new`, plus mailbox attributes `\Memos`, `\Scheduled`, `\Snoozed` ([RFC 9979](https://www.rfc-editor.org/rfc/rfc9979.html)).
- **Apple Mail color flags:** 7 colors encoded as a 3-bit value in `$MailFlagBit0/1/2` on top of `\Flagged` — none=red, Bit0=orange, Bit1=yellow, Bit0+1=green, Bit2=blue, Bit0+2=purple, Bit1+2=gray (all three set is unassigned) — long reverse-engineered ([MailMate list](https://mailmate.freron.narkive.com/KyNEBpjZ/mlmt-flags-tags-colours), [Mozilla Connect](https://connect.mozilla.org/t5/ideas/support-for-apple-multicoloured-flags/idi-p/91440)) and now canonically specified in RFC 9979 §3, which also mandates clearing the bits when unflagging and says flagless `$MailFlagBit`s MUST be ignored.
- **MDN read receipts:** [RFC 8098](https://www.rfc-editor.org/rfc/rfc8098.html) (`Disposition-Notification-To` + `message/disposition-notification`). Policy: never auto-send (privacy), offer per-message/per-sender opt-in, and honor `$MDNSent` for state. Apple Mail has no MDN UI (unverified but long-observed) — interop asymmetry is normal.
- **Junk reporting:** store `$Junk`/`$NotJunk` keywords, move to `\Junk` SPECIAL-USE mailbox; Gmail maps spam to the `[Gmail]/Spam` label/folder.

### 2.8 The IMAP sync substrate (context for all of the above)

Data safety ("never lose mail") is mostly IMAP4rev2 [RFC 9051](https://www.rfc-editor.org/rfc/rfc9051.html) (Aug 2021, obsoletes 3501) hygiene: `UIDVALIDITY`/`HIGHESTMODSEQ` tracking, `CONDSTORE`+`QRESYNC` ([RFC 7162](https://www.rfc-editor.org/rfc/rfc7162.html)) for single-round-trip resync including `VANISHED`, `ENABLE`, `LIST-EXTENDED`, `LIST-STATUS`, `SPECIAL-USE`, `MOVE` (RFC 6851), `UIDPLUS` (RFC 4315) for APPENDUID/COPYUID, `ESEARCH` (RFC 4731), `IDLE` (RFC 2177), `NAMESPACE` (RFC 2342), `ID` (RFC 2971), `LITERAL+/-` (RFC 7888), `SASL-IR`, `UTF8=ACCEPT`. Get the local-store ↔ server reconciliation right here and drafts/settings follow for free.

### 4.2 Recommendations

1. **Discovery**: implement the full chain — known-provider shortcuts (Gmail/M365/Yahoo/iCloud/Fastmail by MX *and* domain) → Autodiscover V1 → ISPDB → `autoconfig.<domain>`/`.well-known` → SRV → hostname guessing → manual. Cache outcomes per-domain. *Trade-off:* it's a lot of code; the counter-argument is "just use ISPDB + guessing like Thunderbird" — defensible, but Thunderbird famously fails on Exchange corporate mail, which is exactly the audience that pays.
2. **Auth**: OAuth via `ASWebAuthenticationSession` + reverse-domain custom scheme (loopback fallback), PKCE, Keychain token store; register client IDs with Google (start the restricted-scope verification early — it's the long pole), Microsoft (multi-tenant Entra app), and apply for Yahoo access on day one. Keep app-password flow as first-class UI for iCloud/Fastmail/Yahoo fallback. *Counter-argument:* skip OAuth entirely and standardize on app passwords — simpler, no verification costs; but Google pushes users away from app passwords, Workspace admins can disable them, and OAuth is the only path that survives provider policy drift.
3. **MIME**: build on `mail-parser` (Stalwart) rather than `mailparse` or hand-rolling; layer `encoding_rs`+`chardetng` charset repair, a TNEF decoder (from the [MS-OXTNEF] spec — write it, it's ~2k lines), and first-class handling of crypto MIME types. *Counter-argument:* vendor and own the parser entirely — an email parser is a correctness-critical, fuzzable surface; owning it is a legitimate long-term call, but `mail-parser` is already hardened at Stalwart scale.
4. **Threading**: JWZ locally (works everywhere, offline), upgrade with `X-GM-THRID` and `Thread-Index`/`ConversationIndex` parsing where present; skip server `THREAD=` except as an optimization.
5. **Sending**: prefer 465 implicit TLS, fall back to 587 STARTTLS; maintain the provider "saves-sent" table; support DSN request; build the outbox/undo-send/send-later queue client-side; opportunistic BURL.
6. **Trust**: parse own-provider `Authentication-Results`, display SPF/DKIM/DMARC verdicts and `$Phishing` warnings; show provider-asserted BIMI now, client-verified BIMI later. *Counter-argument:* security-UI in mail clients has a terrible track record of being ignored/misleading (Gmail's own auth icons are muted) — keep it factual and off-by-default for power users.
7. **Flags**: full Apple `$MailFlagBit*` color support per RFC 9979 at launch — a cheap, visible interop win for Mac users; plus `$Junk`/`$NotJunk`/`$Forwarded`/`$MDNSent`/`$Phishing`.
8. **Crypto**: PGP read+verify+decrypt first (rPGP for license simplicity), S/MIME verify via platform trust, Autocrypt headers in+out. Full key management later — and if PGP becomes a headline feature, re-evaluate Sequoia despite the LGPL.
9. **Sieve**: ManageSieve client + Sieve editor (with a guided UI over `fileinto`/`imap4flags`/`vacation`/`regex`) soon after launch — this *is* the "server-side rules" answer for every non-Gmail/Exchange account.
10. **macOS 27**: nothing found in the [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) or [support notes](https://support.apple.com/en-us/127257) that breaks third-party mail clients; relevant platform APIs (ASWebAuthenticationSession, Keychain, MailKit) are unchanged. Mail.app itself got "better search" and a Smart-Mailbox fix — a hint that Apple is still investing in Mail, so compete on plumbing.

## 5. Risks and open questions

- **Google restricted-scope verification** (`https://mail.google.com/`) is a real gate: app verification plus a possible annual third-party security assessment (CASA; a free tier exists for qualifying apps). Start months before launch; have app-password + Gmail-API fallback plans. ([Google FAQ](https://support.google.com/cloud/answer/13463817?hl=en))
- **Yahoo OAuth is invite-only.** Until approved, Yahoo users need app passwords — build the UX so this isn't a dead end.
- **iCloud has no third-party OAuth**; app-specific passwords are the only route (the "supported apps may use your Apple Account" carve-out is not publicly documented — open question whether a new client can get on it).
- **Microsoft SMTP AUTH basic-auth sunset keeps moving** (now: default-off end of 2026, removal TBD 2027) — supporting OAuth makes this moot, but on-prem Exchange remains password/NTLM country; keep `PLAIN`+TLS support.
- **`draft-ietf-mailmaint-autoconfig` is mid-revision** post-WGLC; implement the deployed format now, track the draft.
- **TNEF/Autodiscover-V2/`prod-autodetect` are Microsoft-undocumented surfaces** — they work today, could shift tomorrow; isolate behind provider adapters.
- **RFC 9979 is brand new** — servers won't set `$hasattachment`/`$muted` etc. for you; treat as client-writable conventions with graceful fallback.
- **Open**: does `imap.mail.me.com` still accept app-specific passwords on macOS 27-era accounts (yes per current Apple docs, verified 2026-10-11); whether Exchange Online's on-behalf "send" quirks affect Sent-folder detection on shared mailboxes (unverified); how strictly Google enforces its "minimum scope" policy for IMAP-using apps at re-verification (the FAQ pushes SMTP-only apps to `gmail.send` — full IMAP+SMTP clients are the intended users of the broad scope, but this deserves confirmation with the verification team).
- **Open**: whether Apple exposes any third-party path to iCloud Mail OAuth via the "supported third-party apps" mechanism mentioned in [HT204397](https://support.apple.com/en-us/102654).
