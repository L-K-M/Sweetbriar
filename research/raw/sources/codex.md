# Sweetbriar: supporting non-standard email sources

Research date: **2026-10-11**. Unless a publication or effective date is stated, provider policies, prices, and implementation status below were checked on this date. Recommendations are identified as judgments; unresolved evidence or permission questions are marked **(unverified)**.

## 1. TL;DR

- **Build direct, independent protocol backends behind one durable Rust store.** Recommendation: IMAP/SMTP for breadth, Graph for Microsoft cloud accounts, Gmail API for Gmail, and JMAP as both an implementation target and a useful modeling reference.
- **Do not launch Exchange Online support on EWS.** Microsoft documents worldwide allow-list enforcement from **2026-10-10**; permanent shutdown is **2027-04-01**, with no extensions beyond April. On-premises Exchange is outside this retirement. [October rollout](https://techcommunity.microsoft.com/blog/exchange/ews-deprecation-is-here-%E2%80%93-what-this-means-to-you/4561431), [final deadline](https://techcommunity.microsoft.com/blog/exchange/exchange-online-ews-your-time-is-almost-up/4492361)
- **Treat Microsoft administrator consent as a product requirement.** Its current managed consent policies restrict mail access and explicitly accommodate selected established clients. Publisher verification alone does not put Sweetbriar on that list. [Consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies)
- **Gmail IMAP is not an OAuth-policy escape hatch.** Its full-mail scope is restricted; verification and, when server handling applies, security assessment obligations remain. [Google verification FAQ](https://support.google.com/cloud/answer/13463817?hl=en), [restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)
- **Budget using current Gmail quotas.** Sweetbriar is a new project, so the documented limits are **6,000 units/user/minute**, **1,200,000/project/minute**, and an **80,000,000-unit daily billing threshold**, not legacy quota assumptions. [Gmail quotas](https://developers.google.com/workspace/gmail/api/reference/quota)
- **Default to desktop polling for Graph and Gmail API.** Graph webhooks need a public HTTPS endpoint; Google explicitly recommends polling for installed apps. Recommendation: make any future notification service optional. [Graph webhooks](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks), [Gmail push](https://developers.google.com/workspace/gmail/api/guides/push)
- **Proton has a public Rust core.** Recommendation: ship Bridge support first while resolving direct-service authorization and licensing. [Rust client bindings](https://raw.githubusercontent.com/ProtonMail/clients/main/project/mail/rust/mail-uniffi/Cargo.toml), [Proton terms](https://proton.me/legal/terms)
- **JMAP is an excellent reference backend.** Contacts have a final RFC; calendars remain a draft dated **2026-10-05**. [Contacts](https://www.rfc-editor.org/rfc/rfc9610.html), [calendar status](https://datatracker.ietf.org/doc/draft-ietf-jmap-calendars/)
- **Tuta and HEY need archive workflows today.** Tuta’s Thunderbird add-on is a web-app tab; HEY offers MBOX export rather than IMAP/POP. [Tuta add-on](https://tuta.com/blog/tuta-add-on-in-thunderbird), [HEY access/export](https://www.hey.com/faqs/)
- **Make safety independent of providers.** Recommendation: durable draft revisions, atomic mail/checkpoint commits, a mutation journal, explicit uncertain-send handling, restorable backups, and a rebuildable local search index.

## 2. Findings

### Microsoft

#### EWS: the exact current retirement sequence

Microsoft’s **2026-10-01** announcement, updated **2026-10-02**, gives this worldwide multi-tenant cloud sequence: snapshot tenants with `EWSEnabled=True` and no `EWSAllowedAppIDs` by **October 2, end of day Pacific Time**; populate their lists on **October 8–9, end of day Pacific Time**, using preceding 60-day activity; require a list for `True` from **October 10**. Administrators enabling EWS after the snapshot populate their own lists. Other clouds get separate Message Center timelines. [Current rollout announcement](https://techcommunity.microsoft.com/blog/exchange/ews-deprecation-is-here-%E2%80%93-what-this-means-to-you/4561431)

The next phase selects worldwide `EWSEnabled=Null` tenants without lists: **seven days’ warning**, list population, then `False`. Administrators can temporarily restore `True` with a list. Application-ID `EWSAllowedAppIDs` differs from user-agent `EWSAllowList`; list changes take **24 hours**, and `EWSEnabled` changes typically under **one hour**, potentially **four**. [Current rollout announcement](https://techcommunity.microsoft.com/blog/exchange/ews-deprecation-is-here-%E2%80%93-what-this-means-to-you/4561431)

The final, permanent Exchange Online shutdown starts **2027-04-01**. Administrators lose the ability to override `EWSEnabled`; Microsoft explicitly rules out exceptions beyond April 2027. The policy covers Microsoft 365/Exchange Online, including Microsoft’s own applications. EWS **is not being retired on-premises**: Exchange Server Subscription Edition remains a separate EWS target. Hybrid coexistence calls to cloud mailboxes must migrate; Exchange SE’s ability to call Graph does not make every on-premises mailbox available through the cloud Graph mail API. [Final shutdown and on-premises FAQ](https://techcommunity.microsoft.com/blog/exchange/exchange-online-ews-your-time-is-almost-up/4492361), [hybrid clarification](https://techcommunity.microsoft.com/blog/exchange/introducing-ewsallowedappids-preparing-for-the-final-phase-of-ews-retirement/4529471)

A separate planned EWS restriction for Kiosk/Frontline licenses was withdrawn in the **2026-09-22** update; those accounts follow the general retirement schedule, rather than receiving an extension. [Kiosk/Frontline update](https://techcommunity.microsoft.com/blog/exchange/update-to-ews-access-for-kiosk--frontline-worker-licensed-users/4474299/replies/4524064)

Graph parity must be evaluated feature by feature. Microsoft’s roadmap, updated **2026-09-04**, still targets **Q4 2026** for archive CRUD, several import/export scenarios, and non-draft MIME creation/update. These are estimates. Generic public-folder CRUD and generic Microsoft 365 Group-mailbox CRUD are explicitly excluded; group conversation APIs are a different interface. Recommendation: document these gaps in the account’s capabilities instead of treating Graph as identical to EWS. [EWS replacement roadmap](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-ews-exchange-online)

#### Graph mail: a practical desktop implementation

| Requirement | Verified API behavior and Sweetbriar implication |
|---|---|
| Incremental sync | Folder hierarchy uses `mailFolders/delta`; messages use **per-folder** `messages/delta`. Follow opaque `@odata.nextLink` values until `@odata.deltaLink`, then retain the complete URL. Message delta supports selected properties, but not `$search`. Maintain separate folder and message cursors. [Folder delta](https://learn.microsoft.com/en-us/graph/api/mailfolder-delta?view=graph-rest-1.0), [message delta](https://learn.microsoft.com/en-us/graph/delta-query-messages) |
| Identity across moves | Ordinary message IDs change on moves. Send `Prefer: IdType="ImmutableId"` on each relevant request, including subscriptions. These IDs survive moves within one mailbox, but not moves into an archive mailbox or export/reimport. Namespace IDs by mailbox. [Immutable IDs](https://learn.microsoft.com/en-us/graph/outlook-immutable-id) |
| MIME | `GET /users/{user}/messages/{id}/$value` retrieves MIME. Keep this representation alongside structured metadata and record its source; do not assume it is a byte-identical copy of the original SMTP transaction. [MIME access](https://learn.microsoft.com/en-us/graph/outlook-get-mime-message) |
| Sending | `POST /me/sendMail` accepts JSON or base64 MIME; alternatively create and send a draft. `Mail.ReadWrite` does **not** include sending permission: request `Mail.Send`. A `202 Accepted` response acknowledges acceptance, not completed delivery. Retain the local send record and reconcile Sent Items. [Send API](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0), [permissions](https://learn.microsoft.com/en-us/graph/permissions-reference) |
| Attachments | Below **3 MB**, use the attachment POST; **3–150 MB**, create an upload session and PUT ordered byte ranges. Microsoft’s guide recommends ranges below **4 MB** and warns of a known large-attachment issue in shared/delegated mailboxes. API upload limits do not guarantee that tenant transport policy accepts the message. [Large attachments](https://learn.microsoft.com/en-us/graph/outlook-large-attachments) |
| Search | Message `$search` accepts KQL-style properties and returns at most **1,000 results**. `/search/query` searches bodies and supported attachments for work/school accounts, limited to the signed-in user’s mailbox; delegated mailboxes are excluded. Recommendation: offer server search as a supplement to a complete local index. [Message search parameter](https://learn.microsoft.com/en-us/graph/search-query-parameter), [Microsoft Search limitations](https://learn.microsoft.com/en-us/graph/search-concept-messages) |
| Categories | A user’s master category list has names and colors; messages can have several categories. Model these separately from folder membership. [Category resource](https://learn.microsoft.com/en-us/graph/api/resources/outlookcategory?view=graph-rest-1.0) |
| Focused Inbox | A message’s `inferenceClassification` is `focused` or `other`; sender overrides affect future classification. Preserve the distinction without making it a universal importance flag. [Organization and Focused Inbox](https://learn.microsoft.com/en-us/graph/outlook-organize-messages) |
| Rules | `mailFolders/inbox/messageRules` exposes incoming rules, conditions, actions, exceptions, and execution sequence. Respect `isReadOnly`; not every existing Outlook rule is editable through this API. [Rule resource](https://learn.microsoft.com/en-us/graph/api/resources/messagerule?view=graph-rest-1.0) |

Graph webhooks require a **publicly reachable HTTPS endpoint**, including subscription validation. A laptop’s OAuth loopback callback is not such an endpoint. Azure Event Hubs and Event Grid are alternative cloud delivery mechanisms, not free desktop notification transports. Basic Outlook subscriptions last under **seven days**; subscriptions carrying resource data last under **one day**. Recommendation: initially poll delta queries with adaptive intervals and immediate refresh on activation/network recovery; consider a minimal notification relay only after privacy, cost, and consent review. [Webhook requirements](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks), [Event Hubs](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-event-hubs), [subscription lifetimes](https://learn.microsoft.com/en-us/graph/change-notifications-overview)

Shared/delegated mail is supported with `Mail.Read.Shared` or `Mail.ReadWrite.Shared` and the user’s actual mailbox permissions. Sending as another mailbox needs `Mail.Send.Shared` and Exchange Send As/Send on Behalf rights. Those delegated read scopes **cannot subscribe to shared-mailbox notifications**; the documented notification alternative uses application `Mail.Read`, which changes the deployment/consent model. Recommendation: keep shared mailboxes as separate storage/sync namespaces under one authorization principal and use polling for the desktop path. [Shared mail access](https://learn.microsoft.com/en-us/graph/outlook-share-messages-folders), [sending from another user](https://learn.microsoft.com/en-us/graph/outlook-send-mail-from-other-user)

Current Outlook throttling is per **app-ID/mailbox combination**: **10,000 requests per 10 minutes**, **four concurrent requests**, and **150 MB uploaded per five minutes**. Batching does not remove those limits. Implement mailbox-aware concurrency, jittered backoff, and `Retry-After`; prioritize new mail and sends above historical body downloads. [Service limits](https://learn.microsoft.com/en-us/graph/throttling-limits), [throttling guidance](https://learn.microsoft.com/en-us/graph/throttling)

#### Microsoft standard protocols and app approval

Microsoft documents OAuth 2.0 for IMAP, POP, and SMTP AUTH for both Microsoft 365 and Outlook.com. Delegated scope examples are `https://outlook.office.com/IMAP.AccessAsUser.All`, `https://outlook.office.com/POP.AccessAsUser.All`, and `https://outlook.office.com/SMTP.Send`; `offline_access` obtains refresh-token access. Protocol authentication uses SASL XOAUTH2. Receiving and sending are independently authorized capabilities. [Microsoft OAuth protocol guide](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)

An administrator can disable IMAP/POP per mailbox. SMTP AUTH has tenant and mailbox controls and is disabled when Security Defaults applies, so OAuth does not guarantee availability. Recommendation: prefer Graph for Exchange Online rather than requiring an enterprise to relax these controls. Outlook.com separately requires OAuth2, has POP/IMAP disabled by default, and retired basic authentication on **2024-09-16**. [Exchange app controls](https://learn.microsoft.com/en-us/Exchange/recipients-in-exchange-online/manage-user-mailboxes/managing-email-apps-for-user-mailboxes), [SMTP AUTH controls](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/authenticated-client-smtp-submission), [Outlook.com settings](https://support.microsoft.com/en-us/outlook/pop-imap-and-smtp-settings-for-outlook-com), [consumer retirement](https://support.microsoft.com/en-us/support/known-issues/modern-authentication-methods-now-needed-to-continue-syncing-outlook-email-in-non-microsoft-email-ap)

The **2026-01-27** announcement, updated **January 29**, replaced the old SMTP AUTH basic-auth shutdown schedule. Behavior remains unchanged through December 2026; at the **end of December 2026**, basic auth is disabled by default for existing tenants but administrators may re-enable it. Tenants created after December get OAuth as the supported default. Microsoft will announce a final removal date in the **second half of 2027**; there is no verified final hard-stop date today. This is a basic-auth retirement, not retirement of OAuth SMTP AUTH. [Current SMTP timeline](https://techcommunity.microsoft.com/blog/exchange/updated-exchange-online-smtp-auth-basic-authentication-deprecation-timeline/4489835)

Register Sweetbriar as a native/public-client Entra application supporting organizational accounts and personal Microsoft accounts if both markets are intended. Use authorization-code flow with PKCE, without embedding a confidential client secret. Recommendation: start with delegated `Mail.ReadWrite` and `Mail.Send`, then request mailbox settings/shared-mail permissions only when a feature needs them. [Registration](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-register-app), [authorization code and PKCE](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [permission definitions](https://learn.microsoft.com/en-us/graph/permissions-reference)

Publisher verification associates a verified Microsoft partner identity with the registration. It helps establish publisher identity; it does not certify the app or override tenant policy. As checked **2026-10-11**, Microsoft’s managed recommended consent policy excludes many mail scopes from ordinary end-user consent, while a separate default policy permits named clients including Apple Mail, Spark, eM Client, and Thunderbird. **Sweetbriar is not listed.** Provide an administrator onboarding document, exact client ID/scopes, privacy/data-flow diagram, and actionable consent errors. Even customer-owned registrations cannot override Conditional Access or organizational prohibitions. [Publisher verification](https://learn.microsoft.com/en-us/entra/identity-platform/publisher-verification-overview), [current consent policies](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies)

#### ActiveSync, Thunderbird, and gateways

**Exchange ActiveSync is licensable**, including by application developers and service providers, according to Microsoft’s current licensing program. That is not permission to implement it without a license. Public royalty amounts and a desktop-specific Sweetbriar agreement are **(unverified)**. Recommendation: request written terms only if a concrete customer need survives Graph/EWS comparison; do not make EAS the default Microsoft backend. Its mobile-device policy surface also requires a deliberate product decision. [Microsoft technology licensing](https://www.microsoft.com/en-us/legal/intellectualproperty/tech-licensing/programs)

Thunderbird described its **Rust EWS implementation on 2024-04-19**, integrating with its existing C++/XPCOM application. EWS email support shipped in **Thunderbird 145 in 2025**; its **2025-12-11** retrospective explicitly excluded calendar/contact support at launch. The important current update is **2026-09-23**: Thunderbird reports its Graph email implementation completed and Graph calendar work underway. This verifies implementation progress, not which stable release contains every feature. Sweetbriar should study that boundary rather than imitate last year’s protocol choice. [Rust implementation](https://blog.thunderbird.net/2024/04/adventures-in-rust-bringing-exchange-support-to-thunderbird/), [145 retrospective](https://blog.thunderbird.net/2025/12/video-exchange-email-support/), [September 2026 status](https://blog.thunderbird.net/2026/09/thunderbird-monthly-development-digest-september-2026/)

DavMail exposes POP/IMAP/SMTP, CalDAV/CardDAV, and LDAP in front of Exchange. As checked **2026-10-11**, its official site lists **7.0.0**, and its roadmap identifies new Graph support in that version. Thus it is no longer accurate to describe DavMail as exclusively an EWS gateway. It is Java/GPL-2.0-or-later; operating an independent local gateway is different from incorporating its code. Recommendation: support it through generic account configuration, but verify the selected Graph/EWS mode and feature coverage. An EWS-mode gateway cannot evade Exchange Online retirement. [DavMail](https://davmail.sourceforge.net/), [Graph roadmap](https://davmail.sourceforge.net/roadmap.html), [source/license](https://davmail.sourceforge.net/xref/davmail/exchange/graph/GraphField.html)

### Google

#### Gmail API versus Gmail IMAP

Gmail’s API exposes message/thread IDs, labels, history, drafts, and raw MIME without projecting the account into conventional folders. Labels have a many-to-many relationship with messages; thread labels are the union of labels on existing messages, and future arrivals do not inherit a thread-label operation. Preserve message-level memberships. Archive means removing `INBOX`; trash, deleting permanently, and removing an ordinary label must remain distinct operations. [Label semantics](https://developers.google.com/workspace/gmail/api/guides/labels)

IMAP remains useful through `X-GM-EXT-1`: `X-GM-MSGID` provides cross-folder identity, `X-GM-THRID` provider threading, `X-GM-LABELS` labels, and `X-GM-RAW` Gmail search syntax. The numeric message/thread IDs are unsigned 64-bit decimal equivalents of Gmail API hexadecimal IDs. Do not download another full body each time the same message appears under another label. Discover current capabilities; Google’s old `XLIST` extension is deprecated in favor of standard SPECIAL-USE. [Gmail IMAP extensions](https://developers.google.com/workspace/gmail/imap/imap-extensions)

Gmail API `messages.list`/`threads.list` accept `q`, but search is not identical to the web UI: the API does not perform the same alias expansion or thread-wide searching. Date queries use PST midnight unless epoch seconds are supplied. `messages.get(format=RAW)` supplies base64url RFC message content. Recommendation: use API-native IDs and labels, raw MIME for local storage, and a local query language whose completeness does not depend on Google’s search differences. [API search](https://developers.google.com/workspace/gmail/api/guides/filtering), [message retrieval](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get)

#### OAuth, CASA, and cost

`gmail.readonly`, `gmail.modify`, `gmail.compose`, and `https://mail.google.com/` are **restricted** scopes; `gmail.send` is **sensitive**. Google requires a public app’s restricted-scope verification unless an applicable exception exists. The full-mail IMAP/POP/SMTP scope also requires verification; Google’s FAQ says it must be justified by functionality needing permanent deletion outside Trash, and SMTP-only apps should use the narrower Gmail send API. Choosing IMAP does not bypass these requirements. [Scope classifications](https://developers.google.com/workspace/gmail/api/auth/scopes), [IMAP/SMTP verification FAQ](https://support.google.com/cloud/answer/13463817?hl=en)

Google’s detailed policy requires an independent security assessment where an app can access restricted data **from or through a third-party server**. Scope verification and security assessment are different gates. **Recommendation/inference:** a strictly device-local Sweetbriar implementation, communicating directly with Google and keeping mail, tokens, drafts, and search local, is the strongest case for avoiding the server-data assessment requirement. Obtain Google’s determination during verification; do not promise an exemption merely because the UI is native. A cloud sync engine, email processing service, diagnostic upload, or notification design handling restricted data can change the assessment boundary. [Restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)

As checked **2026-10-11**, the current CASA framework uses **AL1 and AL2**, both lab-tested/lab-verified; Google assigns the level using risk signals. The former Tier 2 self-scanning page explicitly marks that process deprecated. Annual revalidation remains required; an app validated at AL2 continues at that level in subsequent years. Historical claims of a universally free Tier 2 pathway should not be used as a launch budget. [Current assurance levels](https://appdefensealliance.dev/casa/casa-tiering), [deprecated process](https://appdefensealliance.dev/casa/tier-2/tier2-overview), [Google assessment requirements](https://support.google.com/cloud/answer/13465431?hl=en)

Google does not set or collect an assessment fee: developers negotiate with assessors. One current primary price example, **TAC Security’s page checked 2026-10-11**, lists **US$675** for Basic AL1, **US$855** for Premium AL1, **US$4,500** for Enterprise AL1, and **US$5,400** for Enterprise AL2. These are vendor offers, not universal CASA charges or Sweetbriar quotes. Remediation, assessment scope, and renewal costs need separate confirmation; annual reassessment tests the whole application, not only changed code. [Assessor prices](https://tacsecurity.com/google-casa-cloud-application-security-assessment/), [Google cost and renewal FAQ](https://support.google.com/cloud/answer/13463817?hl=en)

#### Sync, push, and quotas

Use `history.list(startHistoryId=...)` for additions, deletions, and label changes. History normally lasts at least a week, but the documentation explicitly allows shorter retention; an expired cursor returns **HTTP 404** and requires full sync. Persist the history checkpoint with applied changes and reconcile inventories after gaps. [Gmail synchronization](https://developers.google.com/workspace/gmail/api/guides/sync), [history API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list)

`watch` publishes changes to a Cloud Pub/Sub topic in the app’s project. Pub/Sub can push to an HTTPS service or use pull subscriptions, so a public webhook is not the only transport. Watches need renewal at least every **seven days**, with daily renewal recommended; notifications contain an account address and history ID, and changes can be delayed/dropped. Google explicitly recommends polling for installed, user-owned devices. Recommendation: poll history locally first; do not ship a shared service-account secret or expose other users’ notifications to clients. [Gmail push guide](https://developers.google.com/workspace/gmail/api/guides/push)

Google updated quotas effective **2026-05-01**, grandfathering projects that used the API during November 2025–April 2026. Sweetbriar’s new project should budget **1,200,000 units/project/minute** and **6,000 units/user/project/minute**. Current costs include `history.list` **2**, `messages.list` **5**, `messages.get` **20**, and `messages.send`/`watch` **100** units. A simple upper-bound calculation gives **300 message GETs/user/minute** if nothing else consumes quota; this is arithmetic, not a guaranteed throughput. [Current quotas](https://developers.google.com/workspace/gmail/api/reference/quota)

The published daily project threshold is **80,000,000 units**. Standard usage is currently described as free, but Google announces charging above standard thresholds later in 2026 with at least **90 days’ notice**; the pages consulted do not establish a verified final billing start date or unit price. Monitor this before launch. IMAP is also subject to administrator controls and Google’s OAuth policies, so it should not be treated as an unrestricted fallback. [Quota/billing page](https://developers.google.com/workspace/gmail/api/reference/quota), [2026 rollout policy](https://developers.google.com/workspace/tools-safety)

### Proton and Tuta

#### Proton Bridge and direct integration

Proton officially supports conventional desktop clients through **Proton Mail Bridge**, available with paid Mail plans. Bridge runs on macOS, Windows, and Linux, decrypts/encrypts locally, and exposes local IMAP/SMTP; Proton does not offer ordinary remote IMAP/POP access. Recommendation: implement a Bridge account preset over the normal IMAP/SMTP driver, using Bridge-generated credentials and a narrowly scoped trust decision for its generated self-signed localhost certificate. [Bridge TLS](https://proton.me/support/bridge-ssl-connection-issue) Bridge must be running. Once plaintext enters Sweetbriar, its cache, search index, backups, and drafts need Sweetbriar’s own protection; Proton’s server encryption does not encrypt those files automatically. [Official access/Bridge guide](https://proton.me/support/imap-smtp-and-pop3-setup), [Bridge repository](https://github.com/ProtonMail/proton-bridge)

Bridge’s code is **GPL-3.0-or-later**. [Copying terms](https://raw.githubusercontent.com/ProtonMail/proton-bridge/master/COPYING_NOTES.md) Its Go dependencies include **`go-proton-api`**, the Proton HTTP API client; **`gluon`**, Proton’s IMAP-server implementation; and **GopenPGP**. `go-proton-api` and `gluon` declare MIT licenses. These are distinct components with distinct reuse obligations: an MIT HTTP wrapper neither includes all account cryptography nor grants an API service contract. [Bridge dependencies](https://raw.githubusercontent.com/ProtonMail/proton-bridge/master/go.mod), [API library](https://github.com/ProtonMail/go-proton-api), [Gluon](https://github.com/ProtonMail/gluon)

The premise that Proton has no shared Rust core is now wrong. Proton’s **2026-02-02** article describes its native mobile apps, launched in 2025, sharing roughly **80% of their code** through Rust, including business logic and list/navigation behavior. Public source is also available: the old **`rust-mail`** repository was archived **2026-06-12** and redirects to **`ProtonMail/clients`**. The current `mail-uniffi` package is non-published and explicitly **AGPL-3.0-only**, with action-queue, account, database, and crypto dependencies. This is inspectable source, not a verified supported third-party SDK distribution. Build completeness and suitability for an independently shipped client remain **(unverified)**. [Native/Rust explanation](https://proton.me/blog/next-generation-proton-mail-mobile-apps), [archived SDK](https://github.com/ProtonMail/rust-mail), [current clients](https://github.com/ProtonMail/clients), [binding manifest/license](https://raw.githubusercontent.com/ProtonMail/clients/main/project/mail/rust/mail/mail-uniffi/Cargo.toml)

Proton’s separate **MIT** `proton-crypto-rs` repository exposes Proton-specific OpenPGP/account crypto, SRP, and device verification. Its default backend uses GopenPGP through `gopenpgp-sys`, requiring Go; the optional pure-Rust backend uses `proton-rpgp` over rpgp. The maintainers expressly do not vet it for general use outside Proton. That warning and the different SDK license matter more than the attractive word “Rust.” [Crypto components and limitations](https://github.com/ProtonMail/proton-crypto-rs)

The current general service terms were modified **2026-10-09**. They restrict credential sharing, unauthorized service access, and automation that deviates from normal human-client behavior or circumvents controls. I found **no verified public third-party Mail API program, support commitment, or explicit permission for Sweetbriar**, and also no verified blanket statement making every direct third-party client forbidden. Therefore, “technically possible,” “source-licensed,” and “service-authorized” must be separate decisions. Recommendation: ship Bridge support; pursue direct access only with Proton’s written agreement and a license/build review. **Strongest counterargument:** the public Rust core could remove Bridge’s paid-plan/setup friction and duplicate processes, making direct support substantially better if Proton cooperates. [Current service terms](https://proton.me/legal/terms)

#### Tuta

Tuta’s support documentation says third-party IMAP/POP/SMTP clients are unsupported. Its **2026-02-18** Thunderbird add-on embeds the **Tuta web app in a Thunderbird tab**; it is not a mail-sync adapter exposing Tuta messages to Thunderbird’s ordinary folders/search. Tuta publishes client code under **GPLv3**, but that does not establish a supported external API or a separate service-access license. [Access limitations](https://tuta.com/support/howto), [what the add-on actually does](https://tuta.com/blog/tuta-add-on-in-thunderbird), [open-source licensing](https://tuta.com/open-source)

Recommendation: do not advertise a native Tuta account backend. Offer verified export/import workflows or open Tuta’s application. A source-derived direct implementation may be technically possible, but API stability, compatibility with its encryption, and contractual permission are **(unverified)** and require vendor discussion. The terms consulted do not resolve a general third-party-client entitlement. **Counterargument:** a cooperative GPL-compatible integration could provide stronger fidelity than exports; that requires an actual supported arrangement. [Tuta terms](https://tuta.com/terms)

### JMAP

**RFC 8620 (July 2019)** defines JMAP Core; **RFC 8621 (August 2019)** defines JMAP Mail. JMAP has discovery/session capabilities, account IDs, opaque state tokens, `get`/`changes`/`set`, query/queryChanges, and separate binary uploads/downloads. Mail supplies stable Email IDs, raw-message blob IDs, mailbox memberships, keywords, threads, and EmailSubmission. This maps well to a shared Rust client without making network JSON the database schema. [JMAP Core](https://www.rfc-editor.org/rfc/rfc8620.html), [JMAP Mail](https://www.rfc-editor.org/rfc/rfc8621.html)

JMAP Core’s EventSource endpoint uses an **outbound server-sent-events connection**; **RFC 8887** adds WebSocket transport. Neither requires Sweetbriar to host a public webhook. Availability is discovered from the server, not assumed. Server-side delayed sending is also conditional: the Mail submission capability advertises `maxDelayedSend`, which is zero when unsupported. `sendAt` is server-set; scheduling uses advertised submission extensions rather than writing an arbitrary timestamp into an Email. [Core push](https://www.rfc-editor.org/rfc/rfc8620.html#section-7.3), [WebSockets](https://www.rfc-editor.org/rfc/rfc8887.html), [submission capability](https://www.rfc-editor.org/rfc/rfc8621.html#section-1.4)

**Fastmail** documents JMAP mail and contacts, IMAP/POP/SMTP, CardDAV, and CalDAV. Personal/testing access can use a user-created JMAP API token at **`https://api.fastmail.com/jmap/session`**. Distributed apps should implement OAuth: contact Fastmail to register the client, use its scopes and PKCE `S256`, and respect registered redirects. Do not ship a shared user’s API token. Its documentation still says JMAP calendar access will open once the specification is finalized; CalDAV is the current documented calendar route. Account-plan entitlement and partnership approval must be checked during onboarding. [Fastmail developer/authentication documentation](https://www.fastmail.com/dev/)

**JMAP Contacts is RFC 9610 (December 2024)**. Calendars are a different maturity level: the current document is **draft-ietf-jmap-calendars-32, published 2026-10-05**, not a finalized RFC as of this research date. Stalwart documents JMAP calendar/contact collaboration alongside CalDAV/CardDAV; implementation of a draft does not make it a final standard or imply Fastmail has deployed it. Pin any experimental calendar implementation to its advertised revision and retain DAV alternatives. [Contacts RFC](https://www.rfc-editor.org/rfc/rfc9610.html), [calendar draft/status](https://datatracker.ietf.org/doc/draft-ietf-jmap-calendars/), [Stalwart calendars](https://stalw.art/docs/collaboration/calendar/), [contacts](https://stalw.art/docs/collaboration/contact/)

As checked **2026-10-11**, Stalwart offers a free **AGPL-3.0 Community edition** and a commercial Enterprise edition sharing the core protocols. It is a practical self-hosted interoperability target; incorporating server code would be a separate licensing decision from using its protocol. [Stalwart editions](https://www.stalw.art/compare/)

Other real server targets include **Cyrus IMAP** and **Apache James**, which document JMAP implementations. Test at least two independent servers and Fastmail before calling support interoperable. For Rust, **`stalwartlabs/jmap-client`** is a concrete MIT/Apache-2.0 candidate covering JMAP Core/Mail and push transports; evaluate its current tests, API, and missing server extensions rather than assuming production suitability. [Cyrus](https://www.cyrusimap.org/), [James JMAP configuration](https://james.apache.org/server/config-jmap.html), [Rust JMAP client](https://github.com/stalwartlabs/jmap-client)

Recommendation: implement JMAP early as a clean reference backend and for standards-oriented providers. **Strongest counterargument:** JMAP alone cannot serve the dominant Microsoft, Google, iCloud, Proton, or Tuta integration requirements; its elegance is not a substitute for the other drivers.

## 3. Options compared

This table is an **architectural assessment** based on the interfaces and policies above, not a claim about measured Sweetbriar performance.

| Strategy | Best reason to choose it | Strongest objection | Sweetbriar decision |
|---|---|---|---|
| IMAP/SMTP everywhere possible | Largest reuse surface, direct device/provider traffic, also supports Bridge/DavMail | Cannot represent every provider feature; Microsoft tenants can prohibit it; Gmail OAuth restrictions still apply | Foundation and fallback, with capability discovery and provider presets |
| Dedicated Graph + Gmail API drivers | Correct provider identity, labels/categories, incremental APIs, richer enterprise behavior | Separate sync engines, consent programs, quotas, and evolving vendor contracts | First-class cloud backends |
| JMAP everywhere | Coherent discovery, states, mail/submission model, outbound push | Insufficient provider coverage | Early reference driver, not the only protocol |
| Local gateway | Reuses standard protocols; official Proton path; DavMail can bridge Exchange | Another process, setup/support burden, translation gaps; gateway policy still matters | Supported interoperability path, not the universal core |
| Hosted account aggregation | Always-on push/scheduling and one client-facing interface | Custody of credentials/mail, recurring infrastructure, Google assessment exposure, enterprise objections | Defer; require a separate explicit product decision |

## 4. Recommendations for Sweetbriar

Everything in this section is a **proposed design**, with protocol facts cited where they constrain the design.

### A JMAP-shaped domain model, with explicit provider identity

Use JMAP’s separation of accounts, messages, memberships, keywords, blobs, threads, and submission as the reference vocabulary. Do not mirror its JSON directly or force every server into its state model. IMAP identity is mailbox-scoped **UIDVALIDITY + UID**; Graph benefits from an immutable-ID preference; Gmail has a cross-label message ID. Those distinctions must survive normalization. [JMAP Mail objects](https://www.rfc-editor.org/rfc/rfc8621.html), [IMAP identities](https://www.rfc-editor.org/rfc/rfc9051.html), [Graph identity](https://learn.microsoft.com/en-us/graph/outlook-immutable-id), [Gmail IDs](https://developers.google.com/workspace/gmail/imap/imap-extensions)

| Core entity | Proposed responsibility |
|---|---|
| `AuthPrincipal` | Provider registration/tenant, authorized user, credential reference, granted scopes; may authorize multiple shared mailboxes |
| `Account` / `MailboxIdentity` | Stable local ID and provider namespace; shared mailbox independent from its owner’s credential |
| `Message` / `RemoteInstance` | Local UUID, immutable content reference, provider IDs/version tags; preserve separate IMAP copies rather than deduplicating them by Message-ID |
| `Collection` / `Membership` | Hierarchical folders, label collections, special roles, permissions; membership is independent of content storage |
| `Flag` / `Tag` / `Classification` | Read/replied/flagged, arbitrary keywords, Gmail labels, Outlook categories/colors, Focused/Other kept semantically distinct |
| `Blob` / `MimeSnapshot` | Immutable bytes, checksum, source representation, download completeness, parsed MIME parts; attachment bytes referenced once |
| `Thread` / `ThreadRelation` | Account-scoped provider thread plus optional local References/In-Reply-To grouping; never merge different providers’ thread IDs |
| `DraftRevision` / `Submission` | Durable composer revisions and attachments; envelope, selected identity, send state, receipt/remote draft IDs, schedule mechanism |
| `SyncCheckpoint` / `PendingOperation` | Driver-owned opaque cursor plus durable mutation intent, dependencies, attempts, and reconciliation state |

Deduplicate **blob bytes**, not distinct message deliveries. Preserve native metadata in versioned typed extension records; do not scatter arbitrary provider JSON through the UI. Export original/available MIME plus a portable metadata manifest so a future backend or storage migration can preserve categories, labels, and provenance. CalDAV/CardDAV and JMAP contacts/calendars should be adjacent services with independent permissions and sync checkpoints, not hidden inside a mail-only trait. [CalDAV, RFC 4791](https://www.rfc-editor.org/rfc/rfc4791.html), [CardDAV, RFC 6352](https://www.rfc-editor.org/rfc/rfc6352.html)

### Capabilities describe semantics, permissions, and reachability

A single `supports_push: bool` is insufficient. Capability values should distinguish **server-supported**, **client-emulated**, **permission-blocked**, **temporarily unavailable**, and **unsupported**, with limits and account-specific scope requirements.

| Capability | Information the core should expose |
|---|---|
| Collections | Folder/label/multiple-membership semantics; hierarchy, special roles, per-collection rights; move versus copy-plus-delete |
| Remote search | Query dialect, searched fields/attachments, result caps, pagination, shared-mailbox coverage, completeness |
| Notifications | IMAP IDLE, JMAP SSE/WebSocket, local polling, or cloud relay; expiry, reachability, renewal, periodic reconciliation |
| Threads | Stable provider thread IDs versus local heuristic grouping; message-level versus thread-level mutation |
| Categories/classification | Named tags, colored categories, Focused/Other, arbitrary keywords; preserve provenance |
| Submission | MIME/structured send, shared send-as rights, attachment/upload limits, remote drafts, delivery receipts |
| Scheduling | Native server scheduling with cancellation; optional hosted scheduling; device-only scheduling requiring an awake/running device |
| Rules | Read/write server rules, Sieve where offered, or local filters; execution location, ordering, supported actions |
| Data/export | Raw MIME availability, partial-download status, permanent-delete ability, archive/shared-mailbox visibility |

Graph’s shared notification restriction, Gmail’s labels, and JMAP’s conditional delayed-send capability demonstrate why these distinctions matter. Provider web-UI features must not be inferred to exist in its client API. Local filters can revive classic-client workflows without claiming that every server executes them while Sweetbriar is closed. Sieve is a concrete optional server-rule language, not a universal mail-server capability. [Shared Graph constraints](https://learn.microsoft.com/en-us/graph/outlook-share-messages-folders), [Gmail labels](https://developers.google.com/workspace/gmail/api/guides/labels), [JMAP submission limits](https://www.rfc-editor.org/rfc/rfc8621.html#section-1.4), [Sieve, RFC 5228](https://www.rfc-editor.org/rfc/rfc5228.html)

### One durable store; independent sync drivers

Implement a small `AccountDriver` interface for discovery/capabilities, incremental pull, body/blob fetch, and mutation execution/reconciliation. Keep submission behind a separately usable interface: a receiving source may have no send service or use another SMTP identity. The driver translates provider changes into normalized batches; **only the storage layer commits mail state and checkpoints**. The UI calls the core, never a provider SDK directly.

Driver-specific synchronization remains unavoidable:

- **IMAP:** folder inventory and per-mailbox UIDVALIDITY/UID state; negotiate CONDSTORE/QRESYNC where available, otherwise reconcile UID/flag inventories. IDLE wakes a sync; it is not the sole correctness mechanism. [IMAP](https://www.rfc-editor.org/rfc/rfc9051.html), [CONDSTORE/QRESYNC, RFC 7162](https://www.rfc-editor.org/rfc/rfc7162.html)
- **Graph:** independent folder-hierarchy and per-folder message delta URLs, mailbox-specific budgets, immutable IDs, shared-mailbox polling. [Message delta](https://learn.microsoft.com/en-us/graph/delta-query-messages)
- **Gmail API:** account history cursor, message/label inventory, quota-aware body fetching, full reconciliation on expired history. [Gmail sync](https://developers.google.com/workspace/gmail/api/guides/sync)
- **JMAP:** session/account capabilities and per-data-type states, bounded changes pages, query-state invalidation/requery, and blob downloads. [JMAP Core](https://www.rfc-editor.org/rfc/rfc8620.html)
- **POP/local/archive:** durable acquisition/import progress and local read state; do not fabricate a server change feed. [POP3](https://www.rfc-editor.org/rfc/rfc1939.html), [mbox](https://www.rfc-editor.org/rfc/rfc4155.html)

Serialize dependent mutations per account/object while allowing bounded independent downloads. Coalesce repeated mark-read/label edits, preserve operation ordering, and distinguish a transient failure from expired authorization, denied consent, invalid cursor, conflict, quota, or missing service. After sleep, reconnect and reconcile. Authentication refresh should be serialized per principal so several mailbox drivers do not race to replace a token.

### Turn the safety goal into demonstrable invariants

Use **SQLite** for authoritative metadata, drafts, operation journal, settings, and checkpoints, with explicitly chosen durability settings. SQLite documents durable WAL commits with `synchronous=FULL`; its guarantees depend on correct filesystem/storage behavior. Immutable MIME/attachment blobs need their own durable write/rename sequence before a transaction references them, plus recovery for unreferenced files. Test the macOS full-sync behavior rather than assuming all platforms’ flush semantics match. [SQLite synchronization](https://www.sqlite.org/pragma.html#pragma_synchronous), [atomic-commit assumptions](https://www.sqlite.org/atomiccommit.html)

Commit received changes and the advanced cursor together. Persist a draft revision and attachment before acknowledging “saved.” Journal outgoing mutations before an optimistic UI update; reconcile eventual server results. Remote deletion becomes a tombstone, with locally held bytes governed by explicit retention/backup policy. Never purge user-created drafts because authentication or a provider cursor failed. Separate “cached,” “downloaded,” and “backed up”: a header-only account cannot promise recovery of unfetched bodies.

Sending needs states such as `queued`, `uploading`, `accepted`, `uncertain`, and `failed`. If the network disappears after submission, preserve the draft/receipt and reconcile; **do not blindly resend**. SMTP explicitly recognizes duplicate-delivery risk after timeouts, and Graph’s 202 is not completed delivery. A Message-ID alone is not a universal idempotency key. Similarly, complete and verify a destination copy before deleting a source during a cross-provider move. [SMTP timeout/duplicate risk](https://www.rfc-editor.org/rfc/rfc5321.html#section-6.1), [Graph send acceptance](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0)

Provide independent, restorable backups of mail, settings, and draft revisions; test restore as well as backup creation. SQLite’s online backup interface is suitable for consistent live database snapshots; blob backup and encryption-key recovery require coordinated design. The promise should be documented recovery behavior under tested failures, not an absolute claim against hardware destruction or inaccessible remote data. [SQLite backup API](https://www.sqlite.org/backup.html)

### Concrete Rust components and native UI boundary

Evaluate **Tokio + reqwest** for async work/HTTP; **oauth2** for authorization flows; **async-imap** and **lettre** for IMAP/SMTP; **mail-parser** and **mail-builder** for MIME; **rusqlite** for explicit SQLite transactions; **jmap-client** for JMAP. These are candidates, not a verified complete email engine. In particular, test IMAP extension coverage, OAuth SASL, cancellation, malformed historical MIME, and large streaming attachments before choosing adapters. Their current upstream documentation was checked **2026-10-11**; no unverified version pin is proposed. [Tokio](https://docs.rs/tokio/latest/tokio/), [reqwest](https://docs.rs/reqwest/latest/reqwest/), [oauth2](https://docs.rs/oauth2/latest/oauth2/), [async-imap](https://docs.rs/async-imap/latest/async_imap/), [lettre](https://docs.rs/lettre/latest/lettre/), [mail-parser](https://docs.rs/mail-parser/latest/mail_parser/), [mail-builder](https://docs.rs/mail-builder/latest/mail_builder/), [rusqlite](https://docs.rs/rusqlite/latest/rusqlite/), [jmap-client](https://github.com/stalwartlabs/jmap-client)

Build a provider-independent local search index, with **Tantivy** as an evaluation candidate. Treat it as rebuildable derived data, never the only copy of a message; expose coverage of downloaded bodies/attachments and supplement with explicitly bounded server search. This costs disk and indexing work but gives stable cross-account syntax and offline search. [Tantivy](https://github.com/quickwit-oss/tantivy)

Expose paginated immutable view records, commands, progress, and batched change notifications to Swift through **UniFFI** or a small C ABI. UniFFI documents Swift bindings; platform shipping/build integration remains Sweetbriar’s responsibility. Keep UI/main-thread decisions in Swift. Credentials belong behind a platform adapter: current `keyring` guidance recommends applications use **`keyring-core` plus selected stores**, rather than its generic CLI-oriented dependency set. Evaluate Apple-native and Secret-Service stores separately for macOS/Linux. [UniFFI](https://mozilla.github.io/uniffi-rs/latest/), [current credential-store guidance](https://docs.rs/keyring/latest/keyring/)

### Implementation order and strongest objection

1. **Immediately start approval work:** Entra publisher/admin-consent documentation; Google’s verification/data-flow determination; Yahoo and Fastmail registration enquiries. These can block release independently of engineering.
2. **Build the durable local account and import/export foundation**, then generic IMAP/SMTP with provider presets, including Proton Bridge and iCloud. Prove draft recovery and uncertain-send handling before adding many servers.
3. **Add a narrow JMAP Mail reference implementation** against Stalwart/Cyrus and Fastmail. Use it to test memberships, shared accounts, blobs, states, and capability discovery; do not expand into calendar drafts yet.
4. **Make Graph and Gmail API the first dedicated commercial-provider drivers.** Graph covers Microsoft cloud mail without relying on enabled IMAP; Gmail API supplies its actual label/history model. Deliver ordinary mail, MIME, drafts, sending, and search before complex rule editors or archive parity.
5. **Add POP, archive/news sources, Zoho REST, and on-premises EWS according to demonstrated demand.** POP/archive import can move earlier for migration users. Keep EWS explicitly on-premises; do not add an Exchange Online EWS launch path.
6. **Defer EAS, proprietary direct Proton/Tuta/HEY APIs, cloud aggregation, and experimental JMAP calendars** until licensing, vendor support, and an actual customer requirement justify them.

**Strongest argument against this recommendation:** maintaining IMAP, Graph, Gmail, and JMAP creates four substantial interoperability/security obligations; a small team could spend years on sync rather than the native experience. A hosted engine or one mature protocol could ship sooner. My recommendation still favors the shared local Rust core because data custody, offline search, native responsiveness, provider fidelity, and long-term portability are project requirements. Mitigate the objection with narrow first-release capabilities and staged drivers, not a promise of immediate feature parity.

[Apple’s migration statement](https://support.apple.com/guide/deployment/integrate-with-microsoft-exchange-dep158966b23/web)
