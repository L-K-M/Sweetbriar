# Sweetbriar: guaranteeing data safety in an email client

Research report — 2026-10-11. "Data safety" here means: never lose or corrupt mail, drafts, outgoing messages, settings or credentials; never delete on the server by mistake; never send twice or not at all without telling the user; and protect users from malicious mail.

## 1. TL;DR

- **Store raw messages as immutable files** (Maildir-style `tmp→fsync→rename→dir-fsync`), keep SQLite strictly as a rebuildable index with per-message SHA-256 — every major loss incident (Catalina Mail, Thunderbird compaction, PST ceilings, Eudora .toc) was a single-file-format or non-transactional-rewrite failure.
- **Never modify shared state blindly:** every user intent becomes a durable queue row (same transaction as its local effect), replayed idempotently as a *state-convergence check*; Mailspring's drop-on-crash queue is the cautionary tale.
- **Never emit a bare `EXPUNGE`** (it kills other clients' `\Deleted` mail — RFC 6851): UID MOVE, else COPY→verify COPYUID→`UID STORE \Deleted`→`UID EXPUNGE`; deletes go via server Trash by default.
- **Local tombstones + a mass-disappearance circuit breaker** stop local bugs (and server glitches) from propagating as real deletions — the Catalina sync-loop lesson.
- **On macOS, real durability needs a bundled SQLite ≥3.51.3** with `fullfsync`+`checkpoint_fullfsync`: the system SQLite substitutes `F_BARRIERFSYNC` and isn't fully ACID, and the 3.7.0–3.51.2 WAL-reset bug (found by Tailscale, reproduced by Antithesis in ~15 min) shows even SQLite needs simulation testing.
- **Keep the store out of iCloud/Dropbox/network filesystems**, back up message files, exclude rebuildable caches from Time Machine.
- **Sending can only ever be at-most-once-visible:** persist the outbox pre-SMTP, reuse the Message-ID on retry, resolve post-`DATA` ambiguity via Sent-folder lookup, and show "possibly sent" honestly.
- **Render mail with JavaScript off and remote content blocked** (including CSS — EFAIL); attachments get `com.apple.quarantine`; OAuth + Keychain/Secret Service for credentials (Google and Microsoft require OAuth in 2026).
- **Build the sync engine as a deterministic state machine and test like FoundationDB/TigerBeetle/Dropbox Nucleus**: seeded simulation with injected faults, proptest against an in-memory IMAP model, and a real-server CI matrix (Dovecot imaptest, Cyrus, Stalwart, Gmail, M365, iCloud, Fastmail).

## 2. Findings

### 2.1 Real incidents: how email clients have lost data

Data loss in shipping email clients clusters into a few recurring root causes: monolithic store files that can't be partially repaired, non-transactional rewrite operations (compaction, rebuild, upgrade), sync engines that propagate mistakes in both directions, and unsafe defaults after updates.

**Apple Mail, macOS Catalina (Oct 2019).** The best-documented modern incident. After upgrading to macOS 10.15, "updating Mail's data store … sometimes says that it succeeded, but large numbers of messages turn out to be missing or incomplete." Worse, "moving messages between mailboxes, both via drag-and-drop and AppleScript, can result in a blank message (only headers) on the Mac. If the message was moved to a server mailbox, other devices see the message as deleted. And eventually this syncs back to the first Mac, where the message disappears as well" ([Michael Tsai, 2019-10-11](https://mjtsai.com/blog/2019/10/11/mail-data-loss-in-macos-10-15/)). One user reported the rebuild path was "trivial to reproduce" and lost 160,000 of 200,000 messages (ibid., update). Covered by [MacRumors](https://www.macrumors.com/2019/10/12/apple-mail-data-loss-macos-catalina/) and [TidBITS](https://tidbits.com/2019/10/11/beware-mail-data-loss-in-catalina/). Root cause: a migration that reported success without verification, plus a move operation that could persist a truncated copy to the server — two violations: (a) migrations must verify counts/checksums before declaring success, (b) a failed local write must never produce a "successfully moved, content empty" state that then syncs out.

**Thunderbird mbox compaction.** A long history; most instructive is the 2022–2024 cluster. [Bug 1777454](https://bugzilla.mozilla.org/show_bug.cgi?id=1777454) (S1): after compacting, new POP3 messages were never added to the mbox file — the message list showed entries whose bodies didn't exist, causing the "wrong message shown" corruption of Bug 1777738. [Bug 1811777](https://bugzilla.mozilla.org/show_bug.cgi?id=1811777): compacting large POP3 folders corrupted decades-old mail ("repair folder does not fix — it just removes most of the affected corrupted messages from even appearing"). The endemic mbox corruption problem was serious enough that Thunderbird tracked it in meta-[Bug 1890230](https://bugzilla.mozilla.org/show_bug.cgi?id=1890230) and fixed it by *rewriting the compactor entirely* ([Bug 1890448](https://bugzilla.mozilla.org/show_bug.cgi?id=1890448), fixed in nightly 2024-05-24, shipped in the 128 ESR line). Follow-up [Bug 1941646](https://bugzilla.mozilla.org/show_bug.cgi?id=1941646) restricted automatic repair-on-failed-compaction to IMAP folders only, because auto-repair of *local* folders is itself a dataloss risk — for local data the correct answer is "restore a backup," not silent rewriting. Root cause: mbox is a single mutable file; compaction is a read-old-write-new operation performed on the only copy, and "repair" tools that drop unparseable bytes destroy data. Design that prevents it: messages as individual files (no compaction needed), and repairs that quarantine rather than delete.

**Outlook PST/OST.** The canonical "format ceiling" incident: ANSI PST files (Outlook 97–2002) had a ~2 GB limit; exceeding it produced "Errors have been detected in the file" and Microsoft's own remedy was a truncation tool that deliberately cut data out ("the truncated data is missing") ([KB 296088](https://ftp.zx.net.nz/pub/Patches/ftp.microsoft.com/MISC/KB/en-us/296/088.HTM); format history [KB 830336](https://ftp.zx.net.nz/pub/archive/ftp.microsoft.com/MISC/KB/en-us/830/336.HTM)). Modern Unicode PST defaults to a 50 GB registry limit ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365-apps/outlook/data-files/configure-size-limit-outlook-data-files)). Root cause: a single binary file format with hard size ceilings and no partial recovery. Design: many small files beat one big file.

**Proton Mail Bridge.** Bridge is a local IMAP/SMTP shim over an encrypted account — architecturally interesting because it has the same problem Sweetbriar does (a local store mirroring a server). Two documented failures:

- Unstable UIDs: Bridge returned message UIDs that changed *without* a UIDVALIDITY change, violating RFC 3501. Consequences reported: incremental backups (offlineimap) silently skipped messages; and at least one report of a client deleting the wrong message because UIDs shifted underneath ([Mark Wadham](https://markwadh.am/blog/psa-your-protonmail-backups-might-not-be-safe.html)). Also "orphaned" messages — present in the account but in no real folder — which backup tools missed entirely (23,793 in his account).
- Bridge itself knows APPEND can fail after the client has already deleted the source message; it catches this by parking the message in a local-only "Recovered Messages" folder — which is deleted if you reset Bridge ([Proton support](https://proton.me/support/what-is-the-recovered-messages-folder-in-bridge)). Design lesson: the safety-net copy must outlive the sync component.
- On re-sync, Bridge created new Gluon databases but leaked the old ones — 3.8 GB of orphaned message store in one report ([gluon issue #452](https://github.com/ProtonMail/gluon/issues/452)).

**K-9 Mail / Thunderbird for Android.** [Issue #9034](https://github.com/thunderbird/thunderbird-android/issues/9034): upgrading to K-9 9.0 silently dropped the per-account "mark message as deleted" setting; the fallback action became "delete immediately," so users' IMAP deletes became real deletes without warning — a *settings-migration* data-loss bug. [Issue #1155](https://github.com/thunderbird/thunderbird-android/issues/1155) shows a different failure: a single failing APPEND (uploading a draft/sent copy, e.g. oversized attachment) poisoned the whole pending-operations queue, so deletes and flag changes behind it never reached the server. Design lessons: migrate settings with safe defaults (never escalate destructiveness), and make the intent queue per-operation resilient — one stuck op must not block independent ops.

**Gmail IMAP delete semantics.** Not a bug but a standing footgun: Gmail's own docs tell IMAP users *don't* save deleted messages to Trash, because "any messages you delete from your email client will get permanently deleted from Gmail in 30 days" — the default mapping archives instead ([Gmail Help](https://support.google.com/mail/answer/78892)). Via the API the behavior is explicit: `autoExpunge` (immediate expunge on \Deleted) and `expungeBehavior` = `archive` | `trash` | `deleteForever` ([Gmail API ImapSettings](https://developers.google.com/workspace/gmail/api/reference/rest/v1/ImapSettings)). A client that assumes \Deleted+EXPUNGE always means "gone forever" will mis-handle Gmail in both directions.

**Sync-loop / propagation risk.** The Catalina case above is the canonical example: a *local* corruption propagated to the server and back. This is the structural hazard of two-way sync: any client-side bug that produces phantom deletions becomes a server-side deletion on all devices. (See §2.2 for the circuit-breaker design.)

**mbsync** documents the careful version of this design: deletion propagation is opt-in (`Gone`/`Delete` operations), affected messages are only *marked* deleted until expunge, a Trash mailbox can snapshot messages before expunging, and state files are lock-protected ([mbsync(1)](https://isync.sourceforge.io/mbsync.html)).

**POP3's standing footgun.** POP3 marks deletions with `DELE` but nothing is removed until `QUIT` moves the session to the UPDATE state — and if the session dies without `QUIT`, "the POP3 session does NOT enter the UPDATE state and MUST not remove any messages" ([RFC 1939 §5–6](https://www.rfc-editor.org/rfc/rfc1939.txt)). That asymmetry is the one safe property POP3 has. The classic loss pattern is the inverse: `RETR` → `DELE` → `QUIT` ("download and delete"), after which the only copy lives in the client's local store — and any local corruption (see every mbox incident above) makes the mail unrecoverable. `UIDL` unique-ids persist across sessions by spec, so a "leave on server" client can dedup reliably; a Sweetbriar POP backend (if shipped) should default to leave-on-server and treat server deletion as an explicit, durable intent like any other.

**Eudora (classic).** Eudora's design is directly relevant because Sweetbriar wants to inherit its virtues: messages lived in `.mbx` (mbox) files plus a per-mailbox `.toc` index holding status/labels — delete removed the message from the `.toc` only, and compaction physically removed it from the `.mbx`. Corrupt `.toc` produced wrong summaries, wrong dates, wrong message bodies shown; rebuilding the `.toc` could resurrect deleted mail or lose all status ([TidBITS repair walkthrough, 2008](https://tidbits.com/2008/04/04/how-to-fix-corrupt-eudora-mailboxes/); recovery instructions in [comp.mail.eudora](https://comp.mail.eudora.ms-windows.narkive.com/webcyEzK/how-to-repair-corrupt-index)); third-party rescue tools exist because rebuilds lose data ([Eudora Rescue](http://qwerky.50webs.com/eudorarescue/readme.htm)). Lessons: keep per-message status near the message, not only in a separate index; rotating backup copies (Eudora made `.001/.002` mailbox backups) foreshadow "snapshot before rewrite."

**Airmail 3 (2018) — security, not just loss.** VerSprite found the `airmail://` URL scheme's `send` command let *any* app or a link in an email send mail from the user's account with arbitrary attachments — `attachment_` params accepted `../../../../` paths, so a crafted link could exfiltrate files including the mail store itself, which lived at a deterministic path ([CVE-2018-15667](https://versprite.com/advisories/airmail-3-for-mac/); [VerSprite writeup](https://versprite.com/resources/vs-labs/phishing-airmail3-mac/); [The Verge](https://www.theverge.com/2018/8/22/17770062/airmail-email-app-update-fix-security-vulnerability-flaw)). A second advisory found an incomplete *blacklist* of frame-owning elements, letting attacker HTML trigger frame navigations past the WebView policy ([CVE-2018-15669](https://versprite.com/advisories/airmail-3-for-mac-3/)). Lessons: URL-scheme actions need user confirmation; block remote content by allowlist, not blacklist; a deterministic predictable store path lowers the cost of any exfil bug.

### 2.2 Sync engine correctness

- **Bare EXPUNGE is dangerous.** RFC 6851 (MOVE) spells it out: the legacy COPY + STORE \Deleted + EXPUNGE sequence is not atomic, and "the third step can have the side effect of expunging more than just the set of moved messages" — any *other* messages flagged \Deleted in that mailbox (yours or another client's) die too ([RFC 6851 §1](https://www.rfc-editor.org/rfc/rfc6851.html)). Safe rules: prefer UID MOVE when the server advertises MOVE; otherwise COPY → STORE +FLAGS.SILENT \Deleted → **UID EXPUNGE** (requires UIDPLUS, [RFC 4315](https://www.rfc-editor.org/rfc/rfc4315.html)); never bare EXPUNGE on a shared-state mailbox.
- **MOVE vs COPY+DELETE trade-off** (opinion): MOVE is atomic-looking but gives you no window to verify the copy landed; the three-step form lets the client confirm COPYUID before deleting the source. For bulk moves the three-step + verification is arguably safer; for user-initiated small moves MOVE is cleaner and avoids the "same message in two places" window.
- **UIDVALIDITY:** [RFC 9051 §5](https://www.rfc-editor.org/rfc/rfc9051.html) (IMAP4rev2, Aug 2021, obsoletes RFC 3501): if UIDVALIDITY changes, all cached UIDs are invalid — the client must treat the mailbox as new. mbsync "is susceptible to UID validity changes (but will recover just fine if the change is unfounded)" ([mbsync(1)](https://isync.sourceforge.io/mbsync.html)). The unsafe response is to trust stale UIDs for deletes (cf. Proton Bridge's UID instability above — the *server-side* equivalent). Relatedly, `UIDNEXT` is only a *prediction* of the next assigned UID — it can change between sessions, so it must never be used as a dedup or anchoring key ([RFC 9051 §6.3.1](https://www.rfc-editor.org/rfc/rfc9051.html)).
- **CONDSTORE/QRESYNC:** [RFC 7162](https://www.rfc-editor.org/rfc/rfc7162.html) (obsoletes 4551/5162): HIGHESTMODSEQ + CHANGEDSINCE give resumable flag sync; QRESYNC folds resync into SELECT/EXAMINE with known UIDs and seq-match — designed exactly for disconnected clients that must not re-download everything.
- **Gmail specifics:** label model — one message, many labels; Gmail maps labels to IMAP *folders* and exposes `X-GM-LABELS`/`X-GM-MSGID`/`X-GM-THRID` via FETCH/STORE/SEARCH — `X-GM-MSGID` is a stable per-message identity across folders, ideal for the intent queue's dedup keys ([Gmail IMAP extensions](https://developers.google.com/gmail/imap/imap-extensions)). \Deleted behavior is governed by `autoExpunge`/`expungeBehavior` (above); All Mail holds everything, so expunging there is the most destructive operation in the account; [Gmail IMAP client settings](https://support.google.com/mail/answer/78892). As of 2026 Google requires OAuth for IMAP/SMTP — less-secure-app password auth was turned off for Workspace accounts 2025-03-14 and rolled out fully by 2025-05-01; consumer app passwords still exist but are discouraged ([Google Workspace Help](https://support.google.com/a/answer/14114704); [Workspace Updates](https://workspaceupdates.googleblog.com/2023/09/winding-down-google-sync-and-less-secure-apps-support.html)).
- **Microsoft 365 / Exchange Online:** OAuth is mandatory (Basic auth dead; SMTP AUTH basic being rejected Mar–Apr 2026 — §2.6). For sync correctness the interesting fact is that **Microsoft Graph's `message: delta` is a purpose-built incremental sync primitive** — per-mailFolder `@odata.deltaLink`/`deltaToken` state tokens return added/updated/deleted message sets, filterable by `changeType`, designed explicitly "to maintain and synchronize a local store" ([message: delta](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0); [delta query guide](https://learn.microsoft.com/en-us/graph/delta-query-messages)). Persisting deltaTokens in the intent queue gives crash-safe resumable sync without IMAP UID semantics — a cleaner M365 path than IMAP4rev1-over-XOAUTH2 (though sending still goes via SMTP AUTH XOAUTH2 or Graph sendMail).
- **Intent queue real-world data point:** Mailspring runs sync in a separate C++ process; all user operations are persisted "Task" models written to SQLite before execution, and the UI is read-only on the DB ([Mailspring CLAUDE.md](https://github.com/Foundry376/Mailspring/blob/master/CLAUDE.md)). Notably, on launch it *deletes* tasks still in `local` state — abandoned mid-flight ops are dropped rather than replayed ([TaskProcessor.cpp](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/TaskProcessor.cpp)). Sweetbriar should do the opposite: replay idempotently (see §4).
- **JMAP (RFC 8620/8621).** The data model is structurally safer than IMAP for moves: an Email has a `mailboxIds` set — "An Email in the mail store MUST belong to one or more Mailboxes at all times (until it is destroyed)" — so a *move is a single per-record atomic update* to `mailboxIds`, not a copy+expunge window ([RFC 8621 §2](https://www.rfc-editor.org/rfc/rfc8621.txt)). But `Email/set` is **not batch-atomic**: "Each creation, modification, or destruction of an object is considered an atomic unit. It is permissible for the server to commit changes to some objects but not others" ([RFC 8620 §"set"](https://www.rfc-editor.org/rfc/rfc8620.txt)) — a 200-message move can partially apply, so the intent queue must reconcile per-record `updated`/`notUpdated` results just as it does for IMAP. Push is Server-Sent Events: a `text/event-stream` endpoint emits `state` events (StateChange objects); `Last-Event-ID` on reconnect lets the server resend missed changes — the server "can use [it] to work out whether the client has missed some changes" ([RFC 8620 §7](https://www.rfc-editor.org/rfc/rfc8620.txt)). Also note `Mailbox/set onDestroyRemoveEmails` defaults false — destroying a Mailbox that still has Emails is rejected unless you opt in ([RFC 8621](https://www.rfc-editor.org/rfc/rfc8621.txt)).
- **Stalwart** is the most complete JMAP/IMAP4rev2 server (feature-complete as of 2025-10-22; 0.16.x line as of 2026-04) and the natural self-hosted conformance target ([Stalwart blog](https://stalw.art/blog/jmap-collaboration/); [changelog](https://github.com/stalwartlabs/stalwart/blob/main/CHANGELOG.md)). Its mail-parser Rust crate had a 2026 CVE for OOM on cyclical MIME structures — parser robustness matters even in Rust ([CVE-2026-26312](https://github.com/stalwartlabs/stalwart/security/advisories/GHSA-jm95-876q-c9gw)).
- **The durable intent queue (design, opinion).** Every user action that mutates server or local state becomes a queue entry: `{op-id, account, type, args, state, attempt-count, durable-idempotency-key}` written to the SQLite outbox/oplog table *in the same transaction* as the local state change it describes — then a worker drains it. Crash between local change and queue write is impossible (one transaction); crash mid-server-op is recovered because replay is idempotent (UIDs/COPYUID/APPENDUID/Email ids name the operation deterministically). Per-op failure isolation (one poisoned op parks, doesn't block the queue — the K-9 #1155 lesson), per-account ordering where the protocol demands it (a MOVE must replay before a delete of the same UID). mbsync is the conservative precedent: propagation of deletions is opt-in and state is journaled; Mailspring is the cautionary tale — persisted "Task" rows dropped on launch instead of replayed ([mbsync(1)](https://isync.sourceforge.io/mbsync.html); [Mailspring TaskProcessor.cpp](https://github.com/Foundry376/Mailspring-Sync/blob/master/MailSync/TaskProcessor.cpp)).
- **Tombstones.** A local delete first writes a tombstone (message hash + server UID + timestamp), applied to the server later. Tombstones do three jobs: (a) the UI shows "deleted" instantly without waiting for sync; (b) a crash before server confirmation can't resurrect the message as a phantom "new" arrival on next sync; (c) they're the circuit breaker's evidence — a mass-delete intent is reviewable before it executes. Retain tombstones until the server confirms the delete *and* one full clean sync has passed.

### 2.3 Local durability on macOS and Linux

The layered picture: SQLite settings determine commit semantics; the OS/filesystem determine what a sync actually means; file-level patterns (temp+rename+dir-fsync) protect everything outside the DB; and the store layout determines how much a corruption can cost.

**SQLite configuration.** The [pragma documentation](https://sqlite.org/pragma.html) gives the matrix:

| `synchronous` | Rollback journal | WAL mode |
|---|---|---|
| `EXTRA` (3) | ACID | ACID (same as FULL) |
| `FULL` (2) | ACID-ish, "maybe not durable" | **ACID** |
| `NORMAL` (1) | maybe not consistent | consistent, **not durable** |
| `OFF` (0) | neither | neither |

In WAL mode, `synchronous=FULL` syncs the WAL on every commit — the correct setting for authoritative data ([SQLite pragma docs](https://sqlite.org/pragma.html)). `synchronous=NORMAL` in WAL is safe *only* for rebuildable caches: "a transaction committed in WAL mode with synchronous=NORMAL might roll back following a power loss." WAL mode itself gives concurrent readers and snapshot isolation ([SQLite WAL docs](https://www.sqlite.org/wal.html)).

**macOS fsync is not a sync.** Apple's fsync(2) man page: fsync "will flush all data from the host to the drive … the drive itself may not physically write the data … and it may be written in an out-of-order sequence … if the drive loses power or the OS crashes, the application may find that only some or none of their data was written" — for real ordering you must use `fcntl(fd, F_FULLFSYNC)` ([Apple fsync(2) man page](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html), quoted in [bonsaidb.io](https://bonsaidb.io/blog/acid-on-apple/)). SQLite exposes this via `PRAGMA fullfsync` (default **off**) and `PRAGMA checkpoint_fullfsync` ([pragma docs](https://sqlite.org/pragma.html)). Two traps: (1) Apple's *bundled* SQLite replaces `fullfsync` with `F_BARRIERFSYNC`, which orders I/O but doesn't flush the drive cache — so an app using the system SQLite is not fully ACID even with the pragma on ([bonsaidb investigation](https://bonsaidb.io/blog/acid-on-apple/); [Michael Tsai](https://mjtsai.com/blog/2025/09/05/sqlite-on-macos-not-acid/), 2025-09-05). Sweetbriar must therefore bundle SQLite (e.g. rusqlite's bundled amalgamation — [rusqlite 0.40.2](https://crates.io/api/v1/crates/rusqlite), fetched 2026-10-11) rather than link the system one. (2) Even with a correct build, `checkpoint_fullfsync` should be set too so the checkpoint path gets F_FULLFSYNC.

**Linux.** `fdatasync()` flushes file data plus only the metadata needed to read it back (size, block pointers) — cheaper than fsync for pre-grown files ([fdatasync(2)](https://www.man7.org/linux/man-pages/man2/fdatasync.2.html)). And a file fsync does **not** persist its directory entry: "an explicit fsync() on a file descriptor for the directory is also needed" ([fsync(2)](https://www.man7.org/linux/man-pages/man2/fsync.2.html)).

**Atomic file writes.** The only safe pattern on POSIX: write temp file in the same directory → fsync(temp) → `rename(temp, final)` → open parent dir → fsync(dirfd). rename gives *name* atomicity, not data durability — the data must already be synced ([LWN: atomicity vs durability](https://lwn.net/Articles/323412/)). Dan Luu's write-ups catalogue what goes wrong: `data=writeback` can commit metadata (size) before data; and fsync error handling itself was broken — Linux could report success on a retry after an EIO while the data was gone ("fsyncgate," 2018; fixed in later kernels) ([Files are hard](https://danluu.com/file-consistency/); [fsyncgate](https://danluu.com/fsyncgate/); [Files are fraught with peril](https://danluu.com/deconstruct-files/)). On APFS, `clonefile(2)` is copy-on-write, requires that the destination not exist, and a later overwrite of a cloned block can even return ENOSPC — useful for cheap snapshots/backups of the message store, not for atomic replacement ([clonefile(2) man page](https://keith.github.io/xcode-man-pages/clonefile.2.html)).

**How databases actually corrupt.** SQLite's own [How To Corrupt](https://sqlite.org/howtocorrupt.html) page: hot-journal files deleted/renamed by external tools (the classic cloud-sync failure), concurrent writers without locks, drives that lie about sync, disk-full mid-write. [SQLite over a network](https://www.sqlite.org/useovernet.html) explains why network/cloud filesystems break the fsync assumptions ACID depends on.

**The 2026 WAL-reset bug — required reading.** In March 2026 SQLite disclosed a real corruption bug in WAL mode itself: when two or more connections on the same database file (separate threads *or processes*) write and checkpoint at the same instant, the WAL reset can lose committed transactions or corrupt the file. Present in **every SQLite release from 3.7.0 (2010) through 3.51.2 (2026-01-09); fixed in 3.51.3 (2026-03-13), with backports 3.44.6 and 3.50.7** ([sqlite.org/wal.html §the_wal_reset_bug](https://sqlite.org/wal.html#the_wal_reset_bug)). It was found by Tailscale after months of production forensics — "a write had vanished into thin air without raising an error" ([Tailscale blog](https://tailscale.com/blog/sqlite-wal-reset-bug)) — and independently, Antithesis reproduced it in ~15 minutes of deterministic simulation once aimed at the checkpoint code ([Antithesis blog](https://antithesis.com/blog/2026/wal-reset-bug/); summary [Michael Tsai](https://mjtsai.com/blog/2026/08/14/sqlite-wal-reset-bug/)). Consequences for Sweetbriar: (1) **bundle SQLite ≥3.51.3** (or a fixed backport) — never the OS copy anyway (see F_BARRIERFSYNC above); (2) prefer a **single writer** connection for the index DB, which also removes the trigger condition as defense-in-depth; (3) this is the strongest possible argument for deterministic-simulation testing of our own code (§2.7).

**Cloud-synced folders corrupt stores.** Dropbox's community explicitly warns against database files in Dropbox ([Dropbox Community](https://community.dropbox.com/en/discussion/193060/what-to-do-with-conflicted-copies)); DEVONthink's support logs "a handful of tickets of data loss" from it ([DEVONtechnologies forum](https://discourse.devontechnologies.com/t/dropbox-and-sync/15279)); iCloud Drive (a sync daemon with file stubs, not a POSIX fs) has documented content-loss on conflicts ([arXiv 2602.19433](https://arxiv.org/html/2602.19433v1), 2026-02 — treat as one study's findings). Real apps now detect and warn: Zotero, Obsidian, and anytype all warn when the data dir sits under OneDrive/Dropbox/iCloud ([anytype PR #2311](https://github.com/anyproto/anytype-ts/pull/2311)). **Design rule: Sweetbriar's store lives under `~/Library/Application Support` / `~/.local/share`, never in a synced folder; warn if the user relocates it into one.**

**Detection and self-healing.** `PRAGMA integrity_check` walks the B-tree and cross-verifies indexes; `PRAGMA foreign_key_check` covers FKs — but neither sees payload bit-rot inside rows ([pragma docs](https://sqlite.org/pragma.html)). The `cksumvfs` shim adds per-page checksums returning `SQLITE_IOERR_DATA` on mismatch ([cksumvfs docs](https://sqlite.org/cksumvfs.html)); for raw message files, store a SHA-256 per file in the index and verify on read — that catches silent corruption the DB can't. Rebuilding: FTS5 supports `INSERT INTO ft(ft) VALUES('rebuild')` ([FTS5 docs](https://www.sqlite.org/fts5.html)); the whole index is re-derivable if raw `.eml` files are authoritative (see §2.4). Checkpointing: auto-checkpoint fires at 1000 WAL pages by default; a periodic `TRUNCATE` checkpoint (`sqlite3_wal_checkpoint_v2`) during idle prevents WAL bloat and checkpoint starvation ([WAL docs](https://www.sqlite.org/wal.html); [wal_checkpoint_v2](https://www.sqlite.org/c3ref/wal_checkpoint.html)).

**Migrations.** SQLite has transactional DDL: read `PRAGMA user_version`, apply each migration in its own transaction, bump `user_version` in the same commit ([pragma docs](https://sqlite.org/pragma.html)). For anything destructive, `VACUUM INTO` a timestamped backup first — the Catalina lesson is that a migration must verify itself before deleting old data.

**Time Machine.** Mark rebuildable caches excluded: `NSURLIsExcludedFromBackupKey`/`isExcludedFromBackup` resource value — note it "causes this property to reset to false" on common file ops, so re-apply on each save ([Apple docs](https://developer.apple.com/documentation/foundation/urlresourcekey/isexcludedfrombackupkey)); `CSBackupSetItemExcluded` can exclude by path ([CoreServices docs](https://developer.apple.com/documentation/coreservices/1445043-csbackupsetitemexcluded)). Back up the raw message store; exclude the SQLite index, FTS index, and derived caches.

### 2.4 Storage formats the user owns

| Format | Unit of risk | Atomic ops | Locks needed | Interop | Verdict for Sweetbriar |
|---|---|---|---|---|---|
| **mbox (any variant)** | whole folder file | none — rewrite to compact | yes | universal-ish | poor: one corruption can kill a folder; compaction is inherently dangerous |
| **Maildir / Maildir++** | one file per message | link/rename delivery | none | Dovecot, mbsync, mutt, mb2md | **best for raw store** |
| **single .eml files** | per message | rename | none | every client imports .eml | equivalent to Maildir minus flag-in-filename semantics |
| **Apple .emlx** | per message | rename | none | Apple-only metadata wrapper | good import source; .emlx = bytecount + RFC822 + plist |
| **PST/OST** | whole file | none | n/a | MS-PST spec, libpst | import/export target only |
| **SQLite-only (blobs)** | the DB | transactional | SQLite | none without app | rejected as sole store — violates "readable without the app" |

- **Maildir** (djb spec, [cr.yp.to/proto/maildir.html](https://cr.yp.to/proto/maildir.html)): `tmp/` → `new/` → `cur/`, unique names, delivery = write tmp + `link()`/`rename()` — "no locks," safe even over NFS. Maildir++ adds `.Folder` subdirectories ([Wikipedia: Maildir](https://en.wikipedia.org/wiki/Maildir)).
- **mbox is four incompatible formats** (mboxo/mboxrd/mboxcl/mboxcl2) with irreversible `>From` quoting ambiguities — mixing readers corrupts mail ([jdebp FGA](http://jdebp.uk/FGA/mail-mbox-formats.html)). Still needed for export (Thunderbird, Apple Mail packages).
- **.emlx**: Apple's per-message format since Tiger — line 1 byte count, RFC 5322 body, then an XML plist with a `flags` bitmask ([Library of Congress fdd000615](https://www.loc.gov/preservation/digital/formats/fdd/fdd000615.shtml); [PRONOM fmt/2055](https://www.nationalarchives.gov.uk/PRONOM/fmt/2055)). Apple Mail keeps them under `~/Library/Mail/V*/…/*.emlx` with the Envelope Index SQLite mapping ROWID→filename. A Sweetbriar importer can decode .emlx trivially.
- **Thunderbird**: mbox remains the default store in 2026; maildir exists but is "not feature complete" and Mozilla literally warns users "willing to risk your data" ([Thunderbird/Maildir wiki](https://wiki.mozilla.org/Thunderbird/Maildir); [support KB](https://support.mozilla.org/en-US/kb/maildir-thunderbird); conversion-tracking [Bug 1306254](https://bugzilla.mozilla.org/show_bug.cgi?id=1306254)). Folder storage = `nsIMsgPluggableStore`; per-folder `.msf` index + mbox file or maildir dir ([Thunderbird source docs](https://source-docs.thunderbird.net/en/latest/backend/folder_storage.html)).
- **PST**: [MS-PST spec](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-pst/141923d5-15ab-4ef1-a524-6dce75aae546) is open; ANSI ≈2 GB ceiling, Unicode default 50 GB; `readpst` (libpst) converts to mbox ([github.com/pst-format/libpst](https://github.com/pst-format/libpst)).
- **Export tooling**: imapsync 2.314 for IMAP↔IMAP/imports (latest release 2025-09-23, [imapsync](https://imapsync.lamiral.info/)); ImportExportTools NG 15.0.3 for Thunderbird mbox/EML export (v15 is a complete rewrite released 2026-09-04, [addons.thunderbird.net](https://reviewers.addons.thunderbird.net/EN-US/thunderbird/addon/importexporttools-ng/versions/)); mb2md for mbox→maildir (Dovecot ships a fork in [dovecot/tools](https://github.com/dovecot/tools/blob/main/mb2md.pl)). Thunderbird's per-folder `.msf` index (Mork format) is itself being migrated to SQLite ([Bug 1572000](https://bugzilla.mozilla.org/show_bug.cgi?id=1572000)).

**Recommendation sketch** (detail in §4): raw RFC 5322 messages as individual files — Maildir++ layout gives flags-in-filename semantics for free — with the SQLite DB (headers/flags/FTS5/threading) as a fully derived, rebuildable index. Per-file SHA-256 in the index for bit-rot detection.

### 2.5 Drafts and outbox

**Drafts.** Autosave is table stakes; the interesting part is sync semantics. Base IMAP draft-sync = `APPEND` to the Drafts mailbox then mark+expunge the old copy ([RFC 3501](https://www.rfc-editor.org/rfc/rfc3501.txt)). Three extensions turn this into a safe protocol: **UIDPLUS** returns `APPENDUID` — UIDVALIDITY + assigned UID — so the client can name the server copy deterministically ([RFC 4315](https://www.rfc-editor.org/rfc/rfc4315.txt)); **CATENATE** composes an APPEND from server-side fragments without re-uploading ([RFC 4469](https://www.rfc-editor.org/rfc/rfc4469.txt)); and **REPLACE** ([RFC 8508](https://www.rfc-editor.org/rfc/rfc8508.txt), Jan 2019) was standardized precisely because "message replacement is a common operation for clients that automatically save drafts" — use it when advertised. Keep one stable Message-ID across a draft's lifetime so other devices see one logical draft. Locally, autosave should be a journaled, content-addressed snapshot (debounce ~1–2 s + on-blur/on-quit snapshot, fsync before showing "saved"); Thunderbird still ships compose-autosave machinery (`AutoSaveInterval` in comm-central, [searchfox](https://searchfox.org/comm-central/search?q=mail.compose.autosave&case_sensitive=false)).

**Undo send is a delay, not a recall.** Gmail holds the message 5–30 s (configurable) before transmitting ([Gmail Help](https://support.google.com/mail/answer/2819488); [Google blog](https://blog.google/products-and-platforms/products/gmail/how-to-unsend-email-gmail/)). Apple Mail: 10 s default, up to 30 ([Apple Support](https://support.apple.com/guide/mail/change-composing-settings-cpmlprefcomp/mac)). Outlook "recall" is a different beast — it works only inside the same Exchange/M365 org; over the internet it fails, and even Microsoft's cloud recall can't retract beyond Exchange Online boundaries ([Microsoft Support](https://support.microsoft.com/en-us/office/recall-an-email-message-that-you-sent-in-outlook-35027f88-d655-4554-b4f8-6c0729a723a0); [Cloud-based Message Recall](https://learn.microsoft.com/en-us/exchange/mail-flow-best-practices/work-with-cloud-based-message-recall)). **For Sweetbriar: a client-side hold queue is the only universal mechanism — the send button enqueues to a durable outbox with an N-second undo window, and the UI must show "sending in N s" honestly.**

**Durable outbox.** RFC 5321's own model: 4yz = transient → retry "some reasonable number of times" (§4.5.4); 5yz = permanent → bounce immediately ([RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html)). Design: persist each outbound message to the outbox *before* any SMTP traffic; exponential backoff with jitter on 4xx; never retry 5xx; a message leaves "sending" state only on 250 or a definitive failure.

**The after-DATA ambiguity.** If the connection drops after the client sends the final `.` but before the 250 reply, the client cannot know whether the server accepted; retrying can produce two copies — documented SMTP reality: "the recipient will end up receiving two copies" ([cr.yp.to/smtp/client.html](https://cr.yp.to/smtp/client.html)); RFC 5321 §6.1 frames the reliability model. PIPELINING doesn't help — DATA must still be the last command in a group and the 250 must be read before declaring success ([RFC 2920](https://www.rfc-editor.org/rfc/rfc2920.txt)). Mitigations: (a) reuse the same Message-ID on every retry so receivers and Sent-folder bookkeeping can match; (b) mark the outbox item `sent-unconfirmed` and on reconnect check the Sent mailbox for that Message-ID before resending; (c) APPEND to Sent using UIDPLUS `APPENDUID` so the Sent copy is idempotent ([RFC 4315](https://www.rfc-editor.org/rfc/rfc4315.txt)). There is no dedup guarantee in base SMTP — the honest invariant is *at-most-once visible send + a durable record, and the user sees "possibly sent" rather than a silent duplicate or silent loss.*

**K-9's queue-poisoning bug** (above, §2.1) is the outbox-side lesson: a failing APPEND blocked all later ops.

**Large attachments.** base64 adds ~33% (76-char lines + CRLF; [RFC 2045 §6.8](https://www.rfc-editor.org/rfc/rfc2045.txt)) — ~19 MB raw fits Gmail's 25 MB cap ([Gmail limits](https://support.google.com/mail/answer/6584); blocked file types [answer/6590](https://support.google.com/mail/answer/6590)). Exchange Online allows up to 150 MB on some plans ([Exchange Online limits](https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits)). Declare size up front via the SMTP SIZE extension so servers can reject before DATA ([RFC 1870](https://www.rfc-editor.org/rfc/rfc1870.txt)). Apple Mail Drop uploads instead of attaching: 5 GB per attachment, 30-day expiry, doesn't count against iCloud storage, 1 TB total ([Mail Drop limits](https://support.apple.com/en-us/108329)). Sweetbriar needs the same pattern: SIZE-check first, then a link-based path above a threshold.

### 2.6 Security

- **Credential storage:** macOS Keychain / Linux Secret Service (libsecret, gnome-keyring, KWallet). Rust: [keyring 4.2.0](https://crates.io/api/v1/crates/keyring) (crates.io, 2026-10-11), [security-framework 3.7.0](https://crates.io/api/v1/crates/security-framework) for direct Keychain APIs. OAuth is now mandatory for Gmail ([Google Workspace Help](https://support.google.com/a/answer/14114704)) and Microsoft 365 — Basic auth was fully disabled for IMAP/POP/EWS in 2022, and SMTP AUTH basic is being rejected progressively from 2026-03-01 to 2026-04-30; SASL XOAUTH2 over IMAP/POP/SMTP is the supported path ([Microsoft: Basic auth deprecation](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-basic-authentication-exchange-online); [SMTP AUTH retirement](https://techcommunity.microsoft.com/blog/exchange/exchange-online-to-retire-basic-auth-for-client-submission-smtp-auth/4114750); [OAuth for IMAP/POP/SMTP](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)). Store refresh tokens, not passwords.
- **HTML rendering:** JavaScript off via `WKWebpagePreferences.allowsContentJavaScript` — the old `WKPreferences.javaScriptEnabled` is deprecated since macOS 11 with explicit guidance to use the per-navigation API ([WebKit WKPreferences.h](https://github.com/WebKit/webkit/blob/main/Source/WebKit/UIProcess/API/Cocoa/WKPreferences.h); [Apple docs](https://developer.apple.com/documentation/webkit/wkwebpagepreferences/allowscontentjavascript)). Even with JS off, remote content (images, CSS, fonts) is a tracking/exfiltration channel: default-block remote loads, proxy what the user allows.
- **EFAIL (USENIX Security 2018):** the canonical lesson — HTML mail is an exfiltration backchannel. CBC/CFB "malleability gadgets" let an attacker splice an `<img src=` into ciphertext; when the client decrypts and fetches remote content, plaintext leaks to the attacker's URL. Exfiltration channels existed in 23/35 S/MIME and 10/28 OpenPGP clients tested ([paper](https://www.usenix.org/conference/usenixsecurity18/presentation/poddebniak); [efail.de](https://efail.de/)). Design rule that survives even if Sweetbriar never ships PGP: *decrypted/plaintext content and remote-resource loading must never coexist in one render context.*
- **Keychain specifics:** store tokens `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` so they can't migrate off-device, and keep `kSecAttrSynchronizable` off for refresh tokens you don't want floating through iCloud Keychain ([Apple docs](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly); [kSecAttrSynchronizable](https://developer.apple.com/documentation/security/ksecattrsynchronizable)). Linux side: Secret Service over D-Bus via libsecret, fronting gnome-keyring/KWallet ([libsecret docs](https://gnome.pages.gitlab.gnome.org/libsecret/)).
- **Encryption at rest:** FileVault protects the powered-off machine but not files from a running compromised process ([Apple Platform Security](https://support.apple.com/guide/security/volume-encryption-with-filevault-sec4c6dc1b6e/web)). App-level option: SQLCipher — 256-bit AES, ~5–15% overhead, HMAC per page; note SQLCipher 4 won't open v1–3 DBs by default ([README](https://raw.githubusercontent.com/sqlcipher/sqlcipher/master/README.md)). Opinion: encrypt the *index* (keyed by a device-local secret in Keychain) rather than the raw .eml files — the latter would break the user-owns-the-format guarantee (see counter-argument in §4).
- **Remote content:** default-block all loads via `WKContentRuleListStore`-compiled rules ([docs](https://developer.apple.com/documentation/webkit/wkcontentruleliststore)); when the user allows remote content, fetch through a proxy — Apple's Mail Privacy Protection is the precedent ("hides your IP address") with an explicit "Load Content" bypass ([MPP](https://support.apple.com/en-us/HT212797)). "Images off" must also mean CSS off — CSS attribute-selector tricks exfiltrate without any images (EFAIL §2.6 above).
- **Phishing signals:** surface DKIM ([RFC 6376](https://www.rfc-editor.org/rfc/rfc6376.txt)) / DMARC ([RFC 7489](https://www.rfc-editor.org/rfc/rfc7489.txt)) / ARC ([RFC 8617](https://www.rfc-editor.org/rfc/rfc8617.txt)) results rather than a silent score; warn on IDN confusables — Chromium's IDN policy doc is a good model ("`ebаy.com`" with Cyrillic а) ([chromium idn.md](https://chromium.googlesource.com/chromium/src/+/main/docs/idn.md)). **BIMI is still only an Internet-Draft** (draft-14 as of today, [datatracker](https://datatracker.ietf.org/doc/draft-brand-indicators-for-message-identification/)) — display it as branding, never as a trust signal.
- **Attachment quarantine:** `com.apple.quarantine` is opt-in by the writing app (`LSFileQuarantineEnabled` Info.plist), recorded in the `QuarantineEventsV2` SQLite DB; Ventura adds a `com.apple.provenance` xattr ([Eclectic Light: quarantine flag](https://eclecticlight.co/2020/10/29/quarantine-and-the-quarantine-flag/); [Ventura provenance](https://eclecticlight.co/2023/03/13/ventura-has-changed-app-quarantine-with-a-new-xattr/)); Gatekeeper "tracks the provenance of files written by downloaded software" ([Apple Platform Security](https://support.apple.com/guide/security/gatekeeper-and-runtime-protection-sec5599b66df/web)). Sweetbriar should quarantine every attachment it writes so Gatekeeper treats them like browser downloads.
- **Parser robustness:** MIME is adversarial input. Rust MIME crates: mail-parser 0.11.9 (Stalwart), mailparse 0.18.0 (crates.io, 2026-10-11); MailCore2 (C++) still maintained (last push 2026-10-06, [repo](https://github.com/MailCore/mailcore2)). Even Rust parsers hit resource-exhaustion bugs — Stalwart's mail-parser had a Feb 2026 CVE for OOM on cyclical MIME structures ([CVE-2026-26312](https://github.com/stalwartlabs/stalwart/security/advisories/GHSA-jm95-876q-c9gw)). Rust kills the ~70%-of-CVEs memory-safety class ([MSRC, 2019](https://web.archive.org/web/2020/https://msrc.microsoft.com/blog/2019/07/we-need-a-safer-systems-programming-language/)) but panics on adversarial MIME are still DoS — fuzz decode paths (headers, charset, base64/QP, PKCS#7) with [cargo-fuzz 0.13.2](https://crates.io/api/v1/crates/cargo-fuzz) / [afl 0.18.2](https://crates.io/api/v1/crates/afl) and cap depth/size.
- **Sandbox/notarization:** App Sandbox + hardened runtime + notarization for macOS distribution ([entitlements docs](https://developer.apple.com/documentation/bundleresources/entitlements)); sandboxed apps can't just read `~/Library/Mail` — Apple Mail import goes through user-granted access (unverified detail — entitlement specifics for Mail import need checking against current docs).

### 2.7 Testing for correctness

The strongest evidence that a sync engine can be made trustworthy comes from three systems that all converged on the same architecture: **deterministic execution + seeded randomized fault injection**.

- **FoundationDB** runs its whole distributed DB in a deterministic simulator (built into the Flow runtime): tens of thousands of simulations nightly, ~10× simulated-to-real time, "equivalent of roughly one trillion CPU-hours" ([SIGMOD'21 paper](https://www.foundationdb.org/files/fdb-paper.pdf); [FDB testing docs](https://apple.github.io/foundationdb/testing.html)).
- **TigerBeetle's VOPR** does the same in Zig: clock/network/disk stubbed, seeded faults (dropped packets, partitions, disk corruption, replica crashes), reproducible by seed+commit; they later split "safety" vs "liveness" modes and (Aug 2026) published on protocol-aware DST that checks invariants per replica, contrasting with Jepsen-style black-box generative tests and Antithesis's hypervisor approach ([VOPR docs](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/internals/vopr.md); [simulator blog](https://tigerbeetle.com/blog/2023-07-11-we-put-a-distributed-database-in-the-browser/); [liveness mode](https://tigerbeetle.com/blog/2023-07-06-simulation-testing-for-liveness/); [protocol-aware DST](https://tigerbeetle.com/blog/2026-08-20-protocol-aware-dst/)).
- **Dropbox Nucleus** — the closest prior art, since it's a *client-side* sync engine: everything runs on a single "control" thread (I/O offloaded), state is three trees (remote / local / last-synced) with the invariant "all three converge," and they run tens of millions of seeded randomized test runs nightly; failing seeds replay deterministically ([Testing our new sync engine](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine); [Rewriting the heart](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)). Nucleus is written in Rust.
- **Antithesis** productized the idea for arbitrary binaries — deterministic hypervisor, fault injection, RL-guided state exploration, perfect replay ([Antithesis docs](https://antithesis.com/docs/introduction/how_antithesis_works/)).
- **Proof it's worth the build cost:** Antithesis reproduced the 16-year-old SQLite WAL-reset corruption (§2.3) in ~15 minutes of simulated time once pointed at the checkpoint path ([Antithesis blog](https://antithesis.com/blog/2026/wal-reset-bug/)); Tailscale needed months of production forensics for the same bug ([Tailscale blog](https://tailscale.com/blog/sqlite-wal-reset-bug)).
- **Property/model testing:** [proptest 1.12.0](https://crates.io/api/v1/crates/proptest) includes a documented state-machine harness ([proptest state-machine docs](https://proptest-rs.github.io/proptest/proptest/state-machine.html)) — implement an in-memory IMAP server model (RFC 3501/9051 semantics + UIDVALIDITY rules) and assert client and model agree across generated op sequences (fetch/flag/move/delete/expunge + reconnects + crashes); shrinking gives minimal repros.
- **Conformance:** Dovecot ships `imaptest`, "a generic IMAP server compliancy tester … Stress testing with state tracking, Scripted testing, Benchmarking" ([README](https://raw.githubusercontent.com/dovecot/imaptest/main/README.md); [docs](https://dovecot.github.io/imaptest/)) — it has an `imap4rev2` mode and seed-reproducible runs. Cyrus's Cassandane suite is now merged into the main repo ([cyrusimap/cassandane, archived](https://github.com/cyrusimap/cassandane)). Real-server CI matrix: Dovecot, Cyrus, Stalwart (JMAP+IMAP4rev2, embeddable Rust workspace), Gmail, M365, iCloud, Fastmail.
- **Fault injection list:** kill -9 mid-sync and mid-APPEND, ENOSPC, connection drop after SMTP DATA, UIDVALIDITY reset mid-session, mass-EXPUNGE events, fsync failure injection, latency/reset injection via [toxiproxy](https://github.com/Shopify/toxiproxy) (Shopify's TCP chaos proxy, actively maintained — last push 2026-10-08) or `tc netem`.

## 4. Recommendations for Sweetbriar (design + invariants)

The design that falls out of the evidence: **raw message files are the source of truth; SQLite is a derived index; every mutation of shared state goes through a durable, idempotent intent queue; and nothing irreversible happens on unverified data.** These are opinion, built on the facts above.

### 4.1 Storage layer

- **Layout:** `~/Library/Application Support/Sweetbriar/` (macOS), `~/.local/share/sweetbriar/` (Linux). Inside: `messages/` — a Maildir++-style tree (`<account>/<folder>/{tmp,new,cur}` — RFC 5322 bytes, one file per message, SHA-256 recorded at ingest); `index.sqlite` (headers, flags, threading, FTS5); `oplog.sqlite` (the intent queue + tombstones; may share the index DB but must be *authoritative*, not rebuildable); `settings.json` + `settings.json.bak` written via temp+rename.
- **Writes:** `tmp/` → fsync → `rename()` → fsync dirfd. Never modify a message file; flag/state changes go in the index (not filename churn — see trade-off below).
- **SQLite:** bundled amalgamation ≥3.51.3 via rusqlite `bundled` (never the system SQLite); WAL; `synchronous=FULL`; `fullfsync=ON` + `checkpoint_fullfsync=ON` on macOS; `journal_size_limit`; single-writer connection; `TRUNCATE` checkpoint on idle; `VACUUM INTO` snapshot before migrations; `PRAGMA integrity_check` weekly and post-migration; per-message SHA-256 verified on read.
- **Backup posture:** message store included in Time Machine; index/FTS/caches excluded via `CSBackupSetItemExcluded(excludeByPath=true)`; warn loudly if the data dir lands inside Dropbox/iCloud/OneDrive/a network mount.

*Trade-off — flags in index vs flags in filename:* strict Maildir puts flags in the filename (`cur/…:2,FRS`), which makes every flag flip a rename — Time Machine then backs the file up again and directory metadata churns. Sweetbriar keeps the Maildir *atomicity discipline* but stores flags only in the index + a small per-folder `flags.json` journal for disaster recovery. Cost: flag state isn't fully recoverable from filenames alone after total index loss. That's acceptable — seen/flagged state is the least valuable byte in the store and `flags.json` covers it.

*Counter-argument (strongest):* "Just use SQLite blobs — transactions give you everything for free." It does give atomicity, but it concentrates all risk in one file (every incident in §2.1 is a single-file-format story), makes the mail unreadable without the app (violates the user-owns-format goal), makes Time Machine deltas huge, and removes the per-message repair boundary. The hybrid keeps both benefits.

### 4.2 Sync engine

- **Intent queue:** every mutation (send, delete, move, flag, draft-save, settings-affecting-server) is a row `{id, account, op, payload, state, idem-key, attempts, created}` committed in the same transaction as its local effects. A single writer thread drains it; per-account ordering for ops touching the same messages; a poisoned op parks after N attempts and surfaces to the user instead of blocking the queue (K-9 #1155).
- **Idempotent replay:** deletes replays as "ensure UID X has \Deleted and is expunged-if-mine"; moves as "ensure message with hash H is in folder B and not in A (verify via COPYUID/MOVE result)"; sends as §2.5's sent-folder-lookup protocol. Replay is a *state-convergence* check, not a blind command re-issue.
- **Delete path:** default delete = move to server Trash (UID MOVE; else COPY→verify COPYUID→`UID STORE \Deleted`→`UID EXPUNGE`). "Delete permanently" is a separate, confirmed op. Bare `EXPUNGE` is never emitted — enforce by making the IMAP layer's API have no such verb.
- **Circuit breaker:** before propagating deletions, sanity-check: if the to-be-deleted set exceeds a threshold (suggest: >50 messages or >20% of the folder, whichever first) since last sync, or UIDVALIDITY changed and the reconciliation produces mass deletes, pause the queue and ask the user. Log the trigger.
- **UIDVALIDITY:** on change, freeze the folder's intent queue, re-sync headers from scratch, rebuild the UID→message map by Message-ID/hash matching, *then* resume. Stale UIDs must never reach a STORE/EXPUNGE (Proton Bridge lesson).
- **Gmail:** treat Gmail's IMAP as its own dialect — read `ImapSettings` semantics (autoExpunge/expungeBehavior) from account config or assume `archive` semantics; prefer the Gmail API path where label fidelity matters.
- **JMAP:** the Email/mailboxIds model is the cleanest move semantics — implement JMAP backends natively, IMAP with the safety rules above.

*Trade-off:* convergence-check replay costs a few extra round-trips vs blind retry — irrelevant at mail scale. The real cost is engineering discipline: every op needs a "did it already happen?" predicate. The counter-argument is Mailspring's approach (persist ops, drop them on crash) — simpler, and acceptable to some users, but it's exactly the class of bug this report exists to prevent.

### 4.3 Outbox and drafts

- Outbox = intent-queue ops of type `send` with states `held (undo window) → queued → smtp-in-flight → sent-unconfirmed → confirmed | failed`. Same Message-ID across retries; post-DATA ambiguity resolved by Sent-folder lookup by Message-ID before any resend; UI shows "possibly sent" — never silent duplicate, never silent drop. 4yz → backoff with jitter; 5yz → fail to user. SIZE declared up front; >threshold attachments go through a link-upload path (Mail Drop-style; provider-specific implementations).
- Drafts: content-addressed local journal (append-only snapshots, debounced + on-blur/on-quit, fsync before "saved"); sync to server Drafts via APPEND/UIDPLUS, REPLACE where advertised; one stable Message-ID per draft lifetime; version history kept locally.

### 4.4 Security defaults

- OAuth everywhere a provider supports it (mandatory for Google + Microsoft in 2026); refresh tokens in Keychain (`ThisDeviceOnly`, non-synchronizable) / libsecret on Linux; never log tokens.
- Rendering: WKWebView, `allowsContentJavaScript=false`, `WKContentRuleList` blocking all remote loads; per-message "load remote content" that routes through a proxy; decrypted content renders in a hermetic context that never loads remote resources (EFAIL rule); attachments written with `com.apple.quarantine`.
- Fuzz all MIME/charset/base64/QP decode paths with cargo-fuzz; depth/size caps; panics are crash-bugs — run parsers behind a guard that turns a panic into "message render failed" rather than a process death.

### 4.5 Test matrix per invariant

| Invariant | Enforcement | Test |
|---|---|---|
| I1 file never modified | Maildir write discipline; no compaction code exists | kill -9 + ENOSPC during ingest; verify no torn/partial files; fsync-failure injection |
| I2 index rebuildable | derived-index design; migration backups | delete `index.sqlite`, rebuild, byte-compare headers/flags vs golden; corrupt-page injection then rebuild |
| I3 no bare EXPUNGE | IMAP client API lacks the verb | model test asserting command grammar; code review + property test |
| I4 intents durable+idempotent | oplog in same txn; convergence replay | crash at every queue state; duplicate-replay; queue-poison isolation |
| I5 mass-delete breaker | threshold check pre-propagation | simulated mass-EXPUNGE/UIDVALIDITY reset; assert queue pauses |
| I6 credential safety | Keychain/Secret Service only | scan store dir for token patterns; assert zero plaintext secrets |
| I7 safe rendering | JS off + content rules + proxy | canary-pixel test: remote load must not fire without consent; EFAIL-style HTML corpus |
| I8 at-most-once visible send | same Message-ID; Sent dedup; `sent-unconfirmed` state | drop after DATA, reconnect, assert single send + correct state |
| I9 no destructive defaults | settings-migration golden files | upgrade-path tests: every persisted setting survives with equal-or-safer semantics (K-9 #9034) |
| I10 verify before overwrite | migration checksummed count verify | faulted migration; assert old data retained until verify passes (Catalina) |

### 4.6 The strongest counter-argument to all of this

The fully-durable design costs roughly 2–3× the code of a naive sync engine and forces uncomfortable UI honesty ("possibly sent", "deletion paused pending confirmation"). A defensible opposing position: *email is already replicated — the server is the backup — so a client that just caches and shows truth-on-server needs no durability heroics.* That position is coherent for pure-IMAP view-only usage, but fails the moment the client does anything the server can't undo: local-only folders, sent-mail bookkeeping, offline deletes queued for later, migrations, and — the Catalina case — local bugs that propagate to the server. Once you accept that local state can corrupt shared state, you need the queue, the tombstones, and the circuit breaker; the rest is engineering degree-of-care. The recommendation stands, but the honest price is that Sweetbriar's sync engine must be built as a state machine from day one — retrofitting this discipline onto a growing codebase is how you get Mailspring's drop-on-crash queue.

## 5. Risks and open questions

1. **JMAP coverage is thin outside Fastmail/Stalwart.** Gmail and Microsoft have no JMAP endpoints; the JMAP path pays off mainly for Fastmail/Cyrus/Stalwart/imap4rev2-native providers. Open: how much of the JMAP abstraction to build before second provider lands (recommend: design the sync engine protocol-agnostic with IMAP and JMAP backends, ship IMAP first).
2. **Gmail is a dialect, not an IMAP server.** Label semantics, All Mail, expungeBehavior — dual-path complexity is real. Alternative (Gmail API) has quota/rate limits and its own failure modes. Open: IMAP-dialect first vs API-first for Gmail.
3. **Microsoft 365 protocol surface.** OAuth is mandatory; XOAUTH2 over IMAP/SMTP works but is legacy-protocol; Microsoft Graph gives richer semantics but a different consistency model. Open: Graph vs IMAP/SMTP-XOAUTH2 for M365 accounts (likely both — Graph for mail, SMTP-XOAUTH2 for send).
4. **Proton** needs Bridge or a from-scratch crypto+API stack — Bridge coupling means inheriting its failure modes (§2.1). Open: Bridge vs direct API (major effort either way).
5. **Time Machine churn** from per-message files — flag changes as index-only updates mitigate; measure real-world churn. Open: should `flags.json` journal be per-folder or per-account?
6. **App Sandbox entitlement specifics** for a mail client that must also import from `~/Library/Mail` and write outside its container — needs verification against current Apple docs (flagged unverified in §2.6).
7. **Attachment-heavy messages**: multi-GB single MIME blobs stress the one-file-per-message model. Open: content-addressed parts store for large bodies, or keep monolithic (simpler, matches Maildir precedent)?
8. **Search index choice**: FTS5 keeps one durability story; Tantivy is faster/fancier but adds a second storage engine with its own crash semantics. Open: FTS5 until proven insufficient.
9. **No vendor publishes sync-engine postmortems** (mbsync's INHERENT PROBLEMS section is the honorable exception). The incident record is skewed to what users could observe; assume more failure modes exist than are documented.
10. **Deterministic simulation is a multi-month investment** — schedule it early (§2.7 shows it finds what production takes months to surface), but it's the first thing a small team cuts. That's a project-management risk, not a technical one.
