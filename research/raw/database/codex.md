# Sweetbriar local store: database research

Research date: **2026-10-11**. Scope: a single-user native macOS app with a reusable Rust core, later Linux. All current-status observations are as of this date; dated releases and historical incidents are identified separately. Facts have inline sources. Recommendations and architectural inferences are labeled. Local measurements are supported by the accompanying benchmark artifacts.

## 1. TL;DR

- **Recommendation: bundled SQLite for the desktop store.** It is a transactional SQL database; a private PostgreSQL server would add useful capabilities but does not itself establish greater power-loss safety. [SQLite overview](https://www.sqlite.org/about.html), [PostgreSQL reliability](https://www.postgresql.org/docs/current/wal-reliability.html).
- Keep SQLite's WAL mode, `synchronous=FULL`, and macOS `fullfsync=ON`; verify settings on every connection that can write or checkpoint. SQLite documents stronger WAL commit synchronization with FULL and `F_FULLFSYNC` with the macOS option. [SQLite PRAGMAs](https://www.sqlite.org/pragma.html).
- Keep the proposed **SQLite 3.51.3+ safety floor** for the WAL-reset fix, released 2026-03-13. A single designated writer does not prove immunity when another connection checkpoints. Fixed older backports also exist. [SQLite WAL-reset explanation](https://www.sqlite.org/wal.html#walresetbug).
- PostgreSQL has valuable checksums and PITR tooling, but the desktop application must own its server lifecycle, major upgrades, backups, and collation maintenance. [Checksums](https://www.postgresql.org/docs/current/checksums.html), [PITR](https://www.postgresql.org/docs/current/continuous-archiving.html), [versioning policy](https://www.postgresql.org/support/versioning/).
- **Measured here:** at one million rows, warm SQLite point reads/pages took about 5.9/57 μs versus PostgreSQL's 148/324 μs. PostgreSQL COPY was competitive on bulk loading; the experiment is Linux/Python, not a macOS/Rust capacity or durability proof. See the methodology below.
- **The closest precedent has changed:** Akonadi now defaults upstream to SQLite; Gentoo followed on 2026-05-23, citing daemon and upgrade costs. This is stronger evidence than old “KMail needs MySQL” advice. [Gentoo notice](https://www.gentoo.org/support/news-items/2026-05-23-kdepim-sql-backend-change.html).
- **Turso deserves monitoring:** its Rust MVCC engine dropped the general beta warning on 2026-07-13. It remains a newer implementation requiring product-specific durability and compatibility qualification. [Turso 0.7](https://turso.tech/blog/turso-0.7.0).
- **Spend safety effort on the entire persistence protocol:** immutable originals, transactional intents and draft revisions, coherent off-device backups, reversible migrations and crash/fault tests. A database transaction alone does not atomically include external files. [SQLite atomic-commit boundaries](https://www.sqlite.org/atomiccommit.html), [PostgreSQL backup boundaries](https://www.postgresql.org/docs/current/continuous-archiving.html).
- **Choose PostgreSQL for a future shared service when its concurrency and recovery tools justify operations.** Desktop caches can still use SQLite. This is a recommendation based on the capabilities and costs assessed below.

## 2. Findings

### Data safety

**Facts, checked 2026-10-11:** PostgreSQL's current stable series remains 18; the support table lists **18.6, released 2026-08-13**, while PostgreSQL 19 is beta. SQLite's release history lists **3.54.0, released 2026-10-09**; 3.51.3 is a safety floor, not the latest release. [PostgreSQL versions](https://www.postgresql.org/support/versioning/), [18.6 release](https://www.postgresql.org/docs/release/18.6/), [SQLite releases](https://www.sqlite.org/changes.html).

SQLite's WAL allows readers and a writer concurrently, with one writer at a time. In WAL mode, `synchronous=FULL` adds a WAL sync before each transaction is reported committed; NORMAL retains consistency but can lose recent commits after a power failure. On macOS, `fullfsync=ON` requests `F_FULLFSYNC`; when enabled it also covers checkpoint syncs, making `checkpoint_fullfsync` redundant. [Isolation](https://www.sqlite.org/isolation.html), [PRAGMAs](https://www.sqlite.org/pragma.html).

PostgreSQL requires `fsync=on`, `synchronous_commit=on`, and `full_page_writes=on` for the intended durable configuration. `wal_sync_method=fsync_writethrough` is its documented macOS option for flushing volatile drive caches; its implementation uses `fcntl(F_FULLFSYNC)`. `pg_test_fsync` measures method costs, but is not a physical power-cut proof. [WAL settings](https://www.postgresql.org/docs/current/runtime-config-wal.html), [reliability](https://www.postgresql.org/docs/current/wal-reliability.html), [flush implementation](https://raw.githubusercontent.com/postgres/postgres/REL_18_STABLE/src/backend/storage/file/fd.c).

The **2018 fsyncgate** issue concerned kernel writeback errors that could discard dirty buffers or disappear across close/reopen. Retrying `fsync` could then falsely succeed. PostgreSQL changed to PANIC and recover rather than continue after a synchronization failure; the fix reached PostgreSQL 11.2 on **2019-02-14**, with backports to other supported branches. This was a real safety failure, but not a reason to reject corrected PostgreSQL in 2026. [PostgreSQL fsync investigation](https://wiki.postgresql.org/wiki/Fsync_Errors), [11.2 release notes](https://www.postgresql.org/docs/11/release-11-2.html).

The **2026 SQLite WAL-reset bug** was found and fixed on 2026-03-03 and released in 3.51.3 on 2026-03-13, with backports in 3.44.6 and 3.50.7. It requires at least two connections, in separate threads or processes, racing writes/checkpoints; the documented affected range is probably 3.7.0 through 3.51.2. Developers used special scheduling instrumentation to reproduce it. Version 3.52.0 was withdrawn for a separate expression-index compatibility issue. [WAL-reset bug](https://www.sqlite.org/wal.html#walresetbug), [release history](https://www.sqlite.org/changes.html).

SQLite documents 100% branch/MC/DC coverage of its core through the proprietary TH3 harness, simulated crash and power-loss tests, fault injection, and SQL/database fuzzing. Public TCL tests also exist; TH3 is not simply a freely available CI dependency. Those are unusually strong engineering evidence, not proof of zero defects: a long-lived race still escaped. Neither project's published bug counts establish comparable field failure rates. [SQLite testing](https://www.sqlite.org/testing.html).

Corruption history extends beyond these headline incidents. SQLite documents past journal/locking defects and integration hazards such as aliases, broken filesystem locks, inherited handles across `fork`, and copying a live store incorrectly. PostgreSQL 18.6 includes fixes with possible reindexing requirements for `btree_gist` and `ltree`; a minor update can require more than replacing a binary. Keep a maintenance-update and integrity-audit policy for either engine. Restrict the authoritative store to a supported local filesystem rather than treating a network or cloud-synchronized folder as interchangeable. [SQLite corruption catalogue](https://www.sqlite.org/howtocorrupt.html), [PostgreSQL 18.6 maintenance notes](https://www.postgresql.org/docs/release/18.6/).

PostgreSQL 18 enables data-page checksums by default for newly initialized clusters. Inspect `SHOW data_checksums` on existing or upgraded clusters; `pg_checksums` checks/enables them offline. SQLite's optional `cksumvfs` adds eight checksum bytes per page, requires eight reserved bytes, and reports bad pages with `SQLITE_IOERR_DATA`; it is not built into the default SQLite VFS. SQLite WAL-frame checksums do not provide this protection for all main-database pages. Checksums detect damage and do not recreate lost data. [PostgreSQL checksums](https://www.postgresql.org/docs/current/checksums.html), [SQLite checksum VFS](https://www.sqlite.org/cksumvfs.html), [WAL format](https://www.sqlite.org/fileformat2.html).

For SQLite, use the online backup API for coherent live snapshots, or `VACUUM INTO` for a compact snapshot. Current `VACUUM INTO` documentation says it syncs the output when the source's synchronous setting is NORMAL or FULL; an interrupted output is still disposable. Copying the main database file while committed data remain in WAL is unsafe. Litestream adds asynchronous off-device replication and recovery, with a lag window and its own checkpoint integration. [Backup API](https://www.sqlite.org/backup.html), [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html), [WAL](https://www.sqlite.org/wal.html), [Litestream design](https://litestream.io/how-it-works/).

PostgreSQL's `pg_basebackup` and archived WAL support physical recovery to a chosen time. This is a substantive operational advantage when Sweetbriar needs frequent historical recovery, provided archive continuity and restore tests actually work. Neither database backup automatically includes external immutable message files. [pg_basebackup](https://www.postgresql.org/docs/current/app-pgbasebackup.html), [PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).

For damaged databases, SQLite offers `integrity_check` and `.recover`/the recovery extension; salvaged data may violate original constraints. PostgreSQL offers `amcheck`/`pg_amcheck`, checksums, and REINDEX for index damage; `pg_resetwal` is a last-resort salvage tool whose output must immediately be dumped and rebuilt. Sweetbriar should preserve the damaged store and recover into a new one, never silently present salvage as a complete restoration. [SQLite recovery](https://www.sqlite.org/recovery.html), [PostgreSQL amcheck](https://www.postgresql.org/docs/current/amcheck.html), [pg_resetwal](https://www.postgresql.org/docs/current/app-pgresetwal.html).

PostgreSQL publishes annual major releases with five years of support; upgrading annually is optional, but a long-lived product must eventually move off unsupported majors. Major changes require `pg_upgrade` or dump/restore. An unattended desktop updater must retain old binaries and a rollback copy, stop both clusters, handle extensions, migrations, space exhaustion and interruption, and verify the new cluster before switching. `pg_upgrade --clone` supports APFS, while hard-link mode restricts rollback once the new cluster runs. Minor upgrades normally replace binaries without converting the cluster. [Versioning policy](https://www.postgresql.org/support/versioning/), [pg_upgrade](https://www.postgresql.org/docs/current/pgupgrade.html).

Changing glibc or ICU collation rules can invalidate text indexes without changing their bytes or checksums, producing incorrect/missing query results. PostgreSQL warns about recorded version mismatches, but `REFRESH VERSION` only updates metadata: rebuild affected objects first. ICU version tracking is available across platforms; libc tracking is documented for GNU libc, FreeBSD and Windows, so do not assume a macOS libc change will produce that warning. An OS/library update can trigger this without a PostgreSQL major upgrade. SQLite custom collations have the same semantic risk if their comparator changes. Prefer stable bytewise keys for identity and separately versioned display/search sort keys. [PostgreSQL collation notes](https://www.postgresql.org/docs/current/sql-altercollation.html), [glibc collation history](https://wiki.postgresql.org/wiki/Collations), [SQLite comparator requirements](https://www.sqlite.org/c3ref/create_collation.html).

### Speed for Sweetbriar's workload

SQLite avoids an interprocess round trip for each query. PostgreSQL's Unix socket avoids a network hop but still needs protocol messages, scheduling, and value conversion. PostgreSQL's MVCC permits concurrent writers; SQLite WAL readers run alongside its single writer. For a desktop app, the important question is whether a short, prioritized writer queue becomes a measured bottleneck. [SQLite query costs](https://www.sqlite.org/np1queryprob.html), [SQLite isolation](https://www.sqlite.org/isolation.html), [PostgreSQL concurrency](https://www.postgresql.org/docs/current/mvcc.html).

Both designs need transaction discipline. Long SQLite read snapshots can hold back checkpoints; PostgreSQL retains old row versions and needs VACUUM, with long-lived transactions limiting reclamation. Concurrent writers also need conflict handling and do not eliminate I/O costs. A synchronous durable commit for every individual downloaded row is a different workload from batched transactions; match commit granularity before comparing engines. [SQLite WAL](https://www.sqlite.org/wal.html), [PostgreSQL vacuum](https://www.postgresql.org/docs/current/routine-vacuuming.html).

For a mailbox list, prefer a covering index starting with `(mailbox_id, received_at DESC, id DESC)` and a keyset cursor `(received_at,id)`, with `id` breaking timestamp ties. PostgreSQL supports `INCLUDE` payload columns; its index-only scans can still visit the heap when the visibility map is not set. Bulk PostgreSQL imports should use COPY, rather than serial per-row requests. [PostgreSQL covering indexes](https://www.postgresql.org/docs/current/indexes-index-only-scans.html), [bulk loading](https://www.postgresql.org/docs/current/populate.html).

**Local experiment, 2026-10-11:** [benchmark.py](codex-artifacts/benchmark/benchmark.py) and [results.json](codex-artifacts/benchmark/results.json) contain a reproducible synthetic test: 100,000 and 1,000,000 messages across ten mailboxes, 1,000-row transactions, an existing list index, 10,000 random point queries and 500 keyset queries returning up to 100 rows. Three repetitions were completed. Message bodies, full-text search, concurrency, and power-cut durability were not tested. Data generation is excluded from insert timers; a final checkpoint is timed separately. Both implementations retrieve results into Python and reuse statements. The 100k-row mailbox wraps, producing four empty pages among 500 queries; at 1M all pages return 100 rows.

Environment: Linux 7.0.0-38, x86-64 Intel Xeon W-2145, 16 logical CPUs, approximately 125.5 GiB visible RAM, ext4 on `/dev/md2`; underlying device type and cache protection are unknown. SQLite **3.53.4**, via APSW 3.53.4.0; PostgreSQL **16.2**, from the local `pgserver==0.1.4` wheel, via psycopg 3.3.6 and a Unix socket. The old PostgreSQL binary is a benchmark convenience, not a recommended shipping version. No system-wide packages were installed. SQLite used WAL/FULL; PostgreSQL used `fsync=on`, `synchronous_commit=on`, `full_page_writes=on`, `wal_sync_method=fdatasync`, and enabled page checksums. Each engine had a 64 MiB configured database cache/buffer pool.

The OS cache was warm and not dropped; engine order was fixed and the host was shared. SQLite's `fullfsync` was off on Linux, so the measurements do not compare the proposed Mac F_FULLFSYNC configurations. PostgreSQL used C locale. Checksums were enabled only for PostgreSQL. [Reproduction notes](codex-artifacts/benchmark/README.md) record dependencies and commands. Psycopg documents automatic pipelining inside `executemany`; the PostgreSQL test therefore avoids a separate round trip per inserted row. [APSW](https://rogerbinns.github.io/apsw/), [pgserver distribution](https://pypi.org/project/pgserver/), [psycopg pipeline behavior](https://www.psycopg.org/psycopg3/docs/advanced/pipeline.html).

Insert times below are medians, with the range of the three repetitions in parentheses:

| Rows | SQLite executemany | PostgreSQL pipelined executemany | PostgreSQL COPY |
|---|---:|---:|---:|
| 100,000 | 1.31 s (1.19–1.32) | 2.50 s (2.26–2.71) | 1.64 s (1.46–1.88) |
| 1,000,000 | 25.58 s (12.10–26.83) | 34.58 s (33.97–56.39) | 19.36 s (18.76–23.88) |

Warm query times are medians of the three run medians:

| Rows | SQLite point / 100-row page | PostgreSQL point / 100-row page, COPY-loaded |
|---|---:|---:|
| 100,000 | 3.9 μs / 53.0 μs | 118.5 μs / 282.9 μs |
| 1,000,000 | 5.9 μs / 57.2 μs | 147.7 μs / 324.2 μs |

Plans confirmed a SQLite covering-index search and a PostgreSQL index-only scan after VACUUM, with no heap fetches in the captured PostgreSQL page plan. At 1M rows the SQLite database was about 270 MiB, and PostgreSQL's table and indexes about 363 MiB, excluding WAL and cluster-wide overhead. Median p95 query latencies at that size were 9.4 μs/108.9 μs for SQLite point/page reads, and 240.9 μs/709.3 μs for COPY-loaded PostgreSQL. These include each driver's costs, not only engine execution.

**COPY had the lower committed-insert time at 1M rows.** Its separately timed final CHECKPOINT took a median 6.26 seconds; SQLite's final checkpoint took 0.0007 seconds after checkpoints already performed during loading. Adding each run's load and final checkpoint, then taking the median, gives **26.91 seconds for COPY and 25.58 seconds for SQLite**. Both had already synchronized commits through their logs before that final checkpoint. The shared host had substantial timing variation, so these totals and write ratios do not establish a general speed winner. SQLite's small reads were substantially faster in this setup.

A published Apple M2 Pro benchmark reports 23,403 versus 7,740 sequential inserts/s, and PostgreSQL reaching 35,370 operations/s with 16 connections. However, it compares SQLite `synchronous=NORMAL` with PostgreSQL `synchronous_commit=on`, so its headline write ratios do not compare equal durable-commit policies. Its authors provide code and disclose the configuration; it is useful evidence of IPC and concurrency effects, not a production capacity estimate. [Published benchmark](https://github.com/andrecasal/sqlite-vs-postgres-benchmark).

SQLite FTS5 supports phrases, prefixes, NEAR, column filters, BM25 and custom tokenizers. PostgreSQL offers `tsvector`/`tsquery` with GIN indexes, dictionaries and language configuration. A separate Rust Tantivy index is another option; evaluate multilingual mail, attachment text, typo tolerance and ranking on a representative corpus. These search features do not require making search authoritative. [FTS5](https://www.sqlite.org/fts5.html), [PostgreSQL FTS indexes](https://www.postgresql.org/docs/current/textsearch-indexes.html), [Tantivy](https://github.com/quickwit-oss/tantivy).

Published FTS comparisons also need scrutiny. VADOSWARE publishes a reproducible PostgreSQL/SQLite/search-server benchmark over movie descriptions, not mail. A sqlite-tantivy author's **2026-01-20** Apple-silicon/Gutenberg benchmark reports 9 μs versus 299 μs median search latency, but compares slightly different document counts and one query class; I did not reproduce or establish semantic/ranking equivalence. Neither justifies a general engine speed ratio for Sweetbriar. SQLite's own email-index example illustrates a separate trade-off: 1,636 MiB of mail produced 743/340/134 MiB indexes for `detail=full/column/none`, with reduced phrase/NEAR capabilities as detail is removed. Search configuration and quality requirements can matter as much as metadata-engine choice. [FTS comparison harness](https://github.com/VADOSWARE/fts-benchmark/), [Tantivy comparison and disclosed limits](https://github.com/russellromney/sqlite-tantivy/blob/main/BENCHMARK_RESULTS.md), [FTS5 index-detail example](https://www.sqlite.org/fts5.html#the_detail_option).

### Shipping a server database and the Akonadi precedent

**Bundling PostgreSQL is feasible; operating it reliably is the larger commitment.** In this experiment its uncompressed installation occupied 28.2 MiB. Initialization took 0.82 s and an already initialized cluster reached its first connection in 73 ms. Seven processes, including one client backend, used about 14.8 MiB summed proportional set size while idle and 85.1 MiB after the workload. These are local Linux measurements, not macOS launch or battery predictions; summed RSS would count shared pages repeatedly.

For comparison, the Postgres.app download page lists a **123 MB** single-version PostgreSQL 18 distribution and a **533 MB** multi-version distribution, checked 2026-10-11. Those include packaging and extensions, so neither number is the minimum Sweetbriar would need. Postgres.app demonstrates a Mac bundle; Blackmagic's historical Resolve 10 Mac guide also documents supplying PostgreSQL for local or shared project databases. Neither establishes current Mac App Store approval for an invisible mail-store server. [Postgres.app downloads](https://postgresapp.com/downloads.html), [Postgres.app documentation](https://postgresapp.com/documentation/), [Resolve 10 guide](https://documents.blackmagicdesign.com/ConfigGuides/DaVinci_Resolve_10_Mac_Config_Guide.pdf).

**Engineering assessment:** Sweetbriar would need signed server/helper executables and libraries, initialization, readiness checks, exclusive ownership of each cluster, connection recovery, shutdown, crash restart, log rotation, autovacuum monitoring, disk-space management, and the upgrade/rollback protocol described above. Run the server as the user, inside the app's own storage, with a private Unix socket and `listen_addresses=''`; avoid a global service or public port. PostgreSQL documents independent TCP-listen and Unix-socket configuration. SQLite eliminates the database-service lifecycle, although its checkpoints, migrations and errors still need management. [Connection settings](https://www.postgresql.org/docs/current/runtime-config-connection.html), [vacuum maintenance](https://www.postgresql.org/docs/current/routine-vacuuming.html).

**macOS constraints, checked 2026-10-11:** Apple's archived sandbox guidance permits child processes to inherit a sandbox through `com.apple.security.app-sandbox` and `com.apple.security.inherit`; dynamically granted file access is not automatically equivalent to static inherited entitlements. Current app-group documentation permits Unix-domain-socket IPC inside the group container, subject to socket-path limits. Mac App Store guideline 2.4.5 requires appropriate sandboxing and a self-contained app bundle without third-party installers or installation in shared locations. These rules do **not** establish a blanket ban on a bundled database process. A signed PostgreSQL prototype actually running, upgrading and recovering inside the macOS 27 sandbox remains **unverified**. Developer ID distribution avoids the Store submission requirement but still needs a tested signing, notarization and sandbox design. [Sandbox entitlements](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html), [app groups](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.application-groups), [review guidelines](https://developer.apple.com/app-store/review/guidelines/).

Flatpak gives applications private persistent XDG directories and restricts host access by default. A bundled server could keep its cluster there and use a socket inside the sandbox; this is an architectural inference, not a tested Sweetbriar package. A `.deb` should likewise keep application ownership of its private cluster rather than depend on whatever PostgreSQL major version the distribution upgrades globally. Flatpak runtime changes can still change linked ICU/glibc behavior, so bundling alone does not solve collation maintenance. [Flatpak permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html), [directory conventions](https://docs.flatpak.org/en/latest/conventions.html), [PostgreSQL collation warnings](https://www.postgresql.org/docs/current/sql-altercollation.html).

#### Akonadi: the closest precedent

Akonadi centralizes mail, contacts and calendar data for several PIM applications. Its database holds cached data and management metadata, while canonical content can live in Maildir, calendar files or remote services. Crucially, its documentation qualifies safe cache deletion on **all pending changes having synchronized**. Calling this database wholly disposable misses offline changes. Sweetbriar's drafts, settings and intent journal are even more explicitly authoritative. [Akonadi user documentation](https://userbase.kde.org/Akonadi).

Historically Akonadi selected MySQL because its SQLite backend was unsuitable for KMail's workload. KDE also documented difficulties with the actual embedded MySQL library: transaction-engine availability and deployment problems led to running a separate local `mysqld`, rather than linking an in-process MySQL engine. PostgreSQL was another supported backend. This history is evidence about that implementation and era, not a finding that modern SQLite cannot support mail. [Historical KDE architecture/FAQ](https://techbase.kde.org/KDE_PIM/Akonadi), [Gentoo's retrospective](https://www.gentoo.org/support/news-items/2026-05-23-kdepim-sql-backend-change.html).

The important 2026 change is verified in both upstream history and released code:

- KDE merged the switch to SQLite as the default on **2026-01-27**. Akonadi **v26.08.2** has `DATABASE_BACKEND="SQLITE"` as its build default; distributions can override it. [Merge record](https://invent.kde.org/api/v4/projects/pim%2Fakonadi/merge_requests/311), [released CMake configuration](https://invent.kde.org/pim/akonadi/-/raw/v26.08.2/CMakeLists.txt).
- Gentoo's **2026-05-23** notice makes SQLite the highest-priority backend for new KDE PIM 26.04.1 configurations. It cites daemon problems, extra database packages and mostly database-upgrade handling bugs, and says upstream work has made SQLite viable again. Existing user configurations are preserved. [Gentoo notice](https://www.gentoo.org/support/news-items/2026-05-23-kdepim-sql-backend-change.html).
- Backend switching now has a real migration tool, `akonadi-db-migrator --newengine sqlite|mysql|postgres`, rather than requiring deletion and resynchronization. Older wiki references to MySQL as the default should not override the release source. [Akonadi migration instructions](https://userbase.kde.org/Akonadi).

Akonadi's PostgreSQL support is more capable than “users must always run pg_upgrade manually.” Released v26.08.2 detects a major-version mismatch, searches for old binaries in several distribution layouts, initializes a new UTF-8/C-locale cluster using `--no-locale`, runs `pg_upgrade`, and switches directories. Missing old binaries or upgrade failure still require intervention. The user-facing PostgreSQL upgrade page, updated **2026-05-04**, documents the manual path. This substantial integration code is precisely the support obligation Sweetbriar would inherit. [Released PostgreSQL backend](https://invent.kde.org/pim/akonadi/-/raw/v26.08.2/src/server/storage/dbconfigpostgresql.cpp), [upgrade instructions](https://userbase.kde.org/Akonadi/Postgres_update).

Two concrete incidents illustrate the obligation, without proving a comparative corruption rate. A Fedora 34 upgrade report in **April 2021** describes a MariaDB 10.4→10.5 transition failing on an unclean old redo log; recovery required the older server and a clean shutdown. A KDE report in **December 2025** describes MariaDB 12.1 rejecting SQL used in Akonadi's initialization. These are version/integration failures; they do not establish that current PostgreSQL loses mail or that SQLite applications cannot fail similarly. [Fedora incident](https://bugzilla.redhat.com/show_bug.cgi?id=1953675), [KDE incident](https://bugs.kde.org/show_bug.cgi?id=512859).

Durability settings also matter when interpreting Akonadi anecdotes: v26.08.2's SQLite setup explicitly selects WAL and `synchronous=1` (NORMAL), while its MySQL configuration selects `innodb_flush_log_at_trx_commit=2`, which does not flush the log to stable storage on each commit. Neither is Sweetbriar's proposed FULL policy for authoritative edits. Their performance or power-loss experience cannot be transferred without matching settings. [SQLite backend](https://invent.kde.org/pim/akonadi/-/raw/v26.08.2/src/server/storage/dbconfigsqlite.cpp), [MySQL configuration](https://invent.kde.org/pim/akonadi/-/raw/v26.08.2/src/server/storage/mysql-global.conf), [MariaDB variable semantics](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables).

**Inference for Sweetbriar:** Akonadi proves that a private server database can work for PIM, including many independent clients. Its 2026 move toward SQLite is strong evidence that service and upgrade costs matter in desktop software. It supplies no controlled benchmark or field-failure denominator establishing an engine's universal superiority.

#### What the SQLite precedents actually show

These observations were checked on 2026-10-11. They identify storage choices, not independently audited durability guarantees.

| Product | Verified storage use | Relevance and limit |
|---|---|---|
| Apple Mail | Independent tools read the SQLite `Envelope Index` and `.emlx` files. [Parser author's implementation](https://github.com/maxgribov/apple-mail-parser) | A metadata/file split is established by direct users of the format. Exact macOS 27 internals and flush settings are **unverified**; Apple supplies no storage contract here. |
| Thunderbird | SQLite Gloda `global-messages-db.sqlite` is rebuildable search data; current folder-storage docs describe mbox/Maildir and Mork `.msf`, with a global SQLite database under development. [Gloda](https://support.mozilla.org/en-US/kb/rebuilding-global-database), [folder storage](https://source-docs.thunderbird.net/en/latest/backend/folder_storage.html) | “Thunderbird stores all authoritative mail in SQLite” would be inaccurate. |
| Mailspring | Its C++ sync engine maintains SQLite data. The SDK guide describes UI reads and task-based changes, but explicitly warns it is outdated. ### Alternatives

**Status and licenses below were checked on 2026-10-11.** “Embedded PostgreSQL” describes two substantially different products.

**PGlite** is PostgreSQL compiled to WASM, packaged for JavaScript/TypeScript, under 3 MB gzipped. Its single-user execution model is not a native, in-process equivalent of PostgreSQL's normal multi-backend server. Adding a JS/WASM host to a Rust/Swift app is a real architectural cost. Its default filesystem is memory-only; browser persistence uses VFS adapters, and `relaxedDurability` explicitly returns before asynchronous persistence. Native macOS power-loss guarantees through its chosen WASM/VFS path are **unverified**. It is attractive for browser/local-first SQL reuse, not presently my choice for Sweetbriar's authoritative desktop store. [PGlite overview](https://pglite.dev/docs/about), [implementation and license](https://github.com/electric-sql/pglite), [filesystems](https://pglite.dev/docs/filesystems).

The Rust crates **`postgresql_embedded`** and **`pg-embed`** download/bundle and manage a **separate native PostgreSQL server**. They reduce process-management boilerplate; they do not remove major upgrades, filesystem durability, maintenance or sandbox obligations. Runtime downloading of executables also conflicts with the intended self-contained shipping model. If PostgreSQL wins later, audit a pinned binary distribution and wrapper, package it at build time, and retain explicit application ownership of upgrades. [postgresql-embedded](https://github.com/theseus-rs/postgresql-embedded), [pg-embed](https://github.com/faokunega/pg-embed).

**libSQL and the Rust Turso engine must be distinguished.** libSQL is the SQLite-derived C engine with Rust APIs, remote access and embedded replication. The newer `turso` engine, formerly Limbo, is a Rust rewrite with its own storage/concurrency implementation. SQLite-family compatibility does not prove identical crash behavior or complete feature compatibility; check the actual engine, mode and version. [libSQL](https://github.com/tursodatabase/libsql), [Turso engine](https://github.com/tursodatabase/turso).

Turso's 2026 development materially changes an answer based on older information:

- **2026-03-04, v0.5:** concurrent MVCC writes moved from preview to beta; the release describes revised commit/recovery handling and concurrency/crash testing. [0.5 announcement](https://turso.tech/blog/turso-0.5.0).
- **2026-05-12, v0.6:** multiprocess WAL access and in-place VACUUM were introduced as experimental. That announcement explicitly excluded multiprocess MVCC at the time. Do not extrapolate that historical restriction into every current mode without checking. [0.6 announcement](https://turso.tech/blog/turso-0.6.0).
- **2026-07-13, v0.7:** the project dropped the general beta warning, reported production use at multiple organizations, and improved MVCC, while still identifying some features as experimental and remaining pre-1.0. [0.7 announcement](https://turso.tech/blog/turso-0.7.0).
- **2026-10-06:** v0.8.2 was released; it is the latest non-prerelease found on the research date. Current documentation enables simultaneous connection writes with `PRAGMA journal_mode='mvcc'` and `BEGIN CONCURRENT`; conflicts require rollback/retry. Default mode remains single-writer. [Release record](https://api.github.com/repos/tursodatabase/turso/releases/tags/v0.8.2), [concurrent-write API](https://docs.turso.tech/tursodb/concurrent-writes).

**Assessment:** Turso is now a serious candidate to track, rather than dismiss as an early beta. It still needs Sweetbriar-specific qualification of macOS durable flushes, recovery, migrations, SQL/FTS behavior and backup interoperability. A newer implementation being memory-safe Rust does not establish preservation of acknowledged writes. For the first authoritative store, SQLite's evidence and tooling outweigh avoiding a single writer before it becomes a measured problem.

**DuckDB** offers transactional storage and multiple writer threads within one native process, but optimizes analytical queries and large-scale data changes. Current documentation also describes the new Quack client/server protocol for multiprocess access; the announcement is dated **2026-05-12**, so an unqualified statement that DuckDB can never have multiple writing clients would be stale. My assessment is that its sensible Sweetbriar role is optional analysis over derived data, rather than the primary draft/list/intent store; this is a workload judgment, not a claim that DuckDB lacks ACID transactions. [Why DuckDB](https://duckdb.org/why_duckdb), [concurrency](https://duckdb.org/docs/current/connect/concurrency), [Quack announcement](https://duckdb.org/2026/05/12/quack-remote-protocol).

The remaining candidates are transactional key/value stores. Their absence of SQL means Sweetbriar must build and validate secondary indexes, query planning, constraints and migrations itself. That engineering assessment is the largest objection to using them for rich mailbox views and classic-client filtering features; attractive point-lookup benchmarks do not price that work.

### Safety beyond the database engine

**Proposed safety contract:** an edit reported as saved must survive process crash, OS crash and power loss on a storage stack that honors durable flushes. Device destruction, undetected hardware damage and deletion require independent recoverable copies. Neither engine can make “never lose anything under every failure” a literal guarantee. SQLite and PostgreSQL both explicitly depend on operating-system/storage behavior. Apple's `fsync` documentation distinguishes flushing OS buffers from the stronger drive-cache request made by `F_FULLFSYNC`. [SQLite assumptions](https://www.sqlite.org/atomiccommit.html), [PostgreSQL storage reliability](https://www.postgresql.org/docs/current/wal-reliability.html), [Apple fsync documentation](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html).

For the proposed metadata-plus-files design, I recommend these invariants:

1. **Publish an original before committing a complete-body reference.** Write the backend's original representation to a temporary file on the same volume, compute and verify SHA-256 plus length, durably synchronize it, rename to its content-addressed final path, and make the directory change durable using a platform-tested routine. Then commit the database row, references and sync cursor together. A crash before that transaction may leave an orphan file; a crash after acknowledged commit must leave a valid referenced object. Represent headers-only/not-yet-downloaded messages explicitly, rather than confusing absent content with complete content.
2. **Record user changes before attempting remote work.** In one SQL transaction, update local state and append an intent with a stable identifier, revision and retry state. A draft revision and its attachment references must become durable before “Saved” appears. Keep old revisions long enough to recover from accidental overwrite or sync conflicts. A remote sync cursor must never advance beyond durably recorded local effects.
3. **Treat garbage collection as a recovery operation.** Remove objects only after proving they are unreachable from current rows, retained draft versions, pending intents and active backups. Use a grace period and reconcile orphan files on startup. The easier crash outcome is unused bytes, rather than missing mail.
4. **Keep rebuildable state subordinate.** Search indexes and summaries need a generation/mutation cursor and a full rebuild path. A lost search index must not lose drafts, tags, settings or account intent history. Separating the search writer can also protect urgent user saves from indexing work.

These are design recommendations, not capabilities automatically supplied by SQLite or PostgreSQL. Linux's `fsync` manual explicitly requires synchronizing the directory to ensure an entry is durable. Current Rust standard-library source uses `F_FULLFSYNC` for its Apple file-sync implementation, so inspect the pinned toolchain and handle errors rather than assuming Rust's `sync_all` is merely plain macOS `fsync`. Directory publication on APFS still needs target-platform testing; the Linux benchmark proves none of it. [Linux fsync](https://man7.org/linux/man-pages/man2/fsync.2.html), [Rust implementation, checked 2026-10-11](https://doc.rust-lang.org/src/std/sys/fs/unix.rs.html).

The remote side introduces a separate limit: a database transaction cannot make SMTP delivery and local bookkeeping atomic. SMTP explicitly discusses duplicate-message risk when delivery succeeds but the final acknowledgment is lost. The intent journal must represent uncertain results and apply provider-specific retry/reconciliation rules; swapping the local engine does not settle them. Likewise, IMAP identities need UIDVALIDITY as well as UID, rather than equating a message identifier with a permanent global identity. [RFC 5321 §6.1](https://www.rfc-editor.org/rfc/rfc5321), [RFC 9051 §2.3.1.1](https://www.rfc-editor.org/rfc/rfc9051).

**Backups must cover authoritative state as one recoverable set.** Take a coherent database snapshot, collect a manifest of referenced immutable objects, prevent their collection while copying, include schema/format versions and settings, then verify hashes and publish the completed backup. Retain several generations and an independent off-device copy. Test restoring a real account with unsent drafts and pending operations, not just opening a database file. SQLite's backup API provides database consistency, while PostgreSQL PITR restores the cluster; external objects still need this manifest protocol. [SQLite backup](https://www.sqlite.org/backup.html), [PostgreSQL PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).

Immutable originals improve recovery but **cannot reconstruct local-only drafts, annotations, settings or unsynchronized intent history** unless those are separately preserved. Frequent snapshots or WAL replication can narrow the off-device recovery-point window; asynchronous copying still has a window. State the local durable-commit promise separately from the disaster-recovery RPO, and expose backup freshness clearly. [Litestream replication](https://litestream.io/how-it-works/).

**Recommended acceptance testing:** maintain an external oracle of acknowledged revisions and object hashes; kill processes at every persistence transition; inject short writes, ENOSPC, EIO and failed sync/rename operations; interrupt checkpoints, backups and migrations; and exercise malformed databases and MIME. After reopening or restoring, every acknowledged state must exist with correct content, and no complete-body reference may be dangling. Structural integrity checks alone do not detect a valid SQL transaction that overwrote the wrong draft. SQLite's fault/crash testing provides a model, but Sweetbriar must test its own file/database protocol. Real or controlled storage power-loss tests are needed in addition to process kills. [SQLite testing approach](https://www.sqlite.org/testing.html).

## 4. Recommendations and counter-arguments

### Recommended desktop implementation

**Choose bundled SQLite**, with the proposed immutable-file architecture, after qualifying the application protocol. This conclusion rests on direct-access latency, a well-matched relational workload, strong existing fault-testing evidence and substantially smaller deployment obligations. It also has direct Rust/mail precedents. It is not a claim that SQLite has fewer defects than PostgreSQL, nor that single-user software can never need concurrent writers.

Use `rusqlite` with a pinned bundled SQLite build; verify the actual `sqlite_version()`/source ID and compile options at runtime. The crate's `bundled` feature supplies SQLite through `libsqlite3-sys`, but the crate version alone is not the database safety floor. Keep all database ownership in the Rust core, behind a storage API shared by Swift and the future Linux UI. [rusqlite bundling](https://github.com/rusqlite/rusqlite).

Retain WAL, FULL and macOS `fullfsync=ON`, foreign-key enforcement, and one designated write owner. Read back important settings, since unknown SQLite PRAGMAs are silently ignored. Checkpoint connections must use the same durable policy. Start with short, bounded sync batches and prioritize draft saves and user intents. Run this work off the UI thread, with bounded read snapshots and cancellation; long WAL readers can prevent checkpoints from completing and grow the log. Measure queue age and UI latency before expanding concurrency. [PRAGMA behavior](https://www.sqlite.org/pragma.html), [WAL checkpointing](https://www.sqlite.org/wal.html).

Prefer `STRICT` tables, CHECK/UNIQUE/foreign-key constraints and explicit schema versions for authoritative state. Keep locale-sensitive display ordering separate from stable identity keys. Prototype `cksumvfs`, including backup, restore and reserved-byte compatibility; adopt it only after proving those paths. If encryption changes the page format, qualify that combination separately. A periodic verified snapshot hash detects changed backup bytes but is not equivalent to checksumming each live page. [STRICT tables](https://www.sqlite.org/stricttables.html), [checksum VFS](https://www.sqlite.org/cksumvfs.html).

For search, evaluate FTS5 and Tantivy independently on a mail corpus before committing to either. Maintain a typed search expression that can combine text matches with mailbox, sender, attachment and date constraints. Benchmark selective and common terms, exact phrases, CJK, accents, addresses, identifiers and updates during search. PostgreSQL FTS is a credible option if PostgreSQL is selected for other reasons; choosing it solely to obtain good search is not justified by the evidence found. [FTS5](https://www.sqlite.org/fts5.html), [Tantivy](https://github.com/quickwit-oss/tantivy), [PostgreSQL text-search controls](https://www.postgresql.org/docs/current/textsearch-controls.html).

### Strongest argument against this recommendation

**PostgreSQL offers a more complete standard operational safety package:** enabled-by-default checksums in new version-18 clusters, physical base backups plus PITR, concurrent writers, consistency-check tooling and a separate database address space. If Sweetbriar needs several independent components making sustained concurrent writes, or frequent historical recovery with an already mature PostgreSQL operations implementation, that could outweigh IPC and deployment costs. Its COPY result here also rebuts the assumption that SQLite must win every bulk-write workload. [Checksums](https://www.postgresql.org/docs/current/checksums.html), [physical recovery](https://www.postgresql.org/docs/current/continuous-archiving.html), [MVCC](https://www.postgresql.org/docs/current/mvcc.html), [server architecture](https://www.postgresql.org/docs/current/tutorial-arch.html).

The strongest objection to the **hybrid file/SQLite plan itself** is the application-owned commit protocol across files and SQL. Storing originals as database BLOBs could simplify atomicity and whole-store backups, with size/performance costs to measure. That objection applies equally to PostgreSQL with external files. Keeping originals outside the database is defensible only after the publication, recovery and backup invariants above are proved.

My judgment remains SQLite because neither sustained competing writers nor a desktop PITR requirement has been demonstrated. Service lifecycle and major upgrades create additional failure paths on every end-user machine, and the closest PIM precedent has recently moved toward avoiding them. Process isolation can also be introduced around a SQLite-owning Rust service if crash containment later justifies IPC; it does not require PostgreSQL.

### Conditions that would change the decision

- **Server-side synchronization or shared team mailboxes:** PostgreSQL becomes a strong first choice for many authenticated clients, concurrent transactions, centrally operated backups/PITR and service observability. This need not change the database inside each desktop client.
- **Measured desktop write contention:** reconsider only after batching, short transactions, prioritized user writes and separation of search indexing fail to meet an agreed latency target. Compare native PostgreSQL and current Turso MVCC on the same corpus, with equal durable acknowledgments, collision/retry workloads and full checkpoint costs. More downloaded rows alone is not evidence of a concurrency limit.
- **Required PostgreSQL-specific capabilities:** complex centrally managed constraints/extensions, server-side querying or an existing supported PostgreSQL deployment can justify sharing that ecosystem. A private desktop cluster still needs upgrade and restore qualification.
- **A predominantly KV or analytical product slice:** choose LMDB/redb, an LSM store or DuckDB for that demonstrated workload. Do not replace relational mail metadata merely to reduce an isolated benchmark number.
- **Turso's qualification catches up:** revisit the Rust rewrite when compatibility, macOS flush semantics, failure recovery and backup behavior pass Sweetbriar's acceptance suite, and it solves a real bottleneck. A version label alone should not trigger migration.

## 5. Risks and open questions

1. **macOS proof is still missing.** Measure FULL/F_FULLFSYNC commit and object-publication latency on macOS 27/APFS, and test sandboxed deployment, sleep/wake, update interruption and power-loss recovery on Apple silicon. Database documentation and a Linux run are not that proof.
2. **Corruption detection policy is unresolved.** Should `cksumvfs` become mandatory, or should verified backups and integrity checks suffice initially? Decide with a working VFS/backup/encryption prototype, not a blanket claim that SQLite has PostgreSQL's default checksums.
3. **Disaster-recovery RPO needs a product decision.** Local durable acknowledgment cannot promise zero loss after destruction of the only device. Offline drafts make this especially important; define backup frequency, retention and key recovery.
4. **Search quality and real workload capacity remain unmeasured.** The synthetic benchmark excludes bodies, FTS, concurrent sync, deletes, attachment extraction, encryption and hardware flush costs on Mac. Obtain a representative 100k–1M-message corpus and agreed ranking/latency tests.
5. **Upgrade and collation invariants need ownership.** Version derived sort keys and search tokenization; test rebuilds and rollback. SQLite's stable file format does not eliminate Sweetbriar schema migrations. [SQLite file-format compatibility](https://www.sqlite.org/fileformat2.html).
6. **Published evidence has limits.** No comparable engine field-corruption rate was established. Apple Mail/Photos details are observed formats, not Apple durability promises; current Akonadi defaults do not automatically migrate existing installations. Treat anecdotes and project-authored benchmarks accordingly.
