Sweetbriar adversarial review, round 1 — 2026-10-11

Claude has the right engineering instincts and an overgrown product plan. The strongest recommendations are durable local intent, immutable acquisitions, explicit uncertainty, native interaction, and rebuildable search. The weakest are treating a JMAP-shaped model as sufficiently specified, putting a comprehensive IMAP implementation before the hardest commercial dependency, writing several rule translators, and using “permissive” as a substitute for a licensing policy.

My recommendation is a **Graph-first, macOS-only pilot with SQLite, a deliberately narrow recovery contract, excellent exact search, and four carefully chosen power features**. Preserve the Rust architecture and future provider seams. Markdown should be a composing format and a reading option. PostgreSQL should remain a candidate for a future hosted service.

I reviewed the position paper, all eleven curated topic documents, the decision agenda, working notes, and selected underlying reports and artifacts. I independently checked the consequential claims against primary sources. A read-only Devin/SWE-2-Max helper checked provider assumptions; a free helper produced no usable report. Recommendations, schedule estimates, and acceptance thresholds below are my proposals, not measured Sweetbriar results. I distinguish incorrect claims from claims that remain unproved.

**D1: Keep immutable acquisitions and SQLite; make recovery a protocol, not a collection of safety words.** The paper does not actually define what its append-only metadata journal guarantees. If SQLite commits a note before the external journal is flushed, reconstruction can lose an acknowledged note. If the external journal records a command before SQLite commits, blindly replaying it can invent an operation. Putting the journal inside the same database solves transaction ordering but gives no independent protection against corruption of that database.

For v1, I would make SQLite the sole transaction authority for mutable state, including versioned user metadata and its event records. Export those records through consistent backup generations, with a stated recovery point. Do not quietly promise that the latest metadata survives database corruption merely because a journal exists. If recovery of every acknowledged metadata edit after database corruption is required, design and qualify that independent recovery mechanism explicitly; it changes the acknowledgement protocol.

A backup generation must contain a completed SQLite snapshot, the immutable objects referenced by that snapshot, an inventory with lengths and hashes, format versions, and any required recoverable key material. Freeze object GC while establishing the snapshot’s object pins; then copy pinned objects and publish the completed manifest last. A snapshot plus an independently swept live object directory is not necessarily a backup. The [SQLite backup API](https://www.sqlite.org/backup.html) covers database consistency, not these external objects.

Restore must create a new recovery incarnation, suppress **all outbound effects** initially, invalidate stale provider cursors as necessary, and reconcile before enabling mutations. An old pending delete is as dangerous as an old pending send. Keep acknowledged submission evidence and ambiguous attempts visible. Never turn reconstruction into re-uploading every retained message.

Keep complete acquisitions immutable even when parsing fails. Define “original” as the bytes acquired from a particular backend, with provenance; a Graph MIME export is not necessarily the original SMTP byte stream. Record completeness independently from parseability and index coverage. Retain user annotations independently from message visibility and account removal.

Start with one object storage implementation, preferably uncompressed per-message objects. Do not add a small-object cutoff and cold compression before measuring file counts, backup time, restore time, and disk use. Qualify publication on APFS and the supported Linux filesystems, including newly created directories, short writes, flush failures, and GC racing publication. A Linux `fsync` recipe is not a macOS power-loss proof.

**The rejected option deserves respect:** SQLite BLOBs provide transactional publication with metadata, simpler inventory, fewer filesystem objects, and fewer application crash boundaries. SQLite’s [35% result](https://www.sqlite.org/fasterthanfs.html) concerns roughly 10 KB objects in its particular benchmark, not arbitrary mail workloads. A large SQLite database with WAL is also not equivalent to an mbox rewritten by a faulty compactor. I would choose BLOBs if the file protocol failed qualification or file/backup overhead dominated the measured workload. Files win only when their operational recovery advantages survive those tests.

**D2: Treat JMAP as a semantic reference, not the universal identity model.** A stable `Email` ID and a set of mailboxes leave a central question unanswered: when do two remote occurrences constitute one logical email?

Two IMAP messages can have identical bytes and Message-ID while remaining independently addressable, independently flagged objects. Deduplicate their bytes; preserve their occurrences. Conversely, one Gmail message with ten labels should normally remain one provider object. An identity policy that merges the former or duplicates the latter will spread errors through rules, undo, search counts, annotations, and deletion.

I would represent these separately:

- Immutable acquisition/blob identity and completeness.
- Account and provider-mailbox namespace.
- Remote occurrences, including IMAP mailbox, UIDVALIDITY, UID, and occurrence-scoped flags.
- Provider objects, keyed by authoritative provider IDs where available.
- Typed folder/label membership and independent categories/tags.
- Local message references, explicit equivalence links, thread hints, and private revisions.

For IMAP, use separate local occurrences unless provider `EMAILID` or a known COPY/MOVE result establishes a stronger relationship. Use Gmail account plus message ID, JMAP account plus Email ID, and Graph mailbox plus immutable ID. References and Message-ID establish correspondence clues, not authorization to mutate another object. [IMAP4rev2](https://www.rfc-editor.org/rfc/rfc9051.html) and [Graph immutable IDs](https://learn.microsoft.com/en-us/graph/outlook-immutable-id) are the relevant contracts.

The UI can still receive a unified message projection. Its unread state must have a documented scope: this occurrence, any visible occurrence, or all occurrences. A local note may belong to a provider object or a particular acquired copy; choose rather than letting deduplication decide.

Graph categories cannot be mailbox membership. A Graph message has a parent folder and a separate categories collection; treating “remove category” as “remove mailbox” is a destructive abstraction error. The curated backend document understands this better than D2’s wording. [Graph message model](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0).

**The rejected provider-specific model is stronger than Claude admits:** separate backend records preserve native semantics and produce fewer unsafe generic operations. Its weakness is duplicated UI and cross-account behavior. Typed shared projections over honest provider records capture much of its advantage. I would accept a simpler JMAP-shaped store after a conformance corpus proves duplicate IMAP copies with differing flags, Gmail multi-label mail, Graph categories/shared mailboxes, and provider moves without losing distinctions. `providerData` alone is not that proof.

**D3: Keep durable intent; tighten the claims and shrink the initial simulator.** “Ensure X” is not automatically idempotent or conflict-safe. An old move intent can undo another client’s later move. A COPY whose reply vanished can create a second destination object on replay. A destination body hash proves equal bytes, not that this particular operation created this particular occurrence.

Each intent needs a scoped target, account configuration generation, preconditions, dependency information, and an explicit reconciliation policy. Apply flag changes as deltas to the intended flags; preserve unrelated remote changes. Serialize dependent moves and deletes, park genuinely terminal failures, and keep authentication or throttling waits distinguishable from poison operations.

After UIDVALIDITY changes, invalidate the old targeting authority. Hash and Message-ID may suggest a correspondence, but **ambiguous rematches must never resume destructive operations automatically**. Quarantine those intents for resolution. The same caution applies when a server changes UIDs without changing UIDVALIDITY.

Use UID MOVE and scoped UID EXPUNGE, with destination evidence and recovery copies appropriate to the operation. COPYUID is a mapping receipt, not a cryptographic durability proof. If the server supplies neither safe MOVE nor UIDPLUS, disable automatic expunge; another client’s `\Deleted` flags must not become Sweetbriar’s purge targets. [UIDPLUS](https://www.rfc-editor.org/rfc/rfc4315.html), [MOVE](https://www.rfc-editor.org/rfc/rfc6851.html).

The mass-disappearance breaker should distinguish an explained user batch action, removal from one folder, actual object destruction, and incomplete observation. “Over 20% of a folder” trips on one message disappearing from a four-message folder; “over 50” trips on routine filing. Freeze unexplained destructive reconciliation and recovery GC, preserve the inventory, and independently recheck. Continue safe downloads, drafting, and unrelated account work. Tune thresholds from real traces. One clean sync is also not a general proof that tombstones can be forgotten across expired cursors, restored backups, or offline devices.

Replace “at-most-once visible” with: **never automatically repeat a submission with an unknown outcome; expose uncertainty and retain the frozen attempt**. A stable Message-ID does not require SMTP deduplication. Absence from Sent is not evidence of non-submission. Track envelope recipients and RCPT results separately; recipient acceptance is not delivery. [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html).

Sent-copy persistence needs a backend-and-submission-specific policy. If SMTP succeeded and a subsequent Sent APPEND failed, repair the copy without repeating submission. Partial recipient failures must not turn accepted recipients into retry targets.

For Graph, prefer creating a draft with immutable ID, persisting that ID, then sending the draft and looking up its Sent copy. Microsoft documents that correlation path. It is stronger evidence than searching by subject or internetMessageId; it still does not make every retry safe. [Graph immutable IDs and sending](https://learn.microsoft.com/en-us/graph/outlook-immutable-id), [send draft](https://learn.microsoft.com/en-us/graph/api/message-send?view=graph-rest-1.0).

**The cheap-engine counterargument is partly right.** Injectable clock, transport, and persistence outcomes belong in the first implementation. A full deterministic runtime, independent models of three protocols, and seven hosted providers in day-one CI do not. Start with reproducible transition tests and crash cuts around object publication, intent commit, delta-page application, and submission acceptance. Grow the model with each implemented operation. I would fund the larger simulator early if several sync engineers can maintain it or traces expose interleavings the narrow harness cannot reproduce. I would never trade away restart and ambiguous-send tests to get a first sender.

**D4: Preserve the boundary; resist building an SDK company inside the mail client.** Commands, idempotency keys, durable receipts, typed errors, bounded windows, and generation-aware subscriptions are the right foundation. UniFFI 0.32.1 is a reasonable pinned starting point, with actual strict Swift 6 compilation and cancellation tests; the [upstream changelog](https://github.com/mozilla/uniffi-rs/blob/main/CHANGELOG.md) is better evidence than generic microsecond estimates.

Begin with a window snapshot plus versioned invalidation/reset and bounded updates. Add positional edits only where a measured interaction benefits. Atomic snapshot/subscription establishment is essential; a full diff vocabulary is optional. Stable ID-based selection and explicit reset behavior matter more than how elegant an AsyncSequence looks.

Keep storage and network ownership in the engine, but build a few modules/crates around real ownership boundaries. The mandatory universal `sb-resources` façade and six adjacent layers add forwarding and type translation without proving isolation. If the original owner’s strict layering rule remains binding, implement it economically with modules; do not turn every box into a crate or every leaf into an interchangeable framework.

**Steelman the shared-view-model alternative:** compose/send/undo workflows and bulk-selection meaning are application state machines that should not diverge by platform. Share those, including capabilities and operation progress. Native focus, IME, and window state need not move into Rust. I would move more view behavior into Rust after a second front end reveals duplicated decisions, or a prototype shows a compact shared state model simplifies both. I would switch FFI tooling only after measuring actual row/body workloads.

**D5 and D6 are sound for the pilot.** Keep editor and interaction state native and domain semantics shared. Keep one engine owner in process. Closing a window and quitting the app must have clearly different notification and scheduling behavior. If after-Quit sync becomes a launch requirement, move ownership into the agent before launch; a transport seam does not eliminate IPC versioning, upgrade coordination, or keychain-access work. The engine-process decision does not require running unsafe document extractors in that same process.

**D7: Deliver exact search before sophisticated search infrastructure.** Start production development with bundled SQLite FTS5. Spend a bounded spike—roughly two engineering weeks, my estimate—comparing it with Tantivy on the same pipeline, then choose. The winner should satisfy exact-hit recall, restrictive filters, CJK cases, responsiveness under sync load, index recovery, disk usage, and ranking judgments. “Materially better” needs a predefined criterion.

FTS5 already supports BM25, per-column weights, custom tokenizers, and auxiliary functions; Tantivy is not the only route to field-sensitive relevance. Tantivy’s `FuzzyTermQuery` and customizable indexing are credible advantages. Neither engine automatically understands mail identifiers, addresses, quoted material, or Japanese text. [FTS5](https://www.sqlite.org/fts5.html), [Tantivy](https://github.com/quickwit-oss/tantivy).

Use one typed query representation with **different allowed subsets and evaluators**. Ranked/fuzzy/semantic search is not a safe rule predicate. Relative dates require an explicit evaluation clock and timezone. Missing body or attachment data must remain “unknown,” especially under negation: `NOT body:invoice` must not file every uncached message. Rule previews need the same completeness semantics as execution.

Remote search should be a supplemental, capability-qualified operation. A local boolean expression is not necessarily translatable into Graph KQL, Gmail’s conversation behavior, or IMAP SEARCH. The planner must identify exact translations, broader candidate queries needing local verification, and unsupported clauses. A 1,000-result cap cannot produce a trustworthy global “no matches.” Merge by scoped provider identity or an established locator, not Message-ID alone. [Graph search limits](https://learn.microsoft.com/en-us/graph/search-query-parameter).

The extraction pipeline must retain searchable content even when quote/signature detection or clean-view conversion is uncertain. Version offsets and source parts so a hit can be shown in its real context. “Best search” means users can find the receipt reliably; it does not require three query UIs, federation on every keystroke, or vectors at launch.

**Steelman Tantivy-first:** an email client advertised around retrieval may need its richer indexing immediately, and FTS5 experiments can become sunk-cost attachment. I would choose Tantivy before the pilot if exact identifier/CJK behavior or judged retrieval misses the agreed targets despite a bounded FTS5 effort. The index is rebuildable; semantic identity and extraction correctness are the less reversible decisions.

**D8: AppKit is a good prior; the editor and reader deserve as much scrutiny as the list.** Keep AppKit windows, menus, responder chain, list, and composer, with SwiftUI settings/onboarding. Budget days for the list comparison, not a second production list. Test keyboard selection, large selections, contextual menus, drag promises, variable heights, and VoiceOver alongside speed.

TextKit 2 is not a promise of a finished composer. Prototype CJK marked text, RTL, pasted HTML, inline attachments, undo across formatting, two compose windows, external editing, and recovery after acknowledged saves. Leave sophisticated rich text for a demonstrated cohort need, but do not assume Markdown is acceptable to everyone.

Reuse a WebView with a navigation generation and revocable, message-scoped resource leases. Old asynchronous fetches must not populate a newly selected message. Sanitization and deny-by-default resource loading belong in the shared pipeline; WebKit supplies additional process isolation. Treat native plain-text rendering and sanitized HTML as different fidelity paths, both tested.

macOS 26/arm64 is a defensible pilot support policy, not an architectural necessity. AppKit Observation already has an opt-in route on macOS 15. [Apple Observation documentation](https://developer.apple.com/documentation/appkit/updating-views-automatically-with-observation-tracking-in-appkit). Choose the eventual floor from recruited users and maintenance cost.

**Steelman SwiftUI-first:** recent list improvements and fewer custom controls may reduce maintenance and accessibility work. I would choose SwiftUI for the main list if the actual interaction corpus matches AppKit and end-to-end latency holds under live changes. Apple’s toolkit direction or an unrelated 100k-item benchmark alone would not change my mind.

**D9: Use GTK as the Ubuntu hypothesis; postpone the permanent choice.** Keep Linux compilation and headless core tests from day one. Build its production UI after the Mac pilot establishes the domain API. At that time, compare a GTK4/libadwaita composer/list/reader with Qt only if KDE users are a meaningful audience. Rust bindings reduce bridge work; they do not remove GTK, IME, accessibility, or WebKit maintenance.

Ship one Linux packaging path first, likely Flatpak. “Plus a .deb” immediately creates a second WebKit/security-update and integration obligation. Add it when users justify owning that obligation.

**Steelman Qt:** KDE integration and a mature text document/editor model may outweigh a C++/QML boundary. Neither Qt nor GTK passes a literal permissive-only dependency policy. Qt module licensing also varies. [GTK licence](https://github.com/GNOME/gtk/blob/main/COPYING), [Qt licensing](https://doc.qt.io/qt-6/licensing.html). I would select Qt if the recruited Linux cohort is KDE-centered or GTK fails the composer/accessibility prototype. Language uniformity is secondary to working native interactions.

**D10: Put Graph first, with an onboarding gate before committing the schedule.** My default first cohort is independent professionals or small organizations using M365, with valuable correspondence and an administrator reachable by the project. Within the first two weeks, enroll at least three organizational tenants and prove login, revocation, Conditional Access behavior, delta retrieval, and submission with Sweetbriar’s own app registration. Publisher verification is not an access grant.

Microsoft’s managed policy excludes broad mail-reading scopes and IMAP access from ordinary consent, with exceptions for named clients. Sweetbriar does not inherit those exceptions, and switching to IMAP does not escape this policy. [Microsoft consent policy](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies). If this access gate fails, choose a reachable cohort and a single Fastmail/JMAP or narrowly supported IMAP path; do not spend six months polishing an inaccessible Graph product.

Why Graph first? It addresses a stated non-standard-source goal, exercises permission-aware capability design, and forces the most consequential distribution constraint into the open. EWS retirement is real, and Apple explicitly promises Graph in an undated macOS 27 update. [Microsoft EWS retirement](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-ews-exchange-online), [Apple deployment guidance](https://support.apple.com/guide/deployment/integrate-with-microsoft-exchange-dep158966b23/web). However, this is a temporary opportunity, already contested by [Thunderbird’s Graph release](https://blog.thunderbird.net/2026/09/thunderbird-desktop-new-protocol-support-microsoft-graph-api/). The durable differentiation must be archive trust and retrieval, not merely escaping EWS.

Graph-first must mean a narrow mail client: one primary mailbox, folder deltas, acquired MIME, drafts/submission, categories, basic filing, and honest capability limits. Poll adaptively. Test moves arriving through source and destination folder deltas in either order. Do not confuse a folder’s removal event with destruction of the mailbox-wide object.

**Steelman IMAP-first:** it reaches independent providers, iCloud, Gmail, and Proton Bridge with one transport, avoids Graph-specific organizational politics, and is a strong fit for archive-minded power users. It is the right first backend if those users actually constitute the paid pilot. But “full extension set,” all named providers, generic fallback behavior, OAuth approvals, and SMTP is a program of interoperability work, not one feature.

Gmail API deserves a stronger status than “optional mode for label-heavy users”: some Workspace administrators disable IMAP. Native history/label semantics are attractive, although quotas matter. Google’s current new-project limits imply `1,000,000 × 20 / 6,000 = 3,333.3 minutes`, or **55.6 hours**, for one raw-message get per email, before extra work. At 100k messages the same lower bound is **5.56 hours**. [Gmail quotas](https://developers.google.com/workspace/gmail/api/reference/quota).

That does not establish IMAP as faster for every archive. Google documents Workspace IMAP downloads of **2,500 MB/day** and uploads of **500 MB/day**; a 25,000 MB download is at least ten daily allowances at that published limit. Measure bytes as well as message counts. [Gmail bandwidth limits](https://support.google.com/a/answer/1071518?hl=en). API thread fetches can reduce calls for multi-message threads, but `threads.get` returns parsed payloads, not raw MIME. [Thread formats](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.threads/get).

Do not casually adopt the IMAP-bulk/API-delta hybrid: it adds two transports, identity joins, differing visibility settings, and more scope/account failure cases. Test a dedicated Gmail adapter before deciding that complexity pays. Proton Bridge remains the practical first Proton route; copying an AGPL SDK does not independently grant service access.

I would reverse Graph-first if the access gate fails, or committed design partners demonstrate substantially stronger demand for private-provider/Bridge workflows. I would move Gmail API ahead of generic IMAP breadth for a proven Workspace cohort, with measured quota and onboarding costs.

**D11: Build explainable local rules, not a multi-provider rule compiler.** Share a deterministic predicate representation with search, and implement a small versioned action vocabulary: local tags, read state, and supported filing operations. Preserve explicit order, stop semantics, preview, trace, and an execution ledger keyed by rule revision and message occurrence/event. A reparse or resync must not silently run every arrival action again.

Defer automatic sends, redirects, shell execution, and broad editheader behavior. They introduce authorization, loop prevention, outcome ambiguity, and recovery problems beyond ordinary filing. Use bounded Rust `regex` where regex is needed; a permissive regex library does not make an unbounded rule workload inexpensive.

Offer server rules as separate, inspectable provider programs. A Sieve editor with advertised extensions and remote validation is valuable without inventing a universal Sieve-compatible runtime. [ManageSieve](https://www.rfc-editor.org/rfc/rfc5804.html). Later, translate only an explicitly defined subset and show unsupported predicates/actions before activation. “Exactly expressible” includes timing, ordering, error behavior, and mailbox identity, not merely a syntactically similar condition.

**Steelman server-first:** vacation, routing, and spam organization should usually run when the Mac is asleep. A good server-rule editor may deliver more daily value than a rich local engine. Client rules still justify themselves for private metadata and cross-account/local workflows. I would prioritize server management when the first cohort chiefly asks for always-on filing, and fund translators only after each provider has a verified semantics suite. The ecosystem document’s “Sieve interpreter is weeks” estimate is not evidence for a product-quality implementation.

**D12: Direct distribution is right; choose actual sandbox and update semantics.** Ship Developer ID, notarization, signed Sparkle updates, and a real App Sandbox build if the chosen integrations work there. Exercise storage, imports, Keychain, Bridge connections, scripting, external editing, and update relaunch in an early signed build. “Mostly sandboxed” describes an intention, not an enforced boundary. [Sparkle sandboxing](https://sparkle-project.org/documentation/sandboxing/).

Treat updater/schema coordination as a durability feature: back up before destructive migration, retain an independently usable recovery/export path, separate beta store upgrades, and never assume that rolling back a binary rolls back its database. Billing outages or expired entitlement must not disable viewing, export, or draft recovery.

**Steelman the Store:** purchase trust and easier discovery may matter more than fees for an unfamiliar client requesting complete mailbox access. I would choose Store-first if pilots repeatedly refuse direct installation or enterprise procurement requires it, and the signed integration prototype proves acceptable constraints. Otherwise, defer a second distribution channel and its review matrix.

**D13: Replace “permissive only” with a compatibility policy.** Permit MIT/Apache/BSD/public-domain code and audited MPL; permit dynamically linked LGPL platform libraries where their distribution obligations can be fulfilled. Require a per-component licence inventory, corresponding-source obligations, and review of actual enabled features and shipped assets. `cargo-deny` helps enforce a chosen policy; it does not classify the whole product for you.

MPL is file-level copyleft, explicitly compatible with a larger proprietary application, including static linking under its conditions. It is not permissive. [Mozilla MPL FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/). GTK and Qt make the literal policy incompatible with either serious Linux-native recommendation. Model weights, tokenizer dictionaries, codecs, and helper executables also need their own review.

**Steelman GPL:** a GPL application can be sold commercially; it could reuse more existing mail infrastructure and make user control more credible. [GNU licensing FAQ](https://www.gnu.org/licenses/gpl-faq.en.html). The real choice is whether the resulting distribution/source obligations fit the business, not whether commercial use is allowed. GPL also does not magically authorize direct Proton service access.

I would choose a GPL product if paid support, sponsorship, or another funding model actually sustains it and reuse sharply reduces maintenance. I would tighten to genuinely permissive dependencies if a concrete distribution or commercial requirement demands it. Neither decision should be postponed indefinitely while contributions accumulate.

**D14: Revive agency through four workflows first.** The initial product should make four promises tangible: recoverable drafts and an inspectable outbox; precise actionable search with a saved view; keyboard filing with undo; and private notes/tags with honest persistence. Identities are essential sending data, even if elaborate routing rules arrive later.

Store extensible identity, annotation, view, and submission records from day one. This does not require shipping clipboard history, a six-clipboard workbench, reading-session semantics, mailbox-attached rules, Redirect, an AppleScript dictionary, App Intents, and a CLI simultaneously. Clipboard history even creates a new store of potentially unrelated sensitive material.

Freeze a versioned command vocabulary early and expose it through menus. Add bounded scripting surfaces as real workflows demand. Reading sessions are a promising experiment: test whether a stable review queue improves a real user’s work before committing its entire attention-state model.

**Steelman the everyday-excellence counterargument:** users may switch for a dependable reader/composer and working accounts, not a historical feature checklist. The revival should therefore be judged by completed tasks and retained weekly use. I would expand the initial power bundle if pilots depend on a specific omitted workflow, such as external editing or automation. Affection for a discontinued client is not sufficient evidence.

**D15: Keep opt-in AI; specify the execution provider.** Use explicit no-AI, on-device, and separately authorized cloud modes if cloud assistance is eventually offered. Never silently fall back. Foundation Models now covers more than an on-device model; select `SystemLanguageModel` and check availability rather than relying on the framework’s name as a privacy boundary. [Apple Foundation Models](https://developer.apple.com/documentation/foundationmodels).

Apple documents a **4,096-token total session budget**, including instructions, schemas, input, and output. That is not 4K tokens of mail plus a free prompt. Long-thread summaries require chunking and evidence-linked outputs. Generated ASTs need validation, especially scope, negation, identities, and dates; valid JSON is not correct intent. [Apple TN3193](https://developer.apple.com/documentation/technotes/tn3193-managing-the-on-device-foundation-model-s-context-window).

**Steelman cloud quality:** a private, explicitly selected cloud option may produce useful summaries or drafting unavailable locally. Privacy-sensitive users can still choose none. I would add it after blinded task evaluations demonstrate a material gain and the data-flow/business model is accepted. I would not put generative search parsing, vector indexes, or a Linux model runtime on the first pilot’s critical path.

Two dangerous omissions deserve the same prominence as errors. Graph’s receivedDateTime-filtered message delta supports only up to **5,000 messages**; it cannot establish complete archive coverage. Use a complete enumeration/unfiltered delta strategy and distinguish the recent-mail fast path. [Graph message delta](https://learn.microsoft.com/en-us/graph/delta-query-messages). And RFC 9979 registers useful keywords and mailbox attributes; it does not supply a portable scheduled-send/snooze control protocol merely by identifying their folders. [RFC 9979](https://www.rfc-editor.org/rfc/rfc9979.html).

I did **not** reject the 2026 facts just because they are newer than familiar training material. The EWS phase-out, Apple’s future Graph update, Thunderbird’s Graph implementation, new Gmail quotas, SQLite WAL-reset fix, and RFC 9979 are supported. The uncertainty is deployment, availability, and product consequence. Microsoft’s phased EWS retirement and Apple’s undated update do not establish an exclusive market opening lasting until Sweetbriar ships. [Microsoft EWS retirement](https://learn.microsoft.com/en-us/exchange/clients-and-mobile-in-exchange-online/deprecation-of-ews-exchange-online), [Apple Exchange deployment](https://support.apple.com/guide/deployment/integrate-with-microsoft-exchange-dep158966b23/web).

**Missing decisions must become explicit commitments, not another feature backlog.** I would add the following before the architecture hardens.

1. **Paying cohort, staffing, and runway.** Choose a reachable group with a repeated unmet job. My proposed first cohort is archive-heavy Mac users in small M365 organizations whose admins will authorize Sweetbriar. The schedule below assumes two or three experienced full-time engineers and accessible pilot users. One engineer should shrink the workflow and provider count. “Long-term project” is not a staffing model.
2. **Product licence and contribution policy.** My starting proposal is an MPL-licensed core and documented recovery/export format, with a paid native application. A fully GPL product is a legitimate alternative with a different funding plan. Decide before accepting contributions; dependency allowlists cannot preserve every future relicensing option.
3. **Revenue and continuing access.** Test a paid annual licence that funds provider maintenance. Explicitly preserve read, export, and recovery after expiry. Avoid promising perpetual compatibility for a one-time payment without the reserves to fund it. Establish whether users will pay before writing five backend adapters.
4. **Sweetbriar metadata across devices.** Make v1 private metadata local, backed up, and explicitly labelled. Remote keywords are not a general synchronization channel for notes, reading queues, and rule revisions. Reserve stable metadata IDs and revisions; later use encrypted records and visible conflict copies. Submission ownership must never be replicated as an instruction for every device to send.
5. **Encryption and key recovery.** Specify whether protection covers raw objects, metadata, indexes, temporary attachments, backups, Spotlight, and notifications. SQLCipher covers the database, not the entire mail vault. For a broad privacy-oriented release I favor a recoverable encrypted vault; qualify the key lifecycle early. A limited unencrypted pilot must say so. Restore on a clean machine without the original Keychain is the test. [SQLCipher design](https://www.zetetic.net/sqlcipher/design/).
6. **Archive versus cache, retention, and storage pressure.** Decide what remains after remote deletion and account disconnection, which objects are pinned, and how recovery expires. Make complete archival acquisition an explicit mode with progress and a manifest. Prioritize draft/intent writes on low disk space; pause acquisition and GC safely. “Never lose data” and unbounded retention are different promises.
7. **Onboarding and authorization.** Define scopes, account identity changes, admin-consent recovery, certificate trust, and secure autoconfiguration. Do not send credentials to arbitrary discovered hosts or bypass Bridge certificate validation. A revoked token pauses the account; it does not delete local history. Validate with the project’s own OAuth app, not a borrowed client ID.
8. **Accessibility and localization.** VoiceOver, complete keyboard access, text scaling, contrast, RTL, and Japanese IME belong in the first UI prototypes. Localized dates and query grammar need a stable interchange representation. Linux AT-SPI requirements should shape shared projection semantics before its UI exists.
9. **Telemetry and diagnostic custody.** Default to no mail-content telemetry. Offer opt-in aggregate performance reporting and a user-reviewable diagnostic package. OAuth tokens, subjects, addresses, provider URLs, and “hashed” stable identifiers can remain sensitive; ordinary crash tooling cannot be assumed safe.
10. **Release evidence and support infrastructure.** Budget real Macs, provider test tenants, CI secrets, signed upgrade tests, format fixtures, a consented messy-mail corpus, and an independent recovery tool. Synthetic million-row tests complement actual interaction and failure tests. Define OS, provider, mailbox-size, and schema support lifetimes.
11. **Security boundaries and automation authority.** Bound attachment extraction, parser resource use, remote content, plugins, URL handlers, and command-line access. Separate read/draft authority from send/delete authority. Some extractors deserve isolation even while the engine remains in process. No AI and local storage alone do not protect a logged-in compromised machine.
12. **Email versus PIM and organizational coverage.** Explicitly declare the pilot email-only and specify primary mailboxes, shared mailboxes, delegated sending, online archives, public folders, sovereign clouds, calendars, and contacts as supported or deferred. If the target cohort cannot switch without shared mailboxes or calendars, that changes the product plan immediately.

These also require an offboarding promise: documented formats, key export/recovery, complete export with reconciliation, and a reader that remains usable if the company disappears.

| Rank | Decision | Why it hurts | Early de-risking |
|---|---|---|---|
| 1 | D3 — Remote effects and uncertainty | Lost mail and duplicate submission cannot be repaired by replacing a crate. | Crash/drop every transition of the implemented move/send paths; retain ambiguous attempts; prove restore cannot execute old effects. |
| 2 | D2 — Identity and metadata ownership | A mistaken merge contaminates annotations, rules, undo, and deletions throughout the store. | Build conformance fixtures for independently flagged duplicates, Gmail labels, Graph categories/moves, account reconfiguration, and later shared mailboxes. |
| 3 | D1/D17 — Persistence, backups, and keys | Acknowledged state may become irrecoverable; format and key changes burden every future release. | Qualify flush/publication ordering, ENOSPC, coordinated GC, corrupted stores, migration failure, and clean-machine keyed restore. |
| 4 | D10 — Cohort and provider access | Six months of correct code is wasted if intended users cannot authorize or adopt it. | Obtain real consent in three independent tenants and weekly pilot usage before broadening protocols; maintain the explicit fallback gate. |
| 5 | D13 — Product licence and financing | Contributor rights and unfunded lifetime obligations are hard to reverse and can strand the project. | Choose distribution/contribution terms, audit the actual dependency tree, and test paid demand before external contributions and compatibility promises accumulate. |

Search-engine choice is consequential, but a derived index can be rebuilt. These five choices can lose the data, the audience, or the ability to keep shipping.

**The first vertical slice should prove a complete mail workflow in one reachable account.** For two or three experienced engineers, I would plan a private pilot over three to six months, with the following gates. This is a planning assumption, not a promise of a general release.

| Period | Deliverable | Evidence needed to proceed |
|---|---|---|
| Weeks 1–2 | Three-tenant Graph authorization probe; signed AppKit/SwiftUI/UniFFI shell; small storage/key-recovery and editor prototypes | Own-app login, revocation and policy behavior; strict Swift build; acceptable IME/VoiceOver; one backup restored without the original machine |
| Month 1 | Read-only Graph inbox/folder reader, immutable acquisition, local recoverable drafts, basic exact search and EML export | Real people can read their own mail; acquisition survives restart; resource limits and renderer isolation work; saved drafts recover |
| Month 2 | Resumable archive backfill, per-folder delta, explicit coverage, saved views, notes/tags, keyboard navigation | Recent-mail acceleration never implies complete coverage; interrupted pagination resumes; duplicates/moves reconcile; backup restores mail and private metadata |
| Month 3 | Read flags, reversible filing, inspectable outbox, reply/forward and Graph draft-based submission, ordinary attachments | Operation-specific crash/drop tests pass before effects are enabled; uncertain send never retries automatically; undo and external-client changes interact honestly |
| Months 4–6 | Ten to twenty active pilot users, retrieval polish, storage-pressure handling, safe upgrade/recovery, paid-demand experiment | Weekly reuse; real retrieval tasks succeed; restore and migration drills pass; maintenance load is tolerable; one second backend only if demand justifies it |

Search should have an explicit corpus of roughly 100 judged tasks, including exact addresses/order numbers, restrictive filters, quotations, and CJK. Test 100k-message accounts and synthetic million-message metadata on an actual reference Mac. My proposed responsiveness target is p95 under 100 ms for cached list windows and ordinary exact searches on an 8 GB Apple-silicon machine during background sync. Measure draft-commit tail latency separately. These are acceptance targets to validate, not benchmark results.

The small fault harness is worth building before the first user: injectable transport/time, scripted responses, and restart/failure cuts around the implemented durable transitions. The complete deterministic three-protocol universe is not. Read-only users can arrive before that universe exists; outbound mutation must wait for its particular safety evidence. Provider recording/replay should grow from consented, redacted real failures.

Explicitly wait on production Linux UI, broad generic IMAP conformance, on-prem EWS, POP/NNTP, Gmail hybrid transport, shared/delegated/sovereign Graph coverage, full PIM, comprehensive PST/TNEF import, three server-rule compilers, sophisticated HTML composition, the entire classic workbench, universal incoming Markdown conversion, generative/semantic search, and a seven-provider nightly matrix. Preserve original attachments and expose unsupported content honestly. Expand only the items the chosen cohort actually needs.

The pilot is complete when a fresh-machine restore recovers acquired mail, acknowledged drafts and private metadata within the stated backup recovery point; restored queues perform no unsolicited outbound effects; ambiguous submission stays ambiguous; exact-search coverage is visible and useful; and users repeatedly choose the app for real work. A beautiful million-row list alone does not pass.

**We share blind spots that the research does not resolve.** First, thirty helper reports are not thirty independent observations. Repeated forum reports and common source material can amplify one anecdote. The curated landscape correctly disclaims failure rates; neither of us has established how many people encounter these problems or will pay to escape them.

Second, “unified native client” may describe our preferences better than a market. Users may accept separate provider apps, browser mail, or today’s native Outlook. The Graph gate proves access, not willingness to replace an established workflow.

Third, we may both overvalue generic infrastructure and million-message benchmarks. Trust comes from retaining yesterday’s draft, finding the correct receipt, and recovering without a specialist. Search tokenization, messy MIME, permissions, and account onboarding may dominate database throughput.

Fourth, server-held mail is not an independent backup of local notes or drafts, and acquired MIME is not automatically original transport evidence. Graph exports, Bridge decryption, forwarding, and server rewriting complicate authenticity. Provenance and crypto-verification scope must remain visible.

Finally, Rust and native UI do not eliminate maintenance economics. Two platforms, OAuth approvals, signing, provider churn, security updates, and support can exceed the available team. A source licence and funding model that let the project survive may protect users better than another storage abstraction.

**D16: Agree with Markdown composition and a clean reading view; disagree with requiring every incoming message to become Markdown for default reading.** Keep stored authority, reader presentation, and composing representation distinct. The owner’s “show original” proposal can preserve immutable storage perfectly well; the objection is fidelity and workflow in the default view.

The strongest case is real: consistent typography, dark mode, accessible structure, unobtrusive quoting, and a text-oriented composer could distinguish Sweetbriar. A clean reader can remove newsletter furniture and reduce rendering variability. MailMate demonstrates a workable Markdown composer producing HTML alternatives. [MailMate composing documentation](https://manual.mailmate-app.com/preferences#markdown-support). I would invest in that experience.

The failure is **lossy simplification presented as faithful reading**. General HTML has structures ordinary Markdown cannot preserve faithfully: merged table cells, direction/language information, meaningful visual relationships, image placement within complex layouts, and distinctions expressed through formatting. A receipt that separates a payee from an amount is not equivalent to a bag of extracted words. Neither original-byte preservation nor an original-view toggle prevents a user acting on a misleading default projection.

Do not automatically interpret arbitrary incoming plain text as Markdown. Asterisks, numbered lines, brackets, indentation, and hard line breaks may be literal content, source patches, or ASCII tables. Likewise, do not make the plain-text alternative authoritative for quotation: quote the part the user actually read. MIME alternatives are intended to represent the same information, but the application must handle messages where they differ. [MIME alternative semantics](https://www.rfc-editor.org/rfc/rfc2046.html).

My implementation would have three layers:

- **Immutable acquisition:** complete provider-acquired MIME, signatures and provenance, never overwritten by conversion.
- **Versioned reading projection:** a structured document with source-part references, quote/attachment boundaries, conversion warnings, and message-scoped resources. Markdown may be an export of this projection; it need not be its internal schema.
- **Versioned compose source:** plain text or a specified Markdown dialect, attachment references, native editing state, and a preview of the actual outgoing MIME.

Initially default to sanitized sender layout for HTML and literal native rendering for ordinary text. Offer a prominent Clean View, remember the user’s choice, and consider clean-by-default for demonstrated safe message classes. Call the fallback “Sender layout”; separately offer raw source. It must retain the same remote-content policy rather than becoming a bypass for unsafe HTML.

Markdown is not a sanitizer. CommonMark includes raw HTML, and generated links/images need policy checks. Disable raw HTML in the composing dialect, sanitize generated output, and deny remote resources by default. [CommonMark raw HTML](https://spec.commonmark.org/0.31.2/#raw-html). Use `pulldown-cmark` or `comrak` for composing; `html5ever` for parsing; evaluate `html2text`/`htmd` as lossy converters, not equivalence proofs. [pulldown-cmark](https://docs.rs/pulldown-cmark/latest/pulldown_cmark/), [htmd](https://docs.rs/htmd/latest/htmd/).

Outgoing mail should normally be `multipart/alternative`: human-readable `text/plain` plus sanitized `text/html`, with related CID resources where needed. Preserve editable Markdown locally; do not require recipients to support `text/markdown`. Its registered media type does not establish ubiquitous reader support. [RFC 7763](https://www.rfc-editor.org/rfc/rfc7763.html). Preserve faithful quoted fragments or warn before simplifying them; forward as an attached original when exact content matters. Verify signed content before projection, and make decrypted-content indexing an explicit privacy choice.

**What would change my mind:** test a consented, stratified corpus of roughly 2,000 messages—receipts, invoices, newsletters, lists/patches, RTL/CJK, inline images, signed mail, and malformed alternatives. Compare real reading tasks with twenty or more pilot users, especially finding amounts, dates, identities and link destinations. If Clean View wins preference and task accuracy, with no observed critical omissions and reliable handling of counterexamples, broaden the default. That supports a presentation choice, never replacing immutable MIME with Markdown.

**D17: Use SQLite. It is already a real transactional database; PostgreSQL does not automatically make a desktop mailbox safer or faster.** Choose the engine by the workload and operations the team can actually support.

The strongest PostgreSQL argument is substantive: MVCC with concurrent writers, mature operational tooling, page checksums, full-page WAL protection, replication, and point-in-time recovery. It deserves serious consideration for a hosted multi-user service. Page checksums detect corruption; they do not themselves repair it. [PostgreSQL checksums](https://www.postgresql.org/docs/current/checksums.html), [continuous archiving/PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).

But bundled local PostgreSQL is still one database on one laptop. It does not create another failure domain, coordinate external MIME files, prevent a buggy DELETE, identify a duplicate message, or resolve an uncertain send. Replication or WAL archives help only if actually deployed and recoverable. Storing MIME transactionally inside PostgreSQL can remove the external-file commit boundary, but SQLite BLOBs offer that tradeoff too.

It also makes Sweetbriar responsible for server process startup/shutdown, socket/authentication permissions, crash recovery, autovacuum, WAL growth, memory, signing/package updates, and major-version cluster upgrades. `pg_upgrade` requires old and new executable/data directories; some fast upgrade modes constrain rollback. [PostgreSQL upgrade documentation](https://www.postgresql.org/docs/current/pgupgrade.html). KDE Akonadi shows that desktop server databases are feasible, while also documenting PostgreSQL major-version migration work. [Akonadi operational documentation](https://userbase.kde.org/Akonadi).

Power-loss durability still needs correct configuration and hardware qualification. PostgreSQL requires appropriate `fsync`, `synchronous_commit`, `full_page_writes`, and WAL flush behavior; its documentation says the default flush method may need changing. On macOS investigate `fsync_writethrough`, rather than assuming ordinary fsync clears the drive cache. [PostgreSQL WAL configuration](https://www.postgresql.org/docs/current/runtime-config-wal.html).

For SQLite, use a qualified bundled build containing the WAL-reset fix—3.51.3 or later, or a documented fixed backport—not whatever the OS provides. With `rusqlite`, verify the actual linked version and feature selection. Use WAL, `synchronous=FULL`, macOS `fullfsync=ON`, foreign keys on every relevant connection, one scheduled writer/checkpoint owner, short read snapshots, bounded import batches, and checked failure returns. Qualify the actual VFS and flush path. [SQLite pragmas](https://www.sqlite.org/pragma.html), [WAL qualification](https://sqlite.org/wal.html). Do not hold a write transaction across network I/O.

The existing artifact is useful precisely because it is modest: on a shared Linux Xeon with SQLite 3.40.1 and one million synthetic metadata rows, first-page median was **0.073 ms**, deep OFFSET median **79.764 ms**, and keyset pagination at the same depth **0.080 ms**. Query shape changed this workload by roughly three orders of magnitude. It is a warm, metadata-only benchmark, not a Mac durability test, full-text test, or PostgreSQL comparison. [Existing benchmark results](codex-artifacts/research/raw/performance/codex-artifacts/bench-results.json).

De-risk the choice with representative 100k/1M workloads on the target Mac: list/search reads during backfill, p95/p99 acknowledged draft latency, WAL/checkpoint disk growth, ENOSPC, backup/restore, and migration failure. Compare PostgreSQL only with equal schemas, durability settings, and end-to-end work. A kill test alone does not prove power-loss safety for either.

**What would change my mind:** a real concurrent-writer or hosted-service requirement, operationally owned PITR/replication, or SQLite missing agreed latency/recovery targets after bounded indexing, batching, and scheduling work. None is demonstrated here. Keep storage APIs domain-specific and formats documented; do not build a universal database abstraction or maintain both engines in v1.
