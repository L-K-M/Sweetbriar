## Layers

The owner's rule: **each layer talks only to the layer directly below
it.** Every layer from L1 to L6 is made of crates, so Cargo enforces the
rule at compile time: a crate can name only the crates it depends on.

```
 L0  Sweetbriar.app (AppKit + SwiftUI)                 later: sweetbriar-gtk
            │                                                │
 L1  SweetbriarBridge (Swift adapter)                   sb-cli (Rust client)
     sb-ffi (UniFFI exports)
            └────────────────────┬───────────────────────────┘
 L2                     sb-service
            commands + receipts, windows, subscriptions, leases, DTOs, CoreError
                                 │
 L3                     sb-engine
            runtime owner; sync scheduler; intents; outbox; drafts; import;
            backup; index jobs; breaker; reconciliation; appearance tokens
                                 │
 L4                     sb-resources
            one narrow, typed façade over the leaves; maps leaf types and errors
                                 │
 L5   sb-store     sb-mime     sb-imap     sb-smtp     sb-platform
                                 │
 L6                          sb-types
            plain shared data types used by more than one leaf
```

**Rules:**
1. **Calls go down one layer only.** First-party dependencies:
   - `sb-ffi` and `sb-cli` (L1) depend only on `sb-service`;
   - `sb-service` only on `sb-engine`;
   - `sb-engine` only on `sb-resources`;
   - `sb-resources` on the L5 crates;
   - L5 crates on `sb-types`, which depends on no first-party crate.
   - Any crate may take `sb-test-support` as a dev-dependency.
2. **Leaves never call each other.**
   - `sb-imap` doesn't parse MIME: it returns bytes.
   - `sb-mime` doesn't touch the store.
   - `sb-store` doesn't know about IMAP.
   - Shared vocabulary types (ids, timestamps, email addresses, byte
     ranges) and **seam traits** (`Fs`, `Clock`, `Random`) live in `sb-types` (L6),
     directly below the leaves. Leaves
     may use it; everything above reaches those types only through
     re-exports in the layer directly below. `sb-types` holds data types
     and trivial constructors only, so it can't become a catch-all.
3. **Types climb through re-exports,** one layer at a time: a DTO
   defined in L5 reaches L3 only through a `pub use` in `sb-resources`.
   Re-exports name items, never whole crates or modules. `sb-service`
   defines its own DTOs for the API surface and re-exports nothing from
   below, so no engine or store type crosses into L1.
4. **Backends never write the store.** `sb-imap` returns observations
   (mailbox lists, UID sets, fetched headers and bodies). The engine
   decides what to apply and applies it through `sb-resources` → `sb-store`.
5. **Seams are traits in `sb-types`; implementations are in
   `sb-platform`.** A leaf such as `sb-store` uses only the `Fs` trait
   from `sb-types`. `sb-resources` (L4) constructs the real implementation
   from `sb-platform` and passes it in. Tests pass the real one or a
   fault-injecting one, both through `sb-test-support`, which may depend
   on any crate. The real `Fs` implements durable flushes
   (`fcntl(F_FULLFSYNC)` on macOS), the exclusive store lock and the
   location check (03). So no leaf calls another leaf,
   and no platform syscall sits in `sb-store`.
6. **Platform services enter at L5** (`sb-platform`). The Swift app
   doesn't implement core logic. Where a native implementation is
   unavoidable (Keychain specifics), `sb-platform` defines a trait. The
   macOS implementation lives in Rust via the platform crates (below),
   not as Swift callbacks (07).

### The layering check

Because every layer is made of crates, Cargo blocks skip-layer and
upward references at compile time. `cargo xtask check-layers` checks the
rest, using only data the Rust toolchain itself produces, so it never
guesses at name resolution. It reads `layers.toml`, which maps each
workspace crate to a layer or role (dev-only, tool) and lists the
allowed first-party dependencies.

- **The crate graph** (`cargo metadata`): every first-party dependency
  matches rule 1; `sb-test-support` appears only as a dev-dependency;
  first-party dependencies are unrenamed path dependencies (no
  `package = …`, no version-only dependency resolved through `[patch]`
  or `[replace]`); every workspace crate is classified.
- **Re-exports** (rustdoc's JSON output, which lists each crate's public
  API with every re-export resolved to its origin crate and kind):
  - a crate's public re-exports of another first-party crate are items:
    never that crate, one of its modules, a glob (except an enum's
    variants) or a macro (whose `$crate` paths would otherwise expand two
    layers up);
  - `sb-service` re-exports nothing from other first-party crates
    (rule 3);
  - rustdoc runs with hidden items included, once with default features
    and once with all features, natively on Linux in `ci.yml` and on
    macOS in `macos.yml`, so feature-gated and platform-specific
    re-exports are seen.
- **Source boundaries** (Cargo's dep-info files, which list every file
  rustc read for a crate, `#[path]` modules and `include!()` targets
  included; every target of every workspace crate, with default and
  with all features): every `.rs` file a crate reads lies inside its own
  directory or its build-script output, whether compiled or read as text
  (dep-info can't tell the two apart). Other data files read with
  `include_str!`/`include_bytes!`, such as test fixtures, are exempt.
- **Toolchain:** rustdoc's JSON output is unstable, so it uses a pinned
  nightly (`nightly-2026-10-10`, JSON format 61). Building still uses
  the stable pin. Moving the nightly pin is its own PR.
- **It fails closed:** an unresolved re-export, an unexpected JSON
  format version or a missing dep-info file is an error. Reviewers still
  read the code, and check what the toolchain output can't show: items
  under `#[cfg(not(doc))]` (rustdoc sets `cfg(doc)`); feature
  combinations other than default and all; doctests, which `cargo check`
  doesn't compile; non-`.rs` files pulled in with `include!()`; files a
  build script reads at run time.
- **Fixtures** (in `xtask/tests/layers/`), each a small workspace that
  compiles:
  - negative: a skip-layer dependency, a renamed first-party
    dependency, a whole-crate re-export, a module re-export, a glob
    re-export, `sb-service` re-exporting an engine item, a re-exported
    first-party macro, a `#[doc(hidden)]` re-export, a source file
    outside the crate (`#[path]` and `include!()`);
  - positive: a legal adjacent item re-export.
- **It runs** in `cargo xtask ci` and `ci.yml`.

## Process model and threading

- **One process (pilot).** The app links the core and runs the engine in
  process. The store lease (03) makes a later move to an agent possible
  without API changes.
- **Runtime:** the engine owns **one multi-threaded Tokio runtime**,
  created by `open_core` and shut down by `Core::shutdown`. FFI calls
  enqueue work on it and await results; no call blocks the Swift caller's
  thread.
- **Store threads:**
  - **Writer:** one dedicated OS thread owns the SQLite writer connection
    and executes submitted write closures in priority order: user
    commands, then sync batches, then index and backup jobs.
  - **Readers:** a small pool of reader connections (default 4) serves
    queries, each read a short transaction.
- **Tasks per IMAP account:**
  - an IDLE watcher;
  - a worker that does sync passes and executes intents;
  - a body-acquisition queue.
  - They hold no SQLite transactions across awaits.
- **Threads are a startup resource.** Open starts the runtime, the
  store's writer and the engine's cleanup worker; an OS that refuses any
  of them fails the open as `Unavailable`. After open the core assumes
  threads can still be started (the runtime's blocking pool grows on
  demand): under OS thread exhaustion, blocking work waits rather than
  fails. The pilot accepts that.
- **Background jobs:** import, export, backup, index and GC are engine
  jobs with progress reporting and cancellation. Each holds its own
  resumable checkpoint in the store.
- **Clock and randomness** come through the `Clock` and `Random` seams
  (rule 5), so tests are deterministic.

### Search ownership (M1.6)

`sb-mime` owns bounded reader-independent extraction (06), with no store
access. `sb-store::query` owns the AST, JSON/text parser and formatter,
validation, parameterized SQL, search keys and scoped coverage reads.
`sb-resources` maps extraction output into store publication inputs and
exposes typed acquisition/queue/query operations; it never schedules jobs.
`sb-engine` owns index and received-address workers, rebuild progress,
Search handles and invalidation. `sb-service` defines its own DTOs,
including parse spans and coverage; `sb-ffi` and `SweetbriarBridge` map
those for macOS. No MIME or SQLite types cross the service boundary.
The fuzz crate can depend directly on the leaf parser, as its MIME target
does; the application layer graph stays unchanged. Reuse existing parser,
JSON and HTML dependencies; any new direct dependency, including timezone
data needed by 06, is pinned and justified at implementation, with lockfile
and notices changes included in that step's size.

## Licence policy for dependencies

- **Sweetbriar's own code** is offered as `Unlicense OR 0BSD`, at the
  recipient's option (`LICENSE`, `LICENSE-0BSD`; owner's decision, D18).
  The workspace `Cargo.toml` sets it under `[workspace.package]`, and
  every crate opts in with `license.workspace = true`. No outside
  contributions are accepted; `CONTRIBUTING.md` says so.
- **Allowed in the linked runtime:** MIT, MIT-0, Apache-2.0,
  BSD-2-Clause, BSD-3-Clause, ISC, 0BSD, Unlicense, CC0-1.0, Zlib,
  Unicode-3.0.
- **MPL-2.0** is allowed by **named exception per package and version**:
  UniFFI's crates, and the CSS parsing family `ammonia` and `lol_html`
  depend on (`cssparser`, `cssparser-macros`, `dtoa-short`,
  `selectors`), added by M1.5. It is file-level copyleft. Unmodified, it needs
  notices plus a pointer to the source; a modified MPL file must be
  published.
- **LGPL** is allowed only for dynamically linked Linux platform
  libraries (GTK, *later*).
- **Never linked:** GPL or AGPL in any form. Proton Bridge (GPLv3) stays
  a separate user-installed program.
- **Enforcement:** `deny.toml` enforces this with an allow-list
  (cargo-deny 0.20 syntax). The starting template is in the crates
  research.
- **Notices:** `THIRD_PARTY_NOTICES.md` is generated by `cargo-about` and
  shipped in the app bundle. CI fails if it's stale.
